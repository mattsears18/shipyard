# issue-work.md §0.5 — verify dispatch-time scope-boundary framing against the issue's live comment thread

On-demand fragment for [`issue-work.md` §0.5](./issue-work.md#05-verify-dispatch-time-scope-boundary-framing-against-the-issues-live-comment-thread-1179) — [#1179](https://github.com/mattsears18/shipyard/issues/1179). Loaded only when the dispatch prompt actually carries a scope-boundary assertion; §0.5 itself documents the trigger and is a no-op otherwise.

## Why this exists

A dispatch prompt can carry a scope-boundary assertion computed by an earlier pass this session — an "Operator residual" ([§6.5](./issue-work.md#65-split-dispatch-disposition-hand-back-the-operatorsecurity-residual-keep-the-issue-open-851)) or "Verification slice" ([§6.6](./issue-work.md#66-verification-disposition-run-the-auditor-file-bugs-disposition--without-a-pr-852)) Context paragraph, a "Phase-1 slice" paragraph, or an ad hoc "CRITICAL SCOPE BOUNDARY" / "DO NOT" framing a human or the orchestrator wrote in by hand. That framing is a snapshot of the issue's state **at the moment it was computed** — scope-preflight time, or an earlier point in a long session — and the issue can move underneath it before you actually act on it: a maintainer completes the barred action via `/shipyard:my-turn`, an operator session does the provisioning, a follow-up comment narrows or resolves what's outstanding. This is especially likely on an `agent-console`-flavored or provisioning-gated issue, which by design accumulates operator/maintainer activity between agent passes. See [RATIONALE → Stale scope-boundary framing repro](../../../../docs/design/issue-work-rationale.md#stale-scope-boundary-framing-repro-1179) for the concrete cross-repo repro that motivated this step.

This is the worker-side counterpart to the orchestrator's own dispatch-composition rule (`commands/do-work/dispatch-rules.md` § "Confidence/status framing composed into the dispatch prompt MUST be comment-thread-aware" — [#781](https://github.com/mattsears18/shipyard/issues/781) / [#1062](https://github.com/mattsears18/shipyard/issues/1062)). That rule keeps the orchestrator from asserting a stale premise *into* the prompt in the first place; this step keeps the worker from trusting a scope-boundary premise that went stale *between* prompt composition and this dispatch's actual execution — including within a single long session, where scope-preflight can run well before the worker itself starts. Neither rule substitutes for the other — a diligent orchestrator-side check reduces how often this step finds a contradiction, but doesn't eliminate the race a long session creates.

## The check

**Diff the dispatch prompt's scope-boundary framing against the `comments` array from step 0's `gh issue view` projection** (already fetched — no extra call needed). Read the issue's most recent comments — especially ones from the issue's own author or the repo owner, or carrying a disposition-style sentinel (`<!-- shipyard-disposition-call -->`, `<!-- do-work-decision-resolved -->`, `<!-- shipyard-resolve-decisions -->`) — and ask: does anything here contradict the dispatch prompt's scope-boundary assertion? Concretely: does a comment show the barred action already completed, the cited blocker already resolved, or the framing's premise no longer holding?

- **No contradiction (the common case)** — proceed exactly as the dispatch prompt describes. This check exists to catch staleness, not to second-guess an assertion the comment thread doesn't dispute.
- **Contradiction found** — the live issue state wins over the dispatch prompt's framing. Re-derive what's actually still outstanding from the comment thread rather than following the stale assertion: don't manufacture a hand-back for an action that's already done, and don't treat a barred-action framing as still current when the comments show otherwise. Note the correction in your PR body or a decision comment (per [§5.5](./issue-work.md#55-record-decision-context-when-applicable)), citing the comment permalink, so the disposition trail is traceable for the next reader.

Then return to `issue-work.md` and continue at step 1.
