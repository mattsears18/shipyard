# issue-work.md — Rationale

The *why* behind [`issue-work.md`](./issue-work.md)'s load-bearing rules — repro write-ups, historical drift, and the extended reasoning that doesn't change what the worker actually does. This is the worker-side companion to [`do-work-RATIONALE.md`](../../commands/do-work-RATIONALE.md); same split, same convention: rule stays in the hot file, story moves here, linked via `See [RATIONALE → ...]`. Split out of `issue-work.md` per [issue #885](https://github.com/mattsears18/shipyard/issues/885) — that file is the hottest per-dispatch context cost in the plugin (loaded on every `issue-work` dispatch, multiplied by `--concurrency`), and this narrative content doesn't need to ride along on every one of those loads.

## External-provisioning guard repro (#628)

The [§4.4](./issue-work.md#44-external-provisioning-guard--dont-commit-dead-config-for-an-unprovisioned-service-628) guard exists because of a concrete failure shape: a worker writes Terraform / config with a placeholder or empty value for a not-yet-provisioned credential (a Sentry DSN, a Stripe secret key, a service account that doesn't exist anywhere yet), opens a PR, it auto-merges, and the change deploys non-functional infrastructure the user never asked to activate — they hadn't even created the account yet. The empty-diff guards elsewhere in the file don't catch this because placeholder config is a **non-empty** diff; only an explicit "does this commit a fabricated stand-in for a real secret" check closes the gap.

## Phantom-merge repro (#356)

The concrete repro behind [§4.5](./issue-work.md#45-pre-pr-create-diff-sanity-check): [`mattsears18/lightwork#1169`](https://github.com/mattsears18/lightwork/pull/1169) merged on 2026-05-25 with a 0-file diff against its parent, auto-closing [`mattsears18/lightwork#1160`](https://github.com/mattsears18/lightwork/issues/1160), which then sat as CLOSED for the rest of the day until a follow-up session noticed the missing code. The PR's body claimed substantial scope (new files, modified files, acceptance criteria checked) — nothing about the PR *looked* empty except the actual diff. This is what motivated a mechanical pre-create diff-count check rather than trusting the PR body's own claims.

## Why bail rather than retry on an empty diff (#356)

If a worker completes step 4 with no diff, one of three things happened: (a) the issue was already fixed by a prior PR and the worker didn't catch it during the verification-first read in step 2; (b) the implementation strategy was wrong and the worker noticed and reverted, leaving the worktree clean; (c) the issue is misclassified (docs-only, spec-clarification, can-be-closed-no-change). In all three cases the right action is to surface the empty state to the orchestrator with a `blocked:` return — the orchestrator's reconcile step classifies the bail (a refuse-class reason like this one lands `needs-human-review` per [#521](https://github.com/mattsears18/shipyard/issues/521)) and a human can route it. Opening an empty PR and letting the merge fire the `Closes #N` keyword corrupts the backlog signal and forces a re-open + investigation — strictly worse than a clean bail.

## Pre-push unit-test gate repro (#658)

The recurring failure [§4.6](./issue-work.md#46-pre-push-local-unit-test-gate-658) closes: a change adds a `Strings.*` leaf without the paired `locales/en.json` key, passes typecheck + lint locally, pushes, and only then fails the required **Unit Tests** gate on an i18n-parity assertion — costing an orchestrator diagnosis plus a separate fix-checks dispatch per occurrence. In one `lightwork` session this recurred three times in a row (PRs #2275, #2284, #2290), each a wasted round-trip a local unit run would have caught. Typecheck and lint are cheap enough that workers reliably ran them anyway; the unit suite is the gate that actually catches repo-specific invariants, and it's exactly the one that was being skipped.

## Why the ungated-merge gate is a script, not prose (#716)

The ungated-admin-direct-merge condition ([§6.a](./issue-work.md#6a-run-the-ungated-admin-direct-merge-pre-check-first--before-any-merge-call-598--602--716)) used to live as prose in two files, and the two copies drifted into contradicting each other — `issue-work.md` claimed the gate only fires when `allow_auto_merge: false` and listed *"repo allows auto-merge"* as a **skip** condition, while the worker-preamble fragment correctly fired on `admin + zero required checks` **regardless of `allow_auto_merge`**. Whichever copy a worker happened to read decided whether the gate fired at all.

The repro: in one session the worker on PR #713 loaded the fragment and correctly held for its checks, while the worker on PR #715 followed `issue-work.md`'s prose, concluded *"auto-merge isn't enabled on the repo"* (it is — `allow_auto_merge: true`), and admin-direct-merged while CI was still `IN_PROGRESS`. The fix moved the condition into exactly one executable place ([`scripts/detect-ungated-admin-direct-merge.sh`](../../scripts/detect-ungated-admin-direct-merge.sh)) so it can no longer drift — a worker calls the script rather than re-deriving the condition from memory.

## Policy-override guard repro (#1088)

[§4.45](./issue-work.md#445-never-disable-a-committed-security-or-supply-chain-control-to-make-ci-pass-1088) closes a `lightwork` repro: a required `npm audit --audit-level=high` check was red on a newly published advisory (js-yaml, GHSA-5p4m-2wfm-xmqj). The fix release (`js-yaml@4.3.1`) had been out for 6d8h — one day short of `apps/lightwork/.npmrc`'s committed 7-day `min-release-age` supply-chain cooldown, whose own inline comment stated the cooldown was left fully intact so that "the cooldown never needs overriding to unblock a merge." The worker ran `npm install --min-release-age=0`, silently overriding it, then pushed and armed auto-merge (`lightwork#3565`). The orchestrator caught it only via the harness's own generic safety-bypass warning — an out-of-band signal, not part of the worker return vocabulary — disarmed auto-merge, and escalated to a human. Nothing in the worker contract would have stopped a repeat, or one where that warning didn't fire.

The local reasoning at every step was sound ("a required check was red, a fix existed, the flag cleared it") — that's exactly why this needed a structural guard rather than trusting per-worker judgment. §4.45 doesn't fire on genuinely-resolving fixes: upgrading past both the vulnerable version *and* the cooldown window, fixing what a linter/hook actually flags, adding a missing `CODEOWNERS` entry rather than removing the requirement. It fires specifically when the "fix" is disabling the control itself. If an override is ever genuinely in scope (rare — a trusted-author comment or the issue body explicitly authorizes waiving a named control, a human decision per [step 2](./issue-work.md#2-read-the-issue-carefully)'s trusted-comment handling, never something the worker infers on its own), the resulting PR still must not arm auto-merge — `auto-merge.md` step 0.3 is the unconditional backstop for that case.

## Why the phantom-merge guard is a script, not an inline snippet (#1340)

[§4.5](./issue-work.md#45-pre-pr-create-diff-sanity-check)'s guard was prescribed as an inline snippet — a `git diff --name-only "origin/$DEFAULT_BRANCH"...HEAD | wc -l | tr -d ' '` command substitution, wrapped in an `if` that itself contains a second `git status --porcelain | wc -l | tr -d ' '` substitution and `if`, all inside the reaped-escape-hatch preamble. This is the same failure shape [#1336](https://github.com/mattsears18/shipyard/issues/1336) found in fix-rebase.md §5.7, in an even larger compound block, and #1340's investigation re-verified it firsthand (not by analogy) in a real worktree-isolated worker session:

1. **The block is refused.** Run verbatim as one Bash call, the harness's worktree-isolation guard deterministically refuses it: *"too complex to verify that it stays inside the worktree; break it into plain, separate commands"* — the [#802](https://github.com/mattsears18/shipyard/issues/802) refusal class. `issue-work` and `spike` workers are always worktree-isolated, so the guard as written could never execute.
2. **The refusal's own remediation over-counts the first check.** Splitting into "plain, separate commands" yields a bare `git diff --name-only <refs> | wc -l` as the entirety of one Bash call. Measured firsthand: under a diff-rewriting shell proxy (`rtk`, [#1333](https://github.com/mattsears18/shipyard/issues/1333)), `git diff --name-only HEAD HEAD` (a ref against itself, true answer 0) came back as a lone `\n` byte, so `wc -l` returns 1 — the `CHANGED_FILES == 0` bail can then never fire, and a worker opens an empty PR whose `Closes #N` closes the issue with no change landed.
3. **The same remediation under-counts the second check — the opposite direction.** A bare `git status --porcelain | wc -l` is corrupted the other way. Measured firsthand against a real 2-file dirty tree ( `README.md` modified, one untracked file): the proxy's raw output is missing the trailing newline after the LAST line only (confirmed via `od -c`), so `wc -l` returns 1 instead of 2. Against a 1-file dirty tree the same corruption drops the count to 0 — a genuinely uncommitted change would read as a clean tree, false-tripping `WORKING_TREE_DIRTY == 0`.
4. **A script-internal invocation is immune to both.** The identical two comparisons, run from inside a `bash <script>` call instead of as isolated top-level Bash calls, returned the correct counts in every case tested (0 and 2, matching ground truth) — confirming the proxy only rewrites the top-level invocation shape, not a script's internal subprocess calls, and that wrapping the check in a script sidesteps both corruption directions at once.

These two corruption directions don't share a single correction — a fix that only guards the over-count (e.g. `assert-rebase-diff-nonempty.sh`'s existing self-check + blank-line shape check, which only apply to `--name-only` output) would leave the `--porcelain` under-count wide open. [`assert-worktree-change-present.sh`](../../scripts/assert-worktree-change-present.sh) adds a direction-specific defense for each: the committed-diff comparison keeps the file-redirect + blank-line shape check + ref-vs-itself self-check `assert-rebase-diff-nonempty.sh` established; the working-tree comparison instead checks that its (non-empty) result ends in a trailing newline — genuine `git status --porcelain` output always newline-terminates every line including the last, so a non-empty result that doesn't is exactly the measured under-count signature. Both checks fail loud (`INDETERMINATE`, exit 2) rather than trust a result that doesn't look genuine.

## Stale scope-boundary framing repro (#1179)

[§0.5](./issue-work.md#05-verify-dispatch-time-scope-boundary-framing-against-the-issues-live-comment-thread-1179) closes a cross-repo repro: a `/shipyard:do-work` session against `mattsears18/lightwork`, dispatching `mode: issue-work` for lightwork#3525 (a test-environment Firebase Admin WIF provisioning issue). The dispatch prompt carried a doubly-emphasized "CRITICAL SCOPE BOUNDARY" — "Completing this end-to-end requires creating a new IAM binding and new Vercel env rows on the test project. Creating or widening access is a hand-back class in this workflow and you must NOT perform it" — computed by a scope pass earlier in the same session, instructing the worker to post a runbook and return `blocked:` rather than open a PR if no code slice existed.

By the time the worker actually ran, both access-granting actions named in the boundary had already been completed by the maintainer via prior `/shipyard:my-turn` sessions — the IAM binding was granted, the Vercel env rows landed days earlier, and the issue's own most recent comment (carrying a `<!-- shipyard-disposition-call -->` sentinel) already stated the only remaining item was a read-only verification probe. Had the worker followed the stale boundary uncritically, it would have either manufactured a bogus "still needs a grant" hand-back for work already done, or treated the barred-grant framing as more current than it actually was.

This particular dispatch happened to survive because its author added "verify it" by hand to the prompt, prompting a `gh issue view --json comments` read that surfaced the true state — the correct mitigation, but one that only fired because a human happened to think to add it. Nothing in the worker contract *guaranteed* that re-check. lightwork's own `CLAUDE.md` already documented the narrower version of this failure class for issue *bodies* going stale ("Operator issues go stale silently... twice now the requested change was already in place"); this is the same failure class one level up the stack — shipyard's own scope-preflight computation, not just the target repo's issue body, can go stale between when it was computed and when the worker acts on it. §0.5 makes the re-check mandatory and spec'd rather than something that only happens when a human writes the caveat in by hand.

## Why self-assign is not a lock (#1248)

[§1](./issue-work.md#1-self-assign-gated-on-backlogself_assign-issue-1248)'s self-assign was previously documented as a "soft lock against a parallel `/do-work` instance". That claim only holds across *different* GitHub identities: a second same-identity session sees its own self-assigned issue as `assignee == @me` (the resumable-work case [#332](https://github.com/mattsears18/shipyard/issues/332) protects) and dispatches it anyway, so no lock actually occurs for the common single-operator case. The real collision guard is the orchestrator's concurrent-session worktree/PID lock.

## Why the per-PR release bump can't be deferred (#460)

The deferral failure mode behind [§4's per-PR release rule](./issue-work.md#4-implement) is concrete: two sibling workers on the same repo can handle its release rule inconsistently, one deferring (leaving `main` undocumented and forcing a separate catch-up release PR that races the version row) and one including it correctly. That inconsistency is why the choice is mandatory rather than per-worker judgment.
