# /do-work — RATIONALE

Human-readable companion to [`commands/do-work.md`](./do-work.md). The runtime spec is the procedural reference the orchestrator executes; this file carries the *why* — design rationale, failure modes, motivating sessions, worked examples, and the long-form discussion that would otherwise bloat the spec. The orchestrator never needs to read this file; humans reviewing or evolving the spec do.

Section anchors mirror the spec's structure, so a maintainer who wants the rationale for a given spec section can navigate by name.

## Recommended permission posture — why Auto mode over full bypass ([#763](https://github.com/mattsears18/shipyard/issues/763))

Run `/do-work` — and the workers it dispatches — under Claude Code's **Auto mode**, not full permission bypass (`--dangerously-skip-permissions`). Auto mode is the middle ground this loop actually needs to stay unattended: a harness-side classifier auto-approves the routine, in-scope tool calls that make up the vast majority of a dispatch (edit, commit, push, `gh` read/write, `Agent` dispatch) with no interactive prompt, but hard-denies the genuinely destructive class outright regardless of what the session or a worker asks for — destructive git (`reset --hard`, `clean -fd`, `stash drop`), `terraform`/`pulumi`/`cdk destroy`, transcript tampering, and `rm -rf` on an unresolved variable. Full bypass removes that backstop entirely, so a misbehaving worker (or a prompt-injection payload smuggled through an issue body — see the untrusted-input handling in [`agents/issue-worker/issue-work.md` § 2](../agents/issue-worker/issue-work.md#2-read-the-issue-carefully)) has a clear, unguarded path to an unrecoverable local action.

**This formalizes what the spec already assumes operationally — it doesn't introduce new behavior.** `dispatch_denials` and `operator_denials` (see [`do-work/orchestrator-state-reference.md`](./do-work/orchestrator-state-reference.md)), the classifier-response branches in [`do-work/operate/01-queue-and-authorization.md`](./do-work/operate/01-queue-and-authorization.md#operator-action-denied-by-the-harness-permission-classifier-746) and [`do-work/dispatch-rules.md`](./do-work/dispatch-rules.md#dispatch-denied-by-the-harness-permission-classifier-718), and every worker's `shipyard:worker-preamble` § "After a classifier denial" contract all exist *because* the Auto-mode classifier is expected to be live and to occasionally deny a call. Running under full bypass instead doesn't break any of that machinery, but it silently defeats the safety property it was built for — every one of those branches becomes dead code that never fires, because there's no classifier there to deny anything.

**Composes cleanly with shipyard's own hooks — verified, not assumed.** The worktree-isolation and edit-scope guards (`enforce-worktree-isolation.sh`, `enforce-edit-scope.sh`, `refuse-broad-process-kill.sh`, `refuse-escape-symlink-commit.sh`, `guard-primary-checkout.sh` — wired in [`hooks/hooks.json`](../hooks/hooks.json)) are `PreToolUse` hooks: a separate, deterministic layer that fires on every matching tool call regardless of which interactive permission mode is in effect. Switching from full bypass to Auto mode doesn't touch, weaken, or duplicate this layer — the hooks remain the enforced floor (they hard-block via exit code 2 whether or not Auto mode's classifier would independently have allowed the call), and Auto mode's classifier sits *in addition to* them as a second, semantic gate over the destructive-action class the hooks don't cover (the hooks are scoped to worktree/edit-scope/process-kill/symlink-commit safety, not to `git reset --hard` or infra-destroy commands). The one place the two layers interact directly — an `allow` rule short-circuiting the classifier for `.claude/worktrees/` cleanup — is verified (not assumed) in [`init.md`'s § 9.6](./init.md#96-optionally-pre-authorize-the-worktree-reap-commands) permission-modes discussion.

**Full bypass remains a user choice, not a shipyard requirement.** Nothing in this spec depends on `--dangerously-skip-permissions` being set — every dispatch, every worker return, every hook fires identically under Auto mode. The loop's normal path (routine dispatch, edit, commit, push, PR-open) clears the Auto-mode classifier without a prompt; only the destructive class it exists to catch is denied.

## Runaway guards — subagent + web-search session caps ([#764](https://github.com/mattsears18/shipyard/issues/764))

A `/do-work` burndown fans out deeply: the orchestrator keeps up to `--concurrency` workers in flight, each dispatched worker can itself spawn subagents (`Agent` calls, now nestable up to 5 levels deep in the harness), and any worker doing research (a `WebFetch`/`WebSearch`-heavy investigate-mode dispatch, a fix-checks worker chasing a flaky-vs-real CI signature) can issue an unbounded number of web searches across a long session. Nothing in this spec today puts an explicit ceiling on either dimension — the practical backstops are the dispatch loop's own termination condition (see [`do-work.md`](./do-work.md)'s session-completion description in its opening paragraph) and human attention, neither of which fires *during* a session that's fanning out faster than intended.

Claude Code exposes two harness-level environment variables that exist specifically as this class of circuit breaker:

- **`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`** (v2.1.212+, default `200`) — caps the total number of subagents a single Claude Code session may spawn across its lifetime, at any nesting depth. Once the cap is hit, further `Agent` dispatches fail at the harness level rather than the orchestrator's own dispatch loop deciding to stop.
- **`CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION`** (v2.1.212+, default `200`) — the session-wide `WebSearch` cap, same mechanism.

**Why this matters more on a self-hosted-runner host than elsewhere.** Several of shipyard's own operating assumptions already single out the case where the machine running `/do-work` also executes the target repo's CI as a self-hosted GitHub Actions runner (see `shipyard:worker-preamble` § "Never run a broad process kill" and the fix-checks-only infra-flake handling) — on that shape, the orchestrator's own resource consumption (CPU, memory, network) is *sharing a host* with in-flight CI, not running in an isolated sandbox. A session that fans out far beyond what a normal burndown needs (a scope-agent loop stuck re-dispatching, a research-heavy investigate-mode worker looping on searches) doesn't just waste tokens — it can also starve the CI runner processes on the same box, compounding into the exact "runner contention" false-CI-failure signature the fix-checks-only mode already has to disambiguate from a real regression. An explicit session cap turns an unbounded-fanout failure into a bounded, loud one (the harness denies further spawns/searches) instead of a silent resource fight with concurrent CI.

**Recommendation, not an enforced default.** Shipyard does not — and cannot — set these itself: they are process-environment variables read by the Claude Code CLI at session start, not a repo-committed config file `/do-work` controls (unlike `shipyard.config.json`'s `concurrency.default`, which shapes *shipyard's own* dispatch pool size). Set them in whatever shell profile, systemd unit, or launchd plist starts the `claude` process on a host that runs `/do-work` unattended for extended burndowns — especially a self-hosted-runner host:

```bash
# ~/.zshrc / ~/.bashrc / the systemd unit's Environment= block for the
# process that invokes `claude` to run /shipyard:do-work unattended.
export CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION=200
export CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION=200
```

The defaults (`200` each) are already sane for the vast majority of sessions — a `--concurrency 1` burndown with a handful of scope-preflight agents and no investigate-mode dispatches will never come close. The guidance here is awareness, not a lower recommended value: know the caps exist, know where to tighten them (a long unattended overnight run on a shared self-hosted-runner host is the case to consider dropping them below 200), and know that hitting one surfaces as a harness-level dispatch failure rather than a shipyard-side error — a worker or the orchestrator itself hitting the cap mid-session should be treated the same as any other harness denial (see `shipyard:worker-preamble` § "After a classifier denial" for the analogous posture toward harness-side refusals) rather than assumed to be a shipyard bug.

**Not currently surfaced by [`/shipyard:status`](./status.md).** The per-session state file `session-state.sh` maintains (`~/.shipyard/sessions/<session-id>.json`) is shipyard's own bookkeeping — it has no visibility into the harness's internal subagent/web-search counters, and there is no documented way for a running session to read its own current count against either cap. `/shipyard:status` therefore does not attempt to render a live count against these limits; doing so without a real data source would fabricate a number that looks authoritative but isn't. If the harness ever exposes these counters (e.g. via the per-dispatch `usage` payload the same way token counts are already exposed — see [`session-state-file.md`'s Cost-tracking write-through](./do-work/session-state-file.md#cost-tracking-write-through)), wiring a running tally into the session state file and rendering it alongside the token total in `/shipyard:status`'s dashboard would be the natural follow-up.

## `fallbackModel` — degrade gracefully under model-tier overload ([#766](https://github.com/mattsears18/shipyard/issues/766))

A long `/do-work` burndown makes a lot of model requests over a long wall-clock window — the orchestrator's own turns, plus every dispatched worker's turns across every worker mode. During that window a given model tier can be **briefly overloaded** (a transient capacity/rate-limit condition on Anthropic's side, not a bug in shipyard or the target repo), and a request that hits it fails a dispatch that would otherwise have succeeded on retry — or on an adjacent, less-loaded tier.

Claude Code (v2.1.166+) exposes `fallbackModel` in `settings.json` for exactly this: configure up to **three** models, tried in order, when a request to the primary model comes back overloaded. It's the same "circuit breaker the harness owns, not shipyard" shape as the [runaway-fanout guards above](#runaway-guards--subagent--web-search-session-caps-764) — a session-level resilience setting, not a repo-committed config file `/do-work` reads or writes.

**Recommendation, not an enforced default — same posture as the runaway guards.** Shipyard cannot set `settings.json` on the user's behalf (this repo's own worker contract forbids editing a live settings file — see `shipyard:worker-preamble`), so this is guidance for whatever `settings.json` governs the `claude` process that runs `/shipyard:do-work` unattended — most valuable on a long overnight burndown, and doubly so on a self-hosted-runner host where the session is already sharing the box with in-flight CI and can least afford to stall a dispatch on a transient overload instead of degrading and continuing:

```jsonc
// ~/.claude/settings.json (or the repo's .claude/settings.json)
{
  "model": "opus",
  "fallbackModel": ["sonnet", "haiku"]
}
```

**Why `sonnet` → `haiku` and not the reverse.** The chain degrades from the primary model toward cheaper/faster tiers — the goal is "still complete the dispatch," not "still complete it at full fidelity." Falling back *up* in tier would defeat the point (an overloaded top tier is usually overloaded because everyone's requests landed there; falling back further up makes the retry land on the same congested tier).

**How this differs from — and composes with — `models.<mode>`.** [`resolve-dispatch-model.sh`](../scripts/resolve-dispatch-model.sh) and its `models.<mode>` config key (see project `CLAUDE.md`'s Configuration section) are a **dispatch-time tier assignment**: they decide, per worker mode, which model family the orchestrator's `Agent` call targets, and that decision is baked into the call before it ever reaches the harness. `fallbackModel` is an **orthogonal, session-level resilience setting**: it doesn't change which tier a mode dispatches on, it only governs what the session's own CLI process retries when *whichever* model was requested — the orchestrator's own session model, or a dispatched mode's resolved tier — comes back overloaded. The two don't conflict: `models.<mode>` answers "which model should this mode use," `fallbackModel` answers "what do we try next when that model is temporarily unavailable."

**A per-family default chain, computed by the same script that resolves `models.<mode>`.** Rather than hand-maintain the tier ordering in prose (and let it drift from `resolve-dispatch-model.sh`'s own family table), `resolve-dispatch-model.sh` exposes an advisory helper for exactly this:

```bash
bash plugins/shipyard/scripts/resolve-dispatch-model.sh --fallback-chain opus
# -> sonnet,haiku
bash plugins/shipyard/scripts/resolve-dispatch-model.sh --fallback-chain sonnet
# -> haiku
bash plugins/shipyard/scripts/resolve-dispatch-model.sh --fallback-chain fable
# -> opus,sonnet,haiku   (caps at Claude Code's documented 3-model fallbackModel limit)
```

Feed it whichever model your primary session (or a given `models.<mode>` entry) resolves to, and copy the comma-separated output into `settings.json`'s `fallbackModel` array. `haiku` returns empty — it's already the cheapest/fastest tier shipyard dispatches on, so there's nowhere lower to degrade to.

**This is a documentation helper, not a new dispatch-time hook — worth being explicit about, given [#727](https://github.com/mattsears18/shipyard/issues/727)'s history with dead `models.*` surfaces.** The `Agent` tool's `model` parameter is a single enum value (`opus`/`sonnet`/`haiku`/`fable`), not a list — there is no per-dispatch fallback-chain parameter to wire `--fallback-chain`'s output into, so it is intentionally **not** called from `dispatch-rules.md` or `setup/07-pool-fill.md` the way the live `models.<mode>` path is. Its only "caller" is a human (or this doc) computing a `settings.json` value once, by hand, outside the dispatch loop. That's a different shape of thing than a config key nothing reads — see the script's own header comment for the fuller distinction.

## Task Budgets — not exposed on the Agent dispatch surface, spiked and closed negative ([#765](https://github.com/mattsears18/shipyard/issues/765))

Shipyard tracks per-worker cost **post-hoc** — the [Cost-tracking write-through](./do-work/session-state-file.md#cost-tracking-write-through) attributes a dispatch's `usage` payload *after* it returns, and the persistent ledger at `~/.shipyard/cost-history.jsonl` (see project `CLAUDE.md`'s Cost-tracking ledger section) rolls that up across sessions. Neither is **pre-emptive**: nothing today gives a dispatched worker a token ceiling it's aware of *while running*, the way a hard `max_tokens` cutoff does without warning. The Claude API has a beta feature built for exactly that gap — **Task Budgets** (`output_config.task_budget: {type: "tokens", total: N}`, beta flag `task-budgets-2026-03-13`, Fable 5 / Sonnet 5 / Opus 4.8 / 4.7 only, minimum `total` 20,000) — which surfaces a countdown the model sees mid-generation and paces itself against, distinct from `max_tokens`'s silent cutoff. [#765](https://github.com/mattsears18/shipyard/issues/765) asked whether shipyard's `Agent`-tool dispatch surface (what every `/do-work` worker mode is spawned through) exposes this, with the `Workflow` tool's own `budget.total/spent()/remaining()` primitive cited as evidence the in-harness pattern already exists somewhere.

**Confirmed: it does not, and there is nothing to wire a `budgets.<mode>` config surface to.** Two independent checks converge on the same negative:

- **The Claude Platform docs state it outright.** The Task Budgets page's own compatibility note reads: *"Task budgets are not supported on Claude Code or Cowork surfaces. Use task budgets directly through the Messages API on a supported model."* (`platform.claude.com/docs/en/build-with-claude/task-budgets`.) Claude Code — the harness this repo's `Agent` tool dispatches through — is explicitly named as unsupported, not merely undocumented.
- **The `Agent` tool's own parameter surface confirms it independently.** `AgentDefinition` (per `code.claude.com/docs/en/agent-sdk/subagents.md` and the tools reference at `code.claude.com/docs/en/tools-reference.md`) exposes `model`, `tools`, `disallowedTools`, `skills`, `mcpServers`, `permissionMode`, `effort`, and `maxTurns` — a *turn* ceiling, not a *token* one. There is no `budget`, `task_budget`, or `token_limit` field on a dispatched subagent, at the `Agent` tool call site or in agent-definition frontmatter (`.claude/agents/*.md`'s YAML header).
- **The `Workflow` tool's `budget` primitive the issue cited is a different mechanism, not a bridge to this one.** It is harness-level userspace accounting — the workflow author calls `budget.remaining()` and decides for itself whether to keep going; the harness doesn't enforce anything at the API level underneath it, and nothing plumbs a `Workflow` budget through to the Messages API's `task_budget` parameter on the model calls the workflow makes. It demonstrates that *a* budget-shaped primitive exists somewhere in the harness family, not that Task Budgets specifically reaches subagent dispatch.

**Decision: no `budgets.<mode>` config surface, and no config-schema stub — both would be dead config with nothing to enforce them.** [#727](https://github.com/mattsears18/shipyard/issues/727) is the standing cautionary precedent this repo already treats as load-bearing (see the `fallbackModel` section above for the same posture applied to a *supported* feature that still isn't wired into dispatch because the parameter shape doesn't fit): a config key that nothing reads is worse than no config key, because it invites a user to set it and get silent no-op behavior. Here the gap is categorically different from `fallbackModel`'s — `fallbackModel` is a real, wireable Claude Code setting that just doesn't have a matching per-dispatch parameter on `Agent` (a shape mismatch); Task Budgets is a Messages API feature the Claude Code harness has explicitly declined to expose *at all* (an availability gap, confirmed by the platform's own docs, not a parameter-shape problem shipyard could route around). Adding `budgets.<mode>` today would be a schema entry with zero effect on any dispatch — the exact anti-pattern #727 exists to name.

**What would actually be required, if this ever becomes buildable.** Task Budgets is a parameter on `client.beta.messages.stream(...)` / `.create(...)` — the raw Messages API a worker would need to call *directly*, bypassing the `Agent`-tool harness entirely, to set one. That is a fundamentally different execution model than how `/shipyard:do-work` dispatches workers today (every mode is an `Agent` call into a Claude Code subagent, never a raw API client call from inside the orchestrator's own process) — building it would mean shipyard's dispatch layer making its own authenticated Anthropic API calls in parallel with the `Agent` tool it already uses, effectively running two different agent-execution paths side by side. That's a large architectural change disproportionate to the problem (a nice-to-have pre-emptive cost ceiling, when the post-hoc ledger + `/shipyard:cost report` already give visibility after the fact), so it is not proposed here. The concrete, cheap trigger to revisit: if Claude Code's own `Agent`-tool dispatch surface (or `AgentDefinition`) ever adds a token-budget-shaped field — the same kind of "harness grew a hook shipyard didn't have before" event that turned `fallbackModel` and the subagent/web-search session caps from nothing into documented, wireable settings — add `budgets.<mode>` mirroring `models.<mode>`'s existing shape (schema entry, `shipyard-config.sh` defaults, a `resolve-dispatch-model.sh`-style resolver) at that point, not before.

**Why this closes #765 rather than leaving it open as a hand-back.** The spike's job was to establish ground truth on feasibility, and it did: the answer is a definitive, dual-sourced "not exposed, nothing to build against." That's a complete resolution, not a blocked remainder waiting on a decision only a human can make — there's no follow-up issue to file for "wait and see if Anthropic ships this later," because there's no action shipyard can take now that would be any less speculative than re-reading the same platform docs again next quarter.

## Session state file — why a file at all

Three failure modes the prose-narrated state was prone to:

1. **Token-expensive.** Every turn paid the cost of re-emitting the eight-or-nine-struct state in prose (the invariant line + status line + state-change banners). On a 200-turn session that's ~20–30K wasted tokens.
2. **Drift-prone.** The LLM could mis-remember which slot held which issue, which soft-cap counters needed decrementing on a release, or which fields had stale values. Mirroring to a structured file with explicit field names makes drift visible to anyone reading the file.
3. **Inspectable.** A separate dashboard (browser, Slack notifier, CI status webhook) had no machine-readable source. The JSON file is the source. External readers do not have to parse orchestrator transcripts to know what's in flight.

The JSON file is **not** working memory for dispatch decisions. The LLM still has to hold the model in its head to walk the dispatch tree. The file is the artifact, not the algorithm.

### Atomic-write contract — why through a helper

Every write goes through `plugins/shipyard/scripts/session-state.sh`, which writes to `<target>.tmp.<pid>` and atomically renames into place. POSIX `rename(2)` is atomic on the same filesystem (the tmp-in-same-dir pattern guarantees this), so a partial-write crash leaves the previous file intact — never a half-written JSON document that downstream readers would choke on. The helper also drops any leftover `.tmp.<pid>` files on cleanup, so a crashed update doesn't accumulate cruft.

The helper is the **only** way the orchestrator writes to the session file — never edit the JSON directly with `Edit` / `Write` / `jq` / a shell heredoc, because none of those preserve the atomic-rename contract.

### Write-through cadence — why batched per turn

The granularity is "after the LLM has updated its working-memory copy of the struct, write through" — not "between every line of orchestrator narration." A single turn that reconciles a completion, releases a slot, and dispatches a replacement does **one** `update` call with multiple `--set` flags (or a small handful of chained calls) at the end of the turn, not a flurry of one-field-at-a-time writes.

### Failure mode — write-through breakage

If a `session-state.sh update` call fails (exit code != 0), the LLM's working memory has already advanced but the file has not. The orchestrator:

1. Logs a single `[session-state] update failed: <exit code> — session file out of sync with working memory; continuing` advisory in the transcript.
2. Continues the turn — does **not** stall dispatch waiting for the file to come back. The working memory is authoritative for dispatch decisions; the file is the mirror.
3. Re-attempts the write on the next turn's natural update cycle. A persistent failure (e.g., disk full, permission lost) will surface as repeated advisories and the user can intervene.

Read-through failures (exit code 3 — session file does not exist on a `read` call mid-session) indicate the file was removed under the orchestrator (manual `rm`, disk failure, end-of-session cleanup that fired too early). Treat as a deferred failure: log the advisory, continue from working memory, and the next `update` call will recreate the file via the `init` recovery path. The orchestrator does not block on file recovery.

## Step 0.5 — why a dedicated orchestrator worktree

Worktree isolation is a property of the whole system, not just the leaves. Three failure modes a "just be careful with cwd" rule fails to prevent:

1. **Race conditions with the user.** The user may be editing files in the primary checkout while `/do-work` is running. An orchestrator-side edit in the same tree can clobber unsaved work or land a commit on a branch the user didn't expect.
2. **Branch confusion.** `git reset` (even `--keep` or `--soft`) moves HEAD. If the user runs `git status` mid-session and sees commits appear and disappear on the branch they were working on, that's actively misleading. A separate worktree means the user's `git status` answer is whatever they were doing before they ran `/do-work` — unchanged.
3. **Symmetry with dispatched agents.** Agents are forbidden from `cd`'ing out of their worktree, from `gh pr checkout`, and from parking on the default branch. The orchestrator holds itself to the same standard.

## Step 1.7 — why a per-repo override file exists

The collaborators API answer can be wrong for the policy the maintainer actually wants: an org repo may have read-only collaborators who should be trusted to *file workable issues* even though they can't push, or a personal repo's maintainer may want to trust a specific external contributor across the board (a long-standing collaborator who works via PRs). `.shipyard/trusted-authors.txt` lets the maintainer state the policy explicitly without depending on GitHub's permissions model.

Bot accounts (`dependabot[bot]`, `github-actions[bot]`, etc.) are NOT auto-trusted. A bot account is still a non-human author and its issue body should be treated as untrusted by default — Dependabot doesn't open *issues* in normal operation, but if a malicious dependency author tampers with metadata that surfaces in a bot-filed issue, the same threat model applies. Maintainers who want to trust a bot add it to `.shipyard/trusted-authors.txt` explicitly. The collaborators API does not return bot accounts, so the fallback path already excludes them.

Cache lifetime is **session-scoped**. Don't re-resolve mid-session — if the maintainer needs to dispatch against a newly-added author during the session, they restart `/do-work`. The cost of one restart vs. the cost of every turn paying a `gh api` call is asymmetric.

## Step 2 — why bucket 0.5 is a security gate

Public-repo issues filed by strangers are untrusted input — an attacker can craft a body that reads like a legitimate bug report ("`foo()` returns null. Suggested fix: add `helper.ts` with `<crafted payload>`") and an `issue-worker` dispatched against it would read the body as instructions, ship a PR, and arm auto-merge. If CI passes (subtle payloads can be designed to pass), the malicious code lands in `main` of a public repo on the maintainer's machine. Worktree isolation prevents *filesystem* damage outside the agent's worktree, but it does NOT prevent malicious code from landing in a merged PR. The author check is the **dispatch-time** filter that keeps strangers' issues out of the workable queue entirely. The defense-in-depth measure (issue body treated as untrusted in `agents/issue-worker/issue-work.md` step 2) sits *behind* this filter — it catches anything that slips through, but the first line of defense is "don't dispatch a worker against an untrusted author."

**Override path for a one-off review.** A maintainer who has reviewed an untrusted-author issue and wants `/do-work` to pick it up has two paths: (a) re-file the issue under the maintainer's own account using the same body (the new issue's `author` is the maintainer, who is implicitly trusted), then close the stranger's original as a reference; (b) add the stranger's login to `.shipyard/trusted-authors.txt`. Path (a) is the right default — it makes the "I vouch for this work" signal explicit on the issue, doesn't require a config change, and the original stranger's history is preserved as a comment/reference on the re-filed one.

## Step 2 — bucket-table mode-selection rationale

**Two-mode rendering exists to optimize for the reader's eye.** A single-row "table" carries table syntax overhead without the alignment payoff — pipes, header divider, column gaps — so it reads as more visual noise than information. A multi-row table benefits from column-alignment because the eye can scan counts in a column instead of bouncing through indented bullets. So the rule: count non-zero buckets; `≥2` → fixed-width aligned text table; `1` → single-line summary; `0` → empty-backlog one-liner.

The **`Workable`-row-always-prints-in-table-mode** rule has a subtle wrinkle worth calling out: when counting rows to pick the *mode*, `<W> == 0` does NOT count as a non-zero bucket — otherwise a session where everything is blocked would render a two-row "table" with a zero-count `Workable` row, which is back to the degenerate shape this rule is trying to avoid. The single-line one-bucket shape (`Workable: 0. Skipped: <N> issues in <bucket> (...)`) is the right surface when there's exactly one real bucket.

Action-recommendation sub-rows (`⚠ likely-clearable` / `⚠ likely-triageable`) do NOT count as their own bucket for mode selection — they're structurally a sub-row under their parent bucket; the parent's non-zero count is what flips the mode.

## Step 2 — inline action-recommendation rationale

Beyond the per-issue unblock recommendation list at the bottom, the orchestrator surfaces **per-bucket candidate counts** under each Skipped-bucket. The intent is to make the "this bucket has N issues you could probably act on right now" signal visible at the bucket itself, not just in a flat recommendation list at the bottom. The orchestrator does NOT auto-act on these — it only surfaces them; the user decides.

The bias is deliberately toward **surfacing too many** candidates rather than too few. A false-positive costs the user one glance, but a false-negative leaves work invisible.

The bucket-5 candidate computation is a pure regex scan over already-fetched issue bodies — cheap, no extra network calls. The bucket-6 candidate computation is O(blocked-issues × referenced-blockers) `gh issue view --json state` lookups, but the `blocker_state` cache (default-on) ensures any reference resolved here is reused by step 3d.2 — no double-paying. Bucket-6 / bucket-7 / step 3d.2 all read and write the same map. Combined extra cost on a backlog of ~50 open issues is well under 1 second wall-clock when parallelized.

## Step 3d — the `blocked:ci` sweep (and why the `blocked:agent-hard` referential sweep was deleted in #521)

`blocked:ci`'s premise is mechanical ("no new commits since the label was applied"), so a timestamp comparison is the right tool. The pre-#521 companion sweep — a `blocked:agent-hard` referential clear keyed on `Blocked by #N` resolution — was a *different* shape (referential, not timestamp-based) because its premise was "a specific other issue must close first." **#521 deleted that sweep** (step 3d.2 sub-sweep a) along with the `blocked:agent-hard` label: a dependency-wait now carries **no** label and is gated directly by the dispatch fetch's `Blocked by #N` body-reference filter, which already stops dropping the issue the instant the referenced blocker closes — making the label-plus-referential-sweep pure redundancy. A refuse (the other population the label bundled) now carries `needs-human-review`, which a human clears; there's nothing for a sweep to auto-clear. So step 3d.2 keeps only the timestamp-based `blocked:ci` sweep (3d.1) plus the legacy-migration (sub-sweep b) and `blocked:agent-soft` (sub-sweep c) sweeps. See the [`blocked:agent-hard` elimination](#blockedagent-hard-elimination-issue-521) section below for the full rationale.

**Why the `blocked:ci` sweep holds rather than clears on ambiguous signals.** A PR whose `blocked:ci` label was applied AFTER the head-branch commit (i.e. nothing has moved since shipyard gave up) MUST stay labeled. The `commit_ts > label_ts` comparison enforces this — if the commit timestamp is older than the label timestamp, the PR is genuinely stuck and the original "3 attempts, then give up" semantics still apply. Auto-clear fires only when a new commit has landed since the label was applied.

Failure modes that fall back to "held": the PR's head branch was deleted (rare but possible if the author force-pushed away or deleted the branch from underneath the PR — `gh api .../commits/$head_oid` errors); the `labeled` event aged out of the events API's pagination window (~90 days); a network blip on `gh api`. Any of these means the auto-clear can't make a confident judgment, so the safe default is to preserve the block.

## blocked:agent soft/hard split (issue #300)

**The gap.** Pre-#300 every worker `blocked: <reason>` return stamped a single `blocked:agent` label. Step 4's workable filter excluded the label, the only auto-clear path was step 3d.2's `Blocked by #N` referential sweep at session start, and step A.5's mid-session sweep had the same referential entry point. Issues bailed for *subjective* reasons (cannot-reproduce, ambiguous, scope-judgment, false-positive-against-duplicate-PR-search) were locked out of dispatch for the entire session AND across sessions until a human intervened — even though the bail had nothing to do with a referenced blocker. The reporter's lightwork session 2026-05-24 surfaced 24 open issues, many filed bullet-style without explicit acceptance criteria, where `blocked: ambiguous — no acceptance criteria and title is non-specific` was the predictable first-dispatch outcome. Once stamped, every issue became unreachable in any same-session retry. See [#300](https://github.com/mattsears18/shipyard/issues/300) for the session repro.

**Why split into `-hard` and `-soft`.** Of the 7 worker bail strings in `agents/issue-worker/issue-work.md`, only 3 represent genuine "needs human review" refusals (the prompt-injection / out-of-scope-action triplet — security gates that must not auto-retry). The other 4 are speculative judgments: a different worker reading the same body with slightly different priors could plausibly succeed. Treating both classes identically (uniform `blocked:agent` → permanent hide) was the structural flaw. The split surfaced the distinction as a class-typed label:

- `blocked:agent-hard` (the refuse class) kept the pre-#300 semantics: excluded from step 4's workable filter, auto-cleared only when referenced blockers close. **Eliminated in [#521](https://github.com/mattsears18/shipyard/issues/521)** — see the [`blocked:agent-hard` elimination](#blockedagent-hard-elimination-issue-521) section below. The label conflated *two* populations under "hard": a genuine refuse (no automated recovery path) and a dependency-wait (auto-cleared by the referential sweeps), and #521 routes each to a mechanism that already fits — refuse → `needs-human-review`, dependency-wait → no label (the `Blocked by #N` body-ref filter).
- `blocked:agent-soft` is documented as "subjective bail; auto-cleared at next session." Step 4's filter does NOT exclude it. Step 3d.2 sub-sweep c removes it at every session start. Within a session, `session_blocked_soft` + `blocked_agent.soft_retry_minutes` (default 30 min) prevents tight retry loops while still allowing the issue to be re-considered after the rest of the session has moved forward. **Unchanged by #521.**

**Why orchestrator-side classification (not worker-side).** The worker's return-string vocabulary stays unchanged — the 7 `blocked: <reason>` strings in `issue-work.md` map 1:1 to the orchestrator's reason→class table in `steady-state.md` step A.1. Reasons: (1) the existing worker fix-checks shims emit the same set of bail strings — making the classification orchestrator-side means each new worker mode can be added without re-deriving the table at the worker level; (2) the classification policy is operator-tunable in one place (the orchestrator prompt) rather than fanned out across 5 worker files; (3) older worker versions (cached deployments) continue to work without coordinated upgrades.

**Why time-based in-session retry (not files-touched).** The issue body offered two options for the within-session auto-clear: time-based (`blocked_agent_soft_retry_minutes`) or files-touched ("a different worker shipped a PR touching files the deferred issue's scope agent claimed"). Time-based wins on simplicity: zero new state (the timestamp is already in `session_blocked_soft`'s value), zero coupling to scope-agent path tracking (which would need to persist `claimed_paths` per soft-blocked issue across the whole session), and one clear knob (`soft_retry_minutes`). Files-touched would be a more semantically precise trigger, but the predicate is harder to compute correctly and the gain over a 30-minute timer is modest — most soft-bailed issues either resolve on the immediate retry (rare — the orchestrator's hardening between attempts is minimal) or wait until the session's next backlog re-fetch surfaces them naturally as the timer expires.

**Why `30 min` as the default `soft_retry_minutes`.** Sessions run in the 30 min – 3 hour range typically; a 30-minute soft-block window means a soft bail is re-considered roughly twice per long session. Tight enough to recover within the same session in the typical case, loose enough that a tight worker-bail-orchestrator-redispatch-worker-bail-again loop doesn't churn through tokens on the same issue. `0` (off; always re-consider immediately) and arbitrary positive values are both valid for testing or operator override via repo / user / local config.

**Legacy `blocked:agent` migration (re-pointed in #521).** Pre-#300 issues still carry the bare label. Sub-sweep b (in step 3d.2) migrates each one. Pre-#521 it migrated to `blocked:agent-hard`; #521 re-points it by the same refuse/dependency-wait discriminator the bail handler uses — a legacy issue with an open `Blocked by #N` becomes a dependency-wait (label removed, body-ref filter gates it) and any other legacy issue becomes a refuse (→ `needs-human-review`). The legacy GitHub label object stays registered for a manual cleanup; once a few sessions show zero legacy hits, the label and the migration code can be dropped.

## blocked:agent-hard elimination (issue #521)

**The insight.** `blocked:agent-hard` was applied for two unrelated reasons: (1) a **refuse** — `steady-state.md`'s bail-classification table stamped it on security / scope / prompt-injection refuses plus the conservative "(anything else) → hard" default, which have **no** automated recovery path (a human must look); and (2) a **dependency-wait** — a worker bailed "blocked by #N", hit the conservative default → hard, and the body carried a `Blocked by #N` reference. The session-start [step 3d.2 sub-sweep a] and the [#245] mid-session sweep existed *only* to auto-clear the label in the dependency-wait case when #N closed.

**Why the label was redundant for dependency-waits.** The auto-clear the dependency-wait case relied on is **already provided independently** by `/do-work`'s `Blocked by #N` body-reference filter (bucket 7 / step 4): it drops an issue while a referenced blocker is open and stops dropping it the instant the blocker closes. The `blocked:agent-hard` label on a dependency-wait was redundant with that filter; sub-sweep a was just reconciling the redundant label. So #521 drops the label for dependency-waits (they ride the body-ref filter, no label) and deletes both sweeps (sub-sweep a + the #245 mid-session sweep).

**Why a refuse routes to `needs-human-review`.** A security / scope / prompt-injection refuse has no automated recovery path — it's "Claude gave up; a human must actually look," exactly the semantics `needs-human-review` already encodes and that `/my-turn` already surfaces. Folding the refuse class onto `needs-human-review` removes the redundant label while preserving the worker's bail reason in the issue comment, and advances the binary-backlog north star (#515): every open issue is either workable-by-`/do-work` (no gate label) or workable-by-human (`needs-human-review`).

**Why this is safe to do without a referential auto-clear for refuses.** A refuse is *not* waiting on another issue to close — there's no mechanical signal that would let a sweep auto-clear it. That's the whole reason it's a refuse and not a dependency-wait. So losing the referential sweep for the refuse population costs nothing: those issues never had a mechanical clear path to begin with; a human clearing `needs-human-review` is the only correct resolution, same as it was when they carried `blocked:agent-hard` with no body reference (the pre-#521 "held" case).

## Step A.1 `shipped` — why agent worktrees are reaped immediately, not at end-of-session

**The gap (issue #282).** The original design deferred all agent-worktree reaps to end-of-session cleanup. That worked while there was no overlap between an issue-work worker's worktree and a later drain-phase fix-rebase dispatch — but `agents/issue-worker/fix-rebase.md` step 1 needs to `git switch <head>` where `<head>` is the just-shipped PR's branch (`do-work/issue-<N>`). Git enforces one-worktree-per-branch, so if the original issue-work worker's worktree is still on disk holding `do-work/issue-<N>`, the fix-rebase agent can't check out the head. The reporter's session (`lightwork-20260523T193509Z-9686`, PR #1117 against issue #1042) saw the fix-rebase worker work around this by creating a temporary `do-work/issue-1042-rebase` branch and force-pushing to origin's `do-work/issue-1042`, but the local artifacts couldn't be cleaned up cleanly — the worker returned `rebased #1117` successfully but left a temp branch behind, and its end-of-task contract ("leave your worktree on the PR's head branch") was unsatisfiable.

**Why Option C (immediate reap on `shipped`) over A or B.** The filing listed three options:

- **Option A — fix-rebase reaps the colliding original worktree before checkout.** Adds reap logic to a *worker* (the fix-rebase agent), which means propagating `SHIPYARD_ORCHESTRATOR_PID` into the subagent context and giving subagents permission to touch peer worktrees. The orchestrator is the principal that owns lifecycle decisions; pushing reap authority down into a worker inverts that relationship and opens a footgun (a misbehaving worker could reap a still-live peer).
- **Option B — drop the "leave worktree on head branch" rule for fix-rebase.** Documents the artifact-leak rather than fixing it. End-of-session cleanup is the safety net, but the temporary `<head>-rebase` branches still litter `.git/refs/heads/` until next session, and the `mergeStateStatus` log line on PR #M technically refers to a head branch that doesn't match the local checkout. Spec drift to dodge a fixable problem.
- **Option C — orchestrator reaps the issue-work worktree the moment `shipped` is reconciled.** The orchestrator already owns the audit-log audit / classify-lock infrastructure (see [`scripts/worktree-reap.sh`](../scripts/worktree-reap.sh) and [#284](https://github.com/mattsears18/shipyard/issues/284)). Reaping immediately reuses that machinery, frees the PR's head branch before any drain-phase fix-rebase could collide with it, AND reduces mid-session disk usage / worktree count. The end-of-session pass remains as the safety net for `blocked` / `errored` / peer-alive-deferred cases.

**Why peer-alive defers rather than force-reaps.** The classify-lock check should always return `dead` or `self-ancestor` on a just-returned agent (its harness PID is gone, OR it's our own orchestrator PID because the harness wrote our PID into the lock — the #138 self-ancestor case). A `peer-alive` classification at this moment means something unusual — maybe the worker returned but the harness hasn't torn down its bash process yet, or some race between the agent return and the orchestrator reconcile. Defer rather than risk yanking a still-live process's worktree; end-of-session cleanup is the catch-all. The cost of a deferral is one worktree lingering for a few minutes longer until end-of-session — far cheaper than the cost of a false-positive reap on a live process.

**Why drop the local branch ref too.** `git worktree remove` deletes the worktree directory but leaves the local branch ref (`refs/heads/do-work/issue-<N>`) pointing at the last commit the worker pushed. A subsequent `git switch do-work/issue-<N>` (in a fix-rebase agent's worktree) would succeed — but the branch's local HEAD is stale relative to origin's HEAD if anything has been force-pushed since (which can happen via a rebase or a fix-checks-only force-push). The fix-rebase agent's `git fetch origin "$HEAD_REF" && git switch "$HEAD_REF"` fetches the current origin ref but `git switch` to a local branch name resolves to the local ref. Dropping the local branch with `git branch -D` forces the next `git switch` to resolve via `origin/<HEAD_REF>` — guaranteed-fresh. `-D` (force) rather than `-d` because the branch may have unmerged commits relative to local `main` (which is normal — the canonical record is on origin, not this branch).

**Why not also reap on `blocked #<N>`.** A `blocked` return is a deterministic worker failure — the agent stopped before pushing, OR pushed partial work that needs human inspection. The worktree may hold uncommitted diagnostic artifacts; reaping it loses information. Leave `blocked`-return worktrees for end-of-session cleanup so a human inspecting the session log can `cd` into `.claude/worktrees/agent-<id>` and see what the agent left behind. The asymmetry is intentional: `shipped` = work is durably on origin, worktree is recoverable junk; `blocked` = worktree might be the only record of what went wrong.

## Step 4 — why the `author` field is fetched

The `author` field on the `gh issue list` payload has two uses, both downstream of this fetch:

1. **Step 4's client-side filter** enforces the trusted-author allowlist — without it, the post-fetch filter can't distinguish an issue filed by `<owner>` from one filed by `@stranger123`, and the security gate fails open. The search-qualifier syntax has no `-author:` form that can filter for "anyone except this list," so the filter is necessarily client-side.
2. **Step 7's author-trust computation** uses it (carried through into `ready_issues`) to decide `originating_author_trust ∈ {trusted, external}` at dispatch time — the third defense-in-depth layer. In normal operation the step 4 filter already dropped any external-author issue, so step 7 only ever sees `trusted` candidates. But if the filter regresses, the dispatch-time gate still fires.

## Step 4 — auto-triage priority rationale

When torn between two tiers, pick the lower-severity one — over-labeling `P0` poisons the priority signal for the rest of the session. Anything that would have been "taste / would-be-nice" doesn't get a priority label at all (and falls to the unlabeled tier at ranking time).

Skip any issue that already carries one or more `P0`/`P1`/`P2` labels — preserve the human judgment that set them, even if you'd have picked a different tier. Don't remove existing priority labels, and don't add a second one. If multiple priority labels somehow coexist on the same issue, leave them alone (a human can clean up); ranking will use the highest one. Legacy `P3` labels from older sessions are treated as unlabeled — re-triage them to a P0/P1/P2 tier if you'd file them, otherwise leave them be.

## Step 4.5a — why per-workflow CI aggregation matters

Every commit on `<default-branch>` typically has *multiple* workflow runs (e.g. `ci`, `release`, `claude-review`). They run independently. A single `success` entry in `gh run list` proves only that ONE workflow passed — a sibling workflow on the same SHA, or the latest run of the *same* workflow, can still be red. So the wrong question is "is the newest run green?" — the right question is "for each workflow, is its most recent completed run green?" Evaluate at the **per-workflow** granularity.

Two specific traps to avoid:

- **Don't filter `--status completed` in the `gh run list` call.** Doing so hides in-progress workflows entirely. If `CI` is still running on the newest commit but `Release Please` already finished green, filtering completed-only leaves only the Release Please success visible — and the aggregator falsely concludes "main is green." Fetch all statuses and treat each one according to its `status` field.
- **Don't aggregate across workflows on a single commit.** Workflow A finishing green on commit X tells you nothing about workflow B's status — they're independent. If you aggregate per-commit, a newly-pushed commit with `CI: in_progress` + `Release Please: success` looks "pending or green," which masks the prior `CI: failure` that's still the most recent known CI result.

A third trap — added after [#261](https://github.com/mattsears18/shipyard/issues/261):

- **Don't classify `conclusion == "cancelled"` as a CI failure verdict.** On actively-developed repos, the most-recent *completed* CI run on `main` is frequently a `cancelled` run that was superseded by a newer push (GitHub's concurrency-group auto-cancellation kicks in when a new commit lands on the same branch). That's normal traffic, not a failure — the next non-cancelled run on the newer SHA carries the actual verdict. Treating `cancelled` as red here makes step 4.5a enqueue a spurious `fix-main-ci` divert that the worker correctly returns `noop: main already green` against, burning ~3 min of Sonnet inference (~$2-3) per false positive. The fix is to skip-and-fast-forward past cancelled runs to the next non-cancelled completion within the 60-run window; if no such completion exists, fall through to `main_ci.status = "pending"` and let step-D's next refresh re-evaluate. The same skip-and-keep-looking rule covers the other cancellation causes (hung-then-timeout, manual cancel) because none of them are actionable by `fix-main-ci` either — there's no "fix" for a manual cancellation, only the next run's verdict matters. Worked example: session `dowork-20260523T173249Z-53595` (mattsears18/lightwork) saw `CI` workflow's most-recent completed run come back as `cancelled` (supersession on commit 9445f569) while the next-most-recent CI run on a newer SHA (0d700acd) was `success`. The pre-fix aggregator classified main as red on the cancelled run alone, enqueued a fix-main-ci divert, and the worker burned 178 s and ~129k tokens before returning `noop`.

A fourth trap — added after [#262](https://github.com/mattsears18/shipyard/issues/262):

- **Don't gate `main_ci.status` red on workflows that aren't required by branch protection.** Repos commonly have post-release recovery workflows, infrastructure-state probes, or scheduled cleanup jobs that fail for state-of-the-world reasons unrelated to code health — e.g. `mattsears18/lightwork`'s `Android Release Notes` workflow is a `repository_dispatch`-triggered helper that calls EAS to map a release tag to its Play versionCode and runs `fastlane play_changelog`; when Play Console doesn't yet have the release row (a "Store listings deferred" release like v2.26.1), it fails with `Could not find release for version code '234'`. That's not a CI failure — it's a human-judgment problem the release engineer has to resolve in Play Console. The pre-#262 "any workflow red → main red" rule treated such failures as making main red, enqueueing a `fix-main-ci` divert that the worker correctly returned `noop: main already green` against (because the per-PR required-checks gate was fine). Two costs: (a) ~$2-3 of wasted Sonnet inference per session for the no-op divert, (b) `main_ci.status` stays red indefinitely (across sessions) until the human resolves the infra issue, polluting every status-line print and blocking the green-state cleanup path. The fix is to scope the red-gating set to **branch-protection's required_status_checks** by default (with a config opt-out for repos that don't use branch protection): a workflow that isn't required can't make a PR un-mergeable, so it shouldn't be able to make main "red" either. Workflows outside the required set still get their status computed and surfaced as `non_required_red_workflow_names` (visible in the status line as `(infra: <name>)` and in the end-of-session summary) so the user retains visibility — they just don't trigger a divert. The 404 fall-through (repos with no branch protection) preserves pre-#262 behavior, so this is additive: opt-in via the config when you want explicit control, automatic via branch protection when you've already configured it, and pre-#262 behavior when neither signal is available.

## Step 5 — why the `-label:blocked:ci` filter is still correct

[Step 3d's auto-clear sweep](./do-work/setup/01c-label-recovery-refine.md#3-ensure-label-exists--recover-from-prior-session) already ran by the time the step-5 query fires — it stripped `blocked:ci` from every PR whose head-commit timestamp is newer than the label-application timestamp. So the PRs that still carry the label at this point are the genuinely-stuck ones (no new commits since shipyard gave up), and they should keep being skipped per the original "human needs to look" rule. The filter doesn't hide refreshed PRs anymore — those are unlabeled by step 3d and flow through normally.

## Step 6 — why scope pre-flight has a deferred shape

Scope pre-flight has two return shapes — ready and deferred. The deferred shape exists because some issues read clearly but aren't ship-able by a single worker: external decisions (legal/design), infrastructure provisioning, every-phase-depends-on-the-same-blocker cases. Dispatching an `issue-worker` against one of these just burns agent time before it returns `blocked` mid-implementation. The scoping agent reads the issue + codebase and decides up front whether a worker can finish it.

The bias is *slicing-by-default*, not deferral-by-default ([#298](https://github.com/mattsears18/shipyard/issues/298) reset this direction). A multi-phase body is a **slicing signal**, not a defer signal — the agent's job is to find the smallest dispatchable phase-1 slice and return it as a ready shape with `phase_1_scope` populated. Deferred is reserved for the cases where no first phase can ship independently (every phase needs the same unprovisioned infrastructure, every phase needs the same external decision). A worker that returns `blocked` after scoping costs more than a deferred issue that turns out to have been doable — but a deferred issue that should have been sliced is the more common failure mode in practice, and that's the one this prompt's bias optimizes against.

**Why a `defer_reason_class` is required on every deferred entry ([#298](https://github.com/mattsears18/shipyard/issues/298)).** Free-form `reason` text alone allowed plausible-sounding-prose defers to slip past the audit — "body explicitly recommends per-phase rollout" reads thoughtfully but is the exact failure mode the slicing bias targets. The five-value enum (`external-dependency`, `human-decision-required`, `untrusted-author`, `confirmed-blocker-still-open`, `confirmed-non-shippable-as-single-PR`) forces a commit; the entry surfaces in the pre-drain audit banner and end-of-session summary with its class visible. See the [Phase-slicing bias + classified defers](#phase-slicing-bias--classified-defers-issue-298) rationale below for the worked example and the five-value design.

**Why post a comment on the issue rather than label it.** Deferral is a *diagnosis*, not a *triage decision*. The orchestrator's diagnosis may be wrong; the human reading the comment can override by re-filing the issue with a different scope, or by accepting the diagnosis and escalating. Labels would be premature — they'd commit the orchestrator to a categorization the user hadn't reviewed.

## Step 6 — pre-scope orchestrator-side detectors (issue #346)

The pre-scope detector batch was added because a recurring class of audit-generated issues — anything proposing a new CI workflow, a new linter job, a new deploy step — produced the same structural failure: the scope agent reads the body, picks a `ready` shape (the codebase doesn't have the file yet, the change is bounded, no blockers reference it), the worker is dispatched, the worker generates the proposed `.github/workflows/*.yml` content, commits, pushes — and then `gh pr create` hits the auto-mode classifier's hard wall on `.github/workflows/` modifications and is denied. The branch sits in origin with the work done but no PR; the orchestrator's session summary surfaces it only as "needs manual PR open" rather than as a structural defer reason. Filed as [#346](https://github.com/mattsears18/shipyard/issues/346) after a `mattsears18/mattsears18.com` session hit this on a `dx-auditor`-filed CI security workflow proposal.

The failure mode is unfixable at the worker layer alone. The Don't list in [`do-work/dont.md`](../commands/do-work/dont.md), the worker hard rules in [`issue-worker/issue-work.md`](../agents/issue-worker/issue-work.md), and the auto-mode classifier all correctly forbid `.github/workflows/` writes — that's not the bug. The bug is that an issue proposing such a change should never have been dispatched as `ready` in the first place; the conflict between the body's request and the worker's hard rules is structural and human-only. The right surface to catch it is scope pre-flight, where the orchestrator already has the body in hand and can either dispatch a scope agent or defer.

**Why a pre-scope orchestrator-side detector instead of a scope-agent prompt instruction.** A scope-agent prompt could instruct the agent to defer on workflow-path mentions, but prompts aren't contracts — the same defense-in-depth posture that motivated [#302](https://github.com/mattsears18/shipyard/issues/302)'s orchestrator-side `evidence_pointer` validator applies here. The orchestrator can detect this case in a three-line string match; the scope agent's ~30 s of deliberation adds nothing the orchestrator doesn't already know, and a stale scope-agent prompt (an older version of the agent shipped before this detector existed) would silently bypass the gate. Putting the detector at the orchestrator makes the defer survive every scope-agent version — load-bearing mechanism at the orchestrator, informational at best in the agent prompt.

**Why `human-decision-required` is the correct `defer_reason_class`.** The workflow case fits the existing class taxonomy cleanly: a maintainer needs to evaluate the proposed workflow content for prompt-injection risk (the [GHSA workflow-injection class](https://github.blog/security/vulnerability-research/how-to-catch-github-actions-workflow-injections-before-attackers-do/)), secret-leak risk, and CI-correctness before the change can land. That's a human decision in the CI/infrastructure-policy domain — analogous to "needs CFO sign-off" (billing-policy domain) or "needs legal review" (legal-policy domain). The per-class shape table was expanded to make CI/infrastructure policy an explicit example, and the validator's `human-decision-required` rule was tightened to accept the structured prefix `Proposes .github/workflows/` so the orchestrator's own synthesized evidence_pointer survives the post-synthesis validator pass (though the detector's recording path explicitly skips the validator on synthetic defers — the validator-update is belt-and-suspenders for any future caller that might construct the same pointer shape).

**Why the detector is structured for extensibility.** The detector batch is structured as numbered sub-sections under "Pre-scope orchestrator-side detectors" precisely so additional detectors slot in without re-organizing the surrounding handler. Detector 2 (Claude-Code self-modification target proposals — `.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`) was added by [#348](https://github.com/mattsears18/shipyard/issues/348) following exactly that shape — a pure body string-match → a synthesized deferred entry with `provenance: "orchestrator-judgment"` and a structured `evidence_pointer` matching the validator's per-class shape. Future candidates: bodies that propose new GitHub Actions secrets, bodies that propose changes to `.github/CODEOWNERS`, bodies that propose changes to branch-protection rules via a config file. Each new detector follows the same shape and the section grows by addition rather than rewrite.

**Why the cross-references to drain.md 5.a/5.b matter.** The synthetic defer is `provenance: "orchestrator-judgment"`, which means [drain.md 5.a's pre-drain re-validation](../commands/do-work/drain.md#5a--re-validate-orchestrator-judgment-entries) will fire a fresh scope agent against it. Without the cross-reference, the re-validation would dispatch a scope agent that might return `ready` (a scope agent doesn't have the detector built in) — promoting the issue back to `raw_backlog` for worker dispatch and immediately reproducing the orphan-branch failure mode the detector exists to prevent. The cross-reference at the end of the detector section explicitly states that drain.md 5.a/5.b re-validations re-run the detector batch first; the detector is the load-bearing gate at every scope-dispatch call site, not just the initial pre-flight.

## Step 6 — Detector 2: Claude-Code self-modification target proposals (issue #348)

Detector 2 extends the pre-scope detector batch to catch a second structurally-unshippable class of audit-generated issues: anything proposing changes to `.claude/settings.json`, `.claude/settings.local.json`, or `.mcp.json` at the repo root. Filed as [#348](https://github.com/mattsears18/shipyard/issues/348) after a `mattsears18/mattsears18.com` session 2026-05-25 hit the failure mode against issue [#69](https://github.com/mattsears18/mattsears18.com/issues/69) — a `chore(dx): add Claude Code Stop hook` issue whose body literally included the 12-line JSON diff for `.claude/settings.json`.

The failure mode parallels Detector 1's `.github/workflows/` case but the mechanism is more aggressive: Claude Code's auto-mode classifier treats edits to these paths as **Self-Modification** and applies a HARD BLOCK that is **not cleared by user intent** — even an explicit "make this edit" instruction is rejected. The Edit tool, the Write tool, and the Bash-heredoc paths are all gated by the same intent check. A worker dispatched against such an issue reads the body, generates the proposed diff (using compute and tokens), attempts the Edit, gets a classifier denial, and then — per the failure-mode discussed in `shipyard:worker-preamble` § "After a classifier denial" — is structurally close to one of two bad outcomes: (a) a clean-but-wasted `blocked: classifier denied` return after burning the dispatch cost, or (b) the worse failure-mode the preamble exists to close (a fabricated-reasoning comment posted to the public issue thread when the worker reaches for "ways to make this work" after the deny). Detecting the conflict at scope pre-flight skips the entire failed dispatch.

**Why the path-set is narrow.** The detector matches three specific paths (`.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`) and explicitly excludes `CLAUDE.md` even though the issue body that motivated the detector flagged `CLAUDE.md` as a borderline self-modification target. The reason is asymmetric false-positive cost: many `CLAUDE.md` edits ship cleanly through workers (adding a new repo rule, updating documentation, fixing a typo in the configuration block); only a narrow subset (changes to behavior rules) hits the HARD BLOCK. A blanket `CLAUDE.md`-match would defer substantial work the worker could actually ship, while the three named paths are uniformly blocked. The detector errs on the side of letting work through; if `CLAUDE.md` cases prove common in practice, the detector can be extended without redesign.

**Why both Detector 1 and Detector 2 use `human-decision-required` as the same class.** Both detectors describe a structurally-identical failure: a body that proposes content for a path the harness/auto-mode classifier guards. The decision being named is the same in both cases — whether to accept the proposal — and both belong to a "policy domain" (CI/infrastructure policy for Detector 1, Claude-Code self-modification policy for Detector 2). Putting both detectors under `human-decision-required` keeps the class taxonomy small and matches how the maintainer reads them: a human reviews the proposed diff, decides whether to apply it, and either commits manually or closes as wontfix. The per-class shape table and the validator's `human-decision-required` rule were updated to accept both structured prefixes (`Proposes .github/workflows/`, `Proposes .claude/...`, `Proposes .mcp.json`).

**Defense-in-depth same as Detector 1.** The detector lives at the orchestrator (not in the scope-agent prompt) for the same reason Detector 1 does: prompts aren't contracts. A scope agent prompt could instruct the agent to defer on `.claude/settings.json` mentions, but a stale agent prompt or an agent that over-confidently picks `ready` would silently bypass the gate. The orchestrator's string match is the load-bearing mechanism; the agent prompt would be informational at best. The drain.md 5.a/5.b cross-references re-run the detector batch (now including Detector 2) before any re-validation scope-agent dispatch — same path the workflow detector takes — so a `.claude/settings.json`-proposing body can never slip past via re-validation either.

### Step 6 — Detector 2 extension: config-driven paths, `.claude/hooks/`, deliverable-vs-mention guard (issue #591)

[#591](https://github.com/mattsears18/shipyard/issues/591) extended Detector 2 along three axes after a `mattsears18/mksolutionsky.com` `--concurrency 4` session (`do-work-20260615T211627Z-76440`) burned **two full worker dispatches** (`#69` ≈103k tokens, `#70` ≈112k tokens) hitting the classifier wall on agent-config deliverables before the orchestrator recognized the pattern and pre-deferred the third (`#67`) by hand. The workers behaved correctly (single clean `blocked:` returns, no workaround attempts) — the gap was upstream: nothing in scope pre-flight pre-deferred the conflict.

1. **`.claude/hooks/` coverage.** `#69`'s deliverable was a Stop hook. A Stop hook is usually *wired into* `.claude/settings.json` (so the original three-path set caught it via that mention), but the hook *script files* live under `.claude/hooks/` and an issue can name only that path. Adding `.claude/hooks/` as a trailing-slash directory prefix closes the gap — any path under that directory fires the detector.

2. **Config-driven path set (`scope.self_modification_paths`).** The matched set moved from hardcoded to a config array (default `[".claude/settings.json", ".claude/settings.local.json", ".mcp.json", ".claude/hooks/"]`). The motivating reason from the issue: the HARD BLOCK is an **Auto Mode** property. A user *not* running under Auto Mode would have the Edit succeed normally, so for them the pre-defer is a pure false positive that strands shippable work in the human-review queue. Setting `scope.self_modification_paths: []` disables Detector 2 entirely for those users. The knob lives under `scope` alongside `diagnosis_reuse_hours` and is schema-validated (array of strings, default the four-path set).

3. **Deliverable-vs-mention guard.** The original detector was a literal "body contains the path fragment anywhere" match. That false-positives on **meta-issues that merely discuss these paths** — issue #591 itself is the canonical example: its body names all four paths while describing the *detector*, not requesting a config edit. The guard requires the path to appear in a **deliverable context** (acceptance-criteria / suggested-fix / "add"/"wire"/"create" framing, or a code-fence header naming the file to write) and explicitly does NOT fire when *every* occurrence is incidental meta-discussion (next to *"detector"*, *"classifier"*, *"pre-defer"*, *"scope pre-flight"*, or inside a `## Repro`/`## Summary` narration). The tie-break is asymmetric: when a body has both framings, **prefer firing** — a false-defer costs one human glance; a false-pass costs a ~100k-token wasted dispatch.

**Why the class stays `human-decision-required` (declining the issue's suggested `confirmed-non-shippable-as-single-PR`).** #591's suggested fix proposed `confirmed-non-shippable-as-single-PR` + the `<!-- do-work-needs-decomposition -->` decomposition marker. We declined per the verification-first rule: the suggested fix doesn't fit the actual structure. The deliverable IS shippable as a single PR — it's one config-file edit; it's blocked by a *policy* (the classifier's hard block), not by un-decomposability. `confirmed-non-shippable-as-single-PR` routes to `/decompose-epic`, which would try to shard a one-file edit into sub-issues — nonsensical. `human-decision-required` is exactly right: a specific policy decision is pending (apply the diff manually, or clear `scope.self_modification_paths`), which mirrors Detector 1's `.github/workflows/` defer. Keeping the class also preserves the existing recording path (`needs-human-review` + `<!-- do-work-human-decision-required -->` marker) unchanged.

## Step D — refresh trigger rules: worked example

With `--concurrency 2` on a session with 30 completions, the old fixed cadence ran 15 refreshes. Under event-driven + adaptive backoff:

- Completions 1, 2, 3 are all `shipped` returns; trigger 1 fires each turn. Suppose all three refreshes produce zero delta (main is green, all-authors PRs are below threshold, no new failed `@me` PRs). After completion 3, `refresh_zero_delta_streak = 3`.
- Completion 4 is another `shipped` return; trigger 1 would fire, but rule 4's adaptive-skip kicks in (`streak >= 3`) → defer. No refresh this turn.
- Completion 5 is a `blocked` return → no event-driven trigger. If `now - refresh_last_at < 5 min`, no time-based fire either. Skip.
- Completion 6 is a `green` from fix-checks → trigger 2 would fire, but `streak >= 3` → defer.
- Eventually the 5-min fallback (trigger 3) fires — say between completions 7 and 8 — and that refresh runs unconditionally. If it produces a change (a PR went red while we were skipping), the streak resets to 0 and event-driven trigger 1/2 fires resume normally on the next completion. If it still produces zero delta, the streak ticks to 4 and the next time-based check is another 5 min away.

Net: on a quiet session the refresh count drops well below the old fixed `completions / concurrency` rate. On a busy session where external state IS changing (a main-CI red flares, a PR pileup grows past 10), the streak resets the moment a change appears and refreshes resume at full event-driven cadence. The combination keeps refresh cost low on quiet sessions while staying responsive on busy ones.

**Triggers that explicitly do NOT fire a refresh:**

- A `blocked` / `blocked #<N> at fix-checks` / `blocked rebase #<M>` / `blocked main-ci-fix` / `blocked pr-batch-fix` return. No PR state changed (or the PR is stuck for human attention).
- An `errored` return. Same reasoning — no PR state changed.
- A `noop: not dirty (<reason>)` / `noop: main already green` / `noop: pileup already cleared` return that did not produce or resolve a PR. State may have drifted externally, but the agent's no-op signal alone doesn't justify a refresh; the 5-min fallback (trigger 3) picks it up.
- A `rebased #<M>` return from drain-phase fix-rebase. Drain-phase refreshes are disabled anyway (the drain guard at the top of step D).

## Step E — why the invariant line is load-bearing

The invariant line is the single source of truth for "did this turn do its job?" Whenever you find yourself ending a turn without one, you have skipped step C — the dispatch is unresolved. The `state=<state>` token also makes the per-turn write-through to the session state file visible in the same line: a transcript-only reader can confirm the file got the turn's state-mutation write (or surfaced a documented degradation) without inspecting `$SHIPYARD_HOME/sessions/<session-id>.json` directly.

The `idle_reason` constraints exist because vague reasons ("waiting for completions", "merge train draining", "nothing to do right now") are the recap pattern in disguise. If you can't name the queue-level reason the slot is empty, you haven't actually checked the queues.

Common causes of an incomplete turn that the self-check catches: (a) drafted a recap sentence and ended the turn before issuing the `Agent` tool call; (b) reconciled the completion but forgot the freed slot needs filling; (c) mistakenly believed "auto-merge will handle it" justifies skipping new dispatches.

## Dispatch rules — why soft-collision tiering exists

The soft-collision tier exists because the meta-bottleneck on a docs-heavy backlog is that every issue touches the same few additive-style files (`CHANGELOG.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`, and on the shipyard plugin repo itself, `commands/do-work.md`). Under the original all-hard regime, three workers all wanting to append a CHANGELOG entry would serialize down to one in flight at a time — `--concurrency 4` collapsed to 1 in practice. The soft tier caps simultaneous claimers per distinct path at `--soft-collision-concurrency` (default 3), trading "no merge conflicts ever" for "parallelism on additive paths, with trivial PR-land conflicts the orchestrator handles via fix-rebase."

**Soft caps are per-path, not per-claimer.** A worker claiming `CLAUDE.md` AND `CHANGELOG.md` consumes one slot in each path's counter, not one combined slot. Two workers both claiming `CLAUDE.md` plus a third workers claiming only `CLAUDE.md` puts all three in flight (3/3 on that path's counter); a fourth claiming `CLAUDE.md` parks.

**Soft paths never collide with hard paths of the same file** — they are evaluated against the soft cap, not the hard-collision rule. In practice nothing in the default soft set is also in the hard set, because the soft set is exhaustively additive-docs paths. If a user's `--soft-collision-path` extension somehow overlaps a hard-natured path, the soft tier wins for that path — that's the user's stated intent. Pick globs carefully.

**Cross-worker conflict resolution belongs to the orchestrator.** Agents have no visibility into each other's worktrees — they can't pre-resolve. When two soft-collision PRs both touch `CLAUDE.md`, the second one to land hits a DIRTY mergeStateStatus; the orchestrator dispatches a fix-rebase worker against it. The fix-rebase trivial-conflict-or-bail policy handles additive CHANGELOG/CLAUDE.md/docs conflicts cleanly in 95%+ of cases. If it bails, the PR surfaces in the end-of-session summary as still-DIRTY with a "soft-collision conflict on `<path>` — needs manual merge" note.

**Same-section edits are the accepted residual cost of the tier ([#507](https://github.com/mattsears18/shipyard/issues/507)).** The "trivially resolvable at PR-land time" premise holds when claimers edit *independent sections* of the same soft-collision file — append a CHANGELOG entry, add a bullet under a different heading. It does **not** hold when two or more claimers edit the **same section** of the same file: that yields a genuine *prose-content* conflict, not the coordinated manifest `.version` row + CHANGELOG top-of-file insert that fix-rebase's [§4.6 carve-out](../agents/issue-worker/fix-rebase.md#46-version-coordinated-manifest--changelog-re-number--trivial-resolution-issue-466) resolves deterministically. So fix-rebase **correctly** bails `blocked rebase #<M>: conflict extends beyond coordinated manifest+CHANGELOG rows` — and that bail is *expected*, not a worker bug. We deliberately chose to **document + accept** this (option 1 of [#507](https://github.com/mattsears18/shipyard/issues/507)) rather than make the soft cap section-aware (option 2 — record each candidate's touched heading and treat same-section claims as HARD). Section-granularity would make the premise strictly true, but it costs scope-agent return-shape changes, a richer collision check, and the throughput it buys back is small in practice (same-section collisions are the minority of soft-collision overlaps). Accepting the residual cost keeps the tier simple: the soft cap stays per-path, a same-section collision degrades to the existing still-DIRTY → human-hand-resolve drain branch, and the only thing #507 changed is making that outcome a *documented* expectation instead of an ad-hoc surprise. Repro that motivated this: session `do-work-20260609T025704Z-59825` ran issues #499/#500/#501 as a C=5 batch; all three added surfacing bullets to the **same `my-turn.md` "Pass B" section**, so PRs #504 and #506 went DIRTY and had to be hand-resolved (all five still shipped green — recoverable, hence P2).

## Dispatch rules — section-aware lockfile collision

The section-aware rule replaces an older boolean `touches_lockfile` flag. The boolean was too coarse: any two lockfile-touchers would serialize even if one was editing `overrides` and the other was editing `scripts`. Sections-as-claims lets disjoint sections co-run, which dramatically improves throughput on Dependabot-heavy or polyglot backlogs.

`package-lock.json` / `pnpm-lock.yaml` / `go.sum` / `Cargo.lock` (the generated artifacts) are never claimed as sections — they're regenerated additively post-merge by the package manager, and the merge-train's auto-rebase already handles their textual conflicts via the fix-rebase worker's regenerate-the-lockfile policy.

## Author-trust computation — defense in depth

In normal operation step 2's bucket 0.5 and step 4's client-side filter have already dropped every external-author issue before it reaches `ready_issues`, so the candidate's trust is virtually always `trusted` at the dispatch point. The per-dispatch computation is **defense in depth** — the dispatch-side companion to the intake-side `external-author-gate` GitHub Action and the dispatch-time allowlist filter. If both principal gates somehow regress simultaneously (the GitHub Action is disabled, the orchestrator's bucket-0.5 / step-4 filter is bypassed), step 6 of the worker still refuses to arm auto-merge for an external-origin PR — labeling it `needs-human-review` instead.

## Step E — over-defer self-check rationale

The over-defer self-check (`defers_this_turn > 0 AND dispatched_this_turn == 0 AND in_flight < concurrency`) was added in response to issue [#246](https://github.com/mattsears18/shipyard/issues/246), a session against `mattsears18/lightwork` (session id `e4f91771`, 2026-05-23) that entered drain while 13 workable issues remained.

**The failure mode.** After 5 PRs shipped, the termination assertion's step 4 fresh-fetched 13 net-new issues (`[884, 891, 1042, 1048, 1049, 1050, 1051, 1052, 1073, 1075, 1076, 1077, 1090]`). The spec says: if the net-new set is non-empty, append to `raw_backlog` and retry from step C. But the orchestrator had already added those issues to `deferred_issues` in working memory on earlier turns using its own judgment (not scope-agent returns). By the time the termination assertion ran, the `deferred_issues` subtraction made the net-new set appear empty — so drain fired.

The per-turn `defers_this_turn` token makes this pattern visible: a turn with `defers_this_turn > 0 AND dispatched_this_turn == 0 AND in_flight < concurrency` is the telltale signature. When all three are true, the orchestrator is draining the workable queue through self-defers rather than through actual work, which is the failure mode.

**Why the check isn't simply "never defer without a scope agent."** Orchestrator-judgment defers are sometimes legitimately appropriate mid-session — e.g., an issue whose body clearly describes a 10-step infrastructure migration that no one would expect a single worker to complete. Requiring a scope-agent invocation for every such issue would double the setup cost. The design is: allow orchestrator-judgment defers, but (a) tag them as such via `provenance: "orchestrator-judgment"`, (b) surface them in the invariant line so they're visible, and (c) re-validate them before drain fires. The over-defer self-check is the real-time signal; the pre-drain re-validation pass is the final gate.

**Why `defers_this_turn` resets per turn rather than per session.** A session-level `defers_total` would obscure whether the deferring is concentrated in a few turns (likely legitimate: a scope-refill burst that returns a cluster of genuinely unworkable issues) versus spread uniformly across many turns (likely the "one at a time" over-deferring pattern). A per-turn counter exposes the pattern clearly at the turn level.

## Pre-drain re-validation of deferred entries

The pre-drain re-validation pass ([`drain.md` step 5](./do-work/drain.md#pre-drain-re-validation-of-deferred-entries)) exists because the termination assertion's step 4 contains a structural exploit: it subtracts `deferred_issues` issue numbers from the live backlog before computing the net-new set. An orchestrator that self-defers every remaining workable issue can make the net-new set appear empty and proceed to drain — even though 13+ issues are still on the live tracker and would have been dispatchable. Two sessions exposed the same exploit on different sides of the `provenance` discriminator:

| Session | Provenance class | Issue | Failure mode |
|---|---|---|---|
| `e4f91771` (2026-05-23, `mattsears18/lightwork`) | `orchestrator-judgment` | [#246](https://github.com/mattsears18/shipyard/issues/246) | Orchestrator self-deferred 13 workable issues using its own working-memory judgment (no scope-agent dispatch); termination assertion subtracted them and declared drain. |
| `shipyard-do-work-20260524T165717Z-7245` (2026-05-24, `mattsears18/lightwork`) | `scope-agent` | [#299](https://github.com/mattsears18/shipyard/issues/299) | JIT scope pre-flight at C=1 returned `deferred` on each of 15+ workable issues in sequence; termination assertion subtracted them all and declared drain — but the spec's #246 fix only covered the orchestrator-judgment branch, so step 5 was a no-op and the audit banner was skipped. |

The same exploit, the same response: re-validate before drain fires.

### The orchestrator-judgment worked example (session `e4f91771`)

Three of the deferred issues were incorrectly self-deferred:

| Issue | Orchestrator's defer reason | Why it was wrong |
|---|---|---|
| #1075 | "Gated on #1077 — pushing metadata to managed-publishing-ON Play creates approval-queue noise" | Soft concern (noise in an off-by-default setting), not a hard block. The referenced blocker (#1077) was open, but the defer reason was an over-cautious interpretation of that issue. |
| #891 | "Blocked on #1052 per issue body's recommended fix path" | Issue body recommended SDK 56 upgrade as one fix path, not the only one. Targeted alternatives existed. |
| #1090 | "Just-filed; fix requires interactive `eas credentials` setup OR sensitive credential wiring in CI" | Option B fix path (eas.json + CI materialization) was fully automatable. The orchestrator cited Option A's manual nature without investigating Option B. |

After user intervention, the orchestrator re-evaluated without consulting any new spec — simply being less conservative on the second pass was sufficient to dispatch #1090 and #891. This means the self-defers were not grounded in code evidence; they were speculative.

**Why re-validation against named-blocker state is the right mechanism for #1075-style defers.** If the defer reason names a specific blocker (`Gated on #1077`), the right check is: is #1077 still OPEN? If CLOSED or MERGED, the blocker has resolved and the defer is stale. A single `gh issue view` call per named blocker is cheap and definitive. No scope-agent invocation required for named-blocker defers — the state check is the answer.

**Why scope-agent re-dispatch is the right mechanism for free-form orchestrator-judgment defers.** If the defer reason is a free-form judgment without a specific named blocker ("too complex for a single worker", "needs external decision"), there's no mechanical state to check. The only authoritative answer comes from re-running scope pre-flight. The cost is one scope-agent invocation per free-form defer that actually reaches the pre-drain check — and if those invocations return "ready," the work gets done instead of being silently skipped.

### The scope-agent extension (session `shipyard-do-work-20260524T165717Z-7245`)

The #246 fix was originally written under the assumption that `scope-agent` provenance was evidence-backed ground truth — the spec said the drain transition "accepts these without re-validation." [#299](https://github.com/mattsears18/shipyard/issues/299) showed the assumption doesn't hold in practice. The structural failure shape was identical to the #246 session, just on the other side of the provenance discriminator:

1. Scope pre-flight fires for top candidate (rule 5 / JIT at C=1).
2. Scope agent reads `enhancement, web, ios, android` issue body and returns `deferred` ("cross-platform — looks like a multi-PR migration").
3. Orchestrator records `{ provenance: "scope-agent", reason: <free-form>, deferred_at: ... }`.
4. Next dispatch: another candidate, another scope-agent defer, same pattern.
5. `ready_issues == 0`, `raw_backlog` drains into `deferred_issues`, `in_flight == 0` → termination assertion runs.
6. Step 4 fresh fetch: 24 live issues. Union of `deferred_issues` covers most of them → net-new = 0 → drain fires → session exits.
7. Step 5 was a no-op because the gating condition required `orchestrator-judgment` entries — none existed; all defers were `scope-agent`. No re-validation happened, no audit banner emitted, no signal to the user that 15+ issues were silently dropped.

The over-defer self-check in `steady-state.md` step E (added by #246's same PR) fired but only added an `idle_reason` and ran the same fresh fetch — the `deferred_issues` subtraction still won.

**Why scope-agent defers are also speculative in practice.** The scope-agent prompt is permissive — it's designed to err on the side of deferring when the body suggests breadth (cross-platform, multi-PR, ambiguous acceptance criteria) so the orchestrator doesn't ship a half-fix on an issue that genuinely needs a human's scoping pass first. But the prompt's permissiveness means a single conservative read of a body that *looks* multi-PR (but is actually a tractable single-file fix) produces a `deferred` return that the orchestrator then treats as authoritative for the rest of the session. The rationale's original distinction — orchestrator-judgment is "speculative working-memory state worth re-checking" vs. scope-agent is "evidence-backed" — turned out to be a false dichotomy. Both are speculative; both need the re-validation.

**Why re-dispatching a fresh scope agent is the right mechanism for scope-agent re-validation.** Same reason it's the right mechanism for free-form orchestrator-judgment defers: there's no mechanical state to check (the defer reason is a free-form prose judgment from the scope-agent prompt; no named blocker to look up). The only authoritative answer comes from re-running scope pre-flight. Cost is bounded by `|deferred_issues with scope-agent provenance|` — typically 3–15 per session at C=1, where the JIT pre-flight pattern produces the most defers; at higher concurrency the cost is lower because scope-refill batches amortize.

**Why not cheaper alternatives (variant B from the issue body).** The #299 issue suggested a variant B: gate re-validation on age + count (e.g., re-validate only when `|scope-agent defers| > 3` OR oldest is older than M minutes). It's cheaper but leaves a smaller failure window — a session that defers exactly 3 issues never re-validates. The cost asymmetry favors variant A: a Haiku-pinned scope-agent dispatch is cheap (≈1k tokens), and the alternative (silently dropping a workable issue) is expensive (the issue sits open another N hours until the next session picks it up). The bounded worst case (15 scope-agent invocations on a 15-defer session) is acceptable; the unbounded worst case in variant B (any defer count below the threshold never gets re-validated, indefinitely) is not.

### Why the failure couldn't be caught by step 4's fresh fetch alone

Step 4's fresh fetch compares the live backlog against the union of `in_flight`, `ready_issues`, `raw_backlog`, `deferred_issues`, and closed-this-session issues. An issue that's in `deferred_issues` is excluded from the net-new set regardless of whether the defer was authoritative. The step 4 check was correctly implemented in both `e4f91771` and the `7245` session (both did fire a live fetch); the issue was that `deferred_issues` itself was artificially inflated — by working-memory defers in `e4f91771`, by conservative scope-agent returns in `7245`. The pre-drain step 5 is the fix in both cases: it shrinks `deferred_issues` by re-validating its entries before the termination assertion can use the inflated set to declare "empty net-new."

## Phase-slicing bias + classified defers (issue #298)

The #246 + #299 pre-drain re-validation fix was structural — it stops the orchestrator from constructing an empty net-new set entirely through self-defers. But it left the deeper problem from session `dowork-20260524T112421Z-63727` (mattsears18/lightwork) untouched: when the re-validation fires, the fresh scope agent **re-confirms the original defer** because the body really IS multi-phase. Re-validation as a gate against bad provenance, yes; re-validation as a way to find work in a backlog of legitimately-multi-phase issues, no. The user had to intervene three times in one session with messages like "why do you keep ending these do-work sessions early? there are still 24 issues in the backlog." Each time the orchestrator re-evaluated and successfully dispatched on issues it had just deferred — by phase-slicing them.

The session shipped 7 PRs against issues the initial pass had deferred — every one of them was multi-phase per body, every one was sliced into a dispatchable phase-1 PR with phases 2-N filed as follow-up issues. The pattern was identical across all seven: the original "deferred — multi-phase per body" call wasn't wrong (the body really was multi-phase), it was just the wrong response. The right response is to **find the phase-1 slice and dispatch on that**.

### Why the scope-agent prompt needs to bias toward slicing, not deferring

The original prompt (`If your read of the issue + codebase suggests the fix isn't a single-worker job — multi-PR migration, SDK upgrade, external decision, infrastructure provisioning — return the deferred shape ... When in doubt — default to ready.`) reads as: "look for reasons to defer, defer if you find any, otherwise ready." The new prompt (`Default to slicing, not deferring. If the issue is multi-phase, RETURN the smallest dispatchable phase-1 slice as a ready shape with explicit phase_1_scope text ...`) reads as: "look for the phase-1 slice first, defer only if there's no first phase that can ship independently." This is the same kind of inversion #299 made on the re-validation axis: the spec previously assumed scope-agent defers were authoritative (they weren't); this PR assumes scope-agent defers happen too easily on multi-phase bodies (they did).

The cost asymmetry favors the slicing bias: a phase-1 slice that turns out to be wrong is just a returned-blocked PR (cheap — the worker bails), whereas a deferred multi-phase issue silently drops a sliceable item until the next session. The bias should default to slicing because the cost of a wrongly-sliced ready return is lower than the cost of a wrongly-deferred multi-phase issue.

### Why `defer_reason_class` is a strict five-value enum

The original `deferred_issues` entries carried only a free-form `reason` field. End-of-session summary printing `#1131 — body explicitly recommends per-phase rollout` reads like the orchestrator made a thoughtful call, but in practice that's the orchestrator-judgment failure mode from #246 — the reason is plausible-sounding prose that papered over a sliceable item. By forcing every entry to declare a `defer_reason_class` from a strict five-value enum (`external-dependency`, `human-decision-required`, `untrusted-author`, `confirmed-blocker-still-open`, `confirmed-non-shippable-as-single-PR`), the orchestrator can no longer hide a "I just didn't want to slice this" defer behind a plausible reason — the entry has to commit to a category, and the category surfaces in the pre-drain audit banner and the end-of-session `Deferred:` block.

The five values intentionally don't include "multi-phase per body" as a class — that's exactly the failure mode this change targets. A multi-phase body is not a deferral signal; it's a slicing signal. An entry that genuinely can't be sliced (every phase depends on the same external decision, every phase depends on the same un-provisioned infrastructure) gets `confirmed-non-shippable-as-single-PR` — the only class that absorbs the "I tried to slice and couldn't" diagnosis. A spec violation flag fires when a `confirmed-non-shippable-as-single-PR` defer is re-validated and the fresh scope agent returns a `phase_1_scope`-bearing ready shape (the original defer was a slicing miss, not a true unsliceable case).

### Why `would_be_dispatchable_as_phase_1_if` is encouraged but optional

When the original scope agent does conclude an issue is genuinely unsliceable today, the next question is: *what would change to make it sliceable?* The `would_be_dispatchable_as_phase_1_if` field is the answer — a one-line description of the unblocking condition. The pre-drain re-validation pass reads it and passes it to the fresh scope agent ("the original defer said phase-1 would be dispatchable if X — check whether X is true now"). This makes re-validation evidence-driven rather than re-discovery-driven: the fresh scope agent has a concrete hypothesis to test rather than re-deriving the slicing question from scratch.

The field is *encouraged but optional* because not every defer has a clean unblock condition (an issue gated on a legal review may genuinely be unblock-able only by "legal signs off") and forcing the agent to fill it would push toward fabricated content. When absent, the re-validation pass falls through to a full re-scope without the priming hint — the same path as a fresh scope agent invocation on any other defer.

## Evidence-backed defers (issue #302)

#298 introduced the five-value `defer_reason_class` enum to prevent plausible-sounding-prose defers from sneaking through as orchestrator-judgment. The enum stopped one failure mode (free-form `reason` text alone) but left the deeper one unaddressed: **the prompt instruction was still permissive enough that a scope agent could pick any class and produce a `reason` that sounded mechanical without actually being grounded in evidence**. Session experience on `mattsears18/lightwork` (most enhancement issues carry `labels: enhancement, web, ios, android, P2` and one-paragraph bodies) confirmed the gap: a scope agent reading those bodies would routinely return `deferred` with reasons like `"cross-platform — looks like a multi-PR migration"` and pick `confirmed-non-shippable-as-single-PR` as the class. The class was a valid enum value; the reason was speculative judgment.

The four offending shapes from issue #302's body:

- *"Looks like a multi-PR migration"* — almost any non-trivial cross-platform issue can read this way at a glance.
- *"Touches three platforms — likely complex"* — cross-platform doesn't entail multi-PR; many such issues are tractable single-file fixes.
- *"UX change — probably needs design review"* — the scope agent isn't qualified to gate on design intent.
- *"Body is vague"* — a worker-side bail (`agents/issue-worker/issue-work.md` step 2's `blocked: ambiguous` path), not a scope-side defer.

The downstream cost is asymmetric: a single permissive defer locks the issue out of dispatch for the rest of the session (and #299's drain-time re-validation re-confirms the same defer if the agent's read of the body hasn't changed — which it usually hasn't, because the body itself hasn't changed). Each false-positive scope-agent defer is structurally similar to a refuse-class `needs-human-review` block (formerly `blocked:agent-hard` before [#521](https://github.com/mattsears18/shipyard/issues/521)) except worse: the scope-agent defer that does *not* surface via `needs-human-review` has no human review surface at all, and the only way the issue gets re-considered is on the *next* `/do-work` invocation.

### The fix: mechanical evidence per class, validated by the orchestrator

The fix has two parts — a prompt change and an orchestrator-side validator. The prompt alone wouldn't suffice (a sufficiently confident agent can still produce speculative `evidence_pointer` text); the validator alone wouldn't suffice (without the prompt change agents would still try to defer first, then have their defers rejected at high cost). Together they form the defense-in-depth pattern the rationale uses elsewhere — prompt as first line, mechanical check as load-bearing second line. The same posture as `issue-worker.md` step 2's body-vs-codebase rule: the worker re-derives the implementation from the codebase even when the body suggests one.

**Prompt change.** The scope-agent prompt (setup.md step 6) now reads: *Default to slicing, not deferring. ... Return the deferred shape ONLY when you can cite SPECIFIC MECHANICAL EVIDENCE for the defer — a named open blocker issue (`Blocked by #N`), a missing dependency the worker can't reasonably install/lock/test/ship in the same PR, multi-service coordination that requires synchronized deploys, an external vendor change the worker can't move, or a referenced design artifact (Figma, RFC) that hasn't been imported into the codebase. Speculative reads of the body — "looks like a multi-PR migration", "touches three platforms — likely complex", "UX change — probably needs design review", "body is vague" — are NOT evidence and will be rejected by the orchestrator's per-class validator.*

The four rejected phrases are listed verbatim in the prompt because they're the exact shapes the prior sessions produced. Naming them is more effective than abstract guidance ("avoid speculative judgment") — an agent that sees the canonical bad-pattern catalog can pattern-match its own draft against it before returning.

**Orchestrator-side validation.** Every deferred return now carries an `evidence_pointer` field that the orchestrator validates against a per-class shape table before the entry is recorded. The shapes are intentionally lightweight string matches the orchestrator can run inline:

- `confirmed-blocker-still-open` → must contain at least one `#<digits>` reference; the orchestrator does a single `gh issue view <N> --json state` per cited blocker to confirm it's still OPEN.
- `external-dependency` / `human-decision-required` → must not contain speculative-judgment words (`looks like`, `probably`, `likely`, `seems`, `feels`); `human-decision-required` also rejects generic phrases without a specific decision named.
- `untrusted-author` → must contain `author: <login>` matching GitHub's login regex.
- `confirmed-non-shippable-as-single-PR` → must start with one of: `Missing dependency:`, `Multi-service coordination:`, `Multi-PR sequence:`, `Body cites <artifact>:`. The structured prefixes prevent the same speculative-text shape that motivated this issue.

A deferred return whose `evidence_pointer` fails validation is **rejected** — the orchestrator does not record it in `deferred_issues`. Instead, the issue is pushed back onto `raw_backlog` (preserving rank), an explanatory comment is posted on the issue (so the human can see the rejection), and the next dispatch re-scopes the issue with a fresh scope agent. The rejection is logged with the specific failure reason (`cited blocker #1077 is CLOSED`, `contains speculative phrase "looks like"`, `missing required prefix`) so end-of-session debugging has a concrete trail.

### Why this is the right place to fix it (upstream vs downstream)

#299 added drain-time re-validation as the downstream safety net (every scope-agent defer gets re-dispatched before drain can fire). That's load-bearing — the drain gate prevents the session-termination failure mode. But re-validation runs once per session, at the very end, and burns one scope-agent invocation per defer to do so. If 15 scope-agent defers reach the drain gate, that's 15 fresh scope-agent invocations just to confirm what was already true at scope time. The upstream fix (this issue) prevents the speculative defers from being recorded in the first place — the rejection happens inline at scope time with no extra agent dispatch (the per-class shape checks are pure string/regex matches; only `confirmed-blocker-still-open` does a single cheap `gh issue view` per cited blocker).

The two fixes compose. #299 is the structural gate that prevents premature termination. #302 reduces the input to that gate — fewer speculative defers reach it, so fewer wasteful re-validations happen at drain time. A session with no speculative defers (the steady state we're targeting) sees no re-validations at all because all the defers carry valid evidence and the gate is a no-op. A session with speculative defers gets them rejected inline; a session that somehow still produces a bad defer that passes the inline validator (e.g., a `Blocked by #1077` defer where #1077 is OPEN but the agent is mistaken about it being load-bearing) still gets caught by the drain-time re-validation. Both gates are needed because they catch different shapes of failure: inline catches obviously-speculative text, drain-time catches "evidence looked valid but turned out to be wrong on second look."

### Why re-validation flips an old defer to rejected, not just re-confirmed

The drain-time re-validation in `drain.md` step 5.b was also tightened: when a fresh scope agent re-confirms a defer, the new `evidence_pointer` is also validated against the per-class shape table. If the new pointer fails validation, the entry is promoted to `raw_backlog` and the issue is re-scoped — same path as the inline rejection at scope time. This closes the loophole where a re-validation could re-confirm a defer with stale speculative evidence indefinitely (a "looks like multi-PR" defer at scope time would still be "looks like multi-PR" at drain time, and pre-#302 the re-validation would just re-confirm and skip drain — the issue would stay dropped). Post-#302, the re-validation forces the agent to produce mechanical evidence; if the agent can't, the issue gets re-queued.

## Soft drain — why it's safe to let agents finish

Agents commit at logical milestones (TDD test → commit, implementation → commit) and PRs are opened with `--auto`. Letting an in-flight agent finish naturally never loses work. Killing it mid-edit could.

Substring matching on the trigger phrases is deliberately avoided. Phrases like "don't stop yet" or "I'll drain it later" do not trigger drain mode — only a trimmed body exactly matching `stop` / `drain` / `/do-work stop` does.

## Termination — why the merge train continuing isn't a stop signal

Two independent processes are running: (1) the dispatch loop that fills `--concurrency` slots from the backlog, and (2) the merge train that lands open PRs as their checks turn green. The merge train continues without you. The dispatch loop dies if you stop dispatching. Treat them as orthogonal — never use "the train will drain on its own" or "auto-merge handles it from here" as a justification to stop dispatching new work.

**Don't ever ask the user "should I keep working, summarize, park, or stop?"** Termination is mechanical. As long as ANY of `in_flight` / `failed_prs` / `ready_issues` / `raw_backlog` / `divert_queue` is non-empty, you keep dispatching. Drafting a question about whether to continue, summarize, or idle is itself the bug.

## End-of-session drain — why it exists past the dispatch loop's end

Once the dispatch loop's queues go empty, some PRs the orchestrator opened may still be `pending` CI or waiting for auto-merge. **Don't terminate while the merge train is still draining.** Two independent processes are running: the dispatch loop (now empty) and the merge train. The merge train runs without dispatching anything, but it can still go red mid-flight — a flaky test surfaces, a sibling merge causes base drift on a queued PR, a dependency update breaks at minute 18. If you stop monitoring at minute 15, those failures sit unfixed until the next `/do-work` session.

The drain phase keeps the orchestrator alive past the dispatch loop's end, watching the merge train and dispatching fix-checks workers against newly-red PRs, until either every session-opened PR has settled OR the train has clearly stalled.

**Why the drain handles DIRTY PRs via fix-rebase.** Long sequences of merges advance main faster than open PRs can rebase onto it, leaving PRs in `mergeStateStatus: DIRTY` with no failing checks — just stale base. Auto-merge won't fire on a DIRTY PR. A drain-phase fix-rebase dispatch rebases onto current main and force-pushes; the rebased branch re-enters the merge train naturally.

**Why fix-rebase re-dispatch is split between deterministic-failure and rate-limit gates.** The earlier "one-shot per PR per session" rule conflated two failure modes that need different handling, and [#265](https://github.com/mattsears18/shipyard/issues/265) was the cost of the conflation:

- **Deterministic failure** (`blocked rebase` return). A non-trivial merge conflict produces the same outcome on retry — the conflict markers don't change unless main advances enough to alter the conflict surface. Re-dispatching against the same conflict is wasted spend. This is the original rule's case, and the `rebase_blocked_prs` set still gates it: a PR that returns `blocked rebase` stays out of `D_dirty` for the rest of the session.
- **Merge-train race** (`rebased` return followed by sibling-merge-induced DIRTY). A successful rebase that gets undone by a subsequent main-advancing merge is NOT a stuck state — it's a race the merge train can win if the rebased branch's CI lands before the next conflicting merge. The original rule treated this case the same as a deterministic failure and refused to re-dispatch, stranding the PR. The new `rebase_success_counts` map tracks successful rebases per PR and allows up to 3 re-dispatches before declaring the PR rate-limit-capped (the cap mirrors the 3-attempt fix-checks circuit breaker — same cost ceiling). After the cap, the PR is treated as settled for this session: the merge train is advancing faster than rebase can keep up, and trying further would only burn workers without converging.

The session that surfaced this bug — `dowork-20260523T173249Z-53595` on `mattsears18/lightwork` — saw PR #1083 (CLAUDE.md conflict) manually rebased to f13d4e78 then re-DIRTY'd minutes later when #1101 ("split CLAUDE.md into root + .claude/rules/") merged. The drain noticed the new DIRTY but the orchestrator interpreted "one-shot per PR per session" literally and refused to dispatch, leaving #1083 stranded at session exit when the orchestrator was within a few minutes of being able to handle it autonomously. The combined gate (deterministic-failure exclusion + rate-limit cap on successes) is the smallest spec change that distinguishes the two cases without re-introducing infinite-loop risk on adversarial merge patterns.

**Why fix-rebase is drain-only by default, but not unconditionally ([#1034](https://github.com/mattsears18/shipyard/issues/1034)).** The mode exists to keep the merge train flowing past base-drift hiccups while the orchestrator is winding down, and that's still the primary reason the drain owns most of the D_dirty backlog. But the earlier premise here — "steady-state dispatch never produces a DIRTY PR (a freshly-shipped PR is always on a fresh branch)" — was false on any repo whose release convention bumps a shared manifest/CHANGELOG row on every merge, which is exactly this repo's own documented rule. A freshly-shipped PR *opens* on a fresh branch, but the instant any sibling PR merges past it, its version row is stale and `mergeStateStatus` flips to DIRTY — mid-session, not just at drain. At `--concurrency 1` this isn't a race the way (a)/(b) below describe, it's deterministic: there's only one slot, so there's no "PR auto-merge was about to rebase anyway" and no fix-checks worker to interfere with. See [Don't dispatch fix-rebase mid-session outside the three conditions](#dont-dispatch-fix-rebase-mid-session-outside-the-three-conditions-issue-1034) below for the corrected rule and the conditions under which a mid-session dispatch is now permitted; the drain-only restriction still applies outside those conditions, for the reasons (a)/(b) originally cited: dispatching mid-session with a worker already live on the same branch would either churn a branch auto-merge was about to rebase anyway, or interfere with a fix-checks worker that is mid-flight on it.

**Why the drain ceiling is progress-based, not wall-clock (issue [#374](https://github.com/mattsears18/shipyard/issues/374)).** The original drain had a hardcoded 120-min wall-clock ceiling as the safety net. It fired on the wrong signal: a healthy multi-PR merge train with full E2E sharding (3 shards × ~10–15 min) + Lighthouse (~9 min) + release-please cascades (each sibling re-DIRTY'd on every merge, then rebased + re-CI'd for another 15–25 min round-trip) can legitimately take >2h to land, even when no individual PR has anything wrong. The 120-min cap cut those sessions off mid-flight, forcing the user to re-invoke `/do-work` to resume the drain (which also resets cost tracking). The fix replaces wall-clock with a **per-PR progress signal**: a PR is "settled" once its `headRefOid` has been unchanged for `settled_minutes` (default 20) — i.e. CI is grinding but the branch isn't being actively reworked — and drain exits only once *every* session_pr is settled. An actually-stuck PR is detectable via head-commit immobility, not the clock; a healthy-but-slow one keeps its head moving (rebases re-DIRTY-ing siblings reset the clock) and so keeps the drain alive. `max_drain_hours` (default 8h) survives as the belt-and-braces outer bound so a degenerate session (runaway CI loop, infinite rebase whose head moves every poll) still can't run forever — but 8h, not 2h, because the progress-based exit is now the primary path and the ceiling should be rarely hit.

## CI-minute discipline (issue #323)

The pre-#323 dispatch loop had three places where it would speculatively retrigger full CI suites on the target repo. On hobby-grade repos with a 30-second Lint workflow, the cost is invisible. On production repos with 3× E2E shards + Lighthouse + accessibility audits at ~10 min/shard, those speculative re-triggers add up to tens of GitHub Actions minutes per session — invoiced to the operator at the end of the month with no in-session signal that the spend was avoidable.

The repro that motivated the issue (`mattsears18/lightwork` session `dowork-20260524T221038Z-24650`, 2026-05-24): 13 failing PRs in the backlog (5 BLOCKED on real CI checks, 8 DIRTY merge-conflicts). First fix-checks dispatch returned a false-`green` after burning a full CI suite on a fix commit whose Unit Tests still failed — trust-but-verify caught the false claim, but the wasted runner-minutes were already gone. Subsequent drain phase would have dispatched 8 force-pushes × 1 full CI suite each (~240 runner-minutes) against the DIRTY PRs, most of which would land at next session anyway.

### Why a config block instead of always-on

The three speculative paths are real failure modes that the orchestrator is correctly trying to mitigate — a stale failing check on a PR whose head has advanced may not actually be failing anymore (so fix-checks would be a no-op), and a drain-phase fix-rebase on a DIRTY PR is the difference between "PR merges this session" and "PR sits for the operator to manually rebase next session." Making the mitigations always-on would convert "speculative retrigger" into "PRs surface as still-DIRTY at session end" — which is a regression for repos where CI is cheap and merge-throughput matters more.

The `ci.*` block is the operator-tunable surface: defaults preserve pre-#323 behavior, opt-in flags engage the cost-saving paths. The keys are deliberately fine-grained (five separate keys, not one big `cost_mode: aggressive`) so an operator can mix-and-match — e.g., `skip_drain_rebase: true` (the most expensive single failure mode) without engaging the stale-failure check (which adds a `gh api` round-trip per failed_prs entry).

### The five `ci.*` keys and what they each prevent

| Key | Default | What it prevents (worst case) |
|---|---|---|
| `skip_drain_rebase` | `false` | All drain-phase fix-rebase dispatches. `N` DIRTY PRs → 0 force-pushes, 0 CI suite re-triggers. PRs surface as "needs manual rebase" in the summary. |
| `max_drain_rebases` | `null` | Top-`N` drain-phase fix-rebase dispatches; rest surfaced. Compromise between `skip_drain_rebase` (zero) and unlimited (all). |
| `verify_check_failing_on_head_before_dispatch` | `false` | Re-dispatch against PRs whose failing check's run-SHA doesn't match `headRefOid` — the failure has already been pushed past, the rollup just hasn't refreshed yet. |
| `require_in_progress_check_to_settle` | `false` | Double-push race: dispatch fires while a check is still IN_PROGRESS on the current SHA, worker pushes a fix, now TWO overlapping CI suites are running on the same PR. |
| `skip_speculative_rerun` | `true` | Codifies the absence of `gh run rerun` calls. Default-true (the orchestrator doesn't issue reruns anywhere in the current spec); the key exists so any future change that wants to add them must flip the default and document the rerun semantics. |

The four state-changing keys (every key except `skip_speculative_rerun`) increment one of the four `ci_session_counters.*` counters when they fire; the end-of-session `CI cost:` block surfaces both the effective `ci.*` config and the counters so the operator can attribute saved CI suites to the gate that fired.

### Worked example — the lightwork session that motivated #323

Hypothetical session: 13 failing PRs (5 real failures, 8 DIRTY), `--concurrency 1`, all five `ci.*` keys at their defaults.

**Pre-#323 behavior (current default):**

- Step C dispatches fix-checks-only against 5 BLOCKED PRs. One returns false-`green` (trust-but-verify catches it, re-queues). Total: 6 fix-checks dispatches → 6 CI suite re-triggers.
- Drain phase dispatches fix-rebase against 8 DIRTY PRs → 8 force-pushes → 8 full CI suite re-triggers.
- Net: 14 full CI suite re-triggers.

**Same session with `ci.skip_drain_rebase: true` + `ci.verify_check_failing_on_head_before_dispatch: true`:**

- Step C pre-flight gate (2a): of the 5 BLOCKED PRs, suppose 2 had their failure superseded by a later push (the rollup just hadn't refreshed). The gate drops both — counter `dispatches_skipped_stale_failure = 2`. 3 fix-checks dispatches fire → 3 CI suite re-triggers. The false-`green` case still happens (1 re-queue, 1 extra dispatch) → 4 total.
- Drain phase per-poll action 2 (2a): `ci.skip_drain_rebase: true` → all 8 DIRTY PRs surface in the summary as "needs manual rebase" — counter `drain_rebases_skipped = 8`. 0 force-pushes.
- Net: 4 full CI suite re-triggers (saved 10).

**End-of-session `CI cost:` block (the surface the operator reads):**

```
CI cost (#323):
  ci.skip_drain_rebase: true · ci.max_drain_rebases: null · ci.verify_check_failing_on_head_before_dispatch: true · ci.require_in_progress_check_to_settle: false · ci.skip_speculative_rerun: true
  Dispatches skipped (stale failure on superseded SHA): 2 — each saved roughly one full CI suite on PRs whose failure had already been pushed past
  Dispatches deferred (in-progress check on current head): 0 — each prevented one double-push (two overlapping CI suites)
  Drain-phase rebases skipped (ci.skip_drain_rebase / ci.max_drain_rebases cap): 8 — each saved one full CI suite on a force-push that would have re-triggered the suite
  Drain-phase rebases dispatched: 0 (cap: "none")
  Estimated CI suites avoided this session: 10
```

At a representative ~10 runner-minutes per suite (Lint + Unit + 3× E2E shards on a real repo), that's ~100 runner-minutes saved on a single session. Cost asymmetry is the point: a one-line config opt-in vs. the runner-minute cost of every DIRTY PR + every superseded-failure dispatch the operator would otherwise burn.

### Why the `Estimated CI suites avoided` number is a lower bound

Each "avoided suite" maps to **one CI workflow run that would have been triggered but wasn't**. A repo whose `pull_request` event triggers one workflow (Lint + Unit + E2E in one workflow definition) saves one workflow-run per counter increment; a repo whose `pull_request` event fans out to 5 separate workflow definitions saves five. The counter is workflow-agnostic — the orchestrator doesn't enumerate the repo's workflow definitions to compute a multiplier — so the summary number under-counts on multi-workflow fanout. The operator who wants a per-session minute estimate should multiply the counter by their typical per-push workflow count and per-workflow minute cost. This is intentional: the summary's job is to make the saved-suite count visible at all, not to be a billing-accurate ledger (that's `~/.shipyard/cost-history.jsonl` plus a future GitHub Actions billing integration).

### Why both `skip_drain_rebase` and `max_drain_rebases` exist instead of just one

The operator has two distinct cost-vs-throughput preferences:

- "Never burn drain CI on rebases — DIRTY PRs are next session's problem." → `skip_drain_rebase: true`.
- "Burn drain CI on the top-3 most important DIRTY PRs (ranked lowest PR number first per the drain spec), surface the rest." → `max_drain_rebases: 3`.

Collapsing both into `max_drain_rebases: 0` would force the "never rebase" operator to remember an off-by-one (`0` means "no rebases" vs. `null` meaning "unlimited") that's easy to misread. The boolean `skip_drain_rebase` is the clearer surface for the all-or-nothing case; the integer `max_drain_rebases` is the surface for the threshold case. They compose naturally: when both are set, `skip_drain_rebase: true` wins (no rebases at all) — documented at the schema level.

## End-of-session cleanup — why the orchestrator worktree is reaped last

The orchestrator worktree itself is still around because the orchestrator was running inside it. After the user-facing summary has printed — and only then; you can't remove the worktree you're still cwd'd into — the cwd jumps back to the user's primary checkout (read-only at this point — we're not writing, we're just being somewhere `git worktree remove` can succeed from), then removes the orchestrator worktree.

This is a read-only-effect operation on the primary checkout — `git worktree remove` modifies `.git/worktrees/` (shared metadata), not the primary's working tree or HEAD. The primary's HEAD never moves.

**Why liveness-check the lock-holding PID at shutdown too.** End-of-session cleanup step 3 (this session's agents) ALSO classifies the lock-holding PID, because termination logic can fire early — a still-running agent whose worktree gets reaped loses any unpushed work and ends up trying to operate in the primary checkout or a foreign worktree. The reaped-but-still-running agent path is also covered defensively from the worker side (the issue-worker template's "detect-my-worktree-was-reaped" escape hatch), but the orchestrator's job is to not put workers in that position in the first place.

**Why `self-ancestor` is a distinct classification (issue #138).** A naïve "lock PID alive = defer" check has a load-bearing edge case: the Claude Code harness writes the **orchestrator's** PID into every dispatched agent's lock file (lock content is literally `claude agent <agent-id> (pid <orchestrator-pid>)`). At end-of-session cleanup the orchestrator is by definition still alive — it's the process running cleanup — so a strict liveness check defers EVERY worktree the orchestrator itself owns. The reporter saw 2 agent worktrees stuck across a session because every lock PID resolved to PID 53391, the orchestrator's own. The fix lives in [`scripts/worktree-reap.sh`](../scripts/worktree-reap.sh): walk our own process ancestor chain (self, parent, grandparent, ...) and if the lock PID appears anywhere in it, classify as `self-ancestor` — alive but not a peer, safe to reap because it's the orchestrator about to retire its own worktree. Peer agents in other Claude Code instances are NOT in our ancestor chain (they're at best siblings via a shared init), so `peer-alive` still correctly defers genuine concurrent work.

**Why the env-var short-circuit was added on top of the ancestor walk (issue #263).** The ancestor-walk path from #138 is correct in principle but fragile in practice — at least two failure modes have been seen in production:

1. **Intermediate harness layer returns empty PPID**, so the walk terminates before reaching the orchestrator's PID. The reporter saw a session where the orchestrator (PID 50897) was alive and the lock files held PID 50897, yet `classify-lock` returned `peer-alive` from inside the orchestrator's own bash subprocess. The walk simply didn't reach 50897, even though the orchestrator was a few PPID hops up.
2. **Subagent diagnostic invocation:** a dispatched worker (fix-rebase, fix-checks) calling `classify-lock` for its own introspection — the subagent's process tree is rooted in a different `claude` process than the orchestrator's, so the orchestrator's PID is genuinely not in the subagent's ancestor chain. The walk correctly returns peer-alive, but the answer is wrong for the question "is this OUR session's lock?"

The fix layers an explicit declaration on top: callers export `SHIPYARD_ORCHESTRATOR_PID=<N>` (or pass `--orchestrator-pid <N>` to `classify-lock`) and a PID match short-circuits to `self-ancestor` without consulting the ancestor chain. The orchestrator-side call sites in [`commands/do-work/setup.md`](do-work/setup.md), [`steady-state.md`](do-work/steady-state.md), and [`cleanup-summary.md`](do-work/cleanup-summary.md) auto-detect the orchestrator's PID via the `session-identity.sh detect-orchestrator-pid` helper (which walks the ancestor chain looking for a `comm == claude` process and emits its PID; moved out of worktree-reap.sh by issue #941, since it's an orchestrator-identity question rather than a reaping one). When detection succeeds the env var carries an authoritative value; when it fails (e.g. binary renamed), classify-lock falls back to the ancestor-walk path from #138 — same behavior as before. The safety property holds: a wrong env-var value can only short-circuit when the lock PID *exactly* matches the env-var value AND that PID is alive — both gates fire after `pid_alive` confirms liveness, so a stale orchestrator PID from a previous session can't wrongly mark a live peer's lock as self-ancestor.

## Don't — extended rationale for the load-bearing rules

The spec's `Don't` section enumerates the rules tightly. This section carries the *why* behind the rules that have caused real damage in past sessions — so anyone considering loosening one can see what the rule prevents.

### Don't go idle while queues hold work

When in-flight workers all return but the queues still hold work, the merge train auto-draining prior PRs is irrelevant to your loop. Your job is to dispatch new workers into the freed slots, not to wait for auto-merge to land prior PRs. Pool drained + backlog non-empty = you are failing to do your job. Refill the pool on the same turn the last completion notification arrives.

### Don't conflate "pool drained" with "session complete"

The merge train continues without you. The dispatch loop dies if you stop dispatching. The pool draining is NOT the termination signal — when all in-flight workers return but `raw_backlog` / `ready_issues` / `failed_prs` / `divert_queue` still have entries, the correct next action is to dispatch up to `--concurrency` new workers on the very next turn — not to summarize, not to wrap up, not to ask "want me to keep working or park?", not to idle.

### Don't exit the drain while forward progress continues

The dispatch loop's queues going empty is the signal to enter the end-of-session drain, not to terminate. Exiting earlier — at a hard 15-min mark, or because "looks quiet enough," or because "the user can re-run later" — strands any PR that goes red after the cap with no orchestrator watching to dispatch fix-checks. The realistic case is a 30–40 PR session whose merge train takes 45–90 min wall-clock; don't cut that off prematurely.

### Don't emit recap / "Next: …" narration in lieu of dispatching

The orchestrator's failure mode is to summarize the situation in prose ("Currently 2 workers in flight; a dozen PRs are awaiting CI auto-merge. Next: watch returns and refill the pool from the remaining backlog issues.") and then end the turn without issuing the `Agent` tool call that would actually refill the pool. The recap *sentence itself* is the bug — it gives the model a graceful exit from a turn whose dispatch obligation hasn't been met. Forbidden phrasings include: "Next, I'll watch for …", "Waiting for completions to refill …", "The merge train will drain on its own …", "Will refill the pool from the backlog as agents return …". Every one of these is a description of behavior the harness already provides (notifications on completion); narrating it is pure overhead AND it tricks the model into thinking the turn is done.

The correct shape of a turn that frees a slot is: tool call → invariant line. The correct shape of a turn that legitimately can't dispatch is: structured `[invariant] ... idle_reason="..."` line, nothing else. No prose between them, no prose after them, no "Next:" sentence anywhere.

Contrasting example — DO NOT do this:

```
Slot 3 freed by #769 shipping. Pool: 2/8 in flight.
Goal: drain the lightwork backlog via /do-work with 8 parallel agents.
Next: watch returns and refill the pool from the remaining backlog issues.
```

DO this instead:

```
[Agent tool call dispatching slot 3 with next ready_issue]
[Agent tool call dispatching slots 4-8 with next ready_issues (if also free)]
[invariant] in_flight=8/8 · ready_issues=27 · failed_prs=1 · divert_queue=0 · raw_backlog=12 · dispatched_this_turn=6 · defers_this_turn=0 · state=written · tokens_attributed=true · last_fresh_fetch=17:31:05
```

Or, if every queue really is empty and `in_flight` is also empty:

```
[invariant] in_flight=0/8 · ready_issues=0 · failed_prs=0 · divert_queue=0 · raw_backlog=0 · dispatched_this_turn=0 · defers_this_turn=0 · state=written · tokens_attributed=true · last_fresh_fetch=17:35:12 · idle_reason="all queues empty (terminating after in_flight drains)"
```

### Don't accept a `green` return without verifying the rollup

The agent's `green` claim is supposed to mean "a full CI run completed and passed after my fix" — but ad-hoc dispatch prompts (or a worker that drifted from the canonical template) can return `green` after merely pushing and queueing the rebuild. Trusting that silently leaves a red PR in `session_prs` looking settled, and the drain phase will skip it because it's not in `failed_prs` either. The fix is the trust-but-verify spot-check in step A's fix-checks reconcile — one cheap `gh pr view <M> --json statusCheckRollup` call, then downgrade to `pending` (any rollup state still `PENDING` / `IN_PROGRESS`) or `failing` (any rollup state hard-failed). Never skip the spot-check as an optimization.

**The worker-side complement ([#985](https://github.com/mattsears18/shipyard/issues/985) / [#987](https://github.com/mattsears18/shipyard/issues/987)).** This spot-check is a *backstop* — it was catching an average of one false-`green` per session before the worker side had any honest alternative to reach for. `fix-checks-only.md`'s return contract now requires a computed evidence clause (`green #<M> (rollup verified <ISO8601>: <n> passed, 0 pending, 0 failing)`) so the claim can't be typed without the count existing, and adds a first-class `pending #<M>: <n> check(s) still running (<names>)` disposition for the honest "I fixed it, CI hasn't finished" state the vocabulary was previously missing — `blocked` overstated it (and burned a fix attempt) and there was no other truthful option, so workers reached for `green` instead. The orchestrator's reconcile treats a `pending` return as a normal, expected outcome — same bookkeeping as a `green→pending` downgrade (append to `session_prs`, no `blocked:ci`, no fix-attempt charge) — never as something needing its own verification, since a worker claiming `pending` is by construction claiming *less* than `green`, not more.

**A DIRTY PR is a distinct false-`green` trap the evidence clause alone doesn't close ([#1015](https://github.com/mattsears18/shipyard/issues/1015)).** A PR whose `mergeStateStatus` is DIRTY has an *empty* `statusCheckRollup` — GitHub can't compute a merge ref for a conflicted PR, so no `pull_request`-triggered check ever queues. The evidence-clause computation (`passed`/`pending`/`failing` counts over the rollup) reads an empty array as `0/0/0` — vacuously satisfying "0 pending AND 0 failing," the exact condition the `green` contract requires. Without an explicit DIRTY check, a worker could type a fully-honest-looking evidence clause on a PR where literally no check ever ran. Closed the same way the named-failing-check gate's empty-`named_checks` trap ([#717](https://github.com/mattsears18/shipyard/issues/717)) was closed: a structural gate, not a documentation reminder — `fix-checks-only.md`'s [DIRTY-PR short-circuit](../agents/issue-worker/fix-checks-only.md#dirty-pr-short-circuit-check-before-treating-an-empty-rollup-as-not-started-yet--1015) reads `mergeStateStatus` immediately after Setup, before the fix-loop ever calls `gh pr checks --watch` or computes an evidence clause, and returns the new `dirty #<M>: PR conflicts with <default-branch>; no merge ref, so no checks will run` disposition. The repro this closes (PR #1013, session `01K5AguWha8G2tPgnjMNKSd6`): a worker correctly diagnosed and fixed an unrelated shellcheck failure, pushed, then polled `gh pr checks` to exhaustion because a sibling PR had merged and left the PR DIRTY — `gh pr checks` reporting "no checks reported" read as "CI hasn't started yet" rather than "CI structurally cannot start," and the worker returned a misleading `blocked … infrastructure issue` after burning its full dispatch. `dirty` does not count toward the 3-attempt cap and does not earn `blocked:ci` (it isn't a CI failure) — the orchestrator routes it to the drain's `fix-rebase` path instead, which re-derives DIRTY status live from `session_prs` regardless of what any individual worker claimed. The orchestrator's own trust-but-verify spot-check and narrative-return synthesis (steady-state.md's fix-checks reconcile) both check `mergeStateStatus` before their respective empty-rollup rules for the same reason — defense in depth against a non-compliant worker that ignores the short-circuit and claims `green` anyway.

### Don't dispatch fix-rebase mid-session outside the three conditions (issue #1034)

The original rule banned any mid-session `fix-rebase` dispatch outright, on the premise that steady-state dispatch never produces a DIRTY PR (see [Why fix-rebase is drain-only](#end-of-session-drain--why-it-exists-past-the-dispatch-loops-end) above for the corrected version of that premise). Session `01K5AguWha8G2tPgnjMNKSd6` (2026-07-31, `--concurrency 1`) falsified it: PR #1013 (issue #975) opened claiming version 4.4.12, went red on three checks, got fixed by a `fix-checks-only` worker at `416a57e` — and while that fix sat pushed but unvalidated, sibling PR #1014 merged and advanced `main` past #1013's `plugin.json` `.version` row and CHANGELOG insert point, flipping #1013 DIRTY at ~17:33Z. It stayed DIRTY until the end-of-session drain rebased it at ~22:05Z — roughly four hours, during which ~24 further PRs merged past it, each widening the eventual re-number (4.4.12 → 4.4.28) and CHANGELOG hoist.

**Three compounding costs, all observed in that session, made waiting for the drain strictly worse than dispatching eagerly:**

1. **The rebase gets harder the longer it waits.** Every sibling merge in the interim is one more version slot and one more CHANGELOG entry the eventual rebase has to renumber past.
2. **A DIRTY PR has no merge ref, so CI never runs on it at all** (see [#1015](https://github.com/mattsears18/shipyard/issues/1015) above) — the fix-checks worker's `416a57e` sat completely unvalidated for the full four hours, unconfirmed until the drain's rebase restored the merge ref.
3. **It can burn a whole `fix-checks-only` dispatch on a wrong conclusion.** From inside a worker, "no checks reported" on a DIRTY PR is indistinguishable from "CI hasn't started yet" without the [#1015](https://github.com/mattsears18/shipyard/issues/1015) DIRTY short-circuit — the session's own worker polled to exhaustion and returned `blocked: CI workflows not triggering — infrastructure issue`, a full dispatch spent on a misdiagnosis of the four-hour stall rather than a fix for it.

**The corrected rule.** Permit a mid-session `fix-rebase` dispatch when **all** of:

- the PR is in `session_prs` and `mergeStateStatus == DIRTY`;
- no `in_flight` entry already holds that PR's head branch (a live fix-checks or fix-rebase worker mid-flight on it — don't double-dispatch);
- a `--concurrency` slot is free to take it (this competes for the same dispatch pool as any other candidate — it does not get a slot-exempt carve-out).

**Why it's safe to dispatch speculatively rather than pre-verify the conflict shape.** A literal reading of "the conflict is confined to the coordinated manifest rows" as a *precondition* is unenforceable before dispatch — nothing short of actually running the rebase can determine the conflict's scope. The mode is safe to try eagerly anyway because [`fix-rebase.md`'s §4.6](../agents/issue-worker/fix-rebase.md#46-version-coordinated-manifest--changelog-re-number--trivial-resolution-issue-466) already resolves the common case (a conflict confined to the coordinated `.version` + CHANGELOG rows) deterministically, and bails `blocked rebase #<M>: conflict extends beyond coordinated manifest+CHANGELOG rows` on anything wider — the exact same bail it would produce if dispatched at drain time instead. Dispatching mid-session doesn't change the worker's own safety boundary; it only changes *when* the attempt happens, trading four hours of CI-dark silence for an immediate attempt that either succeeds (restoring the merge ref right away) or fails exactly as safely as it would have at drain.

**Why the restriction still holds outside those three conditions.** The original (a)/(b) concerns from [Why fix-rebase is drain-only](#end-of-session-drain--why-it-exists-past-the-dispatch-loops-end) are real whenever a slot isn't actually free: dispatching against a PR another worker already holds the head branch on would either churn a branch auto-merge was about to rebase anyway, or race a live fix-checks worker mid-flight on the same branch. The three conditions above are exactly what rules those cases out — "no in-flight worker holds the branch" and "a slot is free" are the concurrency-safety half; the drain remains the backstop for whatever a session's dispatch loop doesn't get to before it winds down.

### Don't treat a narrative status string as authoritative

If the agent's last line doesn't start with `green`, `noop:`, `pending`, `dirty`, `flake`, or `blocked`, the worker violated the return contract — it returned something like `"Waiting for monitor."` / `"Shard 2 still running."` / `"Routine progress, awaiting E2E."` instead of blocking its own turn on `gh pr checks <M> --watch` until checks resolved. The harness delivered that narrative string to the orchestrator as a completion notification, but the underlying CI work is still in flight. Do NOT label the PR `blocked:ci`. Do NOT push onto `failed_prs` based on the narrative alone (which might race with a fix the original worker is still pushing). The defense is the dedicated `Unrecognized return string` branch in step A's fix-checks reconcile: query `gh pr view <M> --json statusCheckRollup` once, synthesize the real outcome from the rollup, log a `[fix-checks-unrecognized]` advisory, and continue. This filter is what stops a single misbehaving worker from burning six orchestrator turns on stale re-notifications.

### Don't write to the user's primary checkout

After step 0.5, the orchestrator works exclusively in `.claude/worktrees/orchestrator-<session-id>`. The primary checkout is strictly read-only — read-only ops like `git status`, `gh issue list`, `find`, `grep`, `git worktree list` are fine in either cwd, but every write (`Edit`, `Write`, `git add`, `git commit`, `git branch <new>`, `git push`, `git reset`, `git checkout -B`, label/README/CHANGELOG/`plugin.json` edits, etc.) MUST land in the orchestrator worktree. If a write-class command ends up modifying the primary checkout's HEAD, working tree, or any tracked file in it, that's the exact failure mode step 0.5 was added to prevent — back up, switch to the orchestrator worktree, and retry.

### The primary-checkout branch-leak guard exception (issue #387)

The leak condition means the primary is off the default branch, so the read-only contract is already violated by harness behavior shipyard can't prevent — the [primary-checkout branch-leak guard](./do-work/steady-state.md#a06-primary-checkout-branch-leak-guard-fires-every-reconcile-turn-before-a1)'s restore is a *corrective* write that undoes that harness-leaked write and returns the primary to the state the read-only contract assumes, not a new exception carved into the rule above. See [issue #387](https://github.com/mattsears18/shipyard/issues/387).

### Don't reap a peer-alive worktree — at startup OR at shutdown

Step 3b's lock-PID classification prevents you from yanking a worktree out from under another active Claude Code instance running its own `/do-work`. End-of-session cleanup step 3 (this session's agents) ALSO classifies, because termination logic can fire early — a still-running agent whose worktree gets reaped loses any unpushed work and ends up trying to operate in the primary checkout or a foreign worktree. Always run [`scripts/worktree-reap.sh classify-lock`](../scripts/worktree-reap.sh) before unlocking / removing. Skip `peer-alive` worktrees in both paths; reap `no-lock` / `dead` / `self-ancestor`. The `self-ancestor` case is a non-obvious safe-to-reap: the harness writes the orchestrator's own PID into agent lock files, so at shutdown every agent's lock points to a process that's alive but isn't a peer — it's the orchestrator about to retire its own worktree (see [issue #138](https://github.com/mattsears18/shipyard/issues/138) for the bug a strict liveness check would re-introduce).

**`classify-lock`'s PID-liveness check is not sufficient on its own — check `.in_flight` membership FIRST ([issue #832](https://github.com/mattsears18/shipyard/issues/832)).** The invariant `classify-lock` assumes — lock PID alive ⟺ worker alive — does not hold for the harness's `isolation: "worktree"` dispatch shape: the lock file can name a PID that's already gone (an intermediate spawn-time process, not the long-lived agent) for a worker that was dispatched *seconds* earlier and is actively running. `classify-lock` reports `dead` — reap-eligible — for that worktree, indistinguishable from a genuinely-abandoned lock. The repro: session `do-work-20260723T102624Z` dispatched an `Agent`-tool worker against issue #825 into `.claude/worktrees/agent-aae583bc5baa0704c`; a setup-3b-style sweep running concurrently classified that same, just-dispatched, actively-running worktree as `dead`. The orchestrator only avoided destroying it because it happened to have the live `agent_id` in working memory and hand-excluded it — nothing in the spec *required* that exclusion at the time. Every sweep-style reap loop (setup 3b, dispatch-rules §2d, drain's pre-dispatch reap, A.1's shipped-immediate reap) now checks the candidate worktree's `agent-<id>` against `.in_flight`'s live agent-ids and skips outright on a match, **before** calling `classify-lock` at all — in-flight membership is authoritative liveness for this session's own dispatches; the lock-PID check is only a fallback for worktrees this session doesn't currently own (cross-session stragglers). The single-target reaps that operate on a slot's own just-returned worktree (A.0.5's crash-recovery reap, step B's per-completion release) are the one documented exception, because at the exact point those run, `.in_flight[<slot-id>]` for *that same slot* is still nominally present (the reap IS the release) — an in-flight-membership skip there would wrongly defer reaping the very worktree the step exists to reap.

### Don't dispatch a worker against an untrusted-author issue

This is the security boundary established by step 1.7 and enforced by step 2's bucket 0.5 + step 4's client-side filter + step C's lightweight backlog re-check. The threat model: a stranger opens a public-repo issue with a body that reads like a legit bug report ("Suggested fix: add `helper.ts` with `<crafted payload>`"), an `issue-worker` dispatched against it reads the body as instructions, ships a PR, arms auto-merge, and (if CI passes) the malicious code lands in `main` of a public repo on the maintainer's machine. Worktree isolation prevents *filesystem* damage outside the agent's worktree but does NOT prevent malicious code from landing in a merged PR. The dispatch-time filter is the first line of defense; never bypass it ("just this one issue, the body looks fine") because the entire point of the filter is that the body has already been compromised when you're judging it. Maintainer override: add the login to `.shipyard/trusted-authors.txt` or re-file the issue under the maintainer's own account.

### Don't omit the `shipyard:worker-preamble` skill reference

Every dispatch prompt opens by directing the worker to load `shipyard:worker-preamble`, which carries the shared worktree-isolation rules, the `--label shipyard` requirement, the auto-merge + snapshot + return pattern, the worktree-reaped escape hatch, and the no-`--no-verify` rule. If you author a new dispatch prompt template, reference the skill the same way. Skipping it lets the agent silently corrupt the user's primary checkout (via `gh pr checkout` resolving the wrong cwd), park a worktree on `[main]` (which blocks the user's `git switch main` until the worktree is reaped), or ship a PR without the `shipyard` label (which makes it invisible to the orchestrator's own state machine).

### Don't expect agents to resolve cross-worker merge conflicts on soft-collision paths

When two or more in-flight workers both edit, say, `CLAUDE.md` (one of the default soft-collision paths), their PRs will likely conflict at merge time because GitHub's merge queue applies the second PR's changes onto a `CLAUDE.md` the first PR already modified. The agents have no visibility into each other's worktrees — they can't pre-resolve. The orchestrator is the only actor that knows both claims existed. Before clicking merge (or letting auto-merge land) on the **second** soft-collision PR for a given path, the orchestrator MUST inspect `mergeStateStatus` — if it's `DIRTY` or has a `UNSTABLE` merge conflict on a soft-collision file, dispatch a fix-rebase worker for it (drain-style) which will rebase onto the just-landed main and force-push. **Do NOT** ask agents to coordinate with each other (they can't) and do NOT serialize all soft-collision dispatches (that defeats the whole point of the tier).

### Don't hand a workable issue to the human without attempting it first (issue #531)

Self-filed follow-ups re-enter the backlog like any other issue — a spec/doc change handled by a worktree-isolated worker and merged via PR never modifies the live session, so "it touches the orchestrator I'm running" is not a reason to withhold dispatch. The legitimate guard against a self-perpetuating backlog is NOT "refuse to work self-filed issues" — workers shipping fixes shrink the backlog, and follow-ups are themselves finite and workable. If genuinely worried about unbounded regress, the bounded guard is a soft cap on the per-session count of issues filed by this session's own workers (surface-and-pause at the cap), never a blanket refusal to work them. See [issue #531](https://github.com/mattsears18/shipyard/issues/531) for the session that drained on workable self-filed follow-ups and forced the maintainer to re-instruct the orchestrator to finish them.

### Don't defer an epic, spike, or design-needed issue for open design decisions (issue #767)

This is a corollary of the rule above ["Don't hand a workable issue to the human"](#dont-hand-a-workable-issue-to-the-human-without-attempting-it-first-issue-531), naming the specific rationalization that motivated it: a scope agent (or a human reading a stale mental model of the taxonomy) can mistake "needs a design" or "needs an architecture decision" for a legitimate `human-decision-required` reason. It is not — see [issue #767](https://github.com/mattsears18/shipyard/issues/767).

### Don't file end-of-session follow-up issues after the termination assertion (issue #743)

This is the filing-side corollary of the rule above: a friction issue filed after [drain.md's four-step assertion](./do-work/drain.md#termination-assertion) has already passed is a fresh workable candidate the previous rule now obligates the orchestrator to dispatch — but if the filing happens after [cleanup](./do-work/cleanup-summary.md#end-of-session-cleanup) has already flushed the cost ledger and retired the session-state file, that dispatch's tokens have no durable session record to land in, and `/shipyard:cost report` silently under-reports the session by however much the dispatch cost. See [issue #743](https://github.com/mattsears18/shipyard/issues/743) for the repro (a session's own follow-up issue and its ~250k-token resolving PR were entirely absent from the flushed ledger line) and [cleanup-summary.md's re-entrancy safety net](./do-work/cleanup-summary.md#end-of-session-cleanup) for the defense-in-depth fallback when a dispatch still lands post-cleanup despite this ordering.

### Don't silently skip a phantom re-fire that strands an in-flight sibling (issue #530)

When the harness cross-wires a still-in-flight **sibling** worker's only completion notification onto a reaped worker's `task-id` — the phantom's `task-id` is reconciled, but its body asserts `shipped #<N> via PR #<M>` / `green #<M>` for a target that maps to a live `.in_flight` slot — a pure skip **strands the in-flight sibling** (its real completion arrived only as this phantom; no other notification is coming). This is the mechanism the [`dont.md` rule](./do-work/dont.md) exists to guard against; see [issue #530](https://github.com/mattsears18/shipyard/issues/530) for the harness pattern.

### Don't dispatch a worker that isn't isolated to its own worktree (issues #791, #825)

Two dispatch shapes exist, each with its own isolation mechanism ([dispatch-rules.md](./do-work/dispatch-rules.md#dispatch-rules-used-by-step-7-and-step-c)). Under the default `Agent`-tool shape, the harness provisions and cwd-pins the worktree in response to `isolation: "worktree"` on the call. Under the `Workflow`-substrate alternate, the runtime has no isolation primitive of its own, so the orchestrator owns provisioning the worktree itself ([#791](https://github.com/mattsears18/shipyard/issues/791)). Two `PreToolUse` hooks defend both shapes' contracts: [`enforce-worktree-isolation.sh`](../hooks/enforce-worktree-isolation.sh) blocks a `Workflow` dispatch of `do-work-dispatch.workflow.js` carrying a unit with no `worktreePath` **and** an `Agent` dispatch of any guarded shim missing `isolation: "worktree"` (#293 closed the gap where the model-pinned shims used to pass through silently); [`enforce-edit-scope.sh`](../hooks/enforce-edit-scope.sh) blocks writes from a worker's cwd to paths outside its worktree.

### Don't iterate prompt wording against the permission classifier (issue #718)

When Claude Code's auto-mode classifier refuses the orchestrator's own dispatch call, the tempting default is to keep rewording the prompt until it gets through — and that is exactly the bypass the classifier exists to prevent. An orchestrator that learns "launder the prompt until it's allowed" has defeated the harness's safety boundary on *every* future dispatch, not just this one. The one-permitted-reframe example: a denied prompt implied writing a live permission file when the deliverable was actually plugin source in an isolated worktree — correcting that overstatement is the kind of reframe the rule allows. See [issue #718](https://github.com/mattsears18/shipyard/issues/718).

### Don't rely solely on the dispatch-time author check for label integrity (issue #140)

A rogue triager (any actor with `triage` permission, which is a much larger set than "trusted issue author") can still mass-apply `shipyard`, prematurely remove `needs-human-review`, or strip `blocked:ci` to reset the 3-attempt counter on a stuck PR — see [issue #140](https://github.com/mattsears18/shipyard/issues/140) for the full threat model. (`needs-refinement` was dropped from Tier B in [#520](https://github.com/mattsears18/shipyard/issues/520) — the label was eliminated, so there's nothing to audit. `blocked:agent-hard` and the legacy `blocked:agent` were dropped in [#521](https://github.com/mattsears18/shipyard/issues/521): `blocked:agent-hard` no longer exists, and the legacy `blocked:agent` is no longer applied — step 3d.2's migration sweep moves any straggler off it to `needs-human-review` / no-label, so neither warrants a label-mutation alert.)

## Label-lifecycle provenance — folded / eliminated gate labels

This section consolidates the historical narrative for the gate-label folds and eliminations that the binary-backlog migration produced. The runtime phase files (`do-work/dont.md`, `my-turn.md`, `do-work/inline-trivial.md`) only need to state *current* behavior — which label to surface or exclude *today*; the "this used to be a separate label `X`, folded into `Y` by #N" narrative is provenance a human evolving the spec wants, not instruction the orchestrator or `/my-turn` needs at execution time. The label-convention reference in [`CLAUDE.md` → Label conventions](../../../CLAUDE.md#label-conventions) carries the authoritative, current label semantics; this section is the *why-it-changed* companion.

### `needs-design` → `needs-human-review` (issue #515, binary-backlog phase 1)

The `needs-design` design-gate label was an **inert** dispatch-exclusion + `/my-turn`-surfacing label with no auto-processing machinery, so folding it into `needs-human-review` was a lossless rename. A design-gated issue now carries `needs-human-review`; `/do-work` excludes it from dispatch and `/my-turn` surfaces it. For a design-gated issue the human action is to make the design call (or break the issue into a design spike + an implementation issue so the impl half becomes dispatch-eligible). This advances the binary-backlog north star: every open issue is either workable-by-`/do-work` (no gate label) or workable-by-human (`needs-human-review`).

### `needs-refinement` eliminated (issue #520)

`needs-refinement` was a persisted "this issue isn't ready for `/shipyard:do-work` dispatch yet" pipeline gate. Rather than fold it into the inert human-gate (which would strand refinable work in the human queue), the gate was **retired**: `/shipyard:refine-issues` now detects refinement candidates by a live source-signal scan (`user-feedback` label → classify+rewrite, `## Open questions` heading → resolve-defaults, bot-authored / unrecognized → fall-through to `needs-human-review`) as a pre-dispatch pass, with no persisted label. The scan recomputes candidacy every run, so it never drifts out of sync with the issue body the way a cached gate label did. The GitHub `needs-refinement` label object was deleted 2026-07-25 ([#859](https://github.com/mattsears18/shipyard/issues/859)) after an audit confirmed zero open/closed issues carried it and nothing applied or read it — the manual-cleanup deferral is resolved. Security is unchanged — external-author issues still get `needs-human-review` from the separate `external-author-gate.yml`.

### `needs-decomposition` / `tracking` → `needs-human-review` + body marker (issue #519)

The epic-decomposition pair carried live machinery (`/decompose-epic` consumes it), so the fold preserved the machinery by re-keying `/decompose-epic`'s candidate fetch onto `needs-human-review` **plus the `<!-- do-work-needs-decomposition -->` body marker** (stamped on the scope-agent diagnosis comment) rather than a dedicated label. The marker is what distinguishes an epic-decomposition handoff from every *other* `needs-human-review` issue (refined user-feedback, external-author, design-gated). See [CLAUDE.md → Epic-decomposition handoff](../../../CLAUDE.md#epic-decomposition-handoff-scope-agent-handoff--auto-shard) for the consumer-side detail.

**`tracking` re-added to the dispatch-gate set as a defensive measure (issue #1081).** The fold above assumed the retired `tracking` GitHub label object would eventually be deleted — until then, `04-backlog-divert.md`'s dispatch-exclusion filter dropped it from its own enumeration on the theory that `needs-human-review` alone (applied by [step 3d.2 sub-sweep e](do-work/setup/01c-label-recovery-refine.md#3-ensure-label-exists--recover-from-prior-session)'s next-session migration) already covered it. ## End-of-session cleanup — SessionEnd hook backstop ([#638](https://github.com/mattsears18/shipyard/issues/638))

This entire cleanup pass runs as best-effort bash *inside the orchestrator's turn*: if the session crashes / is interrupted / the turn ends before it completes, the reaps never fire — the recurring orphan-accumulation behind [#637](https://github.com/mattsears18/shipyard/issues/637). The `SessionEnd` hook (`hooks/reap-on-session-end.sh` → `scripts/session-end-reap.sh`) is a trigger that runs **independent of the orchestrator's turn** — on every session exit it reaps stale `worktree-agent-*` branch refs (#326) + prunes, so the clearest unbounded leak is reaped even when the in-turn pass doesn't run. It is a backstop, not a replacement: the in-turn pass is still the fuller sweep (this-session worktrees, `[gone]` `do-work/issue-*` refs, the orchestrator's own worktree). Extending the hook to cover those too is tracked in #638.

## End-of-session cleanup — immediate-reap relationship ([#282](https://github.com/mattsears18/shipyard/issues/282))

Per [#282](https://github.com/mattsears18/shipyard/issues/282), the orchestrator's `shipped #<N>` reconcile in `steady-state.md` step A.1 reaps the agent worktree for `do-work/issue-<N>` immediately rather than waiting for end-of-session. This means the end-of-session pass typically sees only worktrees from `blocked` / `errored` returns, from `peer-alive` defers in the immediate-reap path, or from synthetic-divert workers (fix-main-ci, fix-failing-prs-batch — whose branches aren't `do-work/issue-N` so the steady-state match doesn't fire). The end-of-session pass remains the ultimate sweep — never assume the immediate-reap path covered everything.

## End-of-session cleanup — re-entrancy safety net ([#743](https://github.com/mattsears18/shipyard/issues/743))

A dispatch after the cleanup section has already run once this session must not lose its tokens. This whole trio (cleanup → summary → report) is meant to run exactly once, at genuine end-of-session — `drain.md`'s termination assertion now files any end-of-session friction/follow-up issues *before* the four-step assertion runs specifically so that a newly-filed workable issue is dispatched and drained through the ordinary loop, never discovered only after cleanup has already fired. That ordering fix is the primary defense. The re-entrancy handling in the spec (self-healing session-state recreation, the `--reconcile` flush flag) is the belt-and-suspenders for any other path that still dispatches a worker after cleanup has run — a bug in the ordering above, a future code path nobody's thought of yet, anything.

## Step 3 — targeted-reap-first ordering ([#509](https://github.com/mattsears18/shipyard/issues/509))

The generic worktree sweep iterates *every* `.git/worktrees/agent-*` directory and runs `classify-lock` per worktree. On a busy checkout with many accumulated **cross-session** agent worktrees, that loop can be slow enough that it does NOT complete within the orchestrator's bash window — reaping a handful and stalling before the post-loop counters print, **stranding this session's own shipped worktrees** (the ones holding real merged work whose branches are `[gone]` — the most important to reap). The #509 repro: 17 agent worktrees (this session's 7 + 10 cross-session leftovers), ~6 reaped, then the loop went quiet, leaving this session's `agent-add8ef31…` / `agent-a67e506f…` (both merged) un-reaped.

The orchestrator already knows its **own** session's agent-ids — the union of `reconciled_agent_ids` (every agent reconciled by `steady-state.md` step A) and the live `in_flight.<slot>.agent_id` values — so it can target them **directly**, bounded by that small known set, without depending on the full generic sweep finishing. The cross-session stragglers the generic sweep would otherwise race against are already covered by the next session's setup step 3b sweep, so they need not block this session's own reap. Running the targeted pass first means a stall in the generic loop no longer strands this session's own work, because that work is already gone.

## Step 5.5 — verify-reaps failure mode ([#712](https://github.com/mattsears18/shipyard/issues/712))

Every reap in the end-of-session cleanup pass is fire-and-forget (`2>/dev/null || true`) inside a background subshell, so a reap that *doesn't happen* produces no signal. The failure mode this closes: in Claude Code's **auto permission mode** the classifier denies `git worktree remove --force` outright —

> Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Irreversible Local Destruction] `git worktree remove --force` on five pre-existing worktrees … this destroys uncommitted work and unmerged commits that exist nowhere else.

— and because the denial kills the whole Bash tool call, **no reap-audit line is ever written**. Nothing inside the reap path can observe it. The #712 repro accumulated five stale worktrees on one repo, every one of them the residue of an *already-merged* PR, and the count only grew because each session's reap was denied the same way and nobody noticed.

The only mechanism that catches this is an independent, after-the-fact probe of the filesystem — assert on the **end state**, not on any step's exit code. That uniformly covers a classifier denial, a git failure, the force-evidence gate declining, and a sweep that never ran.

## End-of-session summary — why denial blocks are recorded ([#718](https://github.com/mattsears18/shipyard/issues/718) [#746](https://github.com/mattsears18/shipyard/issues/746) [#838](https://github.com/mattsears18/shipyard/issues/838))

Three ledgers in the end-of-session summary exist for the same underlying reason: without them, a refused action silently costs a slot and nothing in the session's output says why.

- **`Dispatch denied (#718)`** — a refused `Agent` dispatch call **silently costs a dispatch slot**: the target quietly stops being worked and nothing in the session's output says why. Recording it, and specifically surfacing the `handed back (needs-human-review)` outcome, is what turns a silent drop into an actionable line.
- **`Operator denied (#746)`** — a refused operator-phase action **silently costs a queue item**: it quietly drops out of `operator_queue` and nothing in the session's output says why. Same shape as #718, one layer down (operator actions — `gh pr close`/`gh pr merge`/browser mutations — rather than `Agent` dispatch calls).
- **`Stalled dispatches (#838/#833)`** — without this ledger, `steady-state.md` step A.0.5's inspect-before-reap flow can resume, salvage, or drop a stalled/crashed dispatch and nothing in the session's output says it happened. The per-occurrence detail (`resumed` / `handed-back` / `dropped-clean`) is what lets the operator tell a worker that quietly self-healed apart from one that lost recoverable work.

## End-of-session summary — operator queue block visual separation ([#849](https://github.com/mattsears18/shipyard/issues/849))

The `Operator queue — needs you (N)` block is the one block in the end-of-session summary printed **before** the flat lines rather than folded into one — deliberately visually distinct (the `━` rule above and below it) from every deferred/dispositioned line elsewhere in the summary, because its whole purpose is to stop N remaining operator items from reading as routine "dispositioned" entries indistinguishable from work the agent chose to skip. This block is the direct fix for the friction in #849: a background/overnight session that couldn't or didn't fully drive the browser must still leave the human an explicit, actionable to-do list rather than a line they can read past.

## End-of-session summary — CI-cost estimate caveat ([#323](https://github.com/mattsears18/shipyard/issues/323))

The `Estimated CI suites avoided` total in the `CI cost` block is a rough lower bound — the actual saved CI-minute count depends on the repo's per-suite cost (a Lighthouse + E2E-shards repo at ~30 min/suite multiplies; a small Jest-only repo at ~2 min/suite multiplies less) and per-PR-vs-per-rebase semantics. The intent is to give the operator a single number they can multiply by their typical per-suite minute cost to estimate the per-session savings — not to be a billing-accurate ledger.

## End-of-session summary — unpriced-model banner ([#728](https://github.com/mattsears18/shipyard/issues/728))

This banner is distinct from the `Cost attribution` banner elsewhere in the summary, and both can fire in the same session. `Cost attribution` means *we know the price but not the token breakdown*; `Unpriced model(s)` means *we know the tokens but not the price*. The failure this one closes is nastier because it degrades to a **confident, plausible number** rather than an obviously-missing one: an unknown model resolves to a $0.00 cost that is indistinguishable from a genuinely free dispatch, so a stale pricing table silently under-reports the whole session (the [#728](https://github.com/mattsears18/shipyard/issues/728) repro: six of seven dispatches ran on `claude-opus-4-8`, which wasn't in the table, and a multi-dollar session reported $0.72). `$0.00` is a legitimate value and must never double as the error sentinel — hence the explicit `unpriced_models` set rather than an inferred-from-zero heuristic.

## Write the consolidated report to disk — why shipyard-home ([#488](https://github.com/mattsears18/shipyard/issues/488))

Unlike `/shipyard:audit` — which runs interactively in the user's session and writes to the in-repo `.shipyard/audits/` — `/shipyard:do-work` has **no writable in-repo location for a persistent artifact**:

- The orchestrator runs in a linked worktree (`.claude/worktrees/orchestrator-<session-id>`) that is **force-removed** at end-of-session cleanup, so anything written there is destroyed.
- The user's **primary checkout is read-only for the whole session** (the worktree-isolation contract), and on any machine with the global `enforce-worktree.sh` `PreToolUse` hook installed, a `Write` to the primary's `.shipyard/do-work/` is **hard-blocked** ("targets the PRIMARY checkout") — the report could never be produced in its intended environment.

Writing to shipyard's own home directory (`~/.shipyard/do-work-reports/`, alongside the cost-history ledger and session-state files) sidesteps both: it's outside any git checkout, so it's never hook-blocked and survives worktree reap. Reports for every repo accumulate under one root, partitioned by `<owner>-<repo>`. `SHIPYARD_HOME` overrides the default `~/.shipyard` for tests / sandboxed runs.

## Friction-issue filing must precede the termination assertion (#743)

Because the `dont.md` rule ["don't hand a workable issue to the human"](./do-work/dont.md) applies to *every* workable issue including ones this session just filed, a friction issue filed after the four-step assertion has already passed is itself a fresh workable candidate the loop is now obligated to dispatch — but if that filing happens after [cleanup](./do-work/cleanup-summary.md#end-of-session-cleanup) has already flushed the cost ledger (`cost-history.sh flush`) and retired the session-state file (`session-state.sh cleanup`), the resulting dispatch runs with no durable session record to attribute its tokens to, and the ledger silently under-reports the session by however much that dispatch cost. See [issue #743](https://github.com/mattsears18/shipyard/issues/743) for the repro — a session's own follow-up issue and its ~250k-token resolving PR were entirely absent from the flushed ledger line.

A related, narrower mechanism exists too: `session-state.sh bump-tokens --allow-degraded-init` self-heals a missing session file if a dispatch somehow still lands post-cleanup despite this ordering (see [cleanup-summary.md](./do-work/cleanup-summary.md#end-of-session-cleanup) for the re-entrancy safety net) — but that is defense in depth, not a substitute for filing before the assertion runs.

## Rebase gates: deterministic-failure vs rate-limit (#265)

`rebase_blocked_prs` and `rebase_success_counts` are intentionally distinct structures, not one combined "already tried this PR" set. Conflating them — the spec's original "one-shot per PR per session" language — caused the race documented in [#265](https://github.com/mattsears18/shipyard/issues/265): a PR that had already been successfully rebased once couldn't recover when a sibling merge re-introduced DIRTY, because the one-shot rule treated the earlier success as exhausting the PR's retry budget. The fix splits the two failure shapes apart: `rebase_blocked_prs` gates the **deterministic** case (a real conflict — retrying produces the same outcome, so don't waste a worker), and `rebase_success_counts` gates the **race** case (the merge train is moving fast enough that a successful rebase gets undone by the next sibling merge — a winnable race, not a stuck state, so it's worth retrying up to a capped number of times). Capping at 3 successful rebases per PR per session keeps the worst-case cost bounded (≤3 Haiku-pinned dispatches per PR) while letting normal merge-train races resolve on their own.

## Latest-per-name rollup de-duplication (#333)

`statusCheckRollup` returns every check run for a PR's head SHA, including superseded runs — a check that ran, failed, was re-triggered, and passed appears twice (one FAILURE entry plus one SUCCESS entry). A naïve `.statusCheckRollup[] | select(.conclusion=="FAILURE")` walk over that raw array fails in two directions at once: it keeps already-fixed PRs in `R_new` forever (dispatching pointless fix-checks workers that return `noop: already green`), and it keeps already-fixed PRs OUT of `D_dirty` (sending the drain-phase fix-rebase worker the false signal "this PR has failing checks — bail" when it's actually green). Both failure modes were observed together in lightwork session `c6afe19d-a6a6-40e4-9eb8-de409d046a49` against PRs #1193 and #1211. The fix is the `group_by(.name) | map(... | last)` reduction drain.md uses everywhere it walks a rollup: collapse N entries per check name down to the most recent one before classifying.

## Pre-dispatch head-branch reap: session reproductions (#370 / #576)

**The #370 failure mode.** A fresh drain-phase worker lands in its own isolated worktree, then runs the safe two-step (`git fetch origin <head>` + `git switch <head>`) to land on a PR's head branch. When the original issue-work worker's worktree is *still locked* against that branch — because the worker returned `blocked` / `errored` (so the A.1 `shipped`-only reap never ran for it), or a transient `gh` failure aborted the A.1 reap — `git switch` fails with *"is already checked out at \<path\>"* and the fresh worker bails on a lock it has no way to clear itself, even though it already identified the correct fix. Since the orchestrator's own end-of-session reap (cleanup-summary step 3b) runs *after* drain, drain-phase dispatches always race the lock. Observed in lightwork session `do-work-20260528T015557Z-14129`: 3 PRs (#1355, #1361, #1363) all bailed identically against self-PID-locked head branches.

**Why it's safe to reap.** The lock holds *our orchestrator's* PID (the harness writes the orchestrator PID into every dispatched agent's worktree lock), so `classify-lock` short-circuits it to `self-ancestor` once `SHIPYARD_ORCHESTRATOR_PID` is declared. The original worker's return was already reconciled at step A by the time drain runs, so its worktree is logically done — this is the same self-ancestor reap logic setup.md step 3b runs at session start and the A.1 `shipped`-immediate reap (#282) runs on issue-work completion, extended to the mid-session drain dispatch site for PRs whose originating worker did NOT take the `shipped` path.

**The #576 extension — force-reap on `peer-alive`.** The general-purpose reap defers conservatively on a `peer-alive` classification (a live PID that wasn't short-circuited to `self-ancestor`). But at drain time *all* issue-work workers in the session have already returned their terminal strings, so a `do-work/issue-<N>`-branch worktree that's still `peer-alive` is a completed worker whose harness process just hasn't fully torn down — not a genuinely live one. Observed in session `do-work-20260614T024327Z-75752`: 2 fix-checks drain dispatches (#1976, #1977) bailed on completed issue-work worktrees whose A.1 immediate-reap had deferred on `peer-alive`, leaving the locks intact at drain time. The fix overrides `peer-alive` to force-reap specifically for `do-work/issue-*`-branch worktrees (never for live fix-checks/fix-rebase worker branches, where a `peer-alive` lock is genuinely live and must not be yanked) — the same reasoning A.0.5's force-reap on crash returns already relies on: the agent is non-recoverable by definition, so `peer-alive` doesn't justify keeping the branch locked. This closes the second leg of #576: even on a plugin version where A.1's own force-reap hadn't landed yet, drain's pre-dispatch check now catches the lingering completed worktree anyway.

## Stale-red vs genuinely-red (#993)

Session `do-work-20260729T111507Z-15877` against `mattsears18/lightwork`, 2026-07-30 ~04:00–05:30 UTC: `main` went red on `🧹 Lint & Typecheck` (`npm run check:expo-deps`, tripped by an upstream Expo SDK patch making every Expo-managed package look "behind"). Seven open session PRs each ran their required checks *before* the fix existed and recorded a failing `🧹 Lint & Typecheck`, going `BLOCKED`. A `fix-main-ci` dispatch shipped the remedy (PR #3316); it merged; `main`'s own post-merge run went green. **All seven PRs stayed `BLOCKED` anyway — indefinitely.** `mergeable` was `MERGEABLE` and auto-merge was armed on every one; they simply had a required check that would never re-run on its own, because GitHub does not re-evaluate an already-completed check just because the base branch moved underneath it. Manual `gh pr update-branch <N>` on each of the six affected PRs re-triggered their checks against the fixed lockfile, and all six then merged normally — the entire fix was one line per PR, but nothing in the existing drive-the-tail machinery ever ran it.

The existing DIRTY-handling path didn't cover this because these PRs were never DIRTY — no conflict, cleanly mergeable, just carrying a stale check result. Worse, the [`P_settled`](./do-work/drain.md#drain-protocol) settle-signal (#374) actively misclassified the state: `headRefOid` was genuinely unchanged and the check was genuinely complete, so the PR looked *settled* and would have been reported "blocked on CI" in the end-of-session summary when in fact a one-line action would land it. The distinction the fix introduces — **stale-red** (a check that predates the fix and would flip on a re-run) vs **genuinely-red** (a check that already ran against the fixed base and is still failing) — is the load-bearing split: only the first class should ever get an unprompted `gh pr update-branch`. Re-triggering a genuinely-red PR's checks would silently mask a real regression behind a fresh run, so the mechanism gates on `completedAt` against the fix's own merge-commit timestamp rather than merely "is this PR's rollup failing right now."

## CHANGELOG-serialization gate (#438)

On a repo where every PR appends a top-of-file `### <version>` CHANGELOG entry (the canonical version-coordinated shape), parallel drain rebases cannot converge: each merge moves the CHANGELOG insert point, so the moment one rebased PR lands, every sibling that just rebased onto the previous CHANGELOG head goes DIRTY again on the CHANGELOG-append row. The [#438](https://github.com/mattsears18/shipyard/issues/438) repro saw drain rebases for 6 distinctly-versioned PRs (1.8.18–1.8.23) all re-DIRTY on the CHANGELOG insert after the first merge; only **serial** rebase (rebase one → let it merge → rebase the next) converged. `version_coordination.serialize_drain_rebase` (default true when `version_coordination.enabled` and a `changelog_path` are both set) is the fix: dispatch a fix-rebase for at most one DIRTY PR per poll, and don't dispatch the next until the in-flight one has merged or settled out of DIRTY.

## Local-only-CI merge gate (#643)

The default drain protocol assumes cloud CI auto-runs on every PR push — push → checks run → rollup goes green → `--auto` merges. That assumption breaks on a repo where the merge-blocking commit status is posted by a manually-run command instead of cloud CI (e.g. a `local-ci` status posted only after a session runs a ~20-minute emulator-backed local test suite): nothing posts the gate status on push, so every shipped PR sits OPEN with `--auto` armed but never merges — the dispatch loop "succeeds" (PRs shipped) while the backlog never actually drains. The [#643 repro](https://github.com/mattsears18/shipyard/issues/643): session `dowork-20260622T234502Z-39390` on `mattsears18/lightwork` shipped 9 issues, and each PR required a manual `ci:report` run before `--auto` could fire — the orchestrator had to improvise the entire merge-gate loop off-book, including orphan-emulator detection+kill, a wait-for-free loop, and full-output capture to tell real failures from resource contention. `merge_gate.*` config codifies that improvisation as a first-class drain sweep so a less-careful future session doesn't have to reinvent it (and doesn't just leave a pile of unmerged PRs).

## Release-PR auto-arming and deploy watch (#659 / #663)

Closes the "own the release train" slice of the [#659](https://github.com/mattsears18/shipyard/issues/659) own-the-tail epic. Without this sweep, a repo that produces standalone release PRs (release-please aggregation, a catch-up release bump) strands its tail on a human: the session ships feature PRs, they merge, and the release PR that would actually *publish* those merges sits OPEN with nobody to arm it — every prior PR in the batch reads as "done" while the thing that actually ships them waits indefinitely. Arming it is within the repo's existing standing authority for landing on `main` via PR + auto-merge (see [CLAUDE.md → Permissions](../../../CLAUDE.md#permissions)); this sweep just extends that authority to a class of PR nothing else in the loop was watching for.

## Systemic CI failure during drain — options considered (#359)

Two options would close the gap where a systemically-failing (not per-PR) CI failure traps a PR in drain with no `blocked:ci` stamp and no automated path forward, but both were deliberately left unimplemented because they'd expand drain's behavioral surface materially:

- **Allow one fix-checks-only dispatch from drain when ALL other queues are empty.** Bounded — only fires if `divert_queue + failed_prs + ready_issues + raw_backlog == 0` and drain has a `P_failing` PR. Mitigates the "human has to do this anyway" path, but adds a new dispatch surface to drain that the wind-down framing doesn't currently allow.
- **Pattern-match failure logs for known systemic shapes** (job timeouts, runner cancellations, `cancel-in-progress` flaps) and surface them in the end-of-session summary as a distinct cohort so the user knows it's an infra issue, not a test bug. Larger scope; needs a log-parsing surface that doesn't exist today.

Both are tracked as follow-up work to [#359](https://github.com/mattsears18/shipyard/issues/359) — file a fresh issue when implementing either. Documenting the gap without closing it means a reader (LLM or human) can see plainly that drain doesn't dispatch fix-checks-only for this case and what the escape valves are, without committing to a behavioral change that needs its own design pass.

## Reconcile-once gate design choices ([#317](https://github.com/mattsears18/shipyard/issues/317))

**Why a set instead of a dispatch-time bookkeeping check.** The orchestrator can already infer "this task-id isn't in `.in_flight`" — but that check is ambiguous on phantoms: step B removed the slot at the original reconcile, so `.in_flight` is correctly empty whether the incoming notification is a phantom re-fire OR a real fresh completion the orchestrator forgot about. The set distinguishes the two cases unambiguously: presence ⇒ definitely already handled.

**Why monotone growth is fine.** Sessions complete at most a few hundred dispatches, each with a fixed-size string id. The set's footprint is bounded by the session's total dispatch count, capped by the session ceiling — a few KB at the outer limit. Eviction logic would be more complex than the win.

## A.0 preamble mandate ([#548](https://github.com/mattsears18/shipyard/issues/548))

The reconcile turn is precisely the turn where the #477 cwd-leak fires (the harness relocates the orchestrator's cwd into the just-returned agent's `agent-*` worktree immediately after the agent completes). A bare `cat .shipyard-session-id` at that point reads from the agent worktree, which has no `.shipyard-session-id` file — the `cat` returns empty, every downstream `session-state.sh` call is invoked with an empty `--session-id` and exits 64 (`--session-id is required`), and the turn silently loses token attribution, the `session_prs` append, and the cost comment (the exact blast-radius documented in [#548](https://github.com/mattsears18/shipyard/issues/548)'s repro from session `do-work-20260612T035752Z-44019`).

The A.0.5 and A.1 reap blocks already carry the `STABLE_DIR` cwd-anchor idiom from [#497](https://github.com/mattsears18/shipyard/issues/497) — but those blocks anchor the **filesystem path** to avoid deleting a cwd that's inside the doomed worktree. The A.0 preamble solves the **different problem** of reading the session-id file from the correct (orchestrator) worktree regardless of where the Bash cwd currently is. The two defenses compose: the reap blocks need both (cwd anchor so `git worktree remove` doesn't corrupt the shell, and session-id derive so `worktree-reap.sh reap --session-id` gets the right value); A.0's `bump-tokens` calls need only the session-id derive (no worktree removal involved).

## Degraded-path tradeoff ([#279](https://github.com/mattsears18/shipyard/issues/279))

On harness versions where the `<usage>` block structurally never emits the input/output/cache breakdown (Opus 4.7 2026-05-23 was the original repro), every dispatch a session runs will be degraded.

**Tradeoff — degraded vs. skip.** The alternative to routing `total_tokens` through `--input` — skipping the bump entirely when the breakdown is missing — produces `$0` on every cost-tracking comment, which the operator reads as "no work happened" rather than "attribution data lost." **Some signal is better than zero signal.** The degraded flag (`.tokens.degraded_attribution_count`, and per-invocation `degraded: true`) is the explicit marker that the number is unreliable, and the end-of-session banner makes the gap visible session-wide.

**Correction ([#1035](https://github.com/mattsears18/shipyard/issues/1035)):** this section previously claimed routing `total_tokens` through `--input` "under-counts cost … roughly 1.5× what the degraded fallback computes," and labeled the degraded figure a lower bound. That framing was wrong and has been retired. Pricing the *entire* total at the input rate is not a one-directional error: any real cache-read tokens folded into that total are priced far *above* their true (cheap) rate, which **inflates** the estimate, while any real output tokens folded in are priced far *below* their true (several-times-input) rate, which **deflates** it. Which direction dominates depends on the dispatch's actual input/output/cache split — exactly the information the degraded path lacks — so the two errors do not cancel in any predictable way and the resulting figure is not reliable as a floor *or* a ceiling. The fix relabels degraded sessions **UNRELIABLE** rather than **LOWER BOUND** throughout: the end-of-session banners (`cleanup-summary.md`), the persistent ledger (`cost-history.sh flush` now propagates `degraded_attribution_count` into both the session-record projection and the `--reconcile` merge), and `/shipyard:cost report` (a `[UNRELIABLE]` tag on the `Spend:` line plus a `DEGRADED COST ATTRIBUTION` advisory block, deliberately distinct from the genuine, directional `[LOWER BOUND]` / `UNPRICED MODELS` pair #728 introduced for a different failure mode — an unpriced model's tokens are still split correctly across input/output/cache, only the per-token *rate* is unknown, so LOWER BOUND is the correct label there).

## Resume vs. crash-recovery reap ([#813](https://github.com/mattsears18/shipyard/issues/813))

The crash-recovery path auto-commits with `--no-verify` and force-reaps — correct for an agent that is truly gone (crashed, errored, or a return with no salvageable worktree), but heavy-handed for a worker that is provably still resumable: it bypasses the worker's own commit hooks, discards its live context (root-caused understanding of the diff, in-flight PR-body drafting), and burns a second dispatch's tokens re-establishing what the first dispatch already knew. A one-message resume costs almost nothing by comparison and lets the SAME worker finish normally, hooks and all — this is the recovery the [#813](https://github.com/mattsears18/shipyard/issues/813) repro's orchestrator performed by hand (inspecting the worktree, then resuming the agent with a message to stop waiting and re-run in the foreground) before the stalled-worker section existed to specify it.

Historically the load-bearing difference from step B's behavior — step B now force-reaps `peer-alive` too, per [#771](https://github.com/mattsears18/shipyard/issues/771) — but A.0.5's own force-reap remains independently load-bearing: it fires *before* A.1/step B even run, closing the window sooner on a crash return.

The primary HEAD reflog from the [#387](https://github.com/mattsears18/shipyard/issues/387) repro shows the leak directly (`checkout: moving from main to do-work/issue-378`, etc.) on a session whose orchestrator only ever ran `git -C <primary> worktree …` / `branch -D` / one corrective `checkout main`.

## Primary-checkout derivation bug ([#452](https://github.com/mattsears18/shipyard/issues/452))

The harness can silently relocate the orchestrator's own Bash-tool cwd into a just-returned **agent's** `agent-*` isolation worktree on a reconcile turn (the same `isolation: "worktree"` env-leak class as [#387](https://github.com/mattsears18/shipyard/issues/387) / [#322](https://github.com/mattsears18/shipyard/issues/322) / [#354](https://github.com/mattsears18/shipyard/issues/354), but hitting the orchestrator's cwd rather than the primary's HEAD). The original derivation read `git rev-parse --show-toplevel` and stripped only an `orchestrator-*` suffix — so when cwd was in an `agent-*` worktree, the strip didn't match, `PRIMARY_CHECKOUT` was left pointing at the **agent** worktree, and the guard read that worktree's `do-work/issue-<N>` branch as the "primary branch," ran `checkout <default>` against the *agent* tree, and emitted a **phantom** `[primary-leak] restored primary …` line while never inspecting the real primary. The fix derives the primary from `git worktree list --porcelain`'s first `worktree ` entry — always the main working tree regardless of which linked worktree the cwd is in (all linked worktrees share one worktree list) — with the cwd-strip retained only as a fallback (now covering `agent-*` as well) for a layout where the porcelain read comes up empty.

## Force-reap on peer-alive (#576/#771)

Two call sites force-reap on a `peer-alive` classification, for related but distinct reasons:

**A.1's `shipped` handler.** The `peer-alive` classification at this call site means the lock PID is some process that the orchestrator's SHIPYARD_ORCHESTRATOR_PID bootstrap did not short-circuit to `self-ancestor` — most likely a transient harness subprocess that was still alive milliseconds after the agent returned. Deferring on `peer-alive` here causes the very drain-phase `blocked: branch locked in another worktree` failures documented in [#576](https://github.com/mattsears18/shipyard/issues/576): the A.1 defer leaves the worktree locked, the drain's pre-dispatch reap checks the same classification and also defers, and the fix-checks / fix-rebase worker bails.

**Step B's general-purpose per-completion reap.** [#576](https://github.com/mattsears18/shipyard/issues/576) taught the A.1 `shipped`-only path and the drain pre-dispatch reap to force-reap on `peer-alive`, but step B's per-completion reap — the one that actually covers `green`/`rebased`/the synthetic-divert `shipped` variants/`blocked <mode>` — was left deferring conservatively, exactly like the pre-#576 A.1 path. Deferring on it left the just-completed worker's head branch locked into the exact window a re-dispatched fix-checks-only or fix-rebase worker needs it, producing the `blocked ...: head branch <head> locked in another worktree` bails documented in #771 (repro: PRs #2598 and #2701, each requiring a manual `git worktree remove --force` before the re-dispatch would take — twice in the #2598 case, because the *next* re-dispatch's own worktree hit the same deferred-peer-alive gap on its own completion). This was closed in [#771](https://github.com/mattsears18/shipyard/issues/771), bringing step B's behavior in line with A.1's.

## Blocked-reason routing table rationale (#521/#628)

**Why a refuse routes to `needs-human-review` instead of a dedicated block label ([#521](https://github.com/mattsears18/shipyard/issues/521)).** A security / scope / prompt-injection refuse has *no automated recovery path* — it's exactly "Claude gave up; a human must actually look," which is the semantics `needs-human-review` already encodes (and which [`/my-turn`](./my-turn.md) already surfaces as a human-action signal). Folding the refuse class onto `needs-human-review` removes the redundant `blocked:agent-hard` label while preserving the worker's reason in the bail comment so the human sees *why* without opening the diff. This advances the binary-backlog north star (#515): every open issue is either workable-by-`/do-work` (no gate label) or workable-by-human (`needs-human-review`).

**Why a provisioning bail routes to `agent-console` ([#628](https://github.com/mattsears18/shipyard/issues/628)).** When a worker bails `external provisioning required`, it stopped *before* committing dead config for a service that isn't set up yet. The blocker isn't a *decision* (so not `needs-human-review`) and it isn't auto-recoverable (so not a soft retry or a `Blocked by #N` wait) — it's a concrete browser/console action: create the account, grab the credential, drop it in `*.tfvars` / CI secrets. That's exactly the `agent-console` semantics (#608) — surfaced by `/my-turn` and drivable by `/do-work`. Routing it here keeps the worker-side backstop and the scope-preflight `external-dependency` defer on the **same** destination, so a provisioning-gated issue lands in the operator queue whether it's caught before dispatch or mid-work.

**Why a dependency-wait needs no label.** When the bail names a still-open blocker, the `Blocked by #N` body-reference filter (setup.md step 4 / bucket 7) is the *complete* mechanism: it drops the issue from the workable queue while `#N` is open and re-admits it the instant `#N` closes, with no per-session sweep. The pre-#521 `blocked:agent-hard` label on a dependency-wait was redundant with that filter — sub-sweep a (and the [#245](https://github.com/mattsears18/shipyard/issues/245) mid-session referential sweep) existed *only* to reconcile the redundant label. Eliminating the label lets both sweeps go away.

**Why a within-budget-exhaustion bail routes to `soft`, not the conservative `refuse` default ([#1135](https://github.com/mattsears18/shipyard/issues/1135)).** A worker that returns `blocked: verification did not complete within budget` — the canonical phrase `worker-preamble`'s `SKILL.md` now names for this case — hit an environmental/transient condition (a long suite, an auto-backgrounded test run), not a judgment call only a human can make. Before this row existed, such a bail fell through to the table's own conservative default (`refuse` → `needs-human-review`), parking a mechanical retry candidate in the human queue alongside genuine security/scope refusals. The new row matches it to the same `soft` treatment as `cannot reproduce` / `ambiguous`: `blocked:agent-soft`, auto-cleared at the next session's backlog fetch, gated only by `blocked_agent.soft_retry_minutes` in-session. See [`verifying` non-terminal return token — declined for now](#verifying-non-terminal-return-token--declined-for-now-issue-1115-p3-follow-up-to-1113) below for why this one-row fix was chosen over a heavier structured resume mechanism.

**Why soft labels don't bail next session's dispatch.** setup.md step 4's workable filter does NOT exclude `-label:blocked:agent-soft`, AND setup.md step 3d.2 sub-sweep c removes the soft label entirely at every session start. So a soft-blocked issue is workable from the next session's perspective without any other intervention — the label exists purely as in-session documentation that "a worker bailed for a subjective reason; the user may want to clarify the body if they want a different outcome."

**Why soft labels gate in-session re-dispatch.** Once a worker has bailed soft for an issue, immediately re-dispatching another worker against the same issue in the same session would just re-encounter the same ambiguity. The `session_blocked_soft[<N>] = <timestamp>` write blocks step C's lightweight backlog re-check from re-adding `<N>` to `raw_backlog` for `blocked_agent.soft_retry_minutes` minutes (default 30). After the window, step C re-considers the issue — by then the rest of the session may have moved forward (sibling PRs merged, files touched, scope-agent re-dispatched), so the ambiguity may have a different shape.

## `verifying` non-terminal return token — declined for now (issue #1115, P3 follow-up to #1113)

**Decision: do not build a structured, non-terminal `verifying` return token.** Keep the existing `blocked: <reason>` outcome — already legal, already zero-schema-change — as the mechanism for a worker that genuinely exhausts its budget mid-verification. Ship one small, targeted fix instead: [#1135](https://github.com/mattsears18/shipyard/issues/1135), which classifies that specific bail reason as **soft** (retryable) in the routing table above, instead of letting it fall through to the table's conservative `refuse` default.

**Context.** [#1113](https://github.com/mattsears18/shipyard/issues/1113) shipped two hardenings against a worker narrating past an auto-backgrounded verification run instead of ending on a terminal state: P1, a hard rule in `shipyard:worker-preamble`'s `SKILL.md` ("never narrate past an auto-backgrounded verification run — poll it to a terminal result, commit, then return"), and P2, verification-scope guidance in `issue-work.md` §4 (prefer targeted suites over the full discovered battery once the suite count is large). #1113's own body explicitly deferred a third idea — a structured `verifying` token a worker could hand back instead of prose when it *genuinely* cannot finish within budget — judging it lower priority: *"a correct P1 makes this rare."* #1115 asked whether, now that P1 has shipped, that rare-but-not-impossible case is worth building for.

**Why not, right now:**

- **A second hardening landed in the same session, further shrinking the case `verifying` would address.** [#1127](https://github.com/mattsears18/shipyard/issues/1127) (closing [#1111](https://github.com/mattsears18/shipyard/issues/1111)) strengthened the A.0.5 canned resume-message template so a resumed worker is told not to arm *any* new background process for the rest of its dispatch — not merely to stop waiting on the specific thing it was resumed for. That closes the compounding "did it twice in a row" repeat-offender shape directly, on top of P1's single-occurrence catch. Between P1, P2, and #1127, the population `verifying` would exist to serve — a worker that is not narrating, not repeating the mistake on resume, has already scoped its verification sensibly, and *still* cannot finish inside its budget — is now genuinely narrow.
- **Design question 1 from #1115's own framing has no safe answer yet, and building `verifying` without one just moves the #529/#813 backgrounding trap to the orchestrator.** On receiving `verifying`, the orchestrator would need to either re-dispatch-to-await (resume the same agent, or poll again next iteration) or reap-and-re-enqueue. Both #529 and #813 exist because a *worker* ended its turn depending on a backgrounded result that could never resume it — the harness only re-wakes a task with a live foreground call outstanding, not one that went idle waiting on a background child. An orchestrator that receives `verifying` and then itself waits (a `Monitor`, a background poll, a "check back next iteration" loop that isn't actually driven by a live foreground call) recreates the identical failure shape one layer up, at orchestrator cost instead of worker cost. Solving this properly needs a genuine orchestrator-side foreground-wait/resume primitive — something closer to fix-checks-only's self-heartbeating `gh pr checks --watch` pattern, generalized to an arbitrary backgrounded verification handle — which does not exist today and is its own design problem, not a detail to fill in while wiring the token.
- **The implementation cost is real and cross-cutting, sized against the #1101 precedent (`unarmed-policy-override`, the last token added through this exact path).** That PR touched `schemas/worker-return.schema.json`, `steady-state.md` step A.1's reconcile branch, `dispatch-rules.md`'s per-mode return-value lists, **both** `workflows/do-work-dispatch.core.js` and `.workflow.js` `Workflow`-substrate builders, `worker-preamble/SKILL.md`, `issue-work.md`, and new regression coverage — and `scripts/check-dispatch-prompt-parity.mjs` has to stay green across all of it. That's roughly seven files of coordinated wiring to build a resume mechanism for a case the two hardenings above already made rare, before even solving the harder orchestrator-side design question.
- **A much cheaper lever already exists and was sitting unused.** Auditing the routing table above while deciding this issue turned up a live gap: the table's `soft` rows (`cannot reproduce`, `ambiguous`, `suggested fix exceeds expected scope`, duplicate-PR false-positive) are exactly the "transient, a different attempt is reasonably likely to make progress" class — and a genuine within-budget verification-exhaustion bail belongs in that class, not in `refuse`. But no row matches it, so today it falls through to the table's conservative default (`refuse` → `needs-human-review`) — the same *human-decision* bucket as a security refusal or a prompt-injection red flag, for what is actually an environmental/transient condition. That's backwards, and it's a one-row fix, not a new mechanism: #1135 adds the row (plus a canonical phrase for `worker-preamble` to standardize on, so the table can match it reliably) and gets the retryability `verifying` was reaching for — same-session `blocked:agent-soft` treatment, auto-cleared next session — without touching schema, reconcile branches, or either `Workflow` builder.

**If this is ever revisited**, the trigger is not "P3 comes back around to the top of a backlog" — it's evidence that #1135's soft-bail fix is *insufficient*: the SAME issue keeps re-bailing on genuine budget exhaustion across multiple sessions (i.e., the soft-retry window and a fresh session's different scoping aren't enough to make progress) at a rate that costs meaningful re-dispatch overhead, **and** a concrete, safe orchestrator-side wait/resume primitive exists that doesn't require the orchestrator itself to end a turn depending on a backgrounded result (design question 1, actually solved, not deferred again). Until both hold, `verifying` stays a documented-and-declined idea, not a live gap — and if #1135 lands and the recurrence never materializes, that's confirmation the decision here was correct, not a reason to reopen it.

## #1060 supersedes #577 — DIRTY-and-red routes to fix-rebase, not fix-checks

**The old rule ([#577](https://github.com/mattsears18/shipyard/issues/577)).** When drain's per-poll scan found a PR that was simultaneously `mergeStateStatus: DIRTY` and carrying a hard-failure check, it routed that PR to `fix-checks`, not `fix-rebase` — the theory being that `fix-checks-only` would rebase the branch as part of getting it green again, so a dedicated `fix-rebase` pass on top would be redundant work. At the time #577 landed, that theory held: `fix-checks-only` had no DIRTY-specific handling, so a worker dispatched against a DIRTY-and-red PR would naturally end up dealing with the stale base while chasing the failing check.

**What broke it ([#1015](https://github.com/mattsears18/shipyard/issues/1015)).** #1015 added the DIRTY-PR short-circuit to `fix-checks-only`: the very first thing the mode does is check `mergeStateStatus`, and if it's DIRTY, the worker returns `dirty #<M>` immediately — before entering the fix-loop, before calling `gh pr checks --watch`, before attempting anything. This was the correct fix for a *different* problem (#1015's own repro: ~135k tokens spent by a fix-checks-only worker polling a DIRTY PR whose checks could never queue, because the worker had no way to distinguish "checks haven't started yet" from "checks can never start until this is rebased"). But it silently invalidated #577's premise: `fix-checks-only` no longer rebases anything as part of its job. Once #1015 shipped, a `D_dirty_red` PR routed to `fix-checks-only` by #577's rule would bounce straight back out with `dirty #<M>`, having attempted nothing.

**Meanwhile, `fix-rebase.md` had its own, independently-correct-looking bail** ("PR has failing checks — needs fix-checks, not rebase") — a defensive precondition check written for the case where the PR is *not* actually DIRTY-related but stale, and separately red for an unrelated reason. That bail didn't distinguish DIRTY from non-DIRTY when reading "failing checks" — it simply treated any hard-failure check as disqualifying, regardless of `mergeStateStatus`.

**The result: two individually-defensible rules formed a cycle with no exit.** `fix-checks-only` says "this is DIRTY, go to fix-rebase." `fix-rebase` says "this has failing checks, go to fix-checks." Neither mode can make progress on a PR that is both, and — worse than merely stalled — the drain phase's settled definition (`rebase_blocked_prs` membership) meant a session could report the PR as "settled" when it had never actually been touched by either mode.

**Why rebase wins, not "stop counting it as settled."** [#1060](https://github.com/mattsears18/shipyard/issues/1060)'s repro (session `do-work-20260803T010743Z-98363`, `mattsears18/lightwork` PR #3445) established the deciding fact: while a PR is DIRTY, GitHub cannot compute a merge ref for it, so **no `pull_request`-triggered check can ever queue or refresh** — not "hasn't run yet," structurally cannot run. A red check observed on a DIRTY PR is therefore a *fossil* of the last base the PR could still build a merge ref against; it carries zero information about the PR's current health, because nothing has been able to test the PR's current state at all. `fix-checks` cannot act on a fossil — there's no check to re-run, no log to read that reflects the current diff. `fix-rebase` is the only operation that can restore a merge ref, which is the precondition for a check to exist at all. Making the drain merely *aware* of the deadlock (surfacing it louder, but still leaving the PR to bounce) would have been strictly worse than fixing the routing itself — a louder alarm on an unfixable state, instead of removing the state's unfixability.

**The fix, mechanically.** Two bails were inverted at their source, in the same PR:

- `fix-rebase.md` step 2's hard-failure bail is now gated on `mergeStateStatus != "DIRTY"` — a DIRTY PR skips the bail entirely and proceeds with the rebase regardless of what the check rollup shows.
- `drain.md`'s `D_dirty_red` set (DIRTY-and-red PRs) is no longer a distinct dispatch target routed to `fix-checks` — it's an **informational subset** of `D_dirty`, tracked only so the drain log and status line can show which DIRTY PRs are also carrying a stale failure. Every `D_dirty_red` member is dispatched to `fix-rebase` exactly like any other `D_dirty` member. `R_new` (the set that *does* route to `fix-checks`) gained an explicit `mergeStateStatus != "DIRTY"` exclusion so a DIRTY-and-red PR is never double-counted into it.

**Why this couldn't have been fixed by touching only one file.** The issue's own scope-agent pre-flight caught this: fixing `fix-rebase.md`'s bail alone would have been inert, because `drain.md`'s per-poll scan would still never *dispatch* `fix-rebase` against a `D_dirty_red` PR in the first place — it would keep routing those PRs to `fix-checks`, where they'd keep bailing `dirty #<M>` without ever reaching the now-permissive `fix-rebase` bail. Both ends of the #577 rule — its definition in `drain.md` and its enforcement in `fix-rebase.md` — had to flip together, in the same change, or the fix would have shipped a no-op.

**The residual, distinguishable case: `deadlocked_prs`.** Post-#1060, the specific infinite bounce this issue reports can no longer recur — a DIRTY PR never reaches `fix-checks` at all, so there is no cycle to enter. But a narrower combination remains possible: a PR can return `dirty` from a `fix-checks-only` dispatch (e.g. discovered DIRTY mid-dispatch, from an unrelated sibling merge, per the mid-session #1034 dispatch path) and *later*, once routed to `fix-rebase`, hit a genuine non-trivial merge conflict and return `blocked rebase`. That combination is tracked as `deadlocked_prs` (a subset of `rebase_blocked_prs`) purely so the end-of-session summary can name it distinctly — it settles identically to any other `blocked rebase` PR, but its history (an earlier `dirty` observation on the same PR this session) is worth a human's attention when they go to hand-resolve it.

## Why step B keys on agent_id

The A.1 `shipped #<N>` path walks `.git/worktrees/agent-*` and matches on the HEAD ref because the orchestrator's working memory at that point already knows `<N>` but not which agent ran it. Step B runs against a slot that still has `agent_id` in working memory at the moment of release — so we can derive `.claude/worktrees/agent-<agent-id>` directly without scanning. This is faster (no `for` loop, no `git worktree list` parse) and more precise (no risk of matching the wrong worktree on a branch-name collision).

## Why background refill matters

Under the previous synchronous model, every step-C `ready_issues empty but raw_backlog non-empty` case (dispatch rule 5) required blocking ~30 s for a full scope-refill burst before the freed slot could be filled. With background refill, the slot fill-decision uses whatever is already in `ready_issues`: if at least one pre-scoped entry is there, dispatch it immediately; the background refill tops up the queue while the new worker runs. The net effect is that the ~30 s scope-wait at step C never blocks a slot again after the initial batch (started at step 6) has seeded at least one entry into `ready_issues`.

## Dispatch rules — why two dispatch shapes exist, and Agent-tool is the default (#825)

The `Agent`-tool + `isolation: "worktree"` path was the sole dispatch mechanism before the [#782](https://github.com/mattsears18/shipyard/issues/782) Dynamic Workflows migration, was retired as a dispatch target in [#791](https://github.com/mattsears18/shipyard/issues/791), and was restored as the default in [#825](https://github.com/mattsears18/shipyard/issues/825).

The `#782` migration ran in five phases: #787 committed the `Workflow`-substrate script as inert scaffolding; #788 wired `issue-work` to it; #789 wired the remaining six modes; #790 flipped the built-in `dispatch.substrate` default from `"agent"` to `"workflow"` (the 3.0.0 major bump) while retaining the `Agent`-tool path for one release as an instant-revert override; #791 retired that override and deleted the `dispatch.substrate` knob entirely, making the `Workflow` substrate the sole path.

#825 found that sole path could reach a `mode:`-driven worker through every step — self-assign, read, verify, `git rev-parse` — right up to the first `Edit`/`Write` call, which the harness refused with a "parent bg session hasn't isolated yet" error. A controlled retest (dispatching the identical work unit with the parent orchestrator isolated vs. not) reproduced the refusal both ways, ruling out orchestrator-side isolation as the fix. Because `Workflow`-substrate dispatch could not perform a single file write in either configuration, #825 restored the `Agent`-tool shape as the default rather than leave shipyard's autonomous code-writing loop non-functional pending an upstream harness change with no ETA.

The `Workflow` shape stays documented as an alternate rather than being deleted: the choice is reversible on evidence — if a per-`agent()` isolation primitive lands upstream, it can be re-promoted, this time behind a live end-to-end dispatch that actually writes a file (the acceptance gate #791 skipped).

## Dispatch rules — model-tiering cost rationale (#157, #784)

Vantage's cost analysis makes tiering a top cost lever (~50–70% claimed savings vs all-Opus) *and* a quality win (Opus 4.8 is ~4× less likely than 4.7 to silently pass flawed code). See [#157](https://github.com/mattsears18/shipyard/issues/157) for the original cost rationale and [#784](https://github.com/mattsears18/shipyard/issues/784) for the tier-by-role refresh.

## Dispatch rules — fix-rebase moved off Haiku (#854)

`fix-rebase` was originally grouped with `fix-checks-only` under the "mechanical fix modes pin Haiku" tier (#157) on the theory that both are pattern-matching tasks — `fix-checks-only` against a failing log, `fix-rebase` against `git rebase`'s own mechanics (fetch + rebase + force-with-lease). #854 found that theory understates `fix-rebase`'s real task on a conflict: it has to decide whether "both sides differ" means *main advanced this subsystem's design, take main's version* (mechanical — the PR is simply stale) or *two genuinely-competing designs need a human* (semantic — a real judgment call). A drain-phase Haiku `fix-rebase` worker hit exactly that fork on a real PR, misread a stale-collateral conflict in a release-notes pipeline as a live design decision, and bailed to a human with a wrong claim — the design decision had already been settled by a merged sibling PR 36 seconds earlier. Re-dispatching the identical task on Sonnet, with the same information available, resolved it correctly. The mis-classification tax (a wasted dispatch plus a wrong human hand-back that has to be manually corrected) outweighs Haiku's per-run savings on this mode, so `fix-rebase` now pins Sonnet 5 — the same tier as `issue-work` — while `fix-checks-only` (log pattern-matching, no comparable judgment fork) stays on Haiku.

## Dispatch rules — the models config surface was dead until #727

Until #727 the `models.*` config block was a **dead surface**: schema-defined, settable via `/shipyard:config set models.issue_work <id>`, documented in CLAUDE.md, covered by tests — and read by nothing. A user who set `models.issue_work: claude-sonnet-4-6` to cut spend silently kept dispatching on the frontmatter/session default, with no warning anywhere.

## Dispatch rules — why ci skip_speculative_rerun does not disable the flake path (#654)

Setting `ci.skip_speculative_rerun: true` (the default) must NOT suppress the flake auto-heal — a healthy PR starved by a flaky runner would then sit red forever with no recovery, the exact regression [#654](https://github.com/mattsears18/shipyard/issues/654) fixed. The two are orthogonal: the key gates the *undiagnosed* rerun class (still off); the flake path is a *diagnosed* rerun (always available, gated on classification, not on config). A reviewer reading the `ci.*` block should read `skip_speculative_rerun: true` as "the orchestrator never blind-reruns," NOT as "shipyard never reruns" — the classification-gated flake heal is the sanctioned exception and is documented as such here and in `fix-checks-only.md`.

## Dispatch rules — pre-dispatch head-branch reap failure mode (#368)

**The failure mode.** The fresh fix-checks-only worker lands in its own isolated worktree, then runs the safe two-step (`git fetch origin <head>` + `git switch <head>`) to land on the PR's head branch (`fix-checks-only.md` step 1). When the originating issue-work worker's worktree is *still locked* against that head branch, `git switch` fails with *"is already checked out at \<path\>"* and the fresh worker bails — costing one wasted dispatch plus an orchestrator turn of manual deconflict before re-dispatch. This is the exact race [#368](https://github.com/mattsears18/shipyard/issues/368) documented: a fix-checks worker fired against a recently-shipped PR whose check went red, while the originating worker's worktree lingered (its step A.1 immediate-reap (#282) deferred on `peer-alive`, or its worker returned `blocked` / `errored` so the `shipped`-only A.1 reap never ran for it, or a transient `gh` failure aborted the A.1 reap). The drain-phase pre-dispatch reap (#370) covers the *drain* dispatch site; the steady-state 2d block extends the identical self-ancestor reap to the **steady-state** `failed_prs` dispatch site, which #282 (only fires on `shipped`, only matches branch `do-work/issue-<N>`) and #370 (drain-only) leave uncovered.

**Why it's safe to reap.** The lock holds *our orchestrator's* PID (the harness writes the orchestrator PID into every dispatched agent's worktree lock), so `classify-lock` short-circuits it to `self-ancestor` once `SHIPYARD_ORCHESTRATOR_PID` is declared — "this lock is held by an orchestrator that is itself / an ancestor of ours." The originating worker's return was already reconciled at step A by the time this dispatch runs; its worktree is logically done. This is the same self-ancestor reap logic setup.md step 3b runs at session start, the A.1 `shipped`-immediate reap (#282) runs on issue-work completion, and the #370 drain pre-dispatch reap runs during drain — extended to the mid-session steady-state fix-checks dispatch site.

## Dispatch rules — why peer-alive is force-reaped at steady-state pre-dispatch (#771)

This dispatch site only ever fires against a PR whose originating worker has already returned and been reconciled at step A — the same "agent is done by definition" precedent the A.1 `shipped` path (#576) and the drain #370 pre-dispatch reap already apply — so a `peer-alive` classification here is a transient harness artifact, not a genuinely-live conflicting worker. The pre-#771 behavior deferred unconditionally with no override at all (unlike A.1/drain, which already had one), which is exactly the gap that let a re-dispatched fix-checks worker bail on a completed prior worker's still-locked worktree.

## Dispatch rules — derived augmentation-anchor set (#918)

`check-dispatch-prompt-parity.mjs`'s CHECK 3 originally compared against a hand-maintained `AUGMENTATION_ANCHORS` table inside the script — it caught a *known* anchor's text drifting, but was structurally blind to a brand-new augmentation being added to this file and never wired into the corresponding builder. That blind spot wasn't hypothetical: PR #917 ([#851](https://github.com/mattsears18/shipyard/issues/851)) added the operator-residual augmentation, and the very next PR, #919 ([#852](https://github.com/mattsears18/shipyard/issues/852)), added the verification-scope augmentation — both landed with zero coverage in `buildIssueWorkPrompt`, and the static table never grew to notice either, so `dispatch-prompt-parity-880.test.sh` stayed green for both. Two augmentations added, two releases, zero anchor-table updates — exactly the growth-direction blind spot #918 reports (augmentations get *added* far more often than the existing ones get reworded, and the static table only ever catches the latter).

The fix replaces the static table with structural derivation: every bolded `**<Name> augmentation ...**` heading paragraph in this file marks the start of an augmentation, and the checker locates the Context-paragraph blockquote immediately following it, extracting that blockquote's own leading bold span as the anchor phrase to assert present in the applicable builder(s). Adding a new augmentation heading + blockquote to this file therefore extends checker coverage automatically the moment it's authored — no companion edit to the checker script needed, closing the property #880 actually wanted (mirroring `check-worker-return-schema-parity.mjs`'s #856 precedent: derive the comparison set from the canonical source rather than hand-copying it). An augmentation intentionally left unwired for now (the operator-residual and verification-scope augmentations, at the time of #918's fix) carries an explicit `<!-- dispatch-prompt-parity: waived — <reason> -->` marker, so the current gap is a documented, checked-for waiver — the checker still fails if a waived anchor is later found present in a builder (a stale waiver nobody removed once the augmentation actually got wired).

## Dispatch rules — why dispatch-prompt context must be comment-thread-aware (#781)

The repro ([#781](https://github.com/mattsears18/shipyard/issues/781)): a dispatch prompt asserted four checklist items were "genuinely untested (not blocked by anything cited)" when the issue's own first two comments already documented two prior QA passes reproducing all four as blocked on a still-open infra issue — a signal a plain `comments` read would have surfaced.

**Extended to cross-PR/cross-issue merge-state assertions ([#1062](https://github.com/mattsears18/shipyard/issues/1062)).** A second repro hit the same underlying defect — the dispatch prompt asserting an unverified fact as confirmed — one layer over: the composed prompt told the worker a dependency PR "already merged, so `main` has the fix," when a live `gh pr view --json state,mergedAt,mergeStateStatus` at dispatch time would have shown `state: OPEN`, `mergedAt: null`, `mergeStateStatus: BLOCKED`, with auto-merge only just armed and most checks still `QUEUED`/`PENDING`. Low severity that time (the two changes were orthogonal, so the worker could safely proceed against current `main` and document the assumption), but the general risk is real: a worker that trusts "already merged" at face value could implement against a `main` that's missing the dependency's actual integration point. Rather than invent a parallel rule, this was folded into the existing #781 rule as one more instance of "confidence/status framing composed into the dispatch prompt must be freshly verified, not asserted from a stale read" — the mitigation is the same shape too: re-verify live at composition time, or downgrade to a conditional framing the worker knows to re-check rather than trust outright.

## Step 1.3 — silent-direct-merge version-coordination mechanics ([#438](https://github.com/mattsears18/shipyard/issues/438), [#465](https://github.com/mattsears18/shipyard/issues/465))

At `--concurrency ≥ 2`, an ungated silent-direct-merge repo shape breaks version coordination across concurrent PRs in two compounding ways:

1. Whichever PR direct-merges first advances `main`'s manifest version, so every concurrent PR with a lower-or-equal version goes DIRTY even when it was distinctly pre-assigned a version.
2. Every merge also changes the top-of-file CHANGELOG entry, re-DIRTYing even distinctly-versioned rebased PRs on the CHANGELOG insert point — the cascade the [drain CHANGELOG-serialization gate](./do-work/drain.md#drain-protocol) addresses.

This is why [step 1.3](./do-work/setup/01-repo-recovery.md#13-detect-the-silent-direct-merge-repo-shape-admin--ungated-merge-config) treats an `ungated` verdict as worth a session-start warning even though it's advisory-only — at C≥2 the leapfrog above degrades version coordination in a way no individual merge call site can fix on its own.

## Step 1.3 — why detection was extracted to a script ([#720](https://github.com/mattsears18/shipyard/issues/720))

Step 1.3 used to carry its own ~55-line reimplementation of the ungated-admin-direct-merge rule — a *third* copy alongside the `shipyard:worker-preamble` fragment and `issue-work.md`. That is precisely the drift hazard [#716](https://github.com/mattsears18/shipyard/issues/716) was filed for: the copies diverged, and whichever one a given code path happened to read decided whether the gate fired at all. #716 extracted the rule into [`scripts/detect-ungated-admin-direct-merge.sh`](../scripts/detect-ungated-admin-direct-merge.sh); #720 finished the job by routing every remaining call site — including step 1.3 itself and [step 1.35's workflow-scope detector](./do-work/setup/01-repo-recovery.md#135-preflight-warn-on-missing-gh-workflow-oauth-scope-818) — through it. **A condition restated in prose (or re-implemented in bash) in N files will drift; a condition that is one command cannot.**

## Step 1.35 — reactive vs proactive workflow-scope warning ([#812](https://github.com/mattsears18/shipyard/issues/812), [#716](https://github.com/mattsears18/shipyard/issues/716))

GitHub blocks `enablePullRequestAutoMerge` for an OAuth-app token when the PR's diff touches `.github/workflows/*`, unless the token carries the `workflow` scope — `repo` alone is not enough. Issue #812 (landed) teaches the **reactive** half of this problem: a worker discovers the gap at the first failed `gh pr merge --auto` call on a workflow-touching PR and reports the `auto-merge: unavailable — gh token lacks workflow scope` outcome, hoisted into a once-per-session end-of-session banner. Step 1.35 is the **proactive** half — a one-time warning at session start, before the first workflow-touching PR is even opened, when the session shape suggests one is likely.

The detector script backing this warning follows the same single-source-of-truth posture as [step 1.3's merge-shape script](#step-13--why-detection-was-extracted-to-a-script-720): a two-signal condition restated as prose here would drift from the script the way `issue-work.md` and `auto-merge.md` drifted before #716.

## #850 — why not delegate the arm to a worker

Issue [#850](https://github.com/mattsears18/shipyard/issues/850)'s report observed that a worker-opened, workflow-touching PR (lightwork #2999) armed auto-merge and merged fine in the same session where the *orchestrator's own* direct-arm calls (lightwork #2900, #2863) hit the missing-`workflow`-scope block, and floated "dispatch a trivial worker to arm it" (the same way workers already arm their own PRs) as a possible fix.

That reading doesn't survive scrutiny: a dispatched worker (via the `Agent` tool or the `Workflow` substrate) runs on the **same host, as the same user**, and reads `gh`'s credentials from the same place the orchestrator does (`gh auth status` / `GITHUB_TOKEN`) — nothing in shipyard's dispatch machinery provisions a worker with a differently-scoped token. The far more mundane explanation for the #850 repro is ordering: the orchestrator-direct arms (#2900/#2863) most likely ran *before* the human manually ran `gh auth refresh -h github.com -s workflow` in response to an earlier failure that same session (an entirely plausible interactive action — refreshing `gh` auth doesn't require restarting `/shipyard:do-work`), and #2999's worker-side arm simply ran *after* the token had already been widened. Dispatching a whole extra worker purely to retry `gh pr merge --auto` on an existing PR would spend real tokens (a fresh agent, its own worktree provisioning) attempting a call that would fail identically, since it inherits the identical token.

So [#850's fix](../commands/do-work/drain.md#deferred-merge-lander-merge-unarmed-green-session-prs--720) is visibility, not delegation: wire the four orchestrator-direct arm call sites (previously `2>/dev/null || true`, silently discarding *any* arm failure including this one) to detect the same GraphQL signature the worker-side [`auto-merge.md` step 1.1](../skills/worker-preamble/auto-merge.md) already matches, and feed the identical [`workflow_scope_blocked_prs`](../commands/do-work.md#orchestrator-state) list #812 built. The remediation stays a one-time human action either way — the question #850 actually answers is "does every call site that can hit this block report it," not "can shipyard route around a missing scope."

## Step 1.6 — orphan session-file regression ([#227](https://github.com/mattsears18/shipyard/issues/227))

The orphan-session-file sweep exists because a session that doesn't terminate via the happy-path cleanup strands its per-session cost ledger on disk forever, silently under-counting `/shipyard:cost report` by full sessions. See issue #227 for the production repro: a multi-PR `lightwork` session's $11.47 of tracked spend never landed in `~/.shipyard/cost-history.jsonl` because the session crashed before its flush + cleanup chain ran.

## Step 1.6 — two-gate reap protection production failure ([#253](https://github.com/mattsears18/shipyard/issues/253))

The mtime floor alone failed in production when an orchestrator went quiet for >30 minutes during a long drain phase — a peer session's orphan sweep then reaped the still-active session's state file mid-write. The fix layers a PID-liveness gate (`session-state.sh is-active`) **before** the mtime check, so a live owning process is never reaped regardless of how stale its mtime looks. Both gates have to fail before a file is reaped, so even a recycled-pid + recent-mtime scenario (the only known failure mode of `is-active`) still skips the reap.

## Step 1.6.5 — orphan orchestrator worktree production trace ([#280](https://github.com/mattsears18/shipyard/issues/280))

See issue #280 for the production trace that motivated this sweep: a single-slot user's `git worktree list` accumulated multiple `orchestrator-dowork-*` detached-HEAD entries across crash-and-restart cycles, none of which any spec-defined step would ever reap — because step 1.6 only deletes the session JSON, and step 3b only reaps `agent-*` worker worktrees, leaving `orchestrator-*` worktrees from a session that crashed between its own flush/cleanup and its own worktree reap permanently orphaned.

The raw-`rm -rf` fallback in the reap helper is load-bearing for this exact case: `git worktree remove` fails when the worktree dir is on disk but `.git/worktrees/<name>/` metadata has already been pruned, or was never registered at all (e.g., a manual `mv` left an `orchestrator-*` dir without git tracking it) — both of which showed up in the #280 repro.

## GH App alias normalization — why it was needed ([#296](https://github.com/mattsears18/shipyard/issues/296))

GitHub returns two different login shapes for the same GH App account depending on which API the caller hits — REST returns `sentry[bot]`, GraphQL Bot/App actor objects (what `gh issue list --json author` returns) expose `app/sentry` — and the two strings have nothing in common after lowercasing. Before #296, a maintainer who put `sentry[bot]` in `.shipyard/trusted-authors.txt` would see every Sentry-filed issue silently bucketed as untrusted by step 2's bucket-0.5 filter and dropped by step 4's client-side filter, because the comparison value (the GraphQL `app/sentry` shape) never matched the file's REST-shaped entry. The setup-time advisory `[trusted-authors] loaded 2 author(s)` was misleading — the bot was "in the file" but not effectively trusted. The fix (alias normalization at allowlist-load time, described in [step 1.7](./do-work/setup/01-repo-recovery.md#gh-app-alias-normalization-issue-296)) closed the gap by cross-adding both shapes to the resolved set.

## Step 1.7 — CODEOWNERS enforcement gap on this repo ([#867](https://github.com/mattsears18/shipyard/issues/867))

This repo's own [`.github/CODEOWNERS`](../../../.github/CODEOWNERS) names `.shipyard/trusted-authors.txt`, but **the platform-level enforcement toggle is not currently on** — the `main` ruleset's `require_code_owner_review` parameter is `false` (verify with `gh api repos/mattsears18/shipyard/rulesets/16669759 --jq '.rules[] | select(.type=="pull_request") | .parameters.require_code_owner_review'`), so a CODEOWNERS-file-only setup does NOT actually block an unreviewed PR from touching the allowlist. Don't copy this repo as a "reference example" of the enforcement being live until that's fixed — #867 was filed as a regression of the original ask in [#139](https://github.com/mattsears18/shipyard/issues/139).

## Step 3 — label-purpose provenance ([#520](https://github.com/mattsears18/shipyard/issues/520))

The labels step 3a ensures exist each carry fold/elimination history worth knowing when reading the `gh label create` calls:

- The `needs-refinement` gate label was eliminated in #520 — `/refine-issues` now detects refinement candidates by source-signal scan rather than a persisted label.
- `needs-human-review` doubles as the scope-agent epic-handoff surfacing label, applied by step 6's Deferred recording path when the scope agent confirms an issue is non-shippable as a single PR (see [#498](https://github.com/mattsears18/shipyard/issues/498)). The epic-decomposition handoff is distinguished from other `needs-human-review` issues by the `<!-- do-work-needs-decomposition -->` body marker per [#519](https://github.com/mattsears18/shipyard/issues/519), which [`/decompose-epic`](./decompose-epic.md) consumes to auto-shard the epic into dispatch-ready sub-issues (see [#501](https://github.com/mattsears18/shipyard/issues/501)).
- The former `blocked:agent-hard` was eliminated in #521 — agent refuses now route to `needs-human-review` and dependency-waits to the `Blocked by #N` body-ref filter (no label). See [blocked:agent-hard elimination](#blockedagent-hard-elimination-issue-521) above for the full rationale.

## Step 3c — the stale self-assign gap ([#303](https://github.com/mattsears18/shipyard/issues/303))

Prior sessions sometimes leave the `@me` self-assign on an issue after their on-disk worktree has been cleaned up (returned `blocked`, errored before first commit, etc.). The first four rows of step 3c's orphan-worktree table only see issues whose worktree is still present on disk — so this state survives unbounded across sessions, with the issue silently failing the worker-side step-0 pre-flight ("assignee is `@me`, not someone else, so don't bail") and getting re-dispatched against stale prior-session artifacts. #303 closed the gap by adding a fifth row: after the worktree loop, sweep self-assigned issues with no worktree, no PR, and no branch on origin, and clear the assignment so the normal step-4 fetch picks the issue back up.

## Step 6 — Rolling pre-flight dispatches on the first result (issue #233)

The previous spec blocked until all `2 × concurrency` scoping agents returned before step 7 could fire — roughly 30 seconds of synchronous latency before the first worker launched. The rolling model instead fires the same batch in the background and dispatches the moment ONE entry lands in `ready_issues`, hiding the remainder of the scope latency behind real worker execution. First-dispatch latency drops from ~30s (wait for all `2N` agents) to ~5–10s (wait for only the fastest agent in the batch); subsequent dispatches read directly from `ready_issues` with no scope-wait at all once at least one scoped entry is queued.

## Step 6 — Shared regression-test suite inclusion (issue #554)

The scoping agent's `files` return is the source of `claimed_paths`, which the soft-collision partitioning and drain-phase rebase logic both key off. For fix-class issues in a repo that maintains a shared regression-test accumulator file (a single file where every fix appends a test block — e.g. `plugins/shipyard/scripts/tests/do-work-split.test.sh` in `mattsears18/shipyard`), a worker will append to that file by convention even when the issue body never names it. If the scoping agent doesn't include the file in `files`, the orchestrator's collision tracking never learns the candidate claims it — so a sibling PR that legitimately claimed the same file collides with it invisibly. The repro: issue #554's PR #551 bailed `blocked rebase: merge conflict extends beyond coordinated manifest+CHANGELOG rows (plugins/shipyard/scripts/tests/do-work-split.test.sh)` — a conflict that a dispatch-time park would have caught for free, but instead only surfaced as an expensive drain-phase manual-rebase handoff. The fix folds the shared-suite file into `files` proactively via a cheap heuristic (a `*.test.sh`-shaped file touched by 10+ distinct commits, or one named explicitly in the repo's `CLAUDE.md`) rather than waiting for the scope agent to notice it unprompted.

## Step 6 — Provisioning carve-out: shipping the scaffold is the harm (issue #628)

The default-to-slicing bias assumes there's always an inert first phase to ship — some subset of the change that's safe to land even if incomplete. External-service integration issues break that assumption: when the committed config would be non-functional (or would deploy dead) until a human provisions the service and supplies a credential that doesn't exist yet, there is no inert first phase — shipping the scaffold with a fabricated or empty value IS the harm, not a step toward the fix. The repro: a worker deployed non-functional Terraform for a Sentry account the user hadn't created yet, because the scaffolding read as a reasonable phase-1 slice under the general slicing bias. The carve-out routes this shape to the deferred form (`external-dependency`, with the pending provisioning named in `evidence_pointer` and the unblock condition in `would_be_dispatchable_as_phase_1_if`) instead of letting the slicing bias treat "write the scaffolding" as shippable. It does not apply once the credential is already provisioned — an existing CI secret or populated `*.tfvars` the code merely references is functional config and slices normally.

## Step 6 — Inline auto-decompose reuses the decompose-epic worker logic (issue #665)

Reusing `/decompose-epic`'s Worker prompt template inline (rather than re-implementing the sharding logic at the defer call site) is what lets the auto-decompose path inherit the standalone command's guardrails for free, without re-stating them here:

- **The confidence gate and `--max-subissues` cap live inside the worker** (its Step B) — a breakdown that isn't confident (a phase that isn't single-PR-sized, an ambiguous ordering, a sub-issue whose acceptance criteria the codebase can't support) or that would exceed the cap makes the worker escalate (its Step D) rather than shard: it posts the `<!-- do-work-decompose-agent -->` "couldn't auto-decompose: `<reason>`" comment and leaves the pre-existing `needs-human-review` + trigger-marker handoff exactly as it would have been without #665. A low-confidence or over-cap epic is never worse off than the pre-#665 park-for-manual behavior.
- **Untrusted-input discipline is the worker's own** — it treats the epic body as a claim to re-derive against the codebase, not as instructions, and returns `blocked:` on any out-of-scope directive found in the body or comments. The orchestrator's dispatch passes only the issue number and repo, never the body.
- **The parent issue stays `needs-human-review` and OPEN on the success path too** (the worker's Step C keeps the label and posts the `<!-- do-work-decompose-agent -->` idempotency comment) — it remains a human-gated tracking umbrella whose children carry the dispatchable units. A later standalone `/decompose-epic` run skips an already-sharded parent via that same idempotency sentinel, so the inline path and the manual command can never double-shard the same epic.

**Why `subagent_type: "shipyard:decompose-worker"` rather than `general-purpose`.** [#772](https://github.com/mattsears18/shipyard/issues/772) / [#774](https://github.com/mattsears18/shipyard/issues/774) registered a first-class agent identity for this template. It's a naming change only — no behavioral difference from the pre-#772 `general-purpose` dispatch — but a registered name gives the decomposition worker a stable identity for cost/log attribution instead of being indistinguishable from every other general-purpose dispatch in the session.

## Step 6 — Scope-result freshness check (issue #563)

Without a freshness check, the orchestrator re-dispatches a scope agent against an issue even when a marker-tagged diagnosis comment already documents the same conclusion — burning a fresh scope-agent invocation to re-derive something already on the issue. The repro that motivated this: a maintainer bulk-cleared `needs-human-review` labels across a batch of issues while the underlying diagnosis comments (1–4 days old, still accurate) remained posted on them. The next session's scope pre-flight, seeing the label gone, re-dispatched scope agents against all of them — 7 fresh agents returned nearly verbatim re-derivations of the existing comments, at a cost of roughly 330k wasted tokens. The freshness check (a configurable `scope.diagnosis_reuse_hours` window, default 72h) closes this: before dispatching, check for a recent marker-tagged comment whose conclusion the body and comment thread haven't since invalidated, and if it's still fresh, reuse it as a `cached-diagnosis` defer instead of re-scoping.

## Step 6 — Design, architecture, epic, and spike decisions are in-scope (issue #767 repro)

This is the scope-preflight-side extension of [RATIONALE → Don't defer an epic, spike, or design-needed issue for open design decisions (#767)](#dont-defer-an-epic-spike-or-design-needed-issue-for-open-design-decisions-issue-767) — the same rule, one level earlier, applied to whether to dispatch an issue at all rather than to an in-worker implementation choice. ## `SHIPYARD_REPO_ROOT` — per-call-site re-derivation kept over a step-0.4 config snapshot (issue #1105, follow-up to #1059/#1064)

**Decision: keep option (a) — the current per-call-site re-derivation shape (`SHIPYARD_REPO_ROOT` re-derived and exported from the `.shipyard-primary-root` stash at each post-relocation `shipyard-config.sh` call site) — over option (b), a one-time config snapshot at step 0.4 that every later read would consume instead of shelling out again.** #1059/#1063 introduced the pin and its first consumer; #1064 swept the then-known remaining call sites and added [`scripts/tests/shipyard-repo-root-preamble.test.sh`](../scripts/tests/shipyard-repo-root-preamble.test.sh) as the regression guard; #1059's own body deferred the snapshot-at-0.4 alternative as an explicit open design question rather than deciding it. #1105 is that decision.

**Why (a) over (b):**

- **The residual risk #1105 named turned out to be live, not hypothetical, and (a) has a cheap, complete fix for it.** Before deciding anything, this PR audited every `${CLAUDE_PLUGIN_ROOT}/scripts/shipyard-config.sh"` / `resolve-dispatch-model.sh"` call site across `commands/do-work/` (mechanically, not by re-reading #1064's list) and found one the hand-maintained `FILES` array had already missed: `setup/01b-backlog-overview.md`'s step-2 `triage.investigate_dispatch` read calls `shipyard-config.sh` post-relocation with no `SHIPYARD_REPO_ROOT` pin, and was never added to #1064's six-file array (that file grew the call after #1064's sweep, or was simply missed). This is exactly the class of bug the pin exists to prevent — a repo with `.shipyard/config.local.json` set would silently lose that config layer for this one read, no error. Both halves of the fix are in this PR: the missing pin was added to the offending block, and the regression test's `FILES` array was converted from a hardcoded list to the same mechanical `find`-based discovery `scripts/tests/claude-plugin-root-preamble.test.sh` already uses for the analogous `${CLAUDE_PLUGIN_ROOT}` preamble (every `*.md` under `commands/do-work/`, recursively, minus `setup/00-config-worktree.md`, which is excluded explicitly rather than scanned-and-ignored — see the test file's own Scope comment for why a scan there would false-positive). A new file added to `commands/do-work/` is now covered automatically the moment it grows a real call site, with no array to remember to extend — closing the residual risk (a) actually had, at a fraction of the cost of (b).
- **(b) doesn't structurally eliminate the discipline problem — it relocates it.** The pitch for (b) is "collapse N re-derivation points to one choke point, correct by construction." But every `shipyard-config.sh get <path>` call site across the orchestrator would still need to know to read the snapshot instead of shelling out live — a call site that forgets and calls `shipyard-config.sh` directly reintroduces the identical bug class, just one level removed and over a much larger surface (every config read in the orchestrator, not only the subset that currently needs the `SHIPYARD_REPO_ROOT` pin). A regression test for that shape is also less mechanical to write than this one: "calls `shipyard-config.sh` but doesn't carry the pin substring" is a simple grep-shaped predicate; "calls `shipyard-config.sh` directly instead of reading the snapshot file" needs the same kind of predicate but now has to be applied to *every* config read in the tree, including many that have nothing to do with this bug.
- **(b) trades away mid-session config-mutation pickup, and `/shipyard:do-work` sessions are long-running.** A snapshot captured once at step 0.4 goes stale the moment anything changes the merged config mid-session — a maintainer editing `shipyard.config.json` or `.shipyard/config.local.json` while a many-hour autonomous session is in flight, or (per this repo's own `~97 PRs/week` cadence) a config-touching PR landing on `main` mid-session. Per-call-site re-derivation reads live every time, so it picks up any such change on the next read; a snapshot would silently keep serving the value captured at session start. #1059's own body already flagged this tradeoff; nothing in #1105's evidence changes the calculus in the snapshot's favor.
- **(b) is a materially larger, riskier change for a marginal gain now that the coverage gap has a mechanical fix.** #1059's own scope notes call out that (b) "changes the config-read contract everywhere" — every `shipyard-config.sh get <path>` invocation across the orchestrator, not just the ~10 `SHIPYARD_REPO_ROOT`-needing call sites, would need to change shape (either a direct rewrite to a `jq` lookup against a stashed snapshot file, or a `shipyard-config.sh --from-snapshot <path>` mode that keeps call sites textually similar but adds a second code path to `shipyard-config.sh` itself to maintain). That's a much bigger diff to review and a new failure class to reason about (snapshot invalidation, partial/corrupt snapshot writes, staleness) — for a gain that (a) + the mechanical-glob fix already captures for the coverage problem specifically, without touching the config-read contract at all.

**If this is ever revisited**, the trigger should be a new observed failure mode (a)'s live-read model can't address on its own — not a re-litigation of the residual-array-drift risk, which is now closed by the mechanical glob above. Should (b) ever become worth doing anyway (e.g. a future need to *snapshot* config for reproducibility, not just to avoid re-derivation), do not attempt it as a single PR: decompose into an ordered chain — (1) design the snapshot file's shape and the `shipyard-config.sh` read-mode it would need, as its own issue; (2) migrate call sites incrementally, file-by-file, each landing behind its own regression test; (3) only remove the `SHIPYARD_REPO_ROOT` pin machinery once every call site has migrated and the `shipyard-repo-root-preamble.test.sh` suite itself is retired as no-longer-applicable. Shipping the whole migration in one PR would touch too much of the orchestrator's spec tree at once to review safely, and would leave no safe rollback point if the snapshot shape needs revision after the first few call sites migrate.

## Mutually-blocking PR detection — why combining is out of scope (issue #1140)

**Decision: ship detection + loud surfacing only. Automated combining (cherry-picking the smaller PR's commit onto the larger) is deliberately NOT implemented.**

The repro: two open PRs against `mattsears18/lightwork` each fixed the exact required check the OTHER was failing (`🧹 Lint & Typecheck` and `🎭 Web E2E Tests`) — neither could go green alone, stalling an 11-PR-deep merge train, and the drain's only response was to apply `blocked:ci` to both with the real cause ("these two unblock each other") recorded nowhere. The issue's own body sketches a 4-step algorithm that ends in combining the PRs, and explicitly names the guardrails combining would need: file-disjoint diffs only, a hard cap on how many PRs may combine, and a loud comment on the PR. It also names the reason to be cautious: in the reporter's own manual repro, one of the two PRs was human-gated for an unrelated reason, and combining necessarily entangled them.

**Why detection-and-surfacing is the complete deliverable, not a partial one.** Before this change the state was not merely unresolved — it was *invisible*: `blocked:ci` looks identical whether a PR is stuck on a genuine unfixable failure or stuck because its sibling holds the fix. Making the relationship visible (a diagnosis comment naming the specific checks each PR blocks/is blocked by, whether the diffs are file-disjoint, and an end-of-session summary line) closes the actual reported gap — "the real explanation … nowhere in the record" — on its own, with zero risk of a bad automated mutation. A maintainer reading the diagnosis comment can combine manually in under a minute once they know the relationship exists; the hard part this issue reports is realizing the relationship exists at all.

**Why combining is a materially different risk class, not just "the same fix, automated":**

- **It mutates a PR branch that already has a life of its own** — commit history a reviewer has seen, possibly already-posted review comments, CI runs a human may be tracking. Rewriting one PR's branch to include the other's commit changes what "approve this PR" means after the fact, silently, unless the tooling is scrupulous about narrating it (which the issue itself flags as a requirement, not a nice-to-have).
- **The reporter's own repro entangled a PR that was human-gated for an unrelated reason.** A general-purpose automated combiner has no way to know a PR carries an out-of-band gate (a security review, a "don't merge yet" from a stakeholder) unless that gate is itself machine-readable — and most aren't. Detection-only never touches this landmine because it never touches a branch.
- **File-disjointness is necessary but not sufficient for a safe combine.** Two PRs can touch disjoint files and still be semantically entangled (one PR's disjoint-file change assumes an invariant the other PR's disjoint-file change breaks). The issue's own guardrail language ("only attempt when diffs are file-disjoint") is a floor, not a proof of safety — validating "file-disjoint" mechanically is cheap; validating "semantically safe to combine" is not, and a false green here ships a merge nobody actually reviewed as a unit.

**What was actually built.** `scripts/detect-mutually-blocking-prs.sh` is the single executable source of truth for the pairwise relationship (each PR's failing required checks fully covered by the other's passing checks — the "complete blocking set" the issue's step 2 describes), with a pure `--decide-pair` mode so the truth table is unit-tested without a live `gh`. It also reports file-disjointness as an informational signal (so the diagnosis comment can tell a human whether a manual combine is likely mechanical or needs real reconciliation), but disjointness never gates the detection verdict itself — the verdict is about the CI-blocking relationship, which holds regardless of whether combining would be easy. `drain.md`'s wiring is read-only against dispatch state: it changes nothing about `R_new` / fix-checks-only / `blocked:ci` routing, so a detected pair still settles through the exact same path it would have taken before this change — the only difference is that the settling now comes with a comment explaining why.

**Scope: pairs only, not N-PR cycles.** The issue's own phrasing is "a pair (or cycle)." A cycle spanning 3+ PRs is a real but rarer shape (it needs three simultaneous, mutually-covering breakages rather than two) and is left as a documented gap rather than guessed at — the reproduced failure, and the common real-world shape this issue names ("two repo-wide breakages landing within hours of each other"), is a pair.

**If automated combining is ever built**, it should be a separate, explicitly opt-in capability (a `ci.auto_combine_mutually_blocking: true` config knob, default off) — never a silent default — and should implement every guardrail the issue names as a precondition, not an afterthought: file-disjoint diffs only, a hard cap on PR count, and a loud, unambiguous comment on the surviving PR (and the one being superseded) narrating exactly what happened and why, posted *before* the combine takes effect where GitHub's UI allows it.
