# /shipyard:do-work — Don't

The orchestrator's rule list — load-bearing prohibitions across every phase. The *why* for each rule lives in [RATIONALE → Don't extended](../do-work-RATIONALE.md#dont--extended-rationale-for-the-load-bearing-rules); cross-references are inline where the full discussion matters. The thin entry [`commands/do-work.md`](../do-work.md) links here from the [phase routing summary](../do-work.md#phase-routing).

**Dispatch-loop discipline:**

- **Don't go idle while `raw_backlog` or `ready_issues` has items.** Refill the pool on the same turn the last completion notification arrives. ([why](../do-work-RATIONALE.md#dont-go-idle-while-queues-hold-work))
- **Don't conflate "pool drained" with "session complete."** The merge train continues without you; the dispatch loop dies if you stop dispatching. ([why](../do-work-RATIONALE.md#dont-conflate-pool-drained-with-session-complete))
- **Don't conflate "PR merged" with "worker done" — never release a slot or reap a worktree from live PR state ([#1235](https://github.com/mattsears18/shipyard/issues/1235)).** A merged PR means the merge train finished, not that the dispatched worker has returned — a `fix-checks-only` worker's normal tail (push → watch the rollup settle → verify → return) routinely overlaps with auto-merge firing, so the orchestrator can observe `state: MERGED` with every check green while the worker is still executing. The only signal that frees a slot is the worker's own terminal return (parsed at [step A.1](./steady-state.md#a1-parse-the-return-string)) or a formal stall/crash detection ([A.0.5](./steady-state.md#a05-post-return-worktree-reap-for-crashed--narrative-non-terminal-returns-fires-before-a1s-return-string-parsing)) — never a live `gh pr view` / `gh issue view` read taken as a standalone reconcile trigger. This is the same shape of error as the "pool drained" bullet above — a tempting-but-wrong terminal signal — and it is worse here because it defeats two existing guards by reaching them out of order: the `.in_flight` membership guard (see the "Don't reap a live-PID worktree" bullet above, [#832](https://github.com/mattsears18/shipyard/issues/832)) is emptied by the very reconcile that acted on `MERGED`, and [#838](https://github.com/mattsears18/shipyard/issues/838)'s pre-reap unpushed-work inspection is never reached because the orchestrator already believes the slot is free. ([why](../do-work-RATIONALE.md#dont-conflate-pr-merged-with-worker-done-issue-1235))
- **Don't declare termination without running the canonical fresh-fetch query of [drain.md's termination-assertion step 4](./drain.md#termination-assertion).** `raw_backlog == 0` in stored state is a necessary precondition, not a sufficient one — user-filed mid-session issues can sit on the live tracker without surfacing into the cached backlog. Step E's `last_fresh_fetch=<HH:MM:SS|"never">` invariant token is the per-turn evidence; the staleness guard on `idle_reason="all queues empty (terminating after in_flight drains)"` requires `last_fresh_fetch` to be within the last 60s of `now` before the orchestrator may hand off to drain. See [issue #195](https://github.com/mattsears18/shipyard/issues/195) for the regression that prompted the numbered-procedure restructuring of the termination assertion.
- **Don't report "backlog empty" or session completion from queue-emptiness alone ([#1250](https://github.com/mattsears18/shipyard/issues/1250)).** Both exit points — [setup's early exit](./setup/04-backlog-divert.md#4-fetch--rank-the-backlog) (`raw_backlog` empty, no failing PRs) and [drain.md's termination assertion](./drain.md#termination-assertion) (all queues empty on the fresh fetch) — MUST build the completion ledger (`setup/04f-completion-ledger.md`) from that same fetch and place every open issue in exactly one of its buckets before claiming completion. An issue that matches none of the buckets is a filter defect, not evidence the backlog is genuinely empty — report it loudly and keep going. "Queues empty" and "the filter erased the work" are indistinguishable from internal-state arithmetic alone; the ledger is what tells them apart.
- **Don't hand-roll an ad-hoc `gh issue list` query mid-session as a shortcut "is anything left?" check ([#1194](https://github.com/mattsears18/shipyard/issues/1194)).** Every backlog re-fetch — [step C's lightweight backlog re-check](./steady-state.md#c-dispatch-a-replacement-if-work-remains--mandatory-action), step D's periodic refresh, or [drain.md's termination-assertion step 4](./drain.md#termination-assertion) — MUST use the documented wide-fetch (`--state open` only) plus the **full** client-side filter from [setup.md step 4](./setup/04-backlog-divert.md#4-fetch--rank-the-backlog), never a hand-rolled shorthand composed on the spot. The concrete failure this closes: a mid-drain "quick check" written as `select((.assignees|length)==0)` silently drops every issue the session self-assigned — exactly the resumable-work case [#332](https://github.com/mattsears18/shipyard/issues/332) exists to keep visible — and reported a 10-issue backlog as empty. There is no cheaper valid substitute for the canonical procedure; if you need a sanity check mid-drain, re-run the canonical fetch at whichever call-site's spec is closest at hand.
- **Don't hand a workable issue to the human — attempt-then-escalate, never escalate-without-attempting ([#531](https://github.com/mattsears18/shipyard/issues/531)).** If an issue passes the mechanical [step-4 workable filter](./setup/04-backlog-divert.md#4-fetch--rank-the-backlog) (trusted author, no dispatch-gate label, no open `Blocked by #N`, not assigned elsewhere), the orchestrator MUST dispatch a worker against it before terminating. It may NOT surface the issue to the user as "left for a fresh run" / "say the word and I'll work them" / "next step for you" while the agent is itself capable of doing it. **"It's a follow-up I filed this session" / "feels like it should wait" / "it's a meta-issue about the orchestrator" / "it rewrites the path I'm running" are NOT valid defer reasons — they match none of the seven [`defer_reason_class`](./setup/06-scope-preflight.md#6-initial-scope-pre-flight) values** (`external-dependency`, `human-decision-required`, `untrusted-author`, `confirmed-blocker-still-open`, `confirmed-non-shippable-as-single-PR`, `time-gated`, `blocked-by-in-flight-pr`). A defer to the human is gated to exactly those classes; an issue that matches no class is workable and MUST be worked, not deferred off-book. ([why](../do-work-RATIONALE.md#dont-hand-a-workable-issue-to-the-human-without-attempting-it-first-issue-531))
- **Don't defer an epic, spike, or design-needed issue merely because it "has open design decisions" ([#767](https://github.com/mattsears18/shipyard/issues/767)).** See [`06b-scope-carveouts.md`'s design/architecture/epic/spike callout](./setup/06b-scope-carveouts.md#designarchitectureepicspike-decisions-are-in-scope-by-default-not-a-defer-reason-767). Extend the [#661](https://github.com/mattsears18/shipyard/issues/661) "autonomous design / architecture decisions" default from in-worker implementation choices to issue scoping itself: make the reasonable design call and dispatch (sliced with `phase_1_scope` if multi-phase); an epic that genuinely can't ship as one PR still routes to `confirmed-non-shippable-as-single-PR` (decomposition), never to `human-decision-required`. Reserve `human-decision-required` / `needs-human-review` for security/access-control settings, unprovisioned external-service credentials, and genuine product/business/legal judgment calls — not design or architecture. ([why](../do-work-RATIONALE.md#dont-defer-an-epic-spike-or-design-needed-issue-for-open-design-decisions-issue-767))
- **Don't defer a whole `agent-console`/security-flavored issue when it has a shippable code slice ([#851](https://github.com/mattsears18/shipyard/issues/851)).** See [`06b-scope-carveouts.md`'s operator-slice carve-out](./setup/06b-scope-carveouts.md#operator-slice-carve-out--ship-the-code-slice-hand-back-only-the-operator-remainder-851). Test whether the narrow operator/console action can be split from an independently valuable, functional-on-its-own code portion before returning a whole-issue `external-dependency`/`human-decision-required` defer; if it can, dispatch ready with `phase_1_scope` for the code and `operator_residual` for what stays on the issue — the worker ships the slice without closing the issue, then hands the residual back (`agents/issue-worker/issue-work.md` §6.5), mirroring the split shipped by hand in PR [#900](https://github.com/mattsears18/shipyard/pull/900) for issue #867.
- **Don't defer a whole QA-verification-shaped issue when part of it is automatable ([#852](https://github.com/mattsears18/shipyard/issues/852)).** See [`06b-scope-carveouts.md`'s QA-verification carve-out](./setup/06b-scope-carveouts.md#qa-verification-carve-out--run-the-automatable-audit-hand-back-only-the-manual-remainder-852). Test whether any stated acceptance criteria are checkable by an existing shipyard auditor against a reachable surface (typically a live web URL) before returning a whole-issue `external-dependency` defer; if so, dispatch ready with `verification_slice` naming the auditor + surface and `verification_residual` for what stays un-automated — the worker runs the audit, files any `bug` issues the auditor finds, posts a verification-status comment, and dispositions the issue without opening a resolving PR (`agents/issue-worker/issue-work.md` §6.6).
- **Don't file end-of-session friction/follow-up issues after the termination assertion has run, and never during or after [cleanup](./cleanup-summary.md#end-of-session-cleanup) ([#743](https://github.com/mattsears18/shipyard/issues/743)).** File any such issues **before** running the termination assertion (see [drain.md's guidance](./drain.md#termination-assertion)) — the assertion's own step-4 fresh-fetch then picks the new issue up as a net-new candidate and loops back through dispatch instead of terminating around it. ([why](../do-work-RATIONALE.md#dont-file-end-of-session-follow-up-issues-after-the-termination-assertion-issue-743))
- **Don't exit the end-of-session drain while forward progress continues.** Exiting at a hard 15-min mark strands PRs that go red after the cap. ([why](../do-work-RATIONALE.md#dont-exit-the-drain-while-forward-progress-continues))
- **Don't ask the user "should I keep working, summarize, park, or stop?"** Termination is mechanical (see [Termination assertion](./drain.md#termination-assertion)). The only stop signal is the explicit `stop` / `drain` / `/do-work stop` phrase from [Soft drain](./drain.md#soft-drain).
- **Don't emit recap / "Next: …" narration in lieu of dispatching.** A turn that frees a slot has shape: tool call → invariant line. No prose between them, no prose after them, no "Next:" sentence anywhere. Forbidden phrasings include "Next, I'll watch for …", "Waiting for completions to refill …", "The merge train will drain on its own …". ([why + DO/DON'T examples](../do-work-RATIONALE.md#dont-emit-recap--next--narration-in-lieu-of-dispatching))
- **Don't poll for agent completion.** The harness notifies you. Polling burns turns and cache. **Scoped to agent completion specifically ([#1402](https://github.com/mattsears18/shipyard/issues/1402)) — this is NOT a blanket ban on ever arming a bounded watch.** The harness notifies you *for agent completion* because that's a signal the harness itself emits; it has no equivalent notification channel for an arbitrary external environmental condition (a saturated CI queue draining, a runner pool waking up) — nothing will tell you that cleared on its own. A bounded `Monitor` watch of a genuinely external, self-clearing condition — [`paused_on_environment`'s resume probe](./environmental-pause.md) is the one currently wired — is the correct tool there, not the polling this rule forbids. The distinguishing question: is there a wake source other than a poll (an agent that will eventually complete and notify you)? If yes, this rule applies — don't poll, wait for the notification. If no — as when `in_flight` has genuinely drained to zero and nothing else will ever wake this turn — a bounded, terminal-state watch is the sanctioned exception, not a violation of this rule.
- **Don't wait for the whole pool to drain before dispatching replacements.** Fill any single freed slot immediately.
- **Don't run A.0/A.1/B/C/D on a phantom re-fire `task-notification`.** [Step A.−1's reconcile-once gate](./steady-state.md#a1-reconcile-once-gate--skip-phantom-re-fires-mandatory--first-thing-in-the-turn) MUST run before A.0 on every wake; when the incoming `task-id` is already in `reconciled_agent_ids`, log the `[phantom-notification]` advisory and end the turn — no token bump, no slot release, no dispatch, no refresh, no invariant line. This is the **one documented exception** to the "every turn ends with either a tool call or the invariant line" rule from the steady-state turn contract. See [#317](https://github.com/mattsears18/shipyard/issues/317) for the harness pattern and the cost-of-not-having-the-gate.
- **Don't *pure*-silent-skip a phantom re-fire whose body asserts a terminal outcome for a *different, still-in-flight* target ([#530](https://github.com/mattsears18/shipyard/issues/530)).** The silent `return` is correct only for a **genuine wind-down phantom** (body asserts nothing reconcilable, or names only the already-reconciled target). Before skipping, parse the body: if it names an in-flight slot's target, run the [trust-but-verify probe](./dispatch-rules.md#dispatch-rules-used-by-step-7-and-step-c) (issue state + PR `mergeStateStatus`) and, if ground truth confirms the outcome, reconcile the **in-flight sibling** from verified state (keyed on the sibling's `agent_id`, not the phantom's reaped id) rather than silent-skipping. The body's narrative is a *trigger to verify*, never authority to reconcile on its word — a target whose ground truth does NOT confirm falls back to the silent skip. See [Step A.−1's sibling-strand variant](./steady-state.md#a1-reconcile-once-gate--skip-phantom-re-fires-mandatory--first-thing-in-the-turn). ([why](../do-work-RATIONALE.md#dont-silently-skip-a-phantom-re-fire-that-strands-an-in-flight-sibling-issue-530))
- **Don't reconcile a return without first calling `bump-tokens` and (for `shipped` / `green` / `noop: already green` returns) posting the cost-tracking comment via `read-tokens --format comment` + sentinel edit-or-create.** [Step A.0](./steady-state.md#a0-attribute-the-dispatchs-token-usage-mandatory--before-any-return-string-parsing) is MANDATORY on every reconcile turn — without it, `.tokens.totals`, `.tokens.per_issue[<N>]`, `.tokens.per_pr[<M>]`, the durable PR cost-comment, and the persistent ledger at `~/.shipyard/cost-history.jsonl` all stay empty, and the perf umbrella ([#152](https://github.com/mattsears18/shipyard/issues/152)) becomes unmeasurable. Step E's `tokens_attributed=<true|false>` token is the per-turn audit signal — `tokens_attributed=false` on a reconcile turn is a contract violation. See [issue #197](https://github.com/mattsears18/shipyard/issues/197) for the regression that prompted promoting attribution to a numbered first step. **The one sanctioned carve-out ([#855](https://github.com/mattsears18/shipyard/issues/855)):** `bump-tokens` itself still always runs (per-session `.tokens` accounting stays live regardless of the config below), but the two *persistence/publication* sinks it feeds are each independently gated on the effective config — `cost-history.sh flush` self-skips its ledger write when `cost_tracking.enabled: false` (enforced in the script, not just this prose), and the PR-comment post skips when `cost_tracking.comment_on_pr: false` (checked inline in the [shipped-return comment block](./steady-state.md#a1-parse-the-return-string) before the `gh pr comment` call). Neither config value is a license to skip the `bump-tokens` call itself or to leave `tokens_attributed=false` — the opt-out controls what leaves the session's own ephemeral state, not whether the orchestrator tracks its own turn.

- **Don't read `milestones.*` anywhere outside a `milestones.enabled == true` guard ([#1239](https://github.com/mattsears18/shipyard/issues/1239)).** The `milestones` config block ships in #1239 as inert-when-absent-or-disabled scaffolding for #1240–#1244 (dispatch-order `prioritize_dispatch`, filing-time `assign_on_file`, the `sweep_on_loop_end` loop-end sweep). Every future consumer of any of those keys MUST check `milestones.enabled` first and skip entirely when it's false — no GitHub Milestones API call, no read of any other `milestones.*` key, no change to dispatch order or filing behavior. A repo that never opted in must be byte-for-byte identical to a repo running a shipyard version with no `milestones` block at all, not merely "the feature never triggers" while still probing.
- **Don't touch a milestone from inside a dispatched worker's turn — not even one that looks obviously missing or wrong ([#1240](https://github.com/mattsears18/shipyard/issues/1240)).** `shipyard:update-roadmap` (assigns milestones, authors phases, checks bets, detects dependencies) is orchestrator-only — a worker runs in an isolated worktree scoped to a single issue and has no view of the whole backlog, so any milestone decision it made would race a sibling worker doing the same. A worker must never create, rename, renumber, or reassign a milestone, edit a milestone description, or invoke the `shipyard:update-roadmap` skill itself. The one exception: a worker filing a follow-up issue may stamp it with the **parent issue's own existing milestone** — that's inherited filing metadata, not a new milestone decision. This is the worker-side half of the boundary; see `shipyard:worker-preamble`'s [`milestone-prohibition.md`](../../skills/worker-preamble/milestone-prohibition.md) fragment for the rule as the worker itself reads it, and [`shipyard:update-roadmap`](../../skills/update-roadmap/SKILL.md) for the orchestrator-run skill this protects.
- **Don't add a starvation valve to milestone-aware ranking, and don't import a WIP limit ([#1241](https://github.com/mattsears18/shipyard/issues/1241)).** A phase whose priority-ordered work sits unstarted while a later phase's issues would otherwise look "more overdue" is sequencing working as designed, not a defect — do NOT add a rule like "every Nth dispatch takes the oldest issue regardless of phase" to compensate; it quietly undoes the whole point of opting into `milestones.prioritize_dispatch`. Similarly, do NOT flag or demote a phase for holding many `P1`s — under parallel dispatch a phase full of `P1`s dispatches concurrently across worktrees with no WIP-limit-style cost, so a large `P1` count is a sizing signal about the phase, never grounds to reorder it. Both prohibitions mirror `shipyard:update-roadmap`'s own [anti-WIP-limit rule](../../skills/update-roadmap/SKILL.md#the-anti-wip-limit-rule) — the dispatch-ranking side of the same design stance.
- **Don't rank by issue number as a tiebreaker tier, and don't let `--prioritize-label` outrank a global `P0` ([#1241](https://github.com/mattsears18/shipyard/issues/1241)).** `backlog-filter.sh classify`'s milestone-aware `_sort_key` deliberately does NOT add an issue-number tier — shipyard already has `type` (bug > fix(*) > feat(*) > chore(*) > other) as an innermost tiebreaker that lightwork's own ported ordering lacked, and importing a number-based tiebreaker on top would silently replace staleness ordering for every milestone-enabled repo while claiming to only add milestone awareness. Separately: `P0` sits ABOVE `--prioritize-label` in the milestone-on ordering (an explicit, reviewed change from the milestone-off order, where the prioritized-label tier is outermost and CAN rank above a `P0`) — do not "fix" this by moving `--prioritize-label` back above `P0`, and do not apply the swap unconditionally to a repo that has not opted into `milestones.prioritize_dispatch` (that would break the documented `milestones.enabled:false OR prioritize_dispatch:false` byte-identical guarantee). See [`do-work-RATIONALE.md → Milestone-aware backlog ranking`](../do-work-RATIONALE.md#milestone-aware-backlog-ranking--backlog-filtersh-classifys-_sort_key-and-why-the-tiers-sit-where-they-do-issue-1241) for the full tier-by-tier reasoning.
- **Don't let a filing path (`shipyard:filing-github-issues`, `/shipyard:file-issue`, `/decompose-epic`) create a milestone, even the fallback ([#1242](https://github.com/mattsears18/shipyard/issues/1242)).** `milestones.assign_on_file` only ever authorizes *picking among already-existing* milestones (matching a finding against each one's `BET:`, or falling back to `milestones.fallback` when it already exists) or, for `/decompose-epic`'s sub-issues, *inheriting* the parent epic's own milestone — never authoring a new phase or the fallback milestone itself. A filing agent sees one issue at a time and would be authoring phases from a keyhole; that authority stays exclusively with `shipyard:update-roadmap`'s whole-backlog view. When nothing in the cached milestone list fits, file without one — never fail the filing over it, and never invent a milestone to fill the gap.
- **Don't let the end-of-loop roadmap sweep ([#1243](https://github.com/mattsears18/shipyard/issues/1243)) fail the session or block the summary, and don't run it when this session shipped and filed nothing.** [`cleanup-summary.md`'s step 8.5](./cleanup-summary.md#end-of-session-cleanup) wraps `shipyard:update-roadmap`'s Procedure steps 1–6 in a non-fatal try — a `gh` API error, a schema-validation miss, or a malformed milestone title folds into a one-line `Roadmap sweep (#1243): failed — ...` summary advisory, never an exit-status change and never a blocked summary. It also self-skips entirely (no reads, no summary line) when `shipped_count + filed_count == 0` — a drain-only or no-op loop leaves nothing new for a loop-end sweep to catch up on. This is hygiene, not correctness — treat it accordingly.

**Dispatch hygiene:**

- Don't work on issues assigned to other users when `backlog.respect_assignees == true` — checked via `gh api user`. This clause is config-gated (default `false`, issue [#1248](https://github.com/mattsears18/shipyard/issues/1248)): on the default config, assignees don't affect eligibility at all and this rule doesn't apply.
- Don't merge manually. Use `--auto`. Auto-merge waits for green.
- Don't disable required checks or weaken branch protection to make a PR pass.
- Don't re-dispatch the same issue. Once the agent returns `blocked`, label it and never queue it again.
- Don't fabricate acceptance criteria. The agent should infer reasonable ones from title + context; if even that's unclear, it returns `blocked`.
- **Don't instruct a running worker below the floor — trimming scope is fine, ordering a spec violation is not ([#1230](https://github.com/mattsears18/shipyard/issues/1230)).** A mid-flight `SendMessage` to a worker that appears slow or over-scoped may legitimately narrow *scope* — fewer suites, less investigation depth, a smaller acceptance-criteria slice — that's sanctioned and demonstrably useful: two workers redirected this way in one session finished in 4.7 and 2.5 minutes after their scope was cut. It may NOT instruct the worker to violate a **named** `shipyard:worker-preamble` prohibition (e.g. `git add -A`, `--no-verify`), ship an artifact the worker itself already knows is broken or failing, or skip a documented safety check — regardless of elapsed time or how many prior messages already asked the worker to hurry. The concrete near-miss: three escalating interrupts in one session asserted an unverified commit as fact, told a worker to ship known-failing regression tests for a data-loss-adjacent bug "marked as expected-fail," and instructed a bare `git add -A` (the exact anti-pattern `commit-hygiene.md` documents). The worker refused all three and shipped clean — but nothing structural stopped a less careful worker from complying. When impatience is real, send the [sanctioned wrap-up interrupt](./steady-state.md#sanctioned-wrap-up-interrupt--for-a-still-running-worker-the-orchestrator-judges-is-over-scoped-or-running-long-not-gated-by-the-resume-worthy-check-above-1230) instead of improvising escalating pressure.
- **Don't write a worker's own documented short-circuit out of its dispatch prompt — the floor above binds the INITIAL prompt too, not just mid-flight messages ([#1513](https://github.com/mattsears18/shipyard/issues/1513)).** There is one floor, and it reaches the orchestrator over three channels; until #1513 only two of them said so. The bullet above covers a `SendMessage` to an already-**running** worker ([#1230](https://github.com/mattsears18/shipyard/issues/1230)); the classifier bullet below covers a **follow-up after** a worker returned `blocked: classifier denied <op>` ([#1278](https://github.com/mattsears18/shipyard/issues/1278)). Neither reaches the **first** channel — the dispatch prompt that starts the worker — which is also the channel with the weakest natural guard, because the worker has no prior correct stop for the instruction to override; it simply never reaches the stop. So: when a mode's spec says *"stop here, return `<X>`, this belongs to another mode"*, the orchestrator may NOT pre-empt that by writing the short-circuited work into the prompt as an extra task. *"Fix the checks, **and also** rebase it first"* against a DIRTY PR is exactly that move — `fix-checks-only`'s [DIRTY short-circuit](../../agents/issue-worker/fix-checks-only.md#dirty-pr-short-circuit-check-before-treating-an-empty-rollup-as-not-started-yet--1015) returns `dirty #<M>` precisely because the work belongs elsewhere. The correct response is always to route to the mode that owns the work (for DIRTY: the in-process resolver, then `fix-rebase` — see the two bullets below), never to hand the owning mode's job to a mode whose spec explicitly disclaims it. Narrowing a dispatch stays sanctioned exactly as the bullet above describes; this forbids only *widening* one past its mode's documented stop. **The asymmetry is why this needs naming rather than judgment: when a worker refuses, the orchestrator gets a `blocked:` return it is forced to reconcile; when a worker complies, the only trace is whatever prose the worker volunteers.** Silent compliance is the more dangerous direction and is invisible exactly when it succeeds — #1513's repro produced a correct, green, merged PR (session `do-work-20260821T204914Z-74826`, PR #1508) and surfaced only because the worker appended an unprompted note that its spec said otherwise. ([why](../do-work-RATIONALE.md#dont-write-a-workers-own-short-circuit-out-of-its-dispatch-prompt-issue-1513))
- **Don't assert in a dispatch prompt that a deliverable is outstanding without checking that it is ([#1187](https://github.com/mattsears18/shipyard/issues/1187)).** Same category as [`dispatch-rules.md`'s comment-thread-awareness rules (#781/#1062)](./dispatch-rules.md#dispatch-rules-used-by-step-7-and-step-c) — those require grounding a dispatch prompt's assertions about issue/PR *state* in live evidence before passing them through; this extends the same discipline to assertions about artifact *existence*. A scope agent's `phase_1_scope` naming a concrete file to create must be checked against `origin/<default-branch>` first (`git ls-tree origin/<default-branch> -- <path>`) — otherwise the worker is dispatched to build something that already merged. See [`06b-scope-carveouts.md`'s Phase-1 artifact-existence check](./setup/06b-scope-carveouts.md#phase-1-artifact-existence-check--dont-dispatch-a-slice-for-a-path-thats-already-there-1187).
- Don't dispatch two workers whose `claimed_paths.hard` overlap. The soft-collision tier relaxes this for additive docs paths up to `--soft-collision-concurrency` claimers — that's a different rule.
- **Don't widen a peer's `claimed_paths` to a directory when you describe it to another worker ([#1490](https://github.com/mattsears18/shipyard/issues/1490)).** An `Off-limits: <path>` line in a dispatch prompt must reproduce the peer's recorded entries verbatim — file paths when the peer claimed files, a directory only when the peer claimed the whole directory. Rolling files up to their parent dir is easier to phrase, strictly broader than the truth, and reads as authoritative to the receiving worker, which then silently drops work that never collided (the repro: a peer's two file/subdir claims communicated as `apps/lightwork/__tests__/`, ~400 uncontended sibling files, and a planned test dropped for a collision that did not exist). Unlike the [#781/#1062 state-assertion rules](./dispatch-rules.md#dispatch-rules-used-by-step-7-and-step-c), the worker has nothing to re-verify this against — it removes scope rather than handing over a checkable false premise. See [the granularity rule at the `claimed_paths` definition](./dispatch-rules.md#dispatch-rules-used-by-step-7-and-step-c).
- **Don't expect agents to resolve cross-worker merge conflicts on soft-collision paths — the orchestrator owns that.** Dispatch a drain-style fix-rebase worker on the second PR. ([why](../do-work-RATIONALE.md#dont-expect-agents-to-resolve-cross-worker-merge-conflicts-on-soft-collision-paths))
- **Don't treat a `blocked rebase #<M>: conflict extends beyond coordinated manifest+CHANGELOG rows` return on a soft-collision PR as a worker failure — it's expected ([#507](https://github.com/mattsears18/shipyard/issues/507)).** When two+ soft-collision claimers edit the **same section** of the same docs file, the conflict is real prose content, not the coordinated manifest `.version`/CHANGELOG rows that [fix-rebase's §4.6](../../agents/issue-worker/fix-rebase.md#46-version-coordinated-manifest--changelog-re-number--trivial-resolution-issue-466) auto-resolves — so fix-rebase correctly bails. The documented drain branch (steady-state's [blocked-rebase reconcile](./steady-state.md#a-reconcile-the-return)) adds the PR to `rebase_blocked_prs`, comments `Needs manual rebase.`, and surfaces it still-DIRTY for a human to hand-resolve. Don't re-dispatch fix-rebase (same conflict re-bails) and don't make the soft cap section-aware to "fix" it — that's the deliberately-rejected option 2; the residual cost is accepted at `--concurrency ≥ 2`.
- Don't dispatch a candidate whose `lockfile_sections` overlaps an in-flight worker's `lockfile_sections`. Generated lockfiles are not claimed as sections.
- **Don't dispatch a worker that isn't isolated to its own worktree.** For the seven `mode:`-driven workers, under the default `Agent`-tool shape (and for `shipyard:verify-worker`) that means `isolation: "worktree"` on the `Agent` call. Under the `Workflow`-substrate alternate it means `run_in_background: true` **and** a `worktreePath` you pre-provisioned with `git worktree add` on every work unit ([#791](https://github.com/mattsears18/shipyard/issues/791) / [#825](https://github.com/mattsears18/shipyard/issues/825)). Neither hook defending either shape's contract accepts a workaround. ([why](../do-work-RATIONALE.md#dont-dispatch-a-worker-that-isnt-isolated-to-its-own-worktree-issues-791-825))
- Don't skip the initial scope pre-flight to "save time" — one rebase from a missed collision costs more than the whole pre-flight.
- Don't skip the periodic failed-PR refresh.
- **Don't iterate prompt wording against the permission classifier when a dispatch is denied ([#718](https://github.com/mattsears18/shipyard/issues/718)).** Exactly **one** re-dispatch is permitted, and only to **correct** a prompt that *overstated* the work's blast radius — the reframe must make the prompt **more accurate**, never merely more permissive-sounding. If the work genuinely requires the denied capability, the prompt was right and the classifier was right: hand back without spending the reframe. On a **second** denial, stop and hand back to the human — never a third attempt, never a workaround through a different dispatch tool or agent identity / a split dispatch / inline execution on the orchestrator thread (classifier policy targets *effects*, not tool names). Full branch: [dispatch-rules.md § "Dispatch denied by the harness permission classifier"](./dispatch-rules.md#dispatch-denied-by-the-harness-permission-classifier-718). ([why](../do-work-RATIONALE.md#dont-iterate-prompt-wording-against-the-permission-classifier-issue-718))
- **Don't instruct a worker to route around its own worker-internal classifier denial ([#1278](https://github.com/mattsears18/shipyard/issues/1278)).** The bullet above governs the orchestrator's own **dispatch call** being denied; this is the sibling case — one of a live worker's own tool calls (an `Edit`, a `git checkout -B`, a force-push) was denied mid-dispatch, and the worker correctly stopped and returned `blocked: classifier denied <op>` per `shipyard:worker-preamble` § "After a classifier denial" ([#341](https://github.com/mattsears18/shipyard/issues/341)). **That return is a genuine terminal `blocked`** — it is covered by the "Don't re-dispatch the same issue... once the agent returns `blocked`, label it and never queue it again" rule above, and resuming the same live agent via `SendMessage` (or any other follow-up into its existing worktree/branch) is the same act as a re-dispatch for this purpose. Do NOT compose a follow-up instruction proposing a different operation that reaches the same effect as the one just denied — each substitution looks locally reasonable in the moment, which is exactly why it has to be named explicitly: a refspec push (`git push origin HEAD:refs/heads/<branch>`) in place of a denied local branch-create (`git checkout -B` / `git switch -c`); a merge commit in place of a denied force-push; `git update-ref`, `git branch`, or `git format-patch` standing in for either. Classifier policy targets *effects*, not tool names — the #718 bullet above already establishes this for the orchestrator's own dispatch call; this closes the gap where the orchestrator applied that principle to itself but not to its instructions to a worker. Record the denial, surface it the same way an ordinary `blocked:` return is surfaced, and hand the issue to the human (`needs-human-review`) — never a second live instruction proposing an alternative route. **This does not forbid the legitimate, unrelated case of decomposing a refused *compound* command into plain single-purpose commands achieving the identical effect** (the harness's "too complex to verify" syntax refusal, distinct from a classifier *effect* denial — see `shipyard:worker-preamble` § "Worktree discipline" and the [Claude Code's command-shape check](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation) fragment) — that decomposition is the sanctioned response to a different failure shape entirely and remains unaffected by this rule. **This bullet is the post-denial instance of one floor, not a rule of its own** — the classifier-denial framing throughout is the *mechanism that produced the stop*, never a limit on which stops are protected. The same floor over the other two channels is the "running worker" bullet above ([#1230](https://github.com/mattsears18/shipyard/issues/1230), mid-flight `SendMessage`) and the "documented short-circuit" bullet above ([#1513](https://github.com/mattsears18/shipyard/issues/1513), the initial dispatch prompt); read no distinction between the three beyond *when* the instruction is sent, because there isn't one. ([why](../do-work-RATIONALE.md#dont-instruct-a-worker-to-route-around-its-own-classifier-denial-issue-1278))
- **A worker-internal classifier denial does not get a separate auto-merge-suppression mechanism — a deliberate call, not an oversight ([#1278](https://github.com/mattsears18/shipyard/issues/1278)).** Considered and rejected: gating auto-merge arming on "did this dispatch's history include an earlier worker-internal classifier denial." The two rules above (this bullet's orchestrator-side prohibition, plus the worker-side reinforcement in `shipyard:worker-preamble`'s classifier-denial fragment) are structured so a workaround-derived PR should never reach `gh pr create` at all — a mechanical suppression check downstream of that would only ever fire if both already-redundant rules failed simultaneously, a different risk shape from the ungated-admin-direct-merge detector (a *repo-configuration* condition neither party controls, which is why that one earned a script). See [RATIONALE](../do-work-RATIONALE.md#dont-instruct-a-worker-to-route-around-its-own-classifier-denial-issue-1278) for the full reasoning.
- **Don't let a denied dispatch silently cost a slot ([#718](https://github.com/mattsears18/shipyard/issues/718)).** A refused dispatch call produces no worker and **no completion notification** — so without an explicit record the target just quietly stops being worked. Record every denial in `dispatch_denials`, fill the slot with the next candidate in the same turn (a denial consumes a *candidate*, not the *slot*), and surface a `Dispatch denied:` line in the [end-of-session summary](./cleanup-summary.md#end-of-session-summary). Don't write an `.in_flight` slot for a denied dispatch, and don't run step A's reconcile against one — there is nothing to reconcile. **Under the `Workflow`-substrate alternate, do** reap the worktree you pre-provisioned for it ([#791](https://github.com/mattsears18/shipyard/issues/791)) — the orchestrator creates the worktree *before* the call under that shape, so a denial strands a real directory and branch that no other reap path will find. (Under the default `Agent`-tool shape there is nothing to reap — the harness only creates the worktree once the dispatch is allowed.)
- **Don't post the classifier's reasoning to a public GitHub artifact ([#718](https://github.com/mattsears18/shipyard/issues/718)).** On the two-denials hand-back, the issue comment states the **fact and the outcome only** — it must not quote, paraphrase, explain, theorize about, or dispute *why* the harness denied the dispatch, and the orchestrator must not file a follow-up issue arguing the denial was wrong (that's a maintainer decision, made after they see the `Dispatch denied:` line). The verbatim denial text belongs on the **local** surfaces — the session summary and the on-disk HTML report. Same content-integrity boundary the worker operates under (`shipyard:worker-preamble` § "After a classifier denial", [#341](https://github.com/mattsears18/shipyard/issues/341)): a public artifact carrying a reconstructed explanation of a harness decision is a side-channel a future worker, reviewer, or scraper could read as authoritative.

**Failure-handling discipline:**

- Don't retry a `blocked:ci` PR. The label exists so the orchestrator stops banging on the same wall. **Exception:** [step 3d's auto-clear sweep](./setup/01c-label-recovery-refine.md#3-ensure-label-exists--recover-from-prior-session) removes the label at session start from any PR whose head commit is newer than the label's application timestamp (someone pushed since shipyard gave up — fresh chance, 3-attempt counter resets). The sweep is the only mechanism that removes `blocked:ci`; step A is the only mechanism that applies it.
- **Don't accept a `green #<M>` return from a fix-checks-only worker without verifying the rollup.** ([why](../do-work-RATIONALE.md#dont-accept-a-green-return-without-verifying-the-rollup)) A `pending #<M>: ...` return is the worker's own honest, non-overclaiming disposition ([#985](https://github.com/mattsears18/shipyard/issues/985) / [#987](https://github.com/mattsears18/shipyard/issues/987)) — treat it as a normal, expected outcome (append to `session_prs`, no `blocked:ci`, no fix-attempt charge), not as something to second-guess the way `green` is. A `dirty #<M>: ...` return is likewise honest, not a verification-needed claim ([#1015](https://github.com/mattsears18/shipyard/issues/1015)) — route it to the drain's `fix-rebase` path (append to `session_prs`, no `blocked:ci`, no fix-attempt charge). The `green` spot-check itself checks `mergeStateStatus` before its empty-rollup rule, so a worker that wrongly claims `green` on a DIRTY PR gets downgraded to `dirty`, not silently accepted.
- **Don't let a fabricated citation ride an untrusted disposition, `green` or otherwise ([#1205](https://github.com/mattsears18/shipyard/issues/1205), extended by [#1335](https://github.com/mattsears18/shipyard/issues/1335)).** The `green`-only spot-check above is a deliberate cost tradeoff — `pending`/`dirty` are trusted at face value because they claim *less* than `green`, not because a dishonest worker can't produce one. Three occurrences across two sessions showed a worker can fabricate a rollup citation that reads as pre-verified — including one citing a verification timestamp minutes AFTER the orchestrator's own reconcile, one whose own hedging prose ("may be running", "should resolve once the run completes") directly contradicted its definitive `green` line, and one that wrote a fabricated `green` line, narrated its own mistake, and then wrote the correct `dirty` line — three terminal-shaped lines in one return, only the last of which was honest. Before parsing ANY fix-checks-only return into its disposition branch, run [steady-state.md's fabrication pre-check](./steady-state.md#a-reconcile-the-return) — a future-OR-past-dated timestamp citation, hedging language beside a definitive `green`/`noop` claim, or more than one line matching a documented terminal prefix anywhere in the return — all three are API-free string scans. If any trips, force the live `gh pr view` spot-check regardless of which disposition (`green`, `noop`, `pending`, `dirty`) was claimed, and classify off ground truth instead of the worker's word. Never resolve a multi-terminal-line return by picking the first match or the last match — that ambiguity is itself the trigger for live verification, not something to guess past.
- **Don't accept a `green`/`noop` citation whose head SHA doesn't match the PR's live head, and don't reject a SHA-less return outright either ([#1211](https://github.com/mattsears18/shipyard/issues/1211)).** As of #1211 a `green #<M> @<head-SHA> (...)` / `noop: already green #<M> @<head-SHA> (...)` return carries the full `headRefOid` the worker observed the rollup at, checkable by a plain string comparison against a fresh `gh pr view <M> --json headRefOid` — folded into the SAME call the trust-but-verify spot-check already makes, so it costs nothing extra. A mismatch is a fabrication/staleness tell exactly like the #1205 checks above and gets the identical treatment: classify strictly off the live rollup, never off the worker's claim. A return in the OLDER, SHA-less shape (a pre-#1211 worker prompt, or a malformed return) is NOT a hard parse failure — the unconditional live spot-check already covers `green`/`noop` regardless of citation, so a missing SHA never gets LESS scrutiny than a present-and-matching one. Fail toward more verification, never less. ([why](../do-work-RATIONALE.md#dont-accept-a-green-return-without-verifying-the-rollup))
- **Don't treat a fix-checks-only worker's narrative status string as authoritative.** ([why](../do-work-RATIONALE.md#dont-treat-a-narrative-status-string-as-authoritative))
- **Don't dispatch fix-rebase mid-session without trying the in-process resolver first, and even then only when all three conditions hold ([#1034](https://github.com/mattsears18/shipyard/issues/1034), [#1461](https://github.com/mattsears18/shipyard/issues/1461)).** On a DIRTY session PR, FIRST run [`scripts/resolve-manifest-only-dirty.sh`](../../scripts/resolve-manifest-only-dirty.sh) per [steady-state.md's `merge == "DIRTY"` bullet](./d-tail-merge-sweeps.md) / [drain.md's Drain protocol](./drain.md#drain-protocol) (issue [#1377](https://github.com/mattsears18/shipyard/issues/1377)) — `resolve_status == 0` is a `rebased #<M>` reconcile, no worker dispatched. **Only when the resolver defers**, steady-state dispatch is NOT immune to DIRTY PRs — on any repo whose release convention bumps a shared manifest/CHANGELOG row on every merge (this repo's own "ALWAYS cut a release when a PR merges" rule), a sibling merge DIRTYs every other open PR's version row, and at `--concurrency 1` that's a certainty, not a race. Leaving it DIRTY for the drain means no merge ref and no CI queues at all until then — a busy session can strand it for hours (#1034's repro: ~4h, ~24 intervening merges, a whole `fix-checks-only` dispatch burned diagnosing the resulting silence as a CI infrastructure issue). Permit a mid-session `fix-rebase` dispatch when **all** of: the PR is in `session_prs` with `mergeStateStatus == DIRTY`; no in-flight worker already holds that PR's head branch; and a `--concurrency` slot is free to take it. Dispatching under those conditions is safe to attempt speculatively rather than pre-verify, because [`fix-rebase.md`'s §4.6](../../agents/issue-worker/fix-rebase.md#46-version-coordinated-manifest--changelog-re-number--trivial-resolution-issue-466) already resolves a conflict confined to the coordinated manifest `.version` + CHANGELOG rows deterministically, and bails `blocked rebase` — same as it would at drain time — on anything wider. Keep the drain-only restriction for the genuinely ambiguous case: no free slot, or the PR isn't in `session_prs` yet. ([why](../do-work-RATIONALE.md#dont-dispatch-fix-rebase-mid-session-outside-the-three-conditions-issue-1034))
- **Don't reap a worker's worktree on a non-terminal or `failed` stop without first inspecting it for unpushed work ([#838](https://github.com/mattsears18/shipyard/issues/838) / [#833](https://github.com/mattsears18/shipyard/issues/833)).** A return that doesn't start with one of the documented terminal prefixes (`shipped`, `green`, `pending`, `dirty`, `rebased`, `noop`, `blocked`, `reaped`, `awaiting-external`), or a harness notification carrying `status: failed` (the stall watchdog — "no progress for 600s"), is NOT a signal that there's nothing to save. Before [step B's](./steady-state.md#b-release-the-slot) slot release / worktree reap runs, [step A.0.5](./steady-state.md#a05-post-return-worktree-reap-for-crashed--narrative-non-terminal-returns-fires-before-a1s-return-string-parsing) MUST inspect the worktree first — `git log --oneline origin/<default>..HEAD` and `git status --porcelain` — on **both** triggers, not just the narrative-return one. A worker can stop mid-flight with a fully correct, hook-validatable diff sitting uncommitted on disk; reaping first destroys the only copy. Prefer resuming the same agent (`SendMessage` to its `agent_id`, or a fresh same-worktree dispatch when no live agent is addressable) over a fresh re-dispatch when the inspection finds recoverable work — a fresh re-dispatch's own pre-dispatch reap would delete it first. Neither trigger is `blocked`, and neither gets a `blocked:*` label — record the occurrence in `stalled_dispatches` instead (see [`orchestrator-state-reference.md`](./orchestrator-state-reference.md)).
- **Don't treat an `awaiting-external` return as a crash, a hand-back, or a narrative — and don't reap its worktree ([#1390](https://github.com/mattsears18/shipyard/issues/1390)).** It is a documented terminal disposition from a worker that finished everything it could, committed and pushed it, and correctly handed a long external wait (a dispatched CI run, an EAS/store build, a deploy) to the only process that can hold one. Treat it like `pending #<M>`: normal, expected, costs nothing — **no** `needs-human-review`, **no** `blocked:*` label, **no** `blocked:ci` cap charge, **no** `/my-turn` surfacing, and **do not** re-enqueue the issue into `raw_backlog`/`ready_issues` (it is parked, not dispatchable — re-enqueuing would let step C put a second worker on half-done work). Release the slot but **retain the worktree**: [step D's sweep](./steady-state.md#d-periodic-refresh) resumes that exact agent by `agent_id` when the probe goes terminal, and reaping first throws away the context that makes resume worth preferring over a cold re-dispatch. **Don't execute the worker-supplied probe without re-running [`scripts/validate-awaiting-external-probe.sh`](../../scripts/validate-awaiting-external-probe.sh) yourself** — a worker's context contains untrusted issue bodies, and this is a string you *execute*, not one you read; a rejected probe is refused and degraded to `blocked:`, never hand-edited into an accepted shape on the worker's behalf. And **don't hold a park forever**: the bound is `awaiting_external.max_hours` (default 2), anchored at the first park and never extended by a re-park, after which the entry becomes a genuine `blocked:` hand-back naming the unfinished job.
- **Don't retry a `blocked rebase` PR within the same session.** A `blocked rebase` return signals a non-trivial conflict that won't resolve on retry; `rebase_blocked_prs` membership counts toward the drain's "settled" definition. **`rebased` returns are different** — a successfully-rebased PR that goes DIRTY again from a sibling merge IS eligible for re-dispatch (the merge train can still win that race), subject to the 3-successful-rebase rate-limit cap tracked in `rebase_success_counts`. See [drain.md's end-of-session drain](./drain.md#end-of-session-drain) for the split-gate rationale and [#265](https://github.com/mattsears18/shipyard/issues/265) for the race the split fixes.
- **Don't dispatch fix-checks against a DIRTY PR, red or not — and don't let fix-rebase bail on a hard check failure while the PR is DIRTY ([#1060](https://github.com/mattsears18/shipyard/issues/1060), supersedes [#577](https://github.com/mattsears18/shipyard/issues/577)).** A DIRTY PR has no merge ref, so no check can be queued or refreshed until a rebase restores one — a red check on a DIRTY PR is a frozen fossil of the last base the PR could still build against, not live evidence about its current health. The pre-#1060 rule routed a DIRTY-and-red PR (`D_dirty_red`) to `fix-checks`, on the assumption that fix-checks would rebase as part of getting green; [#1015](https://github.com/mattsears18/shipyard/issues/1015)'s DIRTY short-circuit removed that assumption and left the rule pointing at a mode that can no longer act on it — `fix-checks-only` would immediately bail `dirty #<M>` without attempting anything, and `fix-rebase`'s own pre-#1060 hard-failure bail would immediately bail `blocked rebase: PR has failing checks`, so the two modes would bounce the PR back and forth forever (the #1060 repro — session `do-work-20260803T010743Z-98363`, `mattsears18/lightwork` PR #3445). Both bails are gone: `fix-rebase.md` step 2's hard-failure bail is now gated on `mergeStateStatus != "DIRTY"`, and `drain.md`'s `D_dirty_red` set is an informational subset of `D_dirty` (still routed to `fix-rebase`), never a route to `fix-checks`. See [RATIONALE → #1060 supersedes #577](../do-work-RATIONALE.md#1060-supersedes-577--dirty-and-red-routes-to-fix-rebase-not-fix-checks) for the full history.
- **Don't treat a session PR's `mergeStateStatus == "BLOCKED"` as one undifferentiated state, and don't infer "still settling" from open-vs-closed alone ([#1435](https://github.com/mattsears18/shipyard/issues/1435)).** `BLOCKED` reads identically whether a PR is healthily waiting on checks still in flight or is permanently stuck behind a red (or never-triggered) required check — nothing about the field itself distinguishes the two, and a watcher that only tracks open-vs-closed PR count cannot tell a stuck PR from a progressing one either: both are simply "still open," so silence is not evidence of progress. The discriminator is `BLOCKED` ∧ **zero pending checks** — a healthy PR's `BLOCKED` clears the instant its last pending check resolves, so `BLOCKED` with nothing left pending is definitionally not queue latency. [Step 5's failed-PR scan](./setup/04j-failing-pr-snapshot.md#5-snapshot-failing-prs) and the [D-tail dependency-update sweep](./d-tail-merge-sweeps.md) both apply this discriminator and route the result to `failed_prs` → `fix-checks-only`; don't hand-roll a third check elsewhere in the spec that reasons about `BLOCKED` differently. Session repro: `mattsears18/lightwork` session `do-work-20260816T171356Z-9805`, PR #4159 sat `OPEN` / `BLOCKED` / auto-merge-armed with a red required check for ~8 hours before a human happened to notice.

**Worktree + filesystem discipline:**

- **Don't write to the user's primary checkout under any circumstance.** After step 0.5, the orchestrator works exclusively in `.claude/worktrees/orchestrator-<session-id>`. ([why](../do-work-RATIONALE.md#dont-write-to-the-users-primary-checkout)) **One sanctioned exception** ([#387](https://github.com/mattsears18/shipyard/issues/387)): the [primary-checkout branch-leak guard](./steady-state.md#a06-primary-checkout-branch-leak-guard-fires-every-reconcile-turn-before-a1) may run `git -C <primary> checkout <default> && git -C <primary> pull --ff-only` — but **only** when the harness has already leaked a `do-work/*` checkout onto the primary AND the primary tree is clean (the restore is provably lossless). When the primary tree is dirty, the guard NEVER writes — it warns and defers to the human. Do not generalize this into "shipyard may move the primary's HEAD"; it fires only on the leak-detected-and-clean path. ([why](../do-work-RATIONALE.md#the-primary-checkout-branch-leak-guard-exception-issue-387)) **A second sanctioned exception, same clean-tree-only posture** ([#1386](https://github.com/mattsears18/shipyard/issues/1386)): [setup step 0.41's staleness gate](./setup/00-config-worktree.md#041-staleness-gate--self-heal-the-primary-checkout-or-refuse-to-run-1386), via [`heal-stale-primary-checkout.sh`](../../scripts/heal-stale-primary-checkout.sh), may **fast-forward** the primary — but only in the dogfooding case (`CLAUDE_PLUGIN_ROOT` resolved repo-local), only when the primary is behind `origin/<default>` AND on the default branch AND its tree is clean, and only as `merge --ff-only` (never a stash, clean, reset, or branch switch). A fast-forward is strictly weaker than the branch-leak guard's checkout: it discards nothing by construction. Every other case — dirty tree, feature branch, non-fast-forward — **refuses and stops the session** rather than writing.
- **Don't refresh, reset, or re-read the orchestrator worktree mid-session to pick up newer spec — measure the drift and report it ([#1486](https://github.com/mattsears18/shipyard/issues/1486)).** The worktree is created once at [step 0.5](./setup/00-config-worktree.md#05-move-into-the-orchestrators-worktree) and the spec copy it holds is deliberately frozen for the run: a loop whose instructions mutate mid-flight is a worse hazard than one running a known-consistent older copy, and [#1202](https://github.com/mattsears18/shipyard/issues/1202)'s pre-relocation ordering assumes a stable tree. On a dogfooding session that ships changes to `/do-work`'s own spec, that copy can drift far behind `origin/<default-branch>` (nine commits in #1486's repro, seven of those releases shipped by the same session) — the correct response is the **signal**, never a refresh: [step D's sub-step 5](./steady-state.md#d-periodic-refresh) measures it, [step E's `spec_drift=` token](./invariant-line.md) renders it every turn, and [cleanup step 8.7](./cleanup-summary.md#end-of-session-cleanup) reports it once at the end. No `git reset --hard`, no re-entering the worktree, no mid-session spec re-read triggered by drift. A refresh is an explicit operator action or a fresh session — never a background behavior. **Corollary:** never fold `spec_drift` into step D's [delta computation](./steady-state.md#refresh-trigger-rules) or make it a refresh trigger — it increments on nearly every merge, so either would defeat the adaptive backoff outright.
- Don't run end-of-session cleanup from the user's primary checkout — run it from the orchestrator worktree. The exception is cleanup step 6, which removes the orchestrator worktree itself (metadata-only operation, primary HEAD never moves).
- Don't cleanup branches by name or pattern — only by `[gone]` upstream.
- Don't claim a worktree whose branch doesn't match `do-work/*` during orphan triage. That branch is not yours.
- Don't run orphan triage while another `/do-work` session may be active on the same repo. If you suspect a parallel session, ask the user. **This rule is scoped to destructive worktree-reap decisions specifically** — a wrong autonomous guess there destroys real, irreplaceable work. It does NOT extend to [step 1.65's peer-claimed backlog exclusion](./setup/01-repo-recovery.md#165-detect-live-peer-sessions-on-this-repo-1204) ([#1204](https://github.com/mattsears18/shipyard/issues/1204)): that check is advisory and reversible (worst case, an over-conservative exclusion is picked up next session), so it runs and drops peer-claimed candidates from `raw_backlog` autonomously, without asking — halting the whole session to ask "should I proceed?" over a reversible filter is exactly what the "don't ask, keep working" rule above and [#531](https://github.com/mattsears18/shipyard/issues/531)'s attempt-then-escalate rule forbid. See [`04e-peer-session-drop.md`](./setup/04e-peer-session-drop.md) for the full reasoning.
- Don't remove the `shipyard` label on block, abandon, or any other outcome. `shipyard` stays put through the whole cycle; only `blocked:ci` comes and goes via step A (apply) and [step 3d's auto-clear sweep](./setup/01c-label-recovery-refine.md#3-ensure-label-exists--recover-from-prior-session) (remove).
- **Don't omit the `shipyard:worker-preamble` skill reference from any dispatched agent's prompt.** Every dispatch prompt loads the skill instead of inlining the verbatim preamble. Closes [#107](https://github.com/mattsears18/shipyard/issues/107).
- **Don't skip `git worktree unlock` before removing** an agent worktree. Without unlocking, the remove fails with `cannot remove a locked working tree`.
- **Don't reach for `git worktree remove --force` as the first move** ([#712](https://github.com/mattsears18/shipyard/issues/712)). Try the plain `git worktree remove` first — it refuses on a dirty tree, which is exactly the safety property Claude Code's auto-mode permission classifier is protecting when it denies a bare `--force` as `[Irreversible Local Destruction]`. A denied reap silently defeats the entire cleanup subsystem: the reaps are fire-and-forget in a background subshell, so worktrees just accumulate. Escalate to `--force` only behind a preceding, explicit check that establishes the force destroys nothing that exists only in that worktree (the `worktree-reap.sh` helper's evidence gate does this for you — prefer routing removes through `worktree-reap.sh reap`).
- **Don't swallow a failed or denied reap** ([#712](https://github.com/mattsears18/shipyard/issues/712), extended by [#1274](https://github.com/mattsears18/shipyard/issues/1274)). `2>/dev/null || true` makes a permission denial indistinguishable from success. Count what's actually left on disk (`worktree-reap.sh report-unreaped`) and surface `Cleanup: <N> worktree(s) could not be reaped — run /clean_gone` in the end-of-session summary (wired in `cleanup-summary.md`'s step 5.5). Silent-degrade is what let the count reach six unnoticed in the original #712 repro — and, per #1274, let a full session ship 11+ PRs against ~12 stranded worktrees while writing ZERO audit-log entries: the end-of-session probe above only ran once, at session end, and only produced a stdout tally — it never wrote a durable per-worktree record, so there was nothing to inspect mid-session. Every per-dispatch reap call site (A.0.5, A.1's shipped-immediate reap, step B, `dispatch-rules.md` §2d) now runs an immediate, SEPARATE follow-up Bash tool call right after its reap attempt that checks whether the worktree is still present and, if so, writes a `worktree-reap.sh reap --action reaped-failed` audit line on the spot — this has to be a genuinely separate call, because a classifier denial of the reap attempt kills the whole tool call before any recovery code bundled into the SAME call could run. `cleanup-summary.md`'s step 5.5 does the same for whatever `report-unreaped` still finds at session end, as a backstop for anything the per-dispatch verify steps missed. Don't reintroduce the read-only-tally-only shape at either layer — the per-worktree JSONL record, not just the printed count, is what makes the leftover forensically traceable after the fact.
- **Don't reap a live-PID worktree — at startup OR at shutdown.** Every sweep-style reap loop (setup 3b, dispatch-rules §2d, drain's pre-dispatch reap, A.1's shipped-immediate reap) MUST check `.in_flight` membership for the candidate worktree's `agent-<id>` **BEFORE** ever consulting `classify-lock`, and skip reaping outright on a match — in-flight membership is the *authoritative* liveness signal for this session's own dispatches, not a signal `classify-lock`'s lock-PID check can be trusted to reconstruct on its own. `classify-lock`'s lock-PID liveness check is a **fallback** for worktrees this session doesn't currently own (cross-session stragglers) — never the primary gate for a worktree that could belong to a live sibling slot. This distinction is load-bearing, not stylistic: the harness can write a lock file whose PID is already dead (an intermediate spawn-time process, not the long-lived agent) for a worker that was dispatched moments ago and is actively running — `classify-lock` reports `dead` (reap-eligible) for that worktree with no way to tell it apart from a genuinely-abandoned lock (issue [#832](https://github.com/mattsears18/shipyard/issues/832)). A reap loop that trusts `dead` alone, without first excluding `.in_flight` membership, can destroy a live peer's worktree mid-dispatch. The single-target reaps that operate on a slot's *own just-returned* worktree (A.0.5's crash-recovery reap, step B's per-completion release) are the one documented exception — see their inline comments for why an in-flight-membership skip would be wrong there (the slot's own entry is still nominally present in `.in_flight` at that exact point, precisely because that reap *is* the release). Always check the lock PID too, as defense in depth, before unlocking / removing. ([why](../do-work-RATIONALE.md#dont-reap-a-peer-alive-worktree--at-startup-or-at-shutdown))
- **Don't infer liveness — or reap-eligibility — from a worktree's branch name.** ([#836](https://github.com/mattsears18/shipyard/issues/836)) A harness-created `isolation: "worktree"` tree sits on branch `worktree-agent-<agentId>` from the moment it's created until the dispatched worker itself runs `git checkout -B do-work/issue-<N>` (issue-work §3) — a window that can span the worker's entire pre-implementation phase (reading the issue, self-assigning, planning). A filter that treats "not yet on a `do-work/issue-<N>` branch" as a signal of orphan-hood (or, symmetrically, one that treats "on a `worktree-agent-*` branch" as a signal of freshness) has a **race window**: a genuinely in-flight worker dispatched moments ago is indistinguishable, by branch name alone, from a scaffold nobody ever finished setting up. The #836 repro made this concrete: hand-building a removal list filtered on branch name (excluding `do-work/issue-<N>` branches with open PRs, plus this session's known in-flight workers) silently included two *other* live workers' worktrees — still on their harness-assigned `worktree-agent-<agentId>` branch because they hadn't reached §3 yet — and would have destroyed both mid-run had the list been executed. **The only sound liveness signals are `.in_flight` membership (authoritative, checked first per the bullet above) and, as a fallback for cross-session stragglers, `classify-lock`'s PID-liveness check** — never the worktree's current branch name, at any point in its lifecycle.
- **Don't ever run `git stash` from the orchestrator's own worktree — including `push`/`pop`/`apply`/`drop`/`clear` — especially while recovering a dirty worktree ([#1345](https://github.com/mattsears18/shipyard/issues/1345)).** Every `git stash` entry lives under `refs/stash` in the **shared common `.git` dir** every worktree in this repo (the orchestrator's, every dispatched worker's `agent-*` worktree, and the human's primary checkout) points at — it is not scoped to the orchestrator's own isolated worktree the way a commit on its own branch is. A bare `git stash pop` always takes `stash@{0}` regardless of who pushed it, so on any session running `--concurrency > 1` it's a coin flip over which peer's in-progress changes just landed inside the orchestrator's tree; `git stash drop`/`clear` without matching on the message destroys peer entries outright. Both failure directions are silent — a popped peer stash reads as a legitimate local change and can ride into whatever the orchestrator commits next, or a dropped peer stash is just gone, with nothing naming the cause. **Don't confuse this with the unrelated `.shipyard-*` "stash file" convention used throughout this spec** (`.shipyard-session-id`, `.shipyard-plugin-root`, `.shipyard-primary-root` — see [`00f-session-id-storage.md`](./setup/00f-session-id-storage.md)) — those are ordinary files the orchestrator writes inside its OWN worktree via `printf ... > .shipyard-*`, entirely unaffected by and unrelated to `git stash`'s shared ref. To set aside a dirty change while recovering a worktree, `git commit -m "wip: <why>"` (undo with `git reset --soft HEAD~1`) is worktree-local and needs no coordination with peers — the identical substitute a dispatched worker uses; see `shipyard:worker-preamble`'s [`git-stash-prohibition.md`](../../skills/worker-preamble/git-stash-prohibition.md) fragment for the full shared-ref mechanism writeup and the one narrow, isolating procedure for the rare case stashing is genuinely unavoidable.

### Post-relocation Bash blocks must be plain, single-purpose commands ([#1277](https://github.com/mattsears18/shipyard/issues/1277))

**Scope note — this governs any tool that takes a shell command string, not `Bash` alone ([#1547](https://github.com/mattsears18/shipyard/issues/1547)).** The heading and the rule below are phrased in terms of "Bash blocks" because that's the overwhelmingly common case in this spec, but the underlying worktree-isolation command-shape guard scans the command string of **every** tool that accepts one — as of today that includes the `Monitor` tool's `command` parameter, and will include any future tool with the same shape. A `Monitor({command: 'while true; do ...; done'})` call is refused for the identical reason, and by the identical decompose-or-extract remedy, as an inline `while`/`for`/`case` `Bash` block — see `drain.md`'s "Worktree-safe polling pattern" section for the concrete Monitor-arming shape this applies to.

**A plain `git` command refused as "runs `<launcher>` with a git command among its operands" has a different cause and a different fix ([#1558](https://github.com/mattsears18/shipyard/issues/1558)).** This isn't a compound-shape refusal, and decomposing the command won't help. A host-global `PreToolUse` hook (RTK is the known one) rewrites `git …` into `rtk git …`. Once the orchestrator has entered its worktree at step 0.5, the isolation check can't verify that launcher form and refuses it. The rewrite is selective by subcommand, so step 0.5's own `git fetch` / `git rev-list --count` staleness check can be refused while `git rev-parse` still runs. The fix is to call the binary by absolute path, `/usr/bin/git …`, and keep using it for the rest of the session. `-C` anchoring works unchanged. Don't edit or disable the hook. Pass the same instruction on to dispatched workers, since they hit the identical refusal. The worker-side rule and the full refusal shape are in [`skills/worker-preamble/launcher-git-refusal.md`](../../skills/worker-preamble/launcher-git-refusal.md). An object-literal `session-state.sh update --set` refusal from the same session is a separate command-shape refusal, already fixed by `--set-file` / per-field `--set` ([#1561](https://github.com/mattsears18/shipyard/issues/1561)).

**Extends [#1181](https://github.com/mattsears18/shipyard/issues/1181)'s existing preamble-decomposition precedent (`setup/00-config-worktree.md`'s step-0.5 callout: "Decompose, don't re-run the compound preamble") to every post-relocation orchestrator spec block, not just the `CLAUDE_PLUGIN_ROOT` preamble.** #1181 fixed one call site — the step-0.3 `CLAUDE_PLUGIN_ROOT` one-liner — and documented that its compound form is pre-relocation-only. That left every OTHER post-relocation multi-statement block still templated as one fenced compound, each refused by the worktree-isolation guard for the same reason and with no shared decomposition guidance — so each orchestrator improvised its own split, at a cost of one refused tool call per affected block, per session, with no guarantee two improvisations agree.

> **Read [Claude Code's command-shape check](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation) first — this section is necessary but NOT sufficient ([#1308](https://github.com/mattsears18/shipyard/issues/1308)).** The shapes below are genuinely refused and the decompose-or-extract guidance stands. But the trigger that actually fires on an *ordinary* helper invocation — one plain command, no loop, no pipe — is **a braced `${VAR}` parameter expansion**, plus `$(cmd)` in argument position. Neither is a compound shape, so neither is caught by the rule below, which is why #1277's fix (and #1182's, #1289's, #1291's) each shipped without stopping the refusals. Spell expansions unbraced and pass command substitution as an assignment; that fragment carries the controlled experiment. **Both** halves are now CI-enforced tree-wide — braces by [`scripts/brace-expansion-scan.sh`](../../scripts/brace-expansion-scan.sh) ([#1311](https://github.com/mattsears18/shipyard/issues/1311)), argument-position substitutions by [`scripts/command-substitution-scan.sh`](../../scripts/command-substitution-scan.sh) ([#1314](https://github.com/mattsears18/shipyard/issues/1314)) — but a clean scan from both still means only "no decorative braces and no argument-position substitutions," never "this block will run": a block carrying a required-modifier `${VAR:-default}` form is still refused and still needs the decompose-or-extract call below.

#### The measured trigger: an unresolvable shell-variable reference — NOT compoundness, NOT line count ([#1471](https://github.com/mattsears18/shipyard/issues/1471))

**This is the controlled experiment the four prior sweeps ([#1308](https://github.com/mattsears18/shipyard/issues/1308) / [#1311](https://github.com/mattsears18/shipyard/issues/1311) / [#1314](https://github.com/mattsears18/shipyard/issues/1314) / [#1352](https://github.com/mattsears18/shipyard/issues/1352)) each skipped.** Each of those correctly identified *a* refused shape, shipped a real sweep, and still left `setup/04-backlog-divert.md`'s step-4 classify block and `setup/00-config-worktree.md`'s step-0.5 stash block refused — because every one of them was hunting a *token*, and the actual trigger is not a token. Run in a live isolated worktree, one variable at a time, each command repeated 2–3× (see [RATIONALE → The #1471 command-shape experiment](../do-work-RATIONALE.md#the-1471-command-shape-experiment) for the full observation table):

> **Superseded in part by [#1474](https://github.com/mattsears18/shipyard/issues/1474) — read [the corrected rule](#the-corrected-rule-1474-never-let-an-unresolvable-expansion-be-the-whole-word) below before acting on this subsection.** #1471's framing (an unresolvable *variable reference*, most reliably one assigned from a *network* command substitution) is measurably wrong on both halves: there is no local-vs-network split, and it is not about variables. Everything #1471 recorded as *refused* really is refused — the worked examples below stand — but the stated *cause* does not, and building on it is how this gets re-guessed a sixth time.

**The guard refuses a block that REFERENCES a shell variable whose value it cannot statically resolve.** #1471 believed the most reliable instance was a variable assigned from a *network* command substitution — [#1474 measured that to be false](#the-corrected-rule-1474-never-let-an-unresolvable-expansion-be-the-whole-word). The decisive pair — everything held byte-identical except one argument:

```
bash <plugin-root>/scripts/classify-backlog.sh run … --me mattsears18 …      → RUNS
bash <plugin-root>/scripts/classify-backlog.sh run … --me "$ME_LOGIN" …      → REFUSED
```

…where the same block's preamble assigns `ME_LOGIN=$(gh api user --jq '.login')` in both cases. Substituting the literal is the entire fix.

**Four things this experiment RULES OUT, each previously believed:**

| Believed trigger | Verdict | Evidence |
|---|---|---|
| Line count / multi-statement compoundness | **Not it** | The 5-statement preamble plus `classify-backlog.sh --help` RUNS. The same preamble plus a *one*-flag `run --repo <literal>` RUNS. |
| Flag/argument count | **Not it** | The full 8-flag `run … --out …` invocation RUNS when every argument is a literal, preamble and all. |
| Backslash line continuations | **Not it** | The refused block collapsed onto one line is refused identically; the accepted block split across continuations runs identically. |
| Assignment-RHS `$(cmd)` ([#1352](https://github.com/mattsears18/shipyard/issues/1352)'s stated axis) | **Not it, as a general rule** | `ME=$(pwd)` runs. `CLAUDE_PLUGIN_ROOT=$(cat .shipyard-plugin-root 2>/dev/null)` + `export` + use runs. #1352's sweep was still worth having, but its stated cause does not reproduce. |

**One genuinely new, cleanly-isolated syntactic shape** (single variable toggled, 3 refusals vs 4 acceptances) — an **unquoted** command substitution with a literal path suffix glued on:

```
CLAUDE_PLUGIN_ROOT=$(git rev-parse --show-toplevel)/plugins/shipyard      → REFUSED
CLAUDE_PLUGIN_ROOT="$(git rev-parse --show-toplevel)/plugins/shipyard"    → RUNS
```

Quoting is the whole difference; it holds across both `export VAR=…` and split `VAR=…` + `export VAR` forms, and across single-line and multi-line rendering. [`compound-block-scan.sh`](../../scripts/compound-block-scan.sh) now flags it as a third shape alongside the loop and pipe checks — not [`command-substitution-scan.sh`](../../scripts/command-substitution-scan.sh), whose strict assignment-RHS carve-out deliberately sanctions a `$(` sitting immediately after an `=`.

**Also measured, secondary:** shell special parameters (`$?`, `$$`) and unset variables refuse when they form a path-shaped word (`echo $?`, `echo rc=$?`, `echo $UNSET`, `echo "$UNSET/foo"`) but pass inside a `label=value`-shaped word (`echo "rc=$?"`, `echo "x=$?"`). A set environment variable resolves fine (`echo $HOME` runs). **#1474 re-derived this as the same single rule, one notch more general** — the axis is *whole-word vs. literal-adjacent*, not *path-shaped vs. `label=value`-shaped*.

**Two cautions for whoever reads this next.**

1. **The guard is deterministic.** Every command above was re-run 2–3× with no verdict flip. An earlier session hypothesised non-determinism after seeing the same script accepted then refused ~40 minutes apart — that pair differed in more than one way (an argument value *and* a trailing `; echo rc=$?` construct), and the apparent instability disappears once one variable is toggled at a time. Do not build a fix on the premise that this guard is flaky.
2. **The refusal message's trailing "`without the redirect`" is a canned suffix, not a diagnosis.** It appears verbatim on commands containing no redirect at all (`echo $?`). Reading it as a hint sends you after the wrong variable.

**#1471's still-open question — now closed by [#1474](https://github.com/mattsears18/shipyard/issues/1474).** #1471 left it unresolved which command substitutions the guard can statically resolve, noting that `$(cat <file-in-worktree>)` and `$(git rev-parse …)` "behave as resolvable" while `$(gh api …)` does not, and warning against extrapolating a rule without re-running the experiment. #1474 re-ran it: **the answer is none of them, and the apparent difference was the use position, not the substitution.**

#### The corrected rule (#1474): never let an unresolvable expansion be the whole word

**A command is refused when it contains a word whose ENTIRE content is a single unresolvable expansion** — `"$VAR"` or `"$(cmd)"`. That is the whole predicate. Full observation table in [RATIONALE → The #1474 resolvability-boundary measurement](../do-work-RATIONALE.md#the-1474-resolvability-boundary-measurement--and-why-no-does-this-block-run-gate-was-built).

- **"Unresolvable" means every command substitution**, without exception — `$(pwd)`, `$(date)`, `$(cat <file-in-worktree>)`, `$(git rev-parse --show-toplevel)`, `$(gh api …)`, and `$(curl …)` all behave identically. There is no local-vs-network split, and the guard never reads a file to resolve a value.
- **"Resolvable" means** assigned from a literal earlier in the same block (transitively), or present in the process environment (`echo "$HOME"` runs bare).
- **It is not about variables.** `echo "$(pwd)"` is refused as a single statement with no variable in sight.
- **Any adjacent literal text in the same word rescues it** — `"$VAR/foo"`, `"prefix-$VAR"`, `"value=$VAR"`, `"$VAR-suffix"` all RUN. (One measured exception: a lone trailing `.` does *not* rescue it — `"$VAR."` is refused.)
- **Position is irrelevant.** A bare `"$VAR"` refuses as a script path, a flag value, a positional argument, a second word, or inside a `[ -z "$VAR" ]` test. The intuition that only path-shaped positions matter is backwards: the *path-suffixed* use is the safe one.

**What this means when you author a post-relocation block.** The two-statement stash read (`CLAUDE_PLUGIN_ROOT=$(cat .shipyard-plugin-root 2>/dev/null)` + `export CLAUDE_PLUGIN_ROOT`) is fine and stays fine — it contains no bare whole-word expansion. What breaks a block is the *use*:

```
bash "$CLAUDE_PLUGIN_ROOT/scripts/some-script.sh" --flag    → RUNS    (literal suffix)
git -C "$CLAUDE_PLUGIN_ROOT" rev-parse --short HEAD         → REFUSED (bare whole word)
[ -z "$SOME_VAR" ] && SOME_VAR="unknown"                    → REFUSED (bare whole word in the test)
```

So the rule to apply is narrower and more actionable than "substitute every value as a literal": **give the expansion a literal suffix, or substitute the literal outright.** Where neither is possible — a `git -C <root>` or a `[ -z … ]` guard genuinely needs the bare value — substitute the literal, or split the statement into a separate plain call whose value you already hold.

**No CI gate enforces this, deliberately.** #1474 measured the rule, prototyped it against `compound-block-scan.sh`'s six curated files, got **152 findings** dominated by pre-relocation blocks and illustrative pseudo-code, and concluded that distinguishing genuine refusals requires knowing per-block whether it runs post-relocation *and* whether it is executed verbatim — neither of which the markdown expresses. See [RATIONALE → The #1474 scanner decision](../do-work-RATIONALE.md#the-1474-scanner-decision-build-nothing) for the full reasoning. **Do not re-propose that scanner without re-running the experiment first** — five attempts have now been made on this guard, and four of them shipped a fix built on a model that had not been measured.

**Those 152 findings have since been audited to conclusion, and bucket 4 was NOT empty ([#1476](https://github.com/mattsears18/shipyard/issues/1476)).** #1474 *sampled* them and found no confirmed live refusal; the exhaustive pass found **33** — plain post-relocation statements, executed verbatim, carrying a bare whole-word expansion (`git worktree add "$WORKTREE_PATH" …`, `--head-ref "$head_ref"`, `--manifest "$vc_manifest"`, `git fetch origin "$DEFAULT_BRANCH"`). 24 were fixed there; the remaining 9 needed *decomposition* rather than substitution and were closed out by [#1479](https://github.com/mattsears18/shipyard/issues/1479) — **bucket 4 is now empty** across the six curated files. The full tally and classification rule are in [RATIONALE → The #1476 exhaustive audit](../do-work-RATIONALE.md#the-1476-exhaustive-audit-bucket-4-was-not-empty-33-live-refusals-24-fixed); how each residual was decomposed, and how "zero" was verified, in [RATIONALE → The #1479 residual decomposition](../do-work-RATIONALE.md#the-1479-residual-decomposition-the-last-9-bucket-4-findings). Two quantified blind spots in the prototype itself remain open (it is a **floor, not a ceiling**). The build-nothing decision is unchanged by either.

**The rule, stated once:** a post-relocation ```` ```bash ```` block — or, per the scope note above, the `command` string handed to `Monitor` or any other tool taking a shell command string — may contain any number of **plain, independent statements** — sequential `VAR=$(cmd)` assignments, `export`s, `echo`s, and simple `[ cond ] && action` one-liners are all exercised constantly throughout this spec with no reported refusal. What gets refused is a **single command** whose own structure the guard can't cheaply verify stays inside the worktree:

- **No `for`/`while` loop wrapping `gh`/`git` calls.** A loop is inherently a black box to the guard — it can't tell how many operations it performs or against what. Two shapes fix this depending on why the loop exists: **decompose** it into the individual per-item plain commands when the item count is small/bounded and known at spec-authoring time (rare in this corpus); **extract it to a script** (see below) when the item count is data-dependent (the common case — looping over `$session_prs`, a `for wt_dir in $(find ...)` sweep, etc.).
- **No `A | B` pipe spanning a shell command boundary.** `printf ... | some-script`, `echo "$var" | jq ...`, `git show ... | jq ...` are all refused. The fix is almost always mechanical and doesn't need a script: use a **herestring** (`jq '...' <<< "$var"`) or **file redirection** (`some-script < input.json > output.json`, or `jq '...' output.json` reading the file as a positional argument) in place of the pipe — a command's own I/O redirection is not a pipe spanning two commands, and passes the guard cleanly. `case ... in word|word) ... ;; esac`'s pattern-alternation `|` is NOT a shell pipe and is not what this rule targets — don't "fix" a case statement.
- **No `if`/`case` wrapper — not only around multiple `gh`/`git` calls ([#1476](https://github.com/mattsears18/shipyard/issues/1476)).** This bullet used to read "around multiple `gh`/`git` calls," which understates its reach: the [corrected rule](#the-corrected-rule-1474-never-let-an-unresolvable-expansion-be-the-whole-word) refuses `if [ "$VAR" = "true" ]` on the test's own bare whole word, regardless of how many commands the branch wraps or whether they are `gh`/`git` at all — an `if` guarding a single `$CLAUDE_PLUGIN_ROOT/scripts/*.sh` call is refused just the same. #1476's exhaustive audit classified **69 of the 152 findings** into this bullet, most of them exactly that single-call shape. Prefer branching in prose instead, matching the VERDICT-branch style already used throughout this spec (e.g. `dispatch-rules.md` §6.a's ungated-admin-direct-merge check: "`VERDICT == "ungated"` → do X. `VERDICT == "gated"` → do Y."): read the condition as its own plain command, then describe what runs in each branch as separate plain commands, rather than wrapping them in a literal `if ... fi`.

**Decompose in place vs. extract to a script — make the call per block, and record the reasoning (this issue's own resolution did both).** Prefer **decomposition in place** (rewrite the block as several small plain-command fences, `#1181`-style) when the block is a short, fixed sequence with no real iteration. The step-4 backlog `classify` invocation in `setup/04-backlog-divert.md` was originally this rule's worked example — its `printf | classify` and `printf | jq` pipes became file-redirected commands at #1277 time, no script needed — but is no longer one: as later issues (#1241's milestone flags, #1356's probe precompute, #1389's covered-by-open-pr set) each added another config read or precomputed input to the same block, the decomposed form re-accumulated exactly the complexity #1277 removed and was independently refused again (#1398). It was then extracted to [`scripts/classify-backlog.sh`](../../scripts/classify-backlog.sh), joining the extraction example below rather than remaining the decompose-in-place one — a concrete illustration that "decompose in place" is not a one-time decision: a block that stays short earns it permanently, but one that keeps growing new inputs over time can cross back into extraction territory. Prefer **extraction to a script** (mirroring `backlog-filter.sh` / `worktree-reap.sh` / `flake-enforce.sh`'s own precedent, and [#1247](https://github.com/mattsears18/shipyard/issues/1247)'s normative-script direction generally) when the block's logic is a genuine per-item loop over a data-dependent set, or when a block is already mostly a thin wrapper around one script call and the surrounding plumbing is what makes it compound — `04-backlog-divert.md`'s post-main-CI-fix branch-refresh loop (issue #993) is the worked example: its `for pr in $session_prs; do ... done` loop, with three internal `gh pr view | jq` pipes, became [`scripts/stale-check-refresh.sh`](../../scripts/stale-check-refresh.sh), turning the orchestrator's own call into one plain `bash stale-check-refresh.sh run ...` invocation. Extraction also has a durability side-benefit worth weighing: a bash variable (an associative array, a loop-scoped flag) does NOT survive between separate `Bash` tool calls, so any "session-scoped" state a compound block tried to keep in a shell variable across the *separate* call sites that re-run the same section (e.g. session setup and a later periodic refresh) was silently resetting every time regardless of this rule — a script's own state file (a small text or JSON file in the orchestrator worktree, alongside the existing `.shipyard-*` stash convention) is the only mechanism that actually persists correctly across those calls.

**Regression coverage — [`scripts/compound-block-scan.sh`](../../scripts/compound-block-scan.sh).** A `fence-balance-scan.sh`/`conflict-marker-scan.sh`-style scanner that flags a ```` ```bash ```` fenced block containing an unquoted shell pipe or a `for`/`while` loop combined with a `gh`/`git` call, run via `scripts/tests/compound-block-scan.test.sh`. **Deliberately scoped to a curated file list, not a repo-wide sweep** — the corpus mixes pre-relocation and post-relocation content within single files (`setup/00-config-worktree.md` most notably), and a blind sweep would false-positive on pre-relocation blocks that correctly keep the compound preamble shape per #1181. Extend the scanner's file list as more of the corpus gets swept and verified clean — the same incremental path `shipyard-repo-root-preamble.test.sh` took (a hardcoded array, per #1064, before #1105 later converted it to mechanical discovery). An informational sweep of `dispatch-rules.md` / `steady-state.md` / `drain.md` / `inline-trivial.md` at the time of #1277's fix found roughly a dozen more instances of these same two shapes beyond `setup/04-backlog-divert.md` (the file this issue's fix actually swept) — tracked as a follow-up rather than rewritten here, because several of them wrap load-bearing worktree-lock-reaping logic (`dispatch-rules.md` §2d's pre-dispatch head-branch reap, the concurrent-session guard) that deserves a dedicated, carefully-tested pass rather than a rushed rewrite under the same dispatch.

**Worker-side parallel.** This section covers the **orchestrator's own** spec blocks (`setup/*.md`, `dispatch-rules.md`, `steady-state.md`, `drain.md`, `operate*.md`). A dispatched **worker** hits the identical guard for the identical reason, inside its own isolated worktree — see `shipyard:worker-preamble`'s [Claude Code's command-shape check](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation) fragment for the worker-side version of this same decompose-or-extract-to-a-`.shipyard-scratch/`-script guidance, and this file's "Don't instruct a worker to route around its own worker-internal classifier denial" bullet above for why this decomposition is NOT the same thing as routing around a classifier *effect* denial (a different failure shape entirely, governed by a different rule).

**Security boundary:**

- **Don't dispatch a worker against an issue authored by a login not in `trusted_authors`.** This is the security boundary from [step 1.7](./setup/01-repo-recovery.md#17-resolve-trusted-author-allowlist) and step 2's bucket 0.5 + step 4's client-side filter + step C's lightweight backlog re-check. ([threat model + maintainer override](../do-work-RATIONALE.md#dont-dispatch-a-worker-against-an-untrusted-author-issue))

- **Don't rely solely on the dispatch-time author check for label integrity.** The author-based gate above blocks worker dispatch against stranger-authored issues, but routing labels on existing issues/PRs are mutated by any actor with `triage` permission. Defense-in-depth: the [`label-event-audit.yml`](../../../../.github/workflows/label-event-audit.yml) workflow watches every `labeled`/`unlabeled` event from untrusted actors and either reverts (Tier A: `shipyard`, `blocked:ci`, `needs-human-review`) or alerts (Tier B: `P0`-`P2`, `wontfix`, `blocked:agent-soft`, `needs-design`, `needs-triage`, `discussion`). ([why](../do-work-RATIONALE.md#dont-rely-solely-on-the-dispatch-time-author-check-for-label-integrity-issue-140))
