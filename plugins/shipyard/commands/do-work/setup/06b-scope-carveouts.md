#### Design/architecture/epic/spike decisions are in-scope by default, not a defer reason ([#767](https://github.com/mattsears18/shipyard/issues/767))

**"Has open design decisions" is, by itself, NEVER a valid defer reason at scope pre-flight.** This extends the [#661](https://github.com/mattsears18/shipyard/issues/661) "autonomous design / architecture decisions" default — documented in [`do-work.md`'s overview](../../do-work.md) as something the loop already does *inside* a dispatched worker's implementation choices — one level earlier, to the scope-preflight decision of whether to dispatch an issue at all. See [RATIONALE → Design, architecture, epic, and spike decisions are in-scope (#767 repro)](../../../../../docs/design/do-work-rationale.md#step-6--design-architecture-epic-and-spike-decisions-are-in-scope-issue-767-repro) for the repro this closes.

**The rule going forward:**

1. **An issue whose only obstacle is an open design or architecture choice is workable, not deferrable.** The scope agent (and, downstream, the dispatched worker) makes the reasonable design call itself and proceeds — exactly as [#661](https://github.com/mattsears18/shipyard/issues/661) already mandates for in-worker implementation decisions. If the issue is genuinely multi-phase once a design direction is picked, return the **ready** shape with `phase_1_scope` describing the chosen direction and what's sliced out — do not return the deferred shape merely because a design choice had to be made to get there.
2. **A spike / feasibility / research-framed issue is worked to completion, not parked.** "Investigate X and decide the approach", "spike on Y", "design a Z" issues are in-scope: the agent runs the investigation, picks a direction, and ships the committable result (a design note committed in-repo, a decomposition into follow-on issues, or the implementation itself) as the phase-1 deliverable — mirroring the phase-slicing bias the scoping-agent prompt instruction below already applies to any other multi-phase issue. There is no separate "spike" defer path; a spike is a phase-1-sliceable issue like any other.
3. **An epic that genuinely can't ship as a single PR still routes to `confirmed-non-shippable-as-single-PR`** (the epic-decomposition class, [`<!-- do-work-needs-decomposition -->`](06c-scope-handling-ui.md#handling-each-returned-entry-fires-as-each-background-agent-completes) marker, consumed by `/decompose-epic` and the inline auto-decompose path below) — **never `human-decision-required`.** Being an epic, or needing design work to decide how to decompose it, is not itself a `human-decision-required` reason; the mechanical "no phase-1 slice exists" evidence (`Missing dependency:` / `Multi-service coordination:` / `Multi-PR sequence:` / `Body cites <artifact>:`) is what gates that class, exactly as documented in the per-class evidence shapes table below. Most epics DO have a dispatchable phase-1 slice — default to slicing per the scoping-agent prompt instruction; only fall to `confirmed-non-shippable-as-single-PR` when no such slice can be constructed.
4. **Reserve `human-decision-required` / `needs-human-review` strictly for genuine human/operator blockers**: security or access-control settings (auth policy, IAM, sharing permissions — the hand-back class [`do-work.md`'s operator-inclusive-by-default overview](../../do-work.md) already carves out), an unprovisioned external-service credential (routes to `agent-console` via `external-dependency`, per [#628](https://github.com/mattsears18/shipyard/issues/628)), and a genuine product / business / legal judgment call the agent can't reasonably make on its own (pricing, TOS, brand/compliance sign-off) — never a plain "this needs design" or "this needs architecture input" framing.

This does not relax the [evidence-backed defer](#per-class-evidence-shapes--what-evidence_pointer-must-look-like) discipline below — it tightens it: "needs design" was never an accepted `evidence_pointer` shape (the rejected-shapes list already named `"UX change — probably needs design review"` as speculative-judgment text), and this section makes explicit that even a *specific-sounding* design/architecture decision, on its own, does not clear the `human-decision-required` bar — only a product/business/legal/policy decision does.

#### Operator-slice carve-out — ship the code slice, hand back only the operator remainder ([#851](https://github.com/mattsears18/shipyard/issues/851))

**An `agent-console`-bound candidate (or a security-flavored `human-decision-required` one) frequently has a shippable code slice — test for it before deferring the whole issue.** Real repro: `mattsears18/lightwork` issues where the *entire* issue was handed back on an `agent-console`/`external-dependency` defer even though most of the deliverable was ordinary in-repo code — `config/app/*.json` scaffolding where only the token *values* need Vercel/EAS operator access; a regression-guard test where only the actual env-var removal is an operator step; a build/e2e task mislabeled as an operator action outright. This carve-out is the automated, scope-preflight-time version of the split-dispatch pattern this session applied by hand for issue [#867](https://github.com/mattsears18/shipyard/issues/867) / PR [#900](https://github.com/mattsears18/shipyard/pull/900) — a doc-honesty code slice shipped immediately, and the residual security/access-control decision (flipping `require_code_owner_review` on a branch ruleset) was handed back on the same issue via a comment, with the issue re-labeled `needs-human-review` and left OPEN. See [Design/architecture/epic/spike decisions are in-scope by default](#designarchitectureepicspike-decisions-are-in-scope-by-default-not-a-defer-reason-767) above for the sibling carve-out this one extends from design/architecture obstacles to operator/security obstacles.

**The rule:** before returning a whole-issue `external-dependency` (→ `agent-console`) or a security-flavored `human-decision-required` defer, test whether the *narrow operator/console action* can be split out from an *independently valuable, functional-on-its-own* code portion. If it can, do NOT defer the whole issue — return the **ready** shape with `phase_1_scope` describing the code slice, plus `operator_residual` describing exactly what stays on this issue for the operator, plus `operator_residual_security_sensitive` (see the [Ready shape](06-scope-preflight.md#6-initial-scope-pre-flight) field definitions above for both).

**Contrast with the provisioning carve-out ([#628](https://github.com/mattsears18/shipyard/issues/628), documented in the scoping-agent prompt instruction below — mirror-image case, do NOT confuse the two):** the provisioning carve-out forbids slicing when the code has **no standalone value** until a human supplies a credential that doesn't exist yet — shipping the scaffold with a fabricated/empty value IS the harm there. This carve-out is the opposite shape: the code portion is **already correct and independently useful** (a regression-guard test that catches real regressions today, a config inventory that's accurate today, a doc fix that's honest today) and the operator step is a *separate, narrower* follow-on that doesn't gate the code's correctness. Apply the provisioning carve-out's "no standalone value" test first — if the code is genuinely inert without the operator step, this carve-out does not apply and the whole-issue defer stands.

**Worked examples (the shape to look for):**
- Config scaffolding (`config/app/*.json`, a `PUBLIC_ENV_MANIFEST`-style inventory) is pure, functional code → `phase_1_scope`; only the actual secret/token *values* need an operator console → `operator_residual`, `operator_residual_security_sensitive: false`.
- A regression-guard test asserting an env var is absent is pure, functional code → `phase_1_scope`; the actual env-var removal from the provider console is the operator step → `operator_residual`, `operator_residual_security_sensitive: false`.
- A doc-honesty fix correcting a stale claim is pure, functional code → `phase_1_scope` (the #867/#900 shape); flipping a branch-ruleset security setting is the residual → `operator_residual`, `operator_residual_security_sensitive: true` (routes to `needs-human-review`, not `agent-console`, per [#848](https://github.com/mattsears18/shipyard/issues/848)).
- **Also flag likely mislabels** while you're here: if an `agent-console`-framed candidate turns out to be pure build/CI/e2e work with no actual browser/console step at all, say so in your scoping rationale — that's a candidate for the ready shape with no `operator_residual` at all, not a slice.

**Dispatch-site and worker mechanics are documented downstream, not re-derived here:** [`dispatch-rules.md`'s "Phase-1 slice augmentation"](../dispatch-rules.md#dispatch-rules-used-by-step-7-and-step-c) renders `operator_residual` into the dispatch prompt; [`agents/issue-worker/issue-work.md` §5.85's trigger shape (3)](../../../agents/issue-worker/issue-work.md#585-post-pr-create-non-close-parentepic-leak-verification) treats the dispatched issue itself as the protected non-close reference; and [§6.5](../../../agents/issue-worker/issue-work.md#65-split-dispatch-disposition-hand-back-the-operatorsecurity-residual-keep-the-issue-open-851) posts the handback comment and applies the residual label after the code slice ships. **This `operator_residual` framing can itself go stale between when this carve-out computes it and when the dispatched worker actually acts on it** (a maintainer completes the barred action in the interim) — [`agents/issue-worker/issue-work.md` §0.5](../../../agents/issue-worker/issue-work.md#05-verify-dispatch-time-scope-boundary-framing-against-the-issues-live-comment-thread-1179) is the worker-side mandatory re-check against the issue's live comment thread that catches this ([#1179](https://github.com/mattsears18/shipyard/issues/1179)).

#### Phase-1 artifact-existence check — don't dispatch a slice for a path that's already there ([#1187](https://github.com/mattsears18/shipyard/issues/1187))

**A `phase_1_scope` that names a concrete artifact path can go stale between when the artifact actually lands and when a scope pass reads the issue.** Real repro: `mattsears18/lightwork` issue #3559 carried an operator-slice `phase_1_scope` naming a dataset file to curate and commit at a specific path. The orchestrator verified the issue's two named `Blocked by #N` blockers were both closed, but never checked whether the sliced artifact itself already existed on `origin/main` — it had merged the day before via a different PR (lightwork PR #3679). The dispatched worker spent ~262k tokens / ~36 min discovering the deliverable was already done before finding adjacent, genuinely-open work to salvage the slot; a candidate with no adjacent work would have returned an empty diff and burned the slot outright. Full repro: [issue #1187](https://github.com/mattsears18/shipyard/issues/1187).

**The rule:** whenever a `phase_1_scope` (including an operator-slice's code-slice half) names a **concrete artifact path** — a specific file the slice would create — check it against the default branch before dispatch:

```bash
git ls-tree origin/<default-branch> -- <path>
```

- **Empty output (artifact absent)** — dispatch the slice as written; nothing has changed.
- **Non-empty output (artifact present)** — do NOT dispatch the slice as written. Re-scope: either the slice is already complete (narrow or drop `phase_1_scope` to whatever genuinely remains, citing what already landed), or the remaining work is a *modification* of the existing artifact — rewrite `phase_1_scope` to say "extend/modify `<path>`", never "create `<path>`", so the dispatched worker doesn't attempt to recreate something that already merged.

**Keep this narrow.** It fires only when `phase_1_scope` names a path — a prose-only slice (e.g. "implement rate limiting on the sign-in endpoint") has nothing to check against. This is one `git ls-tree` call per sliced candidate, not a general pre-dispatch repo-state audit — it does not replace or subsume the broader [staleness probe](06g-scope-staleness-probe.md#staleness-probe--has-this-already-landed-on-origindefault-branch-992) (#992), which checks the *issue body's* claims rather than the *scope agent's own computed slice target*.

#### QA-verification carve-out — run the automatable audit, hand back only the manual remainder ([#852](https://github.com/mattsears18/shipyard/issues/852))

**A QA-verification-shaped issue frequently has an automatable slice — test for it before deferring the whole issue.** Real repro: `mattsears18/lightwork` #2711 (epic(qa): pre-launch feature & flow verification sweep) and its child #2714 (verify auth & onboarding across web/iOS/Android) were both deferred whole as `external-dependency` (native-device access), even though there was an autonomously-runnable **web slice** — functional-QA against a staged URL with the repo's own audit accounts — that could have run to file real bug issues and mark the web portion verified, while correctly handing back only the native-device portion. `do-work`'s scope-preflight had no branch that reached the existing auditor infrastructure for a plain verification issue, so the whole issue deferred and zero progress was made. This carve-out is the QA-shaped sibling of the [operator-slice carve-out](#operator-slice-carve-out--ship-the-code-slice-hand-back-only-the-operator-remainder-851) immediately above — same "split the automatable from the un-automatable, don't defer the whole thing" shape, applied to verification work instead of code work.

**Detecting a QA-verification-shaped issue.** The deliverable is *verification, not a code change* — look for: a title/body framed as "verify X", "QA sweep of Y", "walk flow Z and file bugs", "pre-launch verification"; acceptance criteria phrased as checkboxes to confirm rather than behavior to implement (e.g. "- [ ] Sign-in works on web" rather than "- [ ] Add rate limiting to the sign-in endpoint"); a `qa` label; no code-change ask anywhere in the body. Contrast with an ordinary bug-fix issue (which describes broken behavior AND expects a fix) or a testing-infrastructure issue (which asks for new automated tests to be written, not for a person/agent to manually exercise the app) — neither of those is QA-verification-shaped, and both keep slicing normally.

**The rule:** before returning a whole-issue `external-dependency` defer for a QA-verification-shaped issue, test whether **any part** of the stated acceptance criteria is checkable by an existing shipyard auditor against a reachable surface (a live web URL is the common case — `shipyard:functional-qa-auditor` for end-to-end flows, or a narrower auditor when the criteria match its remit, e.g. `shipyard:a11y-auditor` for an accessibility-sweep criterion) while the rest genuinely requires native-device access or a human (an iOS/Android build the worker can't install, an in-person hardware check, a subjective design judgment call). If an automatable slice exists, do NOT defer the whole issue — return the **ready** shape with `verification_slice` naming the auditor + surface + the specific criteria it covers, plus `verification_residual` describing what stays un-automated on this issue.

**If NOTHING is automatable** (the whole surface genuinely requires native-device access or a human, e.g. an iOS-only flow with no web equivalent and no simulator credential provisioned), this carve-out does not apply — the whole-issue `external-dependency` defer stands, exactly as before this carve-out existed.

**Worked example (the lightwork repro):** "verify auth & onboarding across web/iOS/Android" → the web leg is automatable (a live URL, staged audit accounts already documented in the repo's own auditing-authenticated-surfaces convention) → `verification_slice: "functional-qa-auditor against https://test.getlightwork.com — sign-in, sign-up, and onboarding flow using the staged audit accounts"`; the iOS/Android legs need real devices → `verification_residual: "verify sign-in/sign-up/onboarding on physical iOS and Android devices"`.

**Dispatch-site and worker mechanics are documented downstream, not re-derived here:** [`dispatch-rules.md`'s "Verification-scope augmentation"](../dispatch-rules.md#dispatch-rules-used-by-step-7-and-step-c) renders `verification_slice`/`verification_residual` into the dispatch prompt; [`agents/issue-worker/issue-work.md` §6.6](../../../agents/issue-worker/issue-work.md#66-verification-disposition-run-the-auditor-file-bugs-disposition--without-a-pr-852) dispatches the named auditor, posts the verification-status comment, and dispositions `#<N>` — this path opens **no *resolving* PR** for the dispatched issue itself (the auditor's own bug-filing PRs, if any land later, are separate, normal `/do-work` dispatches against the filed `bug` issues). The worker's own fragment documents one narrow, non-resolving exception — a small incidental PR that references `#<N>` without closing it, covering an acknowledged coverage gap or a bug the worker already diagnosed ([#1044](https://github.com/mattsears18/shipyard/issues/1044), widened from coverage-only by [#1623](https://github.com/mattsears18/shipyard/issues/1623)) — not re-derived here either.

#### Blocker-phrasing carve-out — recognize dependency constraints in any wording ([#1148](https://github.com/mattsears18/shipyard/issues/1148))

**The mechanical pre-dispatch filter ([`04-backlog-divert.md`'s `Blocked by #N` body-reference drop](04-backlog-divert.md#4-fetch--rank-the-backlog)) only recognizes that one literal phrasing, on purpose** — it's a cheap orchestrator-side string match that runs *before* any scope agent is dispatched, and it stays narrow so it never silently drops an issue from the backlog on a stray, non-blocking word. A real dependency stated in any other wording — `Wants #N`, `Depends on #N`, `Needs #N`, `Requires #N`, `Waiting on #N`, `Must not land before #N`, `After #N`, or a `## Blockers` / `## Dependencies` heading naming an issue — passes that filter untouched and reaches the scope agent, which is where this carve-out applies.

Real repro ([#1148](https://github.com/mattsears18/shipyard/issues/1148), `mattsears18/lightwork`, one session): three issues stated genuine hard dependencies in non-canonical wording — `Wants #3559` under a `## Blockers` heading; `Must not land before #3562` in ordinary body prose; a dependency stated only in a **maintainer comment**, not the body at all. All three passed pre-dispatch scope and cost a full worker dispatch each (the worker itself caught the blocker at its own pre-flight and bailed correctly, so the outcome was right, just expensive). Notably, `Must not land before` doesn't contain any of the verbs a fixed alternation (`blocked by | wants | needs | depends on | requires | waiting on | after`) would match — a verb list alone would still have missed it.

**The rule:** when scoping a candidate, read the body **and** the comment thread (the staleness-probe and freshness-check steps above already require reading comments for other reasons — reuse that read) and ask one open judgment question: *does anything here state an ordering or dependency constraint on another issue or PR, in any wording?* This is deliberately not a fixed verb list — a cheap regex over common verbs is fine as a hint to look closer, but it is never the gate; the judgment call is yours.

**Do NOT hard-defer on a loose match alone.** `needs` / `wants` / `after` / `requires` are common words in ordinary prose ("needs #123's approach", "wants the same treatment as #456") that state no dependency at all. A loose match is a **signal to check**, not a conclusion: when you find a reference that might state a dependency, resolve the referenced `#<N>`'s live state (`gh issue view <N>` / `gh pr view <N>` — open, closed, merged) and read enough of it to judge whether this issue's own acceptance criteria genuinely cannot be met until it resolves. Only return the **deferred** shape with `defer_reason_class: confirmed-blocker-still-open` when you've confirmed the reference is (a) still open and (b) a real, load-bearing gate — not merely related, prior art, or an ordering preference. A vague or already-resolved reference means proceed normally (ready, sliced with `phase_1_scope` if needed) — a false defer here silently drops real work from the backlog, which is worse than the wasted dispatch this carve-out exists to prevent.

**A `## Blockers` / `## Dependencies` heading is a stronger signal than the verb alone.** A reference listed under one of these headings is close to conclusive — a maintainer using a dedicated heading is deliberately declaring a dependency — so weight it accordingly relative to the same wording appearing inside an ordinary prose paragraph (a `Problem` or `Context` section), which warrants more scrutiny before you treat it as load-bearing.

`evidence_pointer` for a blocker-phrasing defer follows the same shape as the canonical case (a `#<digits>` reference the orchestrator's validator can parse — see the per-class evidence shapes table below) — quote the actual wording found (e.g. `Wants #3559` or `Must not land before #3562`) rather than paraphrasing it as `Blocked by`.

#### Time-gate carve-out — a defer purely on a calendar date, never a human handoff ([#1165](https://github.com/mattsears18/shipyard/issues/1165))

**Not every defer is a person-shaped or dependency-shaped blocker — some issues are genuinely only blocked on a future date.** [#1161](https://github.com/mattsears18/shipyard/issues/1161) added the `<!-- do-work-blocked-until: YYYY-MM-DD -->` body marker so the step-4 dispatch filter can drop a time-gated issue and self-admit it once the date elapses, but shipped no way for scope pre-flight to *produce* that marker — before this carve-out, a genuinely time-gated issue had no matching class and either got mis-deferred as `human-decision-required` (wrong — no human decision is needed once the date passes) or the marker had to be hand-written.

**The rule:** if the ONLY obstacle to shipping is a calendar date — a documented migration-window criterion, a scheduled quarantine deadline, a deprecation date named in another file or a maintainer comment — return the **deferred** shape with `defer_reason_class: time-gated` and an `evidence_pointer` in the `Time-gate: <YYYY-MM-DD> — <citation>` shape (see the table below). Do NOT use `human-decision-required` for this — the whole point of the class is that no human decision is pending, only elapsed time. Do NOT use `confirmed-blocker-still-open` either — that class is for a genuine `#N` reference; a bare date has no issue/PR to point at.

**This class never gates with a label.** Unlike every other deferred class, the [Recording path](06c-scope-handling-ui.md#handling-each-returned-entry-fires-as-each-background-agent-completes) applies no `needs-human-review` / `agent-console` label for `time-gated` — it writes the `<!-- do-work-blocked-until: YYYY-MM-DD -->` marker into the issue **body** instead, so the existing step-4 filter picks it up on the next fetch with zero further orchestrator involvement and zero human review needed.

#### Per-class evidence shapes — what `evidence_pointer` MUST look like

| Class | Required `evidence_pointer` shape | Example |
|---|---|---|
| `external-dependency` | A named external system or dependency the worker can't move, with a one-token identifier the orchestrator can read literally — **includes an unprovisioned external service** the integration depends on (#628) | `Stripe API change waiting on rollout` / `expo-router 4.x not yet published to npm` / `Apple Pay merchant ID provisioning pending` / `Sentry account + DSN provisioning pending` |
| `human-decision-required` | The specific decision being waited on, named in concrete terms (product, business, legal, billing, **CI/infrastructure policy**, **Claude-Code self-modification policy**, **a classifier-denied dispatch requiring a permission-policy call, #953**, **an orchestrator-only skill/command invocation proposal, #1294**) — **NOT a plain design or architecture choice** ([#767](https://github.com/mattsears18/shipyard/issues/767); see the callout above) | `copy decision pending for placeholder field in src/components/EmailForm.tsx:42` / `legal review of TOS update pending` / `pricing change requires CFO sign-off` / `Proposes .github/workflows/ci.yml change to make a check pass or relax a CI gate — worker anti-CI-gaming hard rule forbids it` / `Proposes .claude/settings.json change — Claude-Code self-modification HARD BLOCK requires human application (auto-mode classifier blocks worker dispatch)` / `Proposes .claude/hooks/stop-after-edit.sh change — Claude-Code self-modification HARD BLOCK requires human application (auto-mode classifier blocks worker dispatch)` / `Classifier denied dispatch on both permitted attempts (#718) — mode=issue-work` / `Proposes invoking orchestrator-only skill/command \`shipyard:update-roadmap\` — a dispatched worker cannot invoke it (milestone-prohibition.md / the skill's own orchestrator-only boundary blocks worker dispatch)` |
| `untrusted-author` | The login the orchestrator should re-validate against the trust list (lowercased GitHub handle) | `author: drive-by-contributor` |
| `confirmed-blocker-still-open` | One or more `#<N>` references to OPEN issues/PRs the agent confirmed are still open (must be parseable as `#<digits>` references) — any wording that states a genuine dependency, not only the literal word "blocked" (see the [Blocker-phrasing carve-out](#blocker-phrasing-carve-out--recognize-dependency-constraints-in-any-wording-1148)) | `Blocked by #1077` / `Blocked by #1077, #1082` / `Wants #3559` / `Must not land before #3562` |
| `confirmed-non-shippable-as-single-PR` | A specific mechanical reason no phase-1 slice exists — typically a multi-service coordination requirement, a missing dependency that would itself need install+lock+test+ship as its own PR, or a referenced design artifact (Figma URL, RFC document) that hasn't been imported into the codebase yet | `Missing dependency: @company/payments-sdk not in package.json` / `Multi-service coordination: needs synchronized deploy of payments-api + customer-api` / `Body cites Figma file <url> that hasn't been imported into design-tokens.json` |
| `time-gated` ([#1165](https://github.com/mattsears18/shipyard/issues/1165)) | Starts with `Time-gate:`, followed by a `YYYY-MM-DD` date **still in the future** (the orchestrator confirms it parses AND is strictly later than today's UTC calendar date — a past-or-present date means the gate has already lapsed and the issue should have been returned ready), then ` — ` and the file/line or issue-comment citation that commits to the date | `Time-gate: 2026-09-20 — see 04d-investigate-routing.md's "Label-retirement criteria" section` / `Time-gate: 2026-10-01 — per maintainer comment https://github.com/mattsears18/shipyard/issues/1200#issuecomment-123` |

**Rejected evidence_pointer shapes** (the orchestrator's per-class validator will reject any defer whose pointer matches these patterns — see [Handling each returned entry → Deferred entries](06c-scope-handling-ui.md#handling-each-returned-entry-fires-as-each-background-agent-completes) for the rejection path that promotes the issue back to `raw_backlog`):

- *"Looks like a multi-PR migration"* — no specific evidence; the speculative-judgment shape this issue exists to eliminate.
- *"Touches three platforms — likely complex"* — cross-platform ≠ multi-PR. Many cross-platform issues are tractable single-file fixes.
- *"UX change — probably needs design review"* — the scope agent isn't qualified to gate on design intent.
- *"Has open design decisions"* / *"needs an architecture decision"* / *"needs a design"* — not a defer reason at all, regardless of specificity ([#767](https://github.com/mattsears18/shipyard/issues/767)). Make the reasonable design/architecture call and proceed (ready shape, sliced with `phase_1_scope` if multi-phase) — see [Design/architecture/epic/spike decisions are in-scope by default](#designarchitectureepicspike-decisions-are-in-scope-by-default-not-a-defer-reason-767).
- *"It's an epic / needs decomposition, and deciding how to decompose it needs design input"* — an epic's own decomposition uncertainty is not a `human-decision-required` reason either; if it truly can't ship as a single PR, that's `confirmed-non-shippable-as-single-PR` (mechanical no-phase-1-slice evidence), not a design-decision defer.
- *"The issue body itself says this part is out of scope for an autonomous agent"* / *"the body hands this half back to a human"* — an issue's **self-declared limitation on the agent** is a snapshot claim about a capability, not evidence about the work ([#1491](https://github.com/mattsears18/shipyard/issues/1491)). Setup's [self-declared agent-limitation re-validation](06-scope-preflight.md#self-declared-agent-limitation-re-validation--never-trust-an-issues-own-out-of-scope-for-an-agent-claim-1491) re-derives the specific checkable premise against live session state before you ever see the candidate: a `stale` verdict means the claim is simply false and cannot support a defer, and an `upheld` verdict means the premise holds but still isn't a defer reason on its own (a missing `workflow` OAuth scope blocks auto-merge arming, not opening the PR). Either way, quote the body's own limitation sentence back as your evidence and the validator rejects it.
- *"Body is vague"* — that's a worker-side bail (handled by `agents/issue-worker/issue-work.md` step 2's `blocked: ambiguous` path), not a scope-side defer.
- *"Cross-platform — looks like a multi-PR migration"* — the exact shape that drained a prior session (see [RATIONALE → Evidence-backed defers (#302)](../../../../../docs/design/do-work-rationale.md#evidence-backed-defers-issue-302), already linked above).
- Empty string, `null`, or any pointer that doesn't match the per-class shape in the table above.

`would_be_dispatchable_as_phase_1_if` is **optional but encouraged** — a one-line condition under which the issue would become a phase-1 ready candidate (e.g. "Phase-1 stub of the email-first flow is dispatchable once a copy decision is made on the placeholder field"). Used by [`drain.md` step 5.b](../drain.md#5b--re-validate-scope-agent-and-cached-diagnosis-entries)'s pre-drain re-validation to ask whether the unblocking condition has changed — if it has, the issue is promoted back to `raw_backlog` for a fresh scope pass.

Scoping-agent prompt instruction: *Default to slicing, not deferring. If the issue is multi-phase, RETURN the smallest dispatchable phase-1 slice as a ready shape with explicit `phase_1_scope` text listing what's in and what's explicitly out of scope (the worker will file the out-of-scope items as follow-up issues, one per phase). Return the deferred shape ONLY when you can cite SPECIFIC MECHANICAL EVIDENCE for the defer — a named open blocker issue (`Blocked by #N`, or any other wording that states a genuine ordering/dependency constraint on a still-open issue/PR — see the **Blocker-phrasing carve-out** below for how to judge non-canonical phrasing like `Wants #N` / `Must not land before #N` without hard-deferring on a loose match), a missing dependency the worker can't reasonably install/lock/test/ship in the same PR, multi-service coordination that requires synchronized deploys, an external vendor change the worker can't move, or a referenced design artifact (Figma, RFC) that hasn't been imported into the codebase. Speculative reads of the body — "looks like a multi-PR migration", "touches three platforms — likely complex", "UX change — probably needs design review", "body is vague" — are NOT evidence and will be rejected by the orchestrator's per-class validator. **Design/architecture/epic/spike carve-out — these are in-scope work, not a defer reason ([#767](https://github.com/mattsears18/shipyard/issues/767)).** An issue framed as "design X", "spike on Y", "decide the architecture for Z", or an epic whose children aren't yet enumerated is NOT automatically `human-decision-required` or `confirmed-non-shippable-as-single-PR` — make the reasonable design/architecture call yourself and either (a) return ready with `phase_1_scope` describing the chosen direction plus what's sliced out, or (b) if the issue is a genuine epic with no constructible phase-1 slice, return deferred with `confirmed-non-shippable-as-single-PR` and mechanical evidence (never `human-decision-required` for this case — needing a design call to decide how to decompose is not itself a human-decision reason). **Provisioning carve-out — the default-to-slicing bias does NOT apply to external-service setup ([#628](https://github.com/mattsears18/shipyard/issues/628)).** When the issue is "set up / integrate / wire up `<external service>`" (Sentry, Stripe, Datadog, a cloud provider) and the committed config would be **non-functional — or would deploy dead — until a human provisions the service and supplies a real credential that does not exist yet** (a DSN, an API key, a service account, an empty required `*.tfvars`/secret), do NOT treat "write the scaffolding/Terraform" as a shippable phase-1 slice. There is no inert first phase here: shipping the scaffold with a fabricated or empty value IS the harm. Return the **deferred** shape with `defer_reason_class: external-dependency`, an `evidence_pointer` naming the pending provisioning (e.g. `Sentry account + DSN provisioning pending`), and `would_be_dispatchable_as_phase_1_if` set to the unblock condition (e.g. `Sentry account created and DSN set in terraform.tfvars`). (This carve-out does NOT apply when the credential is *already provisioned* — an existing CI secret / env var / populated `*.tfvars` the code merely references — that's functional config and slices normally.) **Operator-slice carve-out — test for a code slice before deferring an `agent-console`/security-flavored obstacle wholesale ([#851](https://github.com/mattsears18/shipyard/issues/851)).** Before returning a whole-issue `external-dependency` (→ `agent-console`) or a security-flavored `human-decision-required` defer, check whether the narrow operator/console action can be split from an independently valuable, functional-on-its-own code portion — config scaffolding that's correct today with only its secret *values* pending, a regression-guard test that's correct today with only the actual removal pending, a doc fix that's honest today with only a security-setting flip pending. If it can, do NOT defer the whole issue: return ready with `phase_1_scope` for the code slice plus `operator_residual` (and `operator_residual_security_sensitive`) for what stays on this issue — see the [Operator-slice carve-out](#operator-slice-carve-out--ship-the-code-slice-hand-back-only-the-operator-remainder-851) section above for the full rule, the contrast with the provisioning carve-out immediately above (which is the mirror-image case — apply its "no standalone value" test first), and worked examples. **QA-verification carve-out — test for an automatable audit slice before deferring a verification-shaped issue wholesale ([#852](https://github.com/mattsears18/shipyard/issues/852)).** When the issue's deliverable is verification, not a code change (checklist-style acceptance criteria like "verify X flow works", "QA sweep of Y", "walk through Z and file bugs"), check whether any of the stated criteria are checkable by an existing shipyard auditor against a reachable surface (typically a live web URL via `shipyard:functional-qa-auditor`) while the rest genuinely need native-device access or a human. If an automatable slice exists, do NOT defer the whole issue: return ready with `verification_slice` naming the auditor + surface + covered criteria, plus `verification_residual` for what stays un-automated — see the [QA-verification carve-out](#qa-verification-carve-out--run-the-automatable-audit-hand-back-only-the-manual-remainder-852) section above for the full rule and worked example. If nothing is automatable, the whole-issue defer stands unchanged. **Blocker-phrasing carve-out — a dependency constraint can be worded any way, not just `Blocked by #N` ([#1148](https://github.com/mattsears18/shipyard/issues/1148)).** Before concluding an issue has no blocker, read the body and comment thread for ANY wording that states an ordering/dependency constraint on another issue or PR (`Wants #N`, `Depends on #N`, `Must not land before #N`, a `## Blockers`/`## Dependencies` heading, etc.), not just the literal phrase `Blocked by`. Do NOT hard-defer on a loose verb match alone — a word like `needs` or `wants` is common in ordinary prose and is not automatically a blocker; when you spot a candidate reference, check that issue/PR's live state and judge whether it's genuinely load-bearing before returning `confirmed-blocker-still-open`. A `## Blockers`/`## Dependencies` heading is a stronger signal than the same wording in ordinary prose — see the [Blocker-phrasing carve-out](#blocker-phrasing-carve-out--recognize-dependency-constraints-in-any-wording-1148) section above for the full rule and worked repro. **Self-declared agent-limitation carve-out — an issue's own "out of scope for an agent" claim is never evidence ([#1491](https://github.com/mattsears18/shipyard/issues/1491)).** A body that declares part of its own work out of scope for an autonomous worker, handed back, or requiring a human is stating a snapshot claim about a *capability* — token scopes, tooling, and policy all move independently of an issue body, and the orchestrator has already re-validated the specific checkable premise against live session state before dispatching you. Never repeat such a sentence back as your `evidence_pointer`, and never narrow `phase_1_scope` to exclude the self-declared-out-of-scope half on the body's say-so alone — scope the issue on what the work actually requires today. **Staleness probe — confirm the issue's claims still hold before returning ready or deferred ([#992](https://github.com/mattsears18/shipyard/issues/992)).** For issues that make concrete, individually-checkable claims about repo state (a named file, a specific literal, a config key, a described-as-missing behavior), spend a cheap bounded check before finalizing your return — a targeted `git grep`/`gh api` read of just that claim, or `git log --grep "#<N>"` / `gh pr list --search "<N> in:body" --state merged` for a merged PR that already touched this issue — never a broad re-read of the repo to do this. If every claim still holds, proceed normally. If only some claims still hold, narrow `phase_1_scope` to the surviving subset and say what was dropped and why (do NOT pass the whole issue through when part of it already shipped — a false "still needed" costs a wasted worker dispatch, but a false "already landed" silently drops real remaining work, so when in doubt that at least one claim survives, keep this a ready return with a narrowed scope rather than the shape below). If NO claim still holds, return the already-landed shape (`{ issue: N, already_landed: "...", evidence_pointer: "..." }`) instead of ready or deferred — but only with a corroborating citation (a merged PR/commit reference, or the claim's confirmed absence at the specific location the body names), never from a single ambiguous grep miss. **IMPORTANT: Before judging actionability, read the issue's comment thread ([#569](https://github.com/mattsears18/shipyard/issues/569)).** A maintainer's resolution commonly lands as a comment + label removal, not a body edit — so a body that still lists "decisions needed" or "open questions" may be stale. If the comment thread contains a maintainer decision comment (look for `<!-- do-work-decision-resolved -->`, or `<!-- shipyard-resolve-decisions -->` — the marker `/shipyard:resolve-decisions` and `/my-turn`'s reused decision-gated walkthrough post automatically once every blocking decision has been answered — or a comment from the issue's author or the repo owner that is titled or begins with "RESOLVED", "Blocking decisions — RESOLVED", or similar explicit resolution language) posted after the body was last edited, **treat the body framing as overridden** and evaluate actionability based on the resolved context, not the pre-decision body. Do NOT return `human-decision-required` solely because the body contains open-question or decision-needed framing if a resolution comment supersedes it — that would silently re-gate an issue a human has already cleared, exactly the loop [#962](https://github.com/mattsears18/shipyard/issues/962) repro'd (a fresh scope pass re-citing the identical policy question a `<!-- shipyard-resolve-decisions -->` comment had already answered hours earlier). If you find a resolution comment, cite it in your scoping rationale; if the issue is now actionable after accounting for it, return the ready shape. If you still believe `human-decision-required` (or `confirmed-non-shippable-as-single-PR`) is correct despite a resolution comment being present, your `evidence_pointer`/reason MUST name what's changed SINCE that resolution — re-asserting the same pre-resolution reasoning is not evidence and will be rejected by the orchestrator's re-gate guard (see [Recording path step 3.5](06c-scope-handling-ui.md#handling-each-returned-entry-fires-as-each-background-agent-completes)). Every deferred return MUST include an `evidence_pointer` field that matches the per-class shape table in setup.md step 6; defers without an `evidence_pointer`, or with one that fails the per-class shape check, are treated as malformed and the issue is promoted back to raw_backlog for a fresh scope pass. For `confirmed-non-shippable-as-single-PR` specifically, your `evidence_pointer` MUST start with one of these four prefixes: `Missing dependency:` / `Multi-service coordination:` / `Multi-PR sequence:` / `Body cites <artifact>:` — free-form text without one of these prefixes is rejected. Examples: `Missing dependency: @company/payments-sdk not in package.json` / `Multi-service coordination: needs synchronized deploy of payments-api + customer-api` / `Multi-PR sequence: requires schema migration PR to land before this feature PR` / `Body cites Figma file <url> that hasn't been imported into design-tokens.json`. **Time-gate carve-out — a defer purely on a future calendar date is its own class, never `human-decision-required` ([#1165](https://github.com/mattsears18/shipyard/issues/1165)).** When the ONLY obstacle to shipping is a documented future date (a migration window, a scheduled deprecation) and no person needs to decide anything once that date passes, return deferred with `defer_reason_class: time-gated` and an `evidence_pointer` in the `Time-gate: <YYYY-MM-DD> — <citation>` shape — see the [Time-gate carve-out](#time-gate-carve-out--a-defer-purely-on-a-calendar-date-never-a-human-handoff-1165) section above for the full rule and worked example. This class never gets `needs-human-review`; it produces a self-clearing body marker instead. **In-flight-PR-collision carve-out — a defer purely on a file/content collision with an OPEN PR is its own class, never `confirmed-blocker-still-open` ([#1426](https://github.com/mattsears18/shipyard/issues/1426)).** When the issue is otherwise fully scoped and shippable, and the ONLY obstacle is that a currently-OPEN PR already holds — textually or semantically — the files this issue's fix must touch, return deferred with `defer_reason_class: blocked-by-in-flight-pr`, the required companion field `blocking_prs: [N, ...]` naming every holding PR, and an `evidence_pointer` in the `Blocked by in-flight PR: #<N> <what's colliding>` shape. **Check whether the collision is semantic, not just textual, before writing the citation**: if the holding PR is rewriting or deleting the specific claim this issue's acceptance criteria depend on (not merely touching the same file), name that claim in the citation — a bare file path loses exactly the information a later re-scope needs to tell whether the premise survived the merge (e.g. `Blocked by in-flight PR: #4157 deletes the "web PostHog is an inert stub" sentence this issue's AC requires`, not just `Blocked by in-flight PR: #4157 touches docs/observability/README.md`). Do NOT use `confirmed-blocker-still-open` for this — that class is for a genuine issue-level ordering dependency (`Blocked by #N` on another **issue**), not a **PR** holding files with no ordering relationship at all; folding a file collision into `confirmed-blocker-still-open` hides "genuinely blocked" among "queued behind my own in-flight work" and is exactly the misclassification this carve-out exists to prevent. This class never gets `needs-human-review` either — no human decision is needed, only a merge — and, like `time-gated`, it now produces a self-clearing marker too ([#1429](https://github.com/mattsears18/shipyard/issues/1429)); see the class's own entry in [setup.md step 6's Deferred shape docs](06-scope-preflight.md#6-initial-scope-pre-flight) for the full rule. **When you're confident the issue would be immediately ready the instant `blocking_prs` resolves — you can already see exactly what the phase-1 slice would be, collision aside — ALSO supply `would_be_ready_scope: { files: [...], phase_1_scope?: "..." }`, the same shape a plain ready return's `files`/`phase_1_scope` carry ([#1448](https://github.com/mattsears18/shipyard/issues/1448)).** This lets the orchestrator skip a second scope-agent dispatch once the collision clears, subject to a mandatory semantic-premise re-validation it runs itself — omit the field whenever you're not confident (e.g. the merge could plausibly change what the phase-1 slice should be); a missing `would_be_ready_scope` just means a fresh scope pass happens later, never a defect. **Phase-1 artifact-existence check — before returning a ready shape whose `phase_1_scope` names a concrete file path, confirm that path doesn't already exist on `origin/<default-branch>` ([#1187](https://github.com/mattsears18/shipyard/issues/1187)).** Run `git ls-tree origin/<default-branch> -- <path>`; if it's already there, do not dispatch the slice as written — narrow `phase_1_scope` to what genuinely remains, or rephrase it to extend/modify the existing artifact rather than create it. See the [Phase-1 artifact-existence check](#phase-1-artifact-existence-check--dont-dispatch-a-slice-for-a-path-thats-already-there-1187) section above for the full rule. When in doubt — default to ready (with phase_1_scope if multi-phase). When the issue truly can't be sliced, pick a `defer_reason_class` from the seven allowed values and set `defer_reason_class` to the **EXACT LITERAL TOKEN** — do NOT paraphrase, invent synonyms, or use free-text descriptions. The seven valid tokens are: `external-dependency`, `human-decision-required`, `untrusted-author`, `confirmed-blocker-still-open`, `confirmed-non-shippable-as-single-PR`, `time-gated`, `blocked-by-in-flight-pr`. Any other string (e.g. `"media_production"`, `"external_console_dependency"`, `"Umbrella / Epic requiring human discretion"`) is an invalid class and will be normalized by the orchestrator at cost of an extra reshaping pass — use the literal token. Populate `evidence_pointer` with the concrete mechanical citation for that class, and, where possible, fill `would_be_dispatchable_as_phase_1_if` with the condition that would unblock the slice — the orchestrator's pre-drain re-validation reads that field to decide whether the unblocking condition has changed.* See [RATIONALE → Deferred shape](../../../../../docs/design/do-work-rationale.md#step-6--why-scope-pre-flight-has-a-deferred-shape) and [RATIONALE → Evidence-backed defers (issue #302)](../../../../../docs/design/do-work-rationale.md#evidence-backed-defers-issue-302).

**Scoping-agent `files` augmentation — shared regression-test suite inclusion.** For **fix-class issues** (issues whose labels include `bug`, `fix`, `regression`, `P0`, `P1`, or `P2`, OR whose title begins with `fix(`, `fix:`, `bug:`, or `regression:`) in repos that maintain a **shared regression-test suite file** (a single accumulator file where each fix adds a test block — e.g. `plugins/shipyard/scripts/tests/do-work-split.test.sh` in `mattsears18/shipyard`), the scoping agent MUST include the shared regression-test file in `files` even when the issue body does not name it. The worker will add a regression block to that file by convention; omitting it from `claimed_paths` silently defeats the collision-tracking guarantee — a sibling PR that DID claim the file will conflict at drain-phase rebase time, converting what should have been a dispatch-time park (cheap) into a drain-phase manual-rebase handoff (expensive). See issue [#554](https://github.com/mattsears18/shipyard/issues/554) and [RATIONALE → Shared regression-test suite inclusion](../../../../../docs/design/do-work-rationale.md#step-6--shared-regression-test-suite-inclusion-issue-554) for the repro. Detect the shared suite file heuristically: look for a `*.test.sh` (or the repo's equivalent test accumulator) touched by 10+ distinct commits, or explicitly named in the repo's `CLAUDE.md` as the shared suite. Add the detected path to `files`. Do NOT add it for feature-class issues (new capabilities where no regression block would be added by convention).

**Scoping-agent test-file naming — suggest a location and subject, never an extension copied from the source file ([#1599](https://github.com/mattsears18/shipyard/issues/1599)).** When `files` or `phase_1_scope` points the worker at a **new** test file, the extension that file must carry is a property of the repo's **test-runner configuration**, not of the code under test — a React component does not imply `.test.tsx` when the runner only collects `.test.ts`. Either (a) name the test's **directory and subject** only (e.g. `__tests__/ — a test for web-push-card's denied state`) and leave the filename to the worker, or (b) if you name a full path, derive it from the collection rule (`jest.config.*` `testMatch`/`testRegex`/`projects`, `vitest.config.*` `include`, `pytest.ini`/`pyproject.toml` `python_files`) or, when that rule is computed rather than declarative, from the naming of existing test files in the same directory. Never default to the source file's extension. The failure this closes is silent: a file no runner project collects looks like coverage, and a negative control run against it passes vacuously in both directions. The worker-side backstop — confirm the runner actually collects a new test file before trusting any result from it — is [`ci-pitfalls.md`](../../../skills/worker-preamble/ci-pitfalls.md) § "A test file the runner never collects is not a passing test"; it applies regardless of what this pass suggests.

`lockfile_sections` (ready shape only) is the set of root-manifest sections the candidate will touch — typically top-level keys in `package.json` (`overrides`, `dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`, `scripts`, `engines`, `config`, `workspaces`, `resolutions`, `pnpm`, etc.). For non-`package.json` lockfile-class files (`Gemfile`, `go.mod`, `Cargo.toml`, `requirements.txt`, generated SQL migrations, root build config like `vite.config.ts` / `tsconfig.json`) use the filename as the section token (e.g., `"go.mod"`, `"Cargo.toml"`, `"migrations"`). Return an **empty array** for issues that don't touch any lockfile-class file. Budget ~30s per scoping agent.
