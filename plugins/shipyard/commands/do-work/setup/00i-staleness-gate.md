### 0.41 Staleness GATE — self-heal the primary checkout, or refuse to run ([#1386](https://github.com/mattsears18/shipyard/issues/1386))

**No-op unless `$SHIPYARD_PLUGIN_ROOT_STALE` was set at [step 0.4](./00-config-worktree.md#04-check-the-repo-level-opt-in-shipyardconfigjson) — then this step is a hard gate, not an advisory.** Run it here, immediately after step 0.4 and before [step 0.42](./00-config-worktree.md#042-immediate-fresh-re-read-on-staleness-1351).

**Why the gate lives at step 0.4's check and nowhere else.** The staleness-recovery steps that came before it — [0.42](./00-config-worktree.md#042-immediate-fresh-re-read-on-staleness-1351) ([#1351](https://github.com/mattsears18/shipyard/issues/1351)), [0.45](./00-config-worktree.md#045-pre-relocation-session-state-init--the-worktree-cross-referencing-sweeps-1202) ([#1202](https://github.com/mattsears18/shipyard/issues/1202)), [0.6](./00-config-worktree.md#06-re-read-stale-spec-files-1191) ([#1191](https://github.com/mattsears18/shipyard/issues/1191)) — are each **gated on the stale file containing the pointer to them**. A primary checkout predating #1351 has no 0.42 pointer to reach, so nothing performs 0.42's diff, so nothing detects that 0.42/0.45/0.6 all exist upstream: every recovery mechanism is invisible at exactly the moment it's needed. The property is *recursive* — any fix phrased as "the stale file should tell you to do X" is one release behind by construction. Step 0.4's staleness check is the one anchor that escapes it: it has been present in essentially its current form since [#907](https://github.com/mattsears18/shipyard/issues/907), so even a badly-drifted checkout reaches it. So this step changes the check's **action**, not its position. See [`heal-stale-primary-checkout.sh`](../../../scripts/heal-stale-primary-checkout.sh)'s own header for the full repro — a 155-commit-stale session that skipped all three recovery steps, ran the pre-relocation worktree sweeps *after* `EnterWorktree`, and filed a P1 issue asserting a spec claim that had already shipped.

**It closes a second, independent class of harm — silent whole-session config reversion.** [Step 0.56](./00k-repo-root-pin.md#056-pin-shipyard_repo_root-to-the-primary-checkout-1059)'s [#1059](https://github.com/mattsears18/shipyard/issues/1059) pin correctly points `SHIPYARD_REPO_ROOT` at the primary checkout so post-relocation reads still see the gitignored `.shipyard/config.local.json` layer. On a **stale** primary that pin selects a `shipyard.config.json` predating the current schema (the repro's `.labels.blocked` / `.labels.blocked_hard`, retired by [#1376](https://github.com/mattsears18/shipyard/issues/1376) inside the drift window), so `shipyard-config.sh` exits 70 on *every* read — and since every consumer is deliberately fail-open, the observable symptom is an empty string with exit 0, indistinguishable from "this repo sets no override." `models.*`, `trust.authors`, `auto_merge.policy`, `concurrency.*`, `cost_tracking.*`, `ci.*` and `flake_registry.*` all revert to built-in defaults for the whole session, routing around [#367](https://github.com/mattsears18/shipyard/issues/367)'s loud warning (which lives in step 0.4's `load`, while this damage surfaces at every *later* `get`). A primary never allowed to be stale cannot carry a config predating its own schema, so the gate closes this path with no separate work.

**Run the gate. It is a script, not a rule to re-derive** — the same single-executable-source-of-truth posture as [`detect-ungated-admin-direct-merge.sh`](../../../scripts/detect-ungated-admin-direct-merge.sh) and [`primary-leak-guard.sh`](../../../scripts/primary-leak-guard.sh). Substitute the literals step 0.4 echoed to stderr (`SHIPYARD_PRIMARY_CHECKOUT_ROOT`, `STALENESS_DEFAULT_BRANCH`); shell variables don't survive the hermetic Bash-tool boundary ([#354](https://github.com/mattsears18/shipyard/issues/354)). `--attempt` is 1 on the first pass and increments on each restart-from-0.3, which is what caps the loop:

```bash
export CLAUDE_PLUGIN_ROOT="${CLAUDE_PLUGIN_ROOT:-$(R=$(git rev-parse --show-toplevel 2>/dev/null); if [ -d "$R/plugins/shipyard/scripts" ]; then echo "$R/plugins/shipyard"; else I=$(jq -r '.plugins["shipyard@shipyard"][0].installPath // empty' "$HOME/.claude/plugins/installed_plugins.json" 2>/dev/null); if [ -n "$I" ] && [ -d "$I/scripts" ]; then echo "$I"; else echo "$R/plugins/shipyard"; fi; fi)}"
"$CLAUDE_PLUGIN_ROOT/scripts/heal-stale-primary-checkout.sh" run \
  --primary "<primary-root literal, 0.4>" \
  --default-branch "<default-branch literal, 0.4>" \
  --attempt 1
```

(This step is **pre-relocation**, so the compound preamble above is the correct form — see [step 0.3's pre-relocation-only callout](./00-config-worktree.md#03-claude_plugin_root-re-export-preamble-every-bash-tool-call); the `.shipyard-plugin-root` stash step 0.5 writes doesn't exist yet.)

Parse the `key=value` lines and branch on `verdict=`:

- **`fresh`** — the primary is not actually behind (a race: it was refreshed between step 0.4's count and this call). Clear `SHIPYARD_PLUGIN_ROOT_STALE` and continue to step 0.42 normally.
- **`healed`** — the primary was fast-forwarded (`head_before` → `head_after`). **Every spec file already read this session is now INVALIDATED, including this one.** Re-read the three bootstrap files from disk — `plugins/shipyard/commands/do-work/dont.md`, `plugins/shipyard/commands/do-work/setup.md`, `plugins/shipyard/commands/do-work/setup/00-config-worktree.md` — with plain `Read` calls against the primary checkout, then **restart setup from [step 0.3](./00-config-worktree.md#03-claude_plugin_root-re-export-preamble-every-bash-tool-call)**, passing `--attempt 2` when this gate is reached again. Treat the freshly-read copies as authoritative and discard the stale ones already in context; the fresh `setup.md` may list sub-phase rows (and `00-config-worktree.md` may list steps) this session has never seen. Record `SHIPYARD_PRIMARY_SELF_HEALED="<head_before> -> <head_after> (<behind_before> commit(s))"` as session-local working memory so the [end-of-session summary](../cleanup-summary.md#end-of-session-summary) reports the heal rather than leaving the write invisible.
- **`dirty-refuse` / `branch-refuse` / `attempt-refuse` / `heal-failed` / `error`** — **STOP. Do not continue setup, do not relocate, do not dispatch.** Print the script's `reason=` verbatim (it names the exact command a human should run) and end the session. Continuing is what produced #1386's bad artifact: a session reasoning confidently from a spec 155 commits out of date.

**The write to the primary checkout is sanctioned and narrow.** [`dont.md`](../dont.md) forbids writes to the user's primary checkout and names one exception — [A.0.6's branch-leak guard](../steady-state.md#a06-primary-checkout-branch-leak-guard-fires-every-reconcile-turn-before-a1) ([#387](https://github.com/mattsears18/shipyard/issues/387)), which may move the primary's HEAD only when the tree is CLEAN, making the restore provably lossless. This gate extends that same clean-tree-only posture to a **fast-forward**, which is strictly weaker: it discards nothing by construction. The script never stashes, never cleans, never resets, and never switches branches — a tree with **tracked** modifications (staged or unstaged) or a primary parked on a feature branch refuses instead. **Untracked files do not count as dirty** ([#1616](https://github.com/mattsears18/shipyard/issues/1616)): a fast-forward cannot lose untracked content, because git refuses the merge rather than overwrite an untracked path an incoming commit adds — that refusal surfaces as `heal-failed` with a reason naming the collision, never a clobber. Untracked tool artifacts (`.codex/`, `AGENTS.md`, editor dirs) are the common maintainer-checkout shape, so counting them as "possible real edits" turned a lossless fast-forward into a session-ending `dirty-refuse`. Do not generalize this into "shipyard may update the primary checkout"; it fires only on the stale-and-tracked-clean-and-on-default path, and only in the dogfooding case where `CLAUDE_PLUGIN_ROOT` resolved repo-local.

**Bounded, one-time migration cost — and the last one.** A checkout stale enough to predate *this* step still misses it, exactly as every prior fix was missed. The difference is that once a session runs step 0.41 it either becomes fresh or stops, so no future recovery step inherits the hole. Steps [0.42](./00h-immediate-reread.md) and [0.6](./00d-reread.md) stay in place as the backstop for that migration window, and become unreachable afterwards (a healed session restarts with `$SHIPYARD_PLUGIN_ROOT_STALE` unset).

**Declined, deliberately: an opt-out flag.** No `--force` / config knob bypasses this gate. An escape hatch that lets a session continue on a stale checkout re-opens the exact hole the gate closes, and the blast radius is already narrow — the check only fires in the dogfooding case (`CLAUDE_PLUGIN_ROOT` resolved repo-local), never on a consumer install, where `CLAUDE_PLUGIN_ROOT` points at a separately-versioned install with its own `/shipyard:update` cadence. A user who genuinely wants to run against an old spec can check it out and re-run; that is a deliberate act, not a silent default.
