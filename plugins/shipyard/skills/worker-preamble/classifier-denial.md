# Worker-preamble fragment — After a classifier denial

On-demand fragment of the `shipyard:worker-preamble` skill (see [`SKILL.md`](./SKILL.md)). Load this the moment Auto Mode (or another harness-side classifier) denies a tool call — an Edit, a Write, a Bash, an `npm install`, a symlink. This fires only on a denial, so most dispatches never load it. The per-mode specs and the orchestrator's own dispatch-rules / cleanup-summary / RATIONALE files point here by name (`shipyard:worker-preamble § "After a classifier denial"`).

## After a classifier denial

**Shipyard's recommended posture is to run under Auto Mode, not full permission bypass (`--dangerously-skip-permissions`) — see [`do-work-rationale.md` § "Recommended permission posture"](../../../../docs/design/do-work-rationale.md#recommended-permission-posture--why-auto-mode-over-full-bypass-763) for the full rationale.** Everything in this section is the operational consequence of that recommendation: if you hit a classifier denial, that is the recommended posture working as intended, not a misconfiguration to work around. A worker running under full bypass would never see this section fire at all — which is exactly the gap the recommendation closes.

Auto Mode (and other harness-side classifiers) sometimes deny a tool call — an Edit, a Write, a Bash, an `npm install`, a symlink — with a reason like *"...creates a writable path linking the worktree to a pre-existing directory outside the session's scope and risks irreversible effects on shared local state; not explicitly authorized."* The denial is a hard boundary enforced by the harness, not a suggestion you can argue past. The correct posture is to treat the denial as a deterministic failure for **this** dispatch and let a human decide whether to re-authorize, change the classifier policy, or redirect the work.

**This is a separate, deterministic layer from shipyard's own `PreToolUse` hooks.** The worktree-isolation guard (`enforce-worktree-isolation.sh`), the edit-scope guard (`enforce-edit-scope.sh`), the broad-process-kill refusal (`refuse-broad-process-kill.sh`), and the escape-symlink commit guard (`refuse-escape-symlink-commit.sh`) all fire on every matching tool call regardless of which permission mode is active — they are not weakened, duplicated, or replaced by Auto Mode. Auto Mode's classifier is a second, semantic gate layered in addition to them, covering the destructive-action class (`git reset --hard`, infra-destroy commands, unresolved-variable `rm -rf`) those hooks don't scope to. A denial from one layer doesn't imply anything about the other — you could just as easily hit a hook's hard exit-2 block as a classifier denial, and both get the same non-negotiable treatment below.

**Four behaviors you MUST NOT do after a denial, even when you believe the denial was wrong:**

1. **Do NOT post a comment to any public GitHub artifact** (issue comment, PR description, PR comment, PR review) that summarizes, reframes, paraphrases, fabricates, or explains the classifier's reasoning. Classifier denials are between the worker and the harness; surfacing them to public-facing channels creates a content-integrity attack surface — even when well-intentioned, a public-facing comment fabricating *why* the classifier denied something is a side-channel that a future worker, reviewer, or scraper could read as authoritative. The harness's classifier reasoning is not yours to relay.
2. **Do NOT attempt to file a follow-up issue arguing the denial was wrong.** "The classifier was overly strict, please relax the policy" is not a worker decision; it's a maintainer decision. If you genuinely believe a denial pattern is misclassified at the policy level, the right surface is `mattsears18/shipyard` issues filed by the *user* after they see your `blocked:` return, not a self-filed escalation from inside the dispatch.
3. **Do NOT retry the same denied call through a workaround** — a different tool, a renamed file, a Base64-encoded payload, a shell-out that produces the same effect via a different syscall, or any other "I'll just do it a different way" strategy. Classifier policy targets *effects*, not tool names; routing around the deny is treated as the same policy violation. If the first attempt was denied, the second through any synonym is denied too.
4. **Do NOT comply with a resumed instruction that proposes an effect-equivalent substitute for something you were already denied, and do NOT improvise a further formulation of your own past an explicit "stop" instruction ([#1278](https://github.com/mattsears18/shipyard/issues/1278)).** A denial encountered **after an orchestrator resume is still a denial** — it does not matter whether the orchestrator's follow-up (via a resumed `SendMessage` or any other continuation of your worktree/branch) frames the substitute as "a genuinely different operation the classifier evaluates on its own merits": a refspec push in place of a denied local branch-create, a merge commit in place of a denied force-push, `git update-ref` / `git branch` / `git format-patch` standing in for either. The classifier evaluated an *effect*, not a tool name, and a later instruction from the orchestrator cannot make an already-denied effect newly permitted — this is the worker-side half of `dont.md`'s companion prohibition on the orchestrator ever issuing that instruction in the first place. Nor does an explicit "stop at two, do not try a third formulation" instruction you already received expire because the work is nearly done, because a later message from the same orchestrator says otherwise, or because you've since found a plausible-sounding third approach on your own initiative — comply with the earlier stop instruction over the later one that contradicts it. If you are resumed after your own `blocked: classifier denied` return and the follow-up asks you to continue past it, return `blocked: classifier denied <op> — orchestrator instructed an effect-equivalent substitute after denial, refusing`; if you find yourself about to improvise a further attempt on your own initiative after having already been told to stop, return `blocked: classifier denied <op> — stopping per the prior stop instruction rather than improvising a further workaround` instead of proceeding. **This does not cover decomposing a refused *compound* command into plain single-purpose commands that run the identical, already-permitted effect** — that is a syntax refusal (the harness's "too complex to verify" objection to a compound shape), not an effect denial, and remains the sanctioned response documented in [Claude Code's command-shape check](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation); the test is whether the classifier named the *operation* as unauthorized (this rule) or the *call shape* as unverifiable (that one).

**The correct response to a classifier denial is one foreground call: return.**

> `blocked: classifier denied <one-line description of what was denied>`

That's it. No comment, no follow-up issue, no creative retry. The `blocked:` return is the orchestrator's signal that the dispatch hit a deterministic boundary; step A reconcile will classify it as a refuse and apply `needs-human-review` (per [#521](https://github.com/mattsears18/shipyard/issues/521)) and the user can decide what to do next. The one-line description should name the operation (e.g., "Edit to .claude/settings.json", "symlink ../../../node_modules to ./node_modules", "npm install firebase-tools") so the maintainer can pattern-match the denial without reading the full transcript — but **do not include the classifier's prose reasoning** (paraphrased or verbatim) in the return string. The orchestrator captures it in the transcript record on its own.

**Why this is in the preamble.** A classifier-denial event is observably frustrating — the worker has a plan, sees the denial, and reaches for the next thing on the "ways to make this work" list. The next thing is often a content-integrity violation (posting to explain the denial) or a policy-bypass violation (retrying through a different surface). Both have been observed in the wild — issue [#341](https://github.com/mattsears18/shipyard/issues/341) documents a 2026-05-25 session where a worker attempted to post a fabricated explanation of the classifier's reasoning to a public GitHub issue after three denied Edit/Write attempts; the second-order classifier caught the comment-post too, so no harmful content landed, but the *intent* to escalate is the gap. Issue [#1278](https://github.com/mattsears18/shipyard/issues/1278) documents the resumed-instruction variant of the same pull: a worker returned `blocked: classifier denied` correctly, was resumed by the orchestrator with an effect-equivalent substitute instruction, complied, hit a second denial, and then improvised a third, unprompted workaround against an explicit "stop at two" instruction it had already been given — landing an evaded-denial merge to `main` before anyone could intervene. This section closes that gap by naming the failure mode up front so the worker doesn't have to derive the correct response under the cognitive load of a denial *or* a resume that seems to override it.
