# A worker never touches the roadmap ([#1240](https://github.com/mattsears18/shipyard/issues/1240))

`shipyard:update-roadmap` (the roadmap-authoring skill — assigns milestones, authors phases, checks bets, detects dependencies) is **orchestrator-only**. It must never be invoked from inside a dispatched worker's own turn, and a worker must never itself create, rename, renumber, or reassign a milestone, or edit a milestone description.

**Why this belongs here, not only in the skill itself.** The skill's own file states the orchestrator-only rule, but that file is read by the *orchestrator*, not by the workers the rule constrains. `shipyard:worker-preamble` carries this rule as its own fragment for the same reason it carries 17 other prohibitions as dedicated fragment files (`git-stash-prohibition.md`, `compound-command-refusal.md`, `nvm-source-refusal.md`, and so on) instead of leaving each one stated once in whichever spec happens to describe the feature: a prohibition is only load-bearing if it lives where the constrained agent actually reads it. A rule stated only in the orchestrator's own skill is invisible to the worker it's meant to constrain.

**Why it matters.** A dispatched worker runs in an isolated worktree scoped to a single issue — it has no view of the whole backlog, which is exactly the context milestone sequencing requires (which phase an issue belongs to depends on every *other* open issue's phase, not just this one). Two concurrent workers each deciding to create or renumber a milestone would race each other: one worker's renumber landing mid-read of another worker's cold-start scan produces an inconsistent roadmap neither worker can detect from inside its own worktree.

**The one exception — filing metadata is not roadmap authorship.** A worker that files a follow-up issue (per `agents/issue-worker/issue-work.md` § "Implement" — a bug spotted mid-implementation that the worker does not fold into its own PR goes to a new issue) resolves that new issue's milestone in two tiers, gated the same as every other filer on `milestones.enabled` + `milestones.assign_on_file` both being `true`. Neither tier is a new milestone decision the worker is making on its own:

1. **Inherit first.** Only within the same repo, though ([#1498](https://github.com/mattsears18/shipyard/issues/1498)): if the issue currently being worked (`#<N>`) already carries a milestone **and the follow-up is being filed against the same repo `#<N>` lives in**, stamp the follow-up with that **parent issue's own existing milestone** — inherited filing metadata from a decision a human or the orchestrator already made. When the follow-up targets a *different* repo (the "file the friction against the plugin repo" flow), `#<N>`'s milestone is a phase title from the working repo's roadmap and means nothing in the target repo — skip tier 1 entirely and go straight to tier 2, which resolves against the target repo throughout.
2. **Fall through when there's nothing to inherit.** When `#<N>` carries no milestone, don't file bare — run [`shipyard:filing-github-issues`](../filing-github-issues/SKILL.md) § "Milestone assignment" in full for the follow-up's own content: match against the open milestone list's `BET:` lines (never against `#<N>`'s title/keywords), and fall back to `milestones.fallback` when nothing matches. This is the identical BET-matching-then-fallback procedure every other filer (an auditor, `/shipyard:file-issue`) already uses — it still only *selects among already-existing* milestones, never authors one.

A worker must NOT invent, guess, or infer a milestone by any means other than these two tiers, and must NOT skip tier 2 and file bare just because tier 1 didn't apply — a parent with no milestone silently producing an unmilestoned child was the gap [#1421](https://github.com/mattsears18/shipyard/issues/1421) closed. As with every filing path, a `gh` error or an inconclusive tier-2 match is a reason to file **without** a milestone, never a reason to skip filing the follow-up itself.

## Don't

- Don't invoke `/shipyard:update-roadmap` (or otherwise run the `shipyard:update-roadmap` skill's procedure) from inside a dispatched `/shipyard:do-work` worker's turn — mode-issue-work, fix-checks-only, fix-rebase, fix-main-ci, fix-failing-prs-batch, investigate, and spike are all off-limits.
- Don't create, rename, renumber, or reassign a GitHub Milestone from inside a worker's turn, for any reason — not even a milestone that looks obviously missing or obviously wrong. This applies to both tiers above: tier 2's BET-matching may only pick an already-existing milestone (or the already-existing `milestones.fallback`), never author a new one — same prohibition `dont.md` states for every other filing path ([#1242](https://github.com/mattsears18/shipyard/issues/1242)).
- Don't edit a milestone's description from inside a worker's turn — that's roadmap authorship (a phase's `BET:`/`DONE LOOKS LIKE:` text), reserved for the orchestrator-run skill.
- Don't inherit `#<N>`'s milestone onto a follow-up filed against a **different** repo — a phase title from the working repo's roadmap doesn't exist in the target repo, and `gh issue create --milestone` would fail or, worse, land on a same-named phase that means something else. Cross-repo follow-ups take tier 2 only ([#1498](https://github.com/mattsears18/shipyard/issues/1498)).
- **Do** stamp a filed follow-up issue with its parent's existing milestone when the parent has one and the follow-up is same-repo; when the parent has none (or the filing is cross-repo), **do** run `shipyard:filing-github-issues` § "Milestone assignment" (BET-matching + the configured fallback, both resolved against the *target* repo) instead of filing bare. Both are inherited/matched filing metadata, not a milestone decision, and both are explicitly in scope ([#1421](https://github.com/mattsears18/shipyard/issues/1421), [#1498](https://github.com/mattsears18/shipyard/issues/1498)).
