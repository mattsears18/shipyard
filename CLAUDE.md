# Repo-scoped rules for `mattsears18/shipyard`

These complement the global rules in `~/.claude/CLAUDE.md`. They apply only when working in this repo.

## Permissions

- **You always have permission to land changes on `main` without asking — but `main` requires a PR.** The repo's branch ruleset rejects direct pushes (`GH013: Changes must be made through a pull request`), so the mechanism is always the same: push to a branch, open a PR, and arm auto-merge. You do NOT need a review gate or to ask first — the user grants this durably because this is personal tooling, not a multi-contributor codebase that needs human sign-off on every change. Use judgment on *how much ceremony*: trivial fixes / config / docs / cleanup → a PR with auto-merge armed lands fast and is fine; substantive code or spec changes → also a PR, but lean on CI to catch regressions and keep the change reviewable in isolation. The constant is the PR; what varies is how carefully you treat the review.
- Worktree-isolation rules from `/shipyard:do-work` (#34) still apply: orchestrated multi-agent sessions work in `.claude/worktrees/orchestrator-<session-id>` so they don't clobber the user's in-progress edits in the primary checkout. The PR-via-auto-merge permission doesn't override the worktree isolation contract for `/do-work` runs.

### Required status checks on `main` — and the two that must never be added

The `main` ruleset (id `16669759`) requires **five** status checks. Until 2026-07-25 it required **none**, which meant `gh pr merge --auto` did not queue behind CI — it fell through to an *immediate direct merge* for an admin, the exact ungated shape [`scripts/detect-ungated-admin-direct-merge.sh`](plugins/shipyard/scripts/detect-ungated-admin-direct-merge.sh) exists to detect (issues #438 / #465 / #598 / #602 / #645 / #716). Run that script (`bash plugins/shipyard/scripts/detect-ungated-admin-direct-merge.sh <owner/repo>`) rather than reasoning about the shape by hand; it is the single executable source of truth and now reports `verdict=gated` for this repo. **The repo argument is POSITIONAL — there is no `--repo` flag**, even though `gh` spells the same argument that way; the flag form exits `64` with `USAGE_ERROR:` on stdout rather than forwarding the nonsense command line to `gh` ([#1502](https://github.com/mattsears18/shipyard/issues/1502)).

Required contexts — all five come from workflows triggered on **every** `pull_request` against `main`:

| Context | Workflow | Guards |
|---|---|---|
| `conflict markers` | `conflict-markers.yml` | unresolved merge markers reaching `main` (see #436 — this already happened once and poisoned every branch cut afterwards) |
| `gitleaks` | `secret-scan.yml` | secrets committed to a **public** repo (unrecoverable — rotation, not revert) |
| `bash test suites` | `tests.yml` | the ~3,800 assertions across 97 suites |
| `shell tests` | `shellcheck.yml` | same suites, second job |
| `shellcheck` | `shellcheck.yml` | ~14K lines of production shell under `plugins/shipyard/scripts/` |

**Never add `External-author gate` or `Audit label event` to the required list.** Both appear as passing checks on a PR that happens to trigger them, which makes them look like reasonable additions — they are not:

- `external-author-gate.yml` triggers on `issues: [opened, reopened]` only. It **never** runs on a pull request, so requiring it blocks every PR permanently.
- `label-event-audit.yml` triggers on `[labeled, unlabeled]`. It runs on a PR only if a label event occurs (e.g. `gh pr create --label shipyard`); a PR that never sees one would hang forever.

A required check that never reports is indistinguishable from one that never passes. This is the same failure family as the deadlock caught in #938 — a plausible-looking ruleset change that bricks the repo — so treat any proposal to extend this list as needing the same live verification: confirm the workflow's trigger actually fires on `pull_request` before requiring its context.

`strict_required_status_checks_policy` is deliberately **`false`**. Setting it `true` requires every PR branch to be up-to-date with `main` before merging, which at this repo's merge volume (~97 PRs/week, mostly autonomous) would force a rebase on nearly every PR and fight `/do-work`'s own rebase handling.

## Release process

**ALWAYS cut a release when a PR merges.** No exceptions for "trivial" docs-only PRs — `/shipyard:update` and the marketplace only see what's in `plugin.json`'s `version` field. A PR that merges without a version bump is invisible to every existing installation, so the work might as well not have shipped.

What "cut a release" means in this repo:

1. Bump `plugins/shipyard/.claude-plugin/plugin.json` `version` (semver — patch bump for fixes / docs / config; minor for new features; major when the user explicitly says so).
2. Add a new `### <version> — <YYYY-MM-DD>` entry at the top of the `## shipyard` section in `CHANGELOG.md`. Match the prose style of recent entries: one summary paragraph leading with what changed and why, then a bullet list naming the specific files / surfaces touched. Cite the closed issue number(s) inline as `closes #N` — the **issue** only, **no PR number** (and no `PR #TBD` placeholder). GitHub already resolves each `closes #N` to the PR that closed it, so a per-entry PR number is redundant; per [#691](https://github.com/mattsears18/shipyard/issues/691) it was dropped from this convention (retiring the `PR #TBD` placeholder + the orchestrator's CHANGELOG-backfill machinery, which existed only to fill that number in after the fact).
3. Commit the bump + CHANGELOG entry, then land it through a PR with auto-merge — like any other change to `main`. Per the [Permissions section](#permissions) above you don't need to ask first, but the branch ruleset rejects direct pushes to `main` (`GH013: Changes must be made through a pull request`), so even a docs + config release bump goes through a PR. The release bump can ride along in the same PR as the change it's releasing (the common case — one PR cuts its own release per the rule above); a standalone catch-up bump still opens its own PR.

There are **no git tags and no GitHub releases** — `plugin.json` is the canonical version surface, and the marketplace checks it directly. Don't introduce a tag/release workflow without asking; the current shape is intentional.

If multiple PRs merge in a tight window without each one cutting its own release (i.e., catch-up situation), bundle them into one version bump with one CHANGELOG entry that names each PR's contribution. The "one release per PR" rule is the steady-state aspiration, not a rigid requirement that forces tiny patch-bump churn.

## Label conventions

One-stop reference for the label families `/shipyard:do-work` and the broader plugin treat as load-bearing. Grouped by what the label *is*, not who applies it.

### Origin labels

Two label families mark *where* an issue came from, not what state it's in:

- `user-feedback` — issue filed via real-world feedback (raw text from a user)
- `audit:<dimension>` — issue filed by a shipyard auditor agent (`audit:security`, `audit:privacy`, `audit:dx`, etc.)

Both are applied at intake and **never removed**. They inform routing (e.g. the `user-feedback` label, combined with a body that still looks like raw feedback, is the source signal that routes an issue to `/refine-issues`' classify+rewrite branch per #145) and provide provenance for the lifetime of the issue. **Being permanent-and-never-removed means the label alone can't double as a live "still needs refining" flag** — an issue can carry `user-feedback` while already refined (hand-filed by a trusted maintainer, or refined by a prior pass). `/refine-issues`' candidate scan accounts for this: the classify+rewrite signal additionally requires the body to still contain the raw-feedback fenced block from the intake contract, so an already-refined `user-feedback` issue is dispatch-eligible immediately instead of re-matching the scan every session forever ([#1055](https://github.com/mattsears18/shipyard/issues/1055)). If we add a new issue origin in the future (e.g. Dependabot follow-ups, `/shipyard:my-turn-filed` items), it joins this class.

We intentionally don't prefix `user-feedback` with `origin:` for naming consistency — that's a breaking change with low payoff. If a sweeping rename ever happens, it's its own issue; for now, document the convention and leave the name.

### Session-stamp label

- `shipyard` — the provenance/session stamp applied to **every issue AND PR** shipyard creates, across all creation paths: `/do-work` orchestrator PRs, worker-filed follow-up issues, `/shipyard:file-issue`, all `audit:*` auditors. Hooks, the orphan-triage sweep, the failing-PR scan, and the end-of-session summary all key off it. Don't remove it. Each creation path must **ensure the label exists first** (idempotent `gh label create shipyard --description "Worked on by /shipyard:do-work" --color 5319E7 2>/dev/null || true`) before applying it — a missing label is created rather than silently dropped. The `audit:<dimension>` origin labels and the `shipyard` session-stamp label are orthogonal: auditor-filed issues carry both. See issue [#573](https://github.com/mattsears18/shipyard/issues/573).

### State labels (auto-managed)

These reflect transient state and are managed by `/shipyard:do-work`.

- `blocked:agent-soft` — added when an agent returns a **subjective** bail (cannot-reproduce / ambiguous / scope-judgment / duplicate-PR false-positive). Auto-cleared at the next session's backlog fetch (step 3d.2 sub-sweep c); in-session retry is gated by the orchestrator's `session_blocked_soft` map after `blocked_agent.soft_retry_minutes` (default 30). It does NOT hide an issue across sessions — it's in-session documentation only. **Decision recorded (#1082): kept, not retired.** It **changes no routing** — it doesn't gate dispatch and doesn't exclude an issue from the workable queue (see `04-backlog-divert.md`'s "intentionally NOT in this set" note); its entire value is a greppable visibility signal for a same-session retry window that a bail comment alone wouldn't surface as cheaply. The label's own GitHub description states this explicitly (`gh label create`'s `--description` in `01c-label-recovery-refine.md`), so a maintainer browsing the label list doesn't mistake it for a real gate.
- `blocked:ci` — added when a PR exhausts the 3-attempt fix-checks cap (the orchestrator's circuit breaker). The step 3d.1 sweep in `plugins/shipyard/commands/do-work.md` auto-clears it when a new commit lands on the PR's head branch (the "stuck" premise no longer holds), letting shipyard retry. **The escalation path has never fired in production** (0 all-time uses across `mattsears18/shipyard` and `mattsears18/lightwork`, per #1082's audit) — not a defect (it means the 3-attempt fix loop has never exhausted), but worth recording as unexercised. `plugins/shipyard/scripts/tests/flake-enforce.test.sh`'s `apply-blocked-ci` case covers the mechanical label-application/gating code, but the 3-attempt orchestrator circuit breaker itself is prose interpreted by the dispatching agent, not a deterministic script — genuinely unit-testing *that* trigger would need an integration-level harness, which is a larger follow-up, not part of this label cleanup. (`do-work-supervisor.test.sh`'s own `blocked:ci` work-exists-gate case was removed along with the supervisor itself in #1150 — shelved and non-functional.)

> **`blocked:agent-hard` eliminated (#521).** A worker `blocked: <reason>` return is no longer stamped with a `blocked:agent-hard` (or legacy `blocked:agent`) label. The orchestrator's [bail handler](plugins/shipyard/commands/do-work/steady-state.md) now splits the non-soft bails by whether the bail names an open `Blocked by #N`: a **refuse** (security / scope / prompt-injection / conservative-default, no open blocker ref) gets `needs-human-review` (a human must look — surfaced by `/my-turn`); a **dependency-wait** (the bail names an open `#N`) gets **no label** — the `Blocked by #N` body-reference filter in the dispatch fetch already drops the issue while the blocker is open and re-admits it the instant the blocker closes, so the label-plus-referential-sweep machinery was pure redundancy and was deleted (step 3d.2 sub-sweep a and the #245 mid-session sweep are gone). **The legacy `blocked:agent` and `blocked:agent-hard` GitHub label objects still exist with zero all-time usage in either repo (#1082) — see [Retired labels](#retired-labels--do-not-reintroduce) for the pending manual-deletion follow-up.** Step 3d.2 sub-sweep b migrates any straggler off `blocked:agent` (dependency-wait → no label, else → `needs-human-review`).

Reserves space for future categories (`blocked:external` for upstream / vendor blocks, `blocked:design` for design-gated work) — those aren't created proactively; add them when the first instance appears, per the `audit:*` precedent.

### Gate labels (intake → human review)

> **Binary-backlog migration (#515 → #536).** The long-term north star is a strictly binary issue backlog: every open issue is either workable-by-`/do-work` (no gate label) or workable-by-human (`needs-human-review` → surfaced by `/my-turn`). Migration narrative for the phased label folds/eliminations that produced the current gate-label set below — provenance in [RATIONALE → Label-lifecycle provenance](./docs/design/do-work-rationale.md#label-lifecycle-provenance--folded--eliminated-gate-labels).

- `needs-refinement` (**eliminated #520**) — formerly a persisted "this issue isn't ready for `/shipyard:do-work` dispatch yet" pipeline gate applied at intake. Retired in the binary-backlog phase-2 slice: `refine-issues` (removed) now detects refinement candidates by a **live source-signal scan** over open issues (`user-feedback` label → classify+rewrite, `## Open questions` heading → resolve-defaults, bot-authored / unrecognized → fall-through to `needs-human-review`) as a pre-dispatch pass, with no persisted label. The scan recomputes candidacy every run, so it never drifts out of sync with the issue body the way a cached gate label did. The GitHub `needs-refinement` label object was deleted 2026-07-25 ([#859](https://github.com/mattsears18/shipyard/issues/859)) — it carried zero open/closed issue usage and nothing applied or read it, so the manual-cleanup deferral is resolved. Security is unchanged — external-author issues still get `needs-human-review` from the separate `external-author-gate.yml`.
- `needs-human-review` — a human sign-off gate: applied by the user-feedback classify+rewrite branch of `refine-issues` (removed), the `/refine-issues` **fall-through branch** (the no-automated-path refinement subset, per #520), the `external-author-gate.yml` workflow, `issue-worker.md` step 6 for external-author PRs, and `do-work/setup.md` step 6's Deferred recording path for `confirmed-non-shippable-as-single-PR`, `external-dependency`, and `human-decision-required` defers. The resolve-defaults branch does NOT apply it — trusted-author issues that pass through resolve-defaults become dispatch-eligible immediately. **As of #515 this label also subsumes the former `needs-design` design-gate** — a design-gated issue now carries `needs-human-review`; `/do-work` excludes it from dispatch and `/my-turn` surfaces it. **As of #519 it also subsumes the former `needs-decomposition` / `tracking` epic-decomposition pair** — a confirmed-non-shippable epic now carries `needs-human-review` plus the `<!-- do-work-needs-decomposition -->` body marker (see the Epic-decomposition section below); the marker is what lets `/decompose-epic` find epic handoffs among the broader `needs-human-review` pool. **As of #536** the label is also applied to `human-decision-required` defers (stamped with `<!-- do-work-human-decision-required -->`), so those issues exit the re-scope loop immediately rather than accumulating identical diagnosis comments across sessions. **As of #608, `external-dependency` defers route to the new [`agent-console`](#agent-console) label instead of `needs-human-review`** — they're browser/console *agent-actionable* actions (paste a secret, toggle a console), which `/do-work` can *drive* rather than only hand back; they keep the `<!-- do-work-external-dependency -->` marker as the discriminator. The two remaining defer classes (`untrusted-author` and `confirmed-blocker-still-open`) do NOT get a gate label — `confirmed-blocker-still-open` rides the `Blocked by #N` body-reference filter, and `untrusted-author` is handled at trust-clearance time. **Naming note (#608, renamed #995):** `needs-human-review` is kept verbatim and now means specifically a genuine human *decision* (policy / ambiguous tradeoff / untrusted-author vetting / non-mechanical epic) — the operator/decision split is `agent-console` vs `needs-human-review`, not a rename of the latter. **As of #767, a plain open design or architecture decision is explicitly NOT one of these** — epics, spikes, and design-needed issues are in-scope autonomous work by default (extending #661's "autonomous design/architecture decisions" default from in-worker choices to issue scoping); the scope-preflight agent makes the reasonable design/architecture call and proceeds rather than deferring. `needs-human-review` still gates a *non-mechanical* epic (no constructible phase-1 slice — `confirmed-non-shippable-as-single-PR`) and genuine product/business/legal/policy decisions, just not "needs design" on its own. See [`do-work/setup/06b-scope-carveouts.md`'s design/architecture/epic/spike callout](plugins/shipyard/commands/do-work/setup/06b-scope-carveouts.md#designarchitectureepicspike-decisions-are-in-scope-by-default-not-a-defer-reason-767). **As of #1091, every code path that applies this label also writes a provenance marker** so `/shipyard:my-turn` can render a distinct action per provenance instead of inferring it from prose — `/my-turn`'s own [provenance table](plugins/shipyard/commands/my-turn.md#pass-b--open-issues) is the single source of truth for the full mapping (marker → producing path → human action); this paragraph only names the markers, not the render. Producers and their markers: refined user-feedback (co-label `user-feedback`, no separate marker), refinement fall-through (`<!-- do-work-refinement-fallthrough -->`, second line after the `/refine-issues` dedupe sentinel), legacy `needs-design` migration (`<!-- do-work-legacy-needs-design -->` — not produced going forward, per the #767 in-scope-by-default rule above), `external-author-gate.yml` / the untrusted-author handoff (`<!-- do-work-untrusted-author-review -->`, #1079), an agent hard-refuse (`<!-- do-work-agent-refuse -->`, #521), investigate-mode or spike-mode's disposition-to-human (`<!-- do-work-investigation-disposition -->`, #514), the epic-decomposition handoff (`<!-- do-work-needs-decomposition -->`, #519), `human-decision-required` defers (`<!-- do-work-human-decision-required -->`, #536), and a classifier-denied dispatch (`<!-- do-work-classifier-undispatchable -->`, #953). **`<!-- do-work-needs-decomposition -->` and `<!-- do-work-classifier-undispatchable -->` predate this convention and are grandfathered spellings of it, not renamed** — both already ride live issues, and a rename would silently break `/decompose-epic`'s and `/my-turn`'s existing lookups against issues stamped before #1091. An absent marker degrades to `/my-turn`'s generic "review and clear, re-scope, or close" render — it is not an error state.
- <a id="agent-console"></a>`agent-console` (#608; **renamed from `needs-operator` in #995** — see [Renamed: `needs-operator` → `agent-console`](#renamed-needs-operator--agent-console-995) below for why and the migration sequence) — **states who acts, not just where the work happens.** The issue is blocked on something completable by manipulating a browser or provider console (paste a CI secret, flip a Firebase/Vercel toggle, close a superseded PR, submit a form), **not** on a human decision. Apply the decision rule below whenever you're choosing between this label and `needs-human-review` — it's the rule the old `needs-operator` name didn't carry:

  > **Can an agent perform this action?**
  > · **Yes**, but outside the build (a cloud console, a deploy platform, a store listing) → `agent-console`
  > · **No** — barred (credential entry, account creation, billing) or genuine human judgment → `needs-human-review`

  The actor can be **a human OR Claude** — `/shipyard:do-work` (operator-inclusive by default) drives these in the user's real, logged-in Chrome via the `claude-in-chrome` extension (see [`do-work/operate.md`](plugins/shipyard/commands/do-work/operate.md)). Applied by `do-work/setup.md` step 6's Deferred recording path for `external-dependency` defers (re-routed here from `needs-human-review` per #608). `/do-work` **excludes** it from *code-worker* dispatch — it isn't code work — exactly like `needs-human-review`, but the default operator phase drains it via the browser (the proactive sweep scans for `agent-console`-labeled issues); under the `--no-operate` / `--hands-off` opt-out it's surfaced as a hand-back instead. `/my-turn` surfaces it as a human-actionable operator item. **Security:** an operator action whose target/value is derived from an *untrusted-author* issue is never driven — the trust boundary applies to browser actions too (see [`do-work/operate/03-error-handling-and-safety.md` → Safety](plugins/shipyard/commands/do-work/operate/03-error-handling-and-safety.md#safety--trust-boundary)). This is the agent-actionable half of the operator-vs-decision split (#608); `needs-human-review` is the decision half. **An `agent-console` item that turns out to be a security/access-control mutation (password policy, IAM, OAuth redirect URIs, sharing/member permissions, etc.) is relabeled to `needs-human-review` at hand-back time** (#848) rather than staying on `agent-console` — `/my-turn` deliberately filters `agent-console` out of its walked human-only queue (pointer-only, since most `agent-console` items really are `/do-work`-drivable), so a security mutation left on that label is invisible to both loops: `/do-work` correctly refuses to auto-drive it, and `/my-turn` never surfaces it individually. See [`do-work/operate/02-execution-and-playbooks.md`'s security hand-back branch](plugins/shipyard/commands/do-work/operate/02-execution-and-playbooks.md#playbooks-by-kind). **An `agent-console`-bound (or security-flavored `human-decision-required`-bound) candidate frequently has a shippable code slice — `/do-work` ships that slice and hands back only the narrow operator/security remainder on the same issue, rather than deferring the whole thing** (#851; the automated counterpart to the split PR [#900](https://github.com/mattsears18/shipyard/pull/900) shipped by hand for issue #867). See [`do-work/setup/06b-scope-carveouts.md`'s operator-slice carve-out](plugins/shipyard/commands/do-work/setup/06b-scope-carveouts.md#operator-slice-carve-out--ship-the-code-slice-hand-back-only-the-operator-remainder-851) and [`issue-work.md` §6.5](plugins/shipyard/agents/issue-worker/issue-work.md#65-split-dispatch-disposition-hand-back-the-operatorsecurity-residual-keep-the-issue-open-851).

  #### Renamed: `needs-operator` → `agent-console` (#995)

  `needs-operator` read as "needs a human operator" — the exact opposite of what it means: the label marks work an **agent** can drive outside the build (a browser, a cloud console), not work that requires a human. On a real `/do-work` session this misreading caused four genuinely agent-barred items (secret writes, an unauthenticated login) to get the *wrong* gate label instead of `needs-human-review`, and — because `/do-work` drives `agent-console`/`needs-operator` while `/my-turn` filters it *out* of the human queue — a genuinely-blocked issue wearing the old name was reachable by neither loop. `agent-console` was chosen (over `agent-ops` / `agent-external`, the issue's alternatives) because the `agent-` prefix makes ownership unmistakable — it cannot be misread as a person — while `console` still conveys *where* the work happens.

  **This repo's own label object was not renamed as part of #995** — zero open or closed issues in `mattsears18/shipyard` carried `needs-operator` at the time of the rename, so there was no live data to migrate here. **Migration for any consuming repo that already has issues on the legacy `needs-operator` label:**

  1. Upgrade shipyard first. Every routing site that reads or writes this gate label (the dispatch-exclusion set, the operator sweep, the `/my-turn` filter, the label-creation loop, the scope-preflight `GATE_LABEL` application) recognized **either** `agent-console` or the legacy `needs-operator` name during the migration window — the label-creation loop only ever created `agent-console`, but every *matching* site accepted `needs-operator` too.
  2. Only **after** upgrading, rename the repo's actual GitHub label object (`needs-operator` → `agent-console`, in place — GitHub preserves every issue's label association across a rename). Renaming the live label *before* upgrading orphans every reference: an unmigrated shipyard install matches on the old literal name only, so a repo that jumps the gun makes its gated issues invisible to both loops — precisely the failure this rename exists to fix, recreated at the infrastructure layer instead of the naming layer.
  3. **The migration window is now CLOSED in this repo's own specs, as of [#1082](https://github.com/mattsears18/shipyard/issues/1082).** Zero issues in either `mattsears18/shipyard` or `mattsears18/lightwork` carried `needs-operator` at closure time, so there was no live data left to strand. Every matching site (`04-backlog-divert.md`'s dispatch-exclusion set, the operator proactive sweep, `/my-turn`'s human-only-queue filter) now recognizes **only** `agent-console` — the legacy `needs-operator` name is no longer matched anywhere. A consuming repo that installed an older shipyard version and never renamed its live `needs-operator` label object must rename it now (step 2 above) before upgrading past this point, or its gated issues become invisible to both loops again — the exact failure #995 fixed, reintroduced by upgrading without migrating.
- `needs-triage` (**eliminated #1120**) — formerly the transitional parking label (#515) for untriaged / bot-filed issues, and investigate mode's entry signal. Retired once entry stopped depending on it: [#1090](https://github.com/mattsears18/shipyard/issues/1090) replaced the label-only gate with a **live detection scan** (bot-shaped trusted author, or symptom-shaped body — see [`04d-investigate-routing.md`](plugins/shipyard/commands/do-work/setup/04d-investigate-routing.md)), keeping the label as a sufficient-but-not-required trigger during a migration window; [#1120](https://github.com/mattsears18/shipyard/issues/1120) closed that window and retired the label outright — dropped from the detection predicate, both `gh label create` calls deleted, every writer re-pointed, the `labels.needs_triage` config key and schema property retired (per the [#1360](https://github.com/mattsears18/shipyard/issues/1360) precedent), and the GitHub label object deleted 2026-08-15. The migration window's stated end date (`2026-09-20`) was **waived by explicit maintainer decision** recorded on #1120; the live-usage condition was independently satisfied (0 open usage in `mattsears18/shipyard` and `mattsears18/lightwork`). **Note the correction:** this bullet previously said the label was applied by `refine-issues` (removed)' escalate-to-triage branch — that was already stale, as that branch has routed to `needs-human-review` since #520. Nothing applies or reads `needs-triage` now; a consuming repo that still carries the label object can delete it at leisure, and an issue still wearing it is treated as an ordinary candidate.
- `discussion` — **manually applied only, never by any automated path.** A maintainer labels an issue `discussion` while they're actively engaged in the comment thread by hand and want `/do-work` to leave it alone in the meantime; `04-backlog-divert.md`'s dispatch-exclusion set and the `blocked:ci`/`wontfix`/`needs-human-review` sibling gates already skip it. Bucket 4 of `01b-backlog-overview.md`'s overview table documents the ownership as "nobody (by design)" (#1076) — no `/my-turn` signal, since this is an intentional, self-terminating human pause, not a stuck state needing surfacing. **Decision recorded (#1082): provisioned, not deleted.** Prior to #1082 the gate existed in four spec files with real dispatch-exclusion effect but no corresponding `gh label create` line, so a fresh repo's label picker never offered it even though the spec assumed it existed; `01c-label-recovery-refine.md`'s idempotent label-creation block now creates it.

### Epic-decomposition handoff (scope-agent handoff → auto-shard)

As of #1654 there is no automated epic-decomposition pipeline. `needs-human-review` + the `<!-- do-work-needs-decomposition -->` body marker survive as a **human-review signal**: scope-preflight still stamps the marker when it judges an epic non-shippable as a single PR, `/my-turn` still surfaces those issues, and a person (or a worker told to) does the sharding. What was removed is the automated consumer. Historical context on the pipeline that used to read it — there is no longer a dedicated `needs-decomposition` label or a `tracking` parent marker (both folded into `needs-human-review`). The `needs-human-review` label is what `/do-work` excludes from dispatch (it's in the step-4 exclusion set); the body marker is the discriminator that lets `/decompose-epic` separate epic handoffs from every *other* `needs-human-review` issue (refined user-feedback, external-author, design-gated). **The `tracking` and `needs-decomposition` label objects themselves were never deleted from any repo, so `04`'s step-4 filter also drops a bare `tracking`-labeled issue directly, as a defensive gate** ([#1081](https://github.com/mattsears18/shipyard/issues/1081)) — this doesn't reintroduce a second gate label into the design, it only closes the dispatch-eligibility window between a stray `tracking` application and the next session's migration sweep (`01c-label-recovery-refine.md`'s sub-sweep e) relabeling it to `needs-human-review`. Neither label should ever be recreated — see that file's "RETIRED" comment block.

- **Trigger:** `do-work/setup.md` step 6's Deferred recording path applies `needs-human-review` AND stamps `<!-- do-work-needs-decomposition -->` on the scope-agent diagnosis comment when a scope agent returns `confirmed-non-shippable-as-single-PR` (#498). It surfaces an epic as a human-handoff: `/do-work` stops re-scoping it every session and `/my-turn` surfaces it.
- **Two distinct sentinels:** `<!-- do-work-needs-decomposition -->` is the *trigger marker* (identifies an epic handoff; persists for the epic's lifetime). `<!-- do-work-decompose-agent -->` is the *idempotency sentinel* (present only after a `/decompose-epic` run; stops re-processing). Don't conflate them.
- **Related non-epic defer markers (#536):** `<!-- do-work-external-dependency -->` marks an `external-dependency` defer diagnosis comment; `<!-- do-work-human-decision-required -->` marks a `human-decision-required` defer. Neither is consumed by `/decompose-epic` — they are dedupe sentinels and human-readable discriminators only.
- **Decision-resolved sentinel (#569):** `<!-- do-work-decision-resolved -->` is the recommended first line for a maintainer comment that records a decision and clears the `human-decision-required` gate. When `/my-turn` (or a human) records decisions that make a gated issue actionable, stamping this sentinel at the top of the comment guarantees the scope-preflight agent sees the resolution as explicit signal — it does NOT need to infer resolution from keyword matching alone. Convention: the comment should begin with `<!-- do-work-decision-resolved -->` on its own line, followed by a summary of what was decided and what the implementation path is. Remove `needs-human-review` from the issue in the same operation. The scope-preflight agent's freshness check (setup.md step 6) honors this sentinel; if it finds a comment with this sentinel posted after the last `<!-- do-work-human-decision-required -->` diagnosis comment, it falls through to a fresh scope-agent dispatch rather than reusing the stale diagnosis.

## Configuration (`shipyard.config.json` + layered overrides)

Shipyard runs against a 4-layer config. Effective config is the deep-merge of all four layers in order — later wins, arrays are replaced (not concatenated), and objects merge key-by-key recursively.

| Layer | Path | Committed? | Purpose |
|---|---|---|---|
| 1. Built-in defaults | hardcoded in `plugins/shipyard/scripts/shipyard-config.sh` | n/a | Always present; bottom layer |
| 2. User-global | `~/.shipyard/config.json` | no (per-user) | Default models, default auto-merge policy, cost-tracking opt-out — across every repo (set via the `default_*` / `cost_tracking_enabled` aliases, remapped onto canonical paths on load) |
| 3. Repo-level | `<repo>/shipyard.config.json` | **yes** | Shared policy, reviewable in PRs; opt-in surface for `/shipyard:do-work` |
| 4. Personal override | `<repo>/.shipyard/config.local.json` | no (gitignored) | Per-repo personal overrides without touching committed policy |

### Opt-in contract

`/shipyard:do-work` checks for `<repo>/shipyard.config.json` at session start (step 0.4):

- **Present**: load the merged effective config and dispatch normally.
- **Missing**: warn and fall back to built-in defaults. The hard refusal gate is deferred until `/shipyard:init` adoption is widespread. Pass `--strict` to opt into the future hard-refusal behavior today.

### Bootstrap and post-bootstrap config management

Bootstrap (`/shipyard:init` — flags, `.gitignore` seeding, pre-write schema validation) and post-bootstrap management (`/shipyard:config show|get|set|edit|validate` — all subcommand forms, `--plain`/`--with-source`/per-layer `--layer`, output samples, error shapes) are both documented in full in [`commands/init.md`](plugins/shipyard/commands/init.md) and [`commands/config.md`](plugins/shipyard/commands/config.md) respectively — this summary would only duplicate a strict subset of either.

Schemas live at `plugins/shipyard/schemas/shipyard.config.schema.json` (repo + local) and `plugins/shipyard/schemas/shipyard.user-config.schema.json` (user-global). Every load and every `set` validates the result before it lands; typos surface as clear errors rather than silent ignores.

### Milestones (`milestones` config block — issue [#1239](https://github.com/mattsears18/shipyard/issues/1239))

Top-level, opt-in roadmap-sequencing block (`enabled` defaults `false`) — independent of every other block, including any future GitHub Projects v2 (`projects`) block, which was designed alongside this and deliberately dropped (a project board mostly restates issue state/labels shipyard already tracks). Ordering is read back from a numeric title prefix `N · Title` (U+00B7 middle dot, spaced) — the separator is fixed, not configurable — and the fallback milestone (default title `Ongoing maintenance`, key `fallback`) always sorts last and never completes. `milestones.enabled == false`, or the block absent entirely, MUST be byte-for-byte inert — see [`do-work/dont.md`'s milestones bullet](plugins/shipyard/commands/do-work/dont.md) for the consumer-side guard. See [`do-work-rationale.md → milestones config block`](./docs/design/do-work-rationale.md#milestones-config-block--config-surface-only-scope-and-why-projects-projects-v2-was-dropped-issue-1239) for the full design writeup.

**`/shipyard:update-roadmap` (issue [#1240](https://github.com/mattsears18/shipyard/issues/1240))** is the first consumer of this block — an **orchestrator-only** skill + thin command that assigns a milestone to every open issue that lacks one, authors new phases (including the cold-start case, a repo with zero milestones), checks each phase's `BET:` against reality, and detects issue dependencies a filer never wrote down. Its autonomy boundary applies the mechanical/reversible cases directly (unmilestoned assignment, the fallback milestone, cold-start phase authoring, stated dependencies) and proposes everything that re-sequences a human-authored plan (moving an already-milestoned issue, closing a phase, rewriting a bet, inferred dependencies). **A dispatched `/shipyard:do-work` worker must never invoke it or touch a milestone** — see `shipyard:worker-preamble`'s [`milestone-prohibition.md`](plugins/shipyard/skills/worker-preamble/milestone-prohibition.md) fragment and the [`do-work/dont.md`](plugins/shipyard/commands/do-work/dont.md) bullet for the worker-side half of that boundary. See [`shipyard:update-roadmap`](plugins/shipyard/skills/update-roadmap/SKILL.md) for the full skill and [`do-work-rationale.md → shipyard:update-roadmap skill`](./docs/design/do-work-rationale.md#shipyardupdate-roadmap-skill--why-the-worker-prohibition-is-a-separate-fragment-why-dependency-detection-splits-applypropose-the-way-it-does-and-the-source-unreachable-fallback-issue-1240) for the design writeup.

**`milestones.prioritize_dispatch` (issue [#1241](https://github.com/mattsears18/shipyard/issues/1241))** is the second consumer — `/do-work`'s backlog ranking becomes milestone-aware when this key AND `enabled` are both `true`: a global `P0` escape, then `--prioritize-label`, then earliest phase with dispatchable work, then the existing `P1`/`P2`/type/staleness tiebreakers within that phase. `scripts/backlog-filter.sh classify`'s `_sort_key` is the normative implementation (non-normative prose lives at each of the three call-sites — `setup/04-backlog-divert.md`, `steady-state.md` step C, `drain.md`'s termination-assertion). With either key `false`, ranking is byte-for-byte identical to a repo with no `milestones` block. See [`do-work-rationale.md → Milestone-aware backlog ranking`](./docs/design/do-work-rationale.md#milestone-aware-backlog-ranking--backlog-filtersh-classifys-_sort_key-and-why-the-tiers-sit-where-they-do-issue-1241) for the full design writeup.

**`assign_on_file` (issue [#1242](https://github.com/mattsears18/shipyard/issues/1242))** is the third consumer — every issue-filing path assigns a milestone at file time rather than waiting for the next `shipyard:update-roadmap` sweep to backfill it: [`shipyard:filing-github-issues`](plugins/shipyard/skills/filing-github-issues/SKILL.md#milestone-assignment-gated-on-milestonesenabled--milestonesassign_on_file-issue-1242) (the shared path all 18 `*-auditor` agents file through) and [`/shipyard:file-issue`](plugins/shipyard/commands/file-issue.md) both match against each open milestone's `BET:`, never the issue's title keywords, and fall back to the already-existing `fallback` milestone or file without one — **a filer never creates a milestone**, cold-start or otherwise, that authority stays with `shipyard:update-roadmap` alone. `/decompose-epic` inherits the parent epic's own milestone onto each sub-issue instead of re-deriving one, extending the same inherited-filing-metadata carve-out `milestone-prohibition.md` already documents for a worker's follow-up-issue filings. Gated on `enabled` AND `assign_on_file` both `true`; either `false` leaves filing byte-for-byte identical to today. See [`do-work-rationale.md → Milestone assignment at filing time`](./docs/design/do-work-rationale.md#milestone-assignment-at-filing-time--matching-against-bet-why-a-filer-never-creates-a-phase-and-sub-issue-inheritance-issue-1242) for the design writeup.

**`sweep_on_loop_end` (issue [#1243](https://github.com/mattsears18/shipyard/issues/1243))** is the fourth consumer — `/do-work`'s end-of-session cleanup (`cleanup-summary.md`'s step 8.5) runs `shipyard:update-roadmap`'s Procedure steps 1–6 immediately before the session summary renders, whenever `enabled` AND `sweep_on_loop_end` are both `true` and this session shipped or filed at least one issue. The sweep's own step 7 (Report) is deliberately skipped — its Applied/Proposed tallies fold into the do-work summary's own `Roadmap sweep (#1243):` line instead of posting a second report — and any sweep-side failure is caught and surfaced as a one-line advisory, never a loop-ending error. `/shipyard:audit` intentionally does NOT get the identical auto-wiring (see [`audit.md`'s "End-of-run summary"](plugins/shipyard/commands/audit.md#end-of-run-summary)) — running the sweep after a bulk audit is left to the operator. See [`do-work-rationale.md → End-of-loop milestone roadmap sweep`](./docs/design/do-work-rationale.md#end-of-loop-milestone-roadmap-sweep--why-its-non-fatal-why-it-skips-on-a-no-op-loop-and-why-the-skills-own-step-7-report-is-suppressed-here-issue-1243) for the full design writeup.

### Don't put secrets in any config layer

The schema rejects keys matching `/token|secret|api_key|password|credential/i` regardless of where they appear. Move secrets to environment variables — even `.shipyard/config.local.json` (which is gitignored) is treated as if it could land in a backup or paste-buffer leak.

## Cost-tracking ledger (`~/.shipyard/cost-history.jsonl`)

Persistent cross-session token-usage records live at `~/.shipyard/`. Every `/shipyard:do-work` session's end-of-session cleanup flushes a rolled-up record into this ledger before reaping the per-session state file.

| Path | Format | Lifetime | Contents |
|---|---|---|---|
| `~/.shipyard/cost-history.jsonl` | append-only JSONL | persistent | One line per completed session: id, repo, started/ended timestamps, token totals, by-model rollup, by-mode rollup |
| `~/.shipyard/cost-history-issues.jsonl` | append-only JSONL | persistent | One line per (repo, issue_number); reader dedupes by latest `last_touched` |
| `~/.shipyard/sessions/<id>.json` | atomic JSON | transient | Per-session live state; reaped at end-of-session |
| `~/.shipyard/flake-registry.jsonl` | append-only JSONL | persistent | One line per flake event (repo, pr, workflow, job, test, session, timestamp); cross-PR/cross-session flake registry (#378) |
| `~/.shipyard/operator-denials.jsonl` | append-only JSONL | persistent | One line per operator-phase action denied by the harness permission classifier (repo, kind, target, denial text, outcome, session, timestamp); cross-session operator-denial registry (#1363) |

**The USD figures come from a hand-maintained pricing table** (`PRICING_JQ` in `plugins/shipyard/scripts/session-state.sh`) — update it whenever Anthropic changes pricing or ships a model. A model missing from the table is **flagged, not silently priced at zero** ([#728](https://github.com/mattsears18/shipyard/issues/728)): its token counts are still recorded, but `bump-tokens` warns on stderr, records the id in the session's `.tokens.unpriced_models` set, and the end-of-session summary + `/shipyard:cost report` label the USD total a **LOWER BOUND**. `$0.00` is a legitimate value and must never double as the error sentinel — a stale table would otherwise report a confidently-wrong near-zero spend. `scripts/tests/pricing-coverage.test.sh` fails CI if any model id shipped in this repo (the `models.*` config defaults or an agent shim's `model:` frontmatter) is missing a pricing row, so a new model can't ship into a $0 hole.

Use `/shipyard:cost report` to query the persistent ledger. `--last 30d` (default), `--repo <owner/name>`, `--by-issue`, `--by-mode`, `--by-model`, `--top N`, `--trend`, and `--format markdown|csv|json` compose. `/shipyard:cost reset` is destructive but safe (moves to `.bak.<ts>` instead of `rm`); `/shipyard:cost export --to <path>.tar.gz` produces a portable backup.

The ledger is local-only — shipyard never uploads it anywhere. To opt a specific repo out of cost-tracking, set `cost_tracking.enabled: false` for that repo; to opt out across every repo from the user-global layer, set `cost_tracking_enabled: false` in `~/.shipyard/config.json` (it remaps onto `cost_tracking.enabled` on load — a repo-level value still wins). `cost_tracking.enabled: false` is enforced inside `cost-history.sh flush` itself (not merely documented) — the ledger write is a no-op when the effective config resolves to `false`, so the opt-out can't silently go inert the way it did before [#855](https://github.com/mattsears18/shipyard/issues/855). The separate `cost_tracking.comment_on_pr: false` knob independently suppresses the per-PR `<!-- do-work-cost-tracking -->` comment `/do-work` posts on a shipped PR, checked in `steady-state.md`'s shipped-return handling. The ledger files are safe to `rm`; deletion only forfeits historical reports.

The **flake registry** at `~/.shipyard/flake-registry.jsonl` (the cross-PR/cross-session flake ledger from #378) follows the same local-only posture: it lives entirely on the local filesystem and is never uploaded anywhere. It records non-PII CI metadata (repo, PR, workflow, job, test id, session id, timestamp), but on a private repo that still accumulates a cross-session record of your test names and PR numbers, so it stays local by design. Collection is **off by default** — flip `flake_registry.enabled: true` to opt in. To opt back out, set `flake_registry.enabled: false`. `flake-registry.sh reset` moves the file to `.bak.<ts>` (recoverable, not `rm`'d); the file is otherwise safe to `rm`, which only forfeits the historical flake-rate window.

The **operator-denial registry** at `~/.shipyard/operator-denials.jsonl` (the cross-session operator-denial ledger from #1363) is the durable half of the `operator_denials` orchestrator-state struct — session-local denials are appended here at end-of-session cleanup, before the per-session state file is retired, so a denial class (e.g. "editing production consent-screen fields on `console.cloud.google.com` is denied") survives past the session that hit it and a future session can tell a one-off denial apart from a repeated, standing constraint via `operator-denial-registry.sh report`. Same local-only posture as the cost ledger and the flake registry — never uploaded anywhere — but a recorded `target` can be a specific admin-console URL or field name, more identifying than a CI test name, so collection is **off by default**: flip `operator_denial_registry.enabled: true` to opt in, `operator_denial_registry.enabled: false` to opt back out. `operator-denial-registry.sh reset` moves the file to `.bak.<ts>` (recoverable, not `rm`'d); the file is otherwise safe to `rm`, which only forfeits the historical denial-pattern window.
